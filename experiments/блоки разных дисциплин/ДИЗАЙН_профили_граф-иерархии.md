# Дизайн: профили «граф-иерархии» для дисциплин (СС/ОВ/ВК) + эталон ЭОМ

Собрано multi-agent разбором реальных вектор-блоков объекта 214 (Alia). Каждая дисциплина —
профиль извлечения графа из вектор-слоя PDF (узлы/рёбра/атрибуты/корень), по образцу
`electrical_singleline` (`singleline_graph_geometry.py`).

## Переиспользуемый костяк (общий слой для всех профилей)
- Vector word extraction + page resolution: `_find_page_index`/`_distinct_tokens` (backend/app/pipeline/stages/block_grounding/singleline_graph_geometry.py) — ищет реальную PDF-страницу блока по редким токенам вместо доверия page_index из result.json (известный баг эталона, воспроизведётся во всех дисциплинах). Обобщить needle-regex как параметр профиля (QF/К-код → 9A2.xxx / Ст.\d / В2.2-N / РГ-\d).
- Геометрические примитивы близости `_near`/`_near_xy`/`_median` — используются во всех профилях без изменений (сбор атрибута в X-колонке/Y-полосе вокруг якоря).
- Ось-агностичная привязка `_bind_codes_columnwise` (offset-corrected nearest column + alias δ±spacing + GEOMETRY_CONFLICT) — ядро колоночной привязки. Абстрагировать до `bind_along_axis(anchors, labels, axis=X|Y)`: X-колонки → фидеры(ЭОМ)/стояки(ВК)/устройства-в-ряду(СС); тот же алгоритм по Y → этажи-ряды.
- Разбиение на ряды `_split_codes_by_y_rows` → обобщить в `cluster_rows_by_axis` (кластеризация по Y с толерансом = шаг/3) — прямой аналог этаж-рядов у СС/ОВ/ВК (пики ~103px СС, Δ93.6px ОВ, ~72px ВК).
- Монотонная функция уровня Y→отметка (`_levels_by_elevation`) — НОВЫЙ общий примитив для ОВ/ВК: линейная регрессия по парам (y, ±NN,NNN), даёт этаж по любой Y даже при стаггерированных подписях 'Этаж N'. Калибровать по медиане отметок каждого листа, НЕ хардкодить шаг.
- Multi-line callout reconstruction `_extract_consumer_geo` + get_text('dict')-lines — сбор многострочной подписи в общей X-колонке: consumer(ЭОМ) ≡ tray-выноска(СС) ≡ zone-стек АПС ≡ описательная строка арматуры ВК (get_text('words') рвёт 'Клапан обратный NRV-R Ду50' на токены).
- field_state / FieldState / NON_REMOVAL_STATES / make_field / derive_field_state (backend/app/services/stage_comparison/graphic_profiles.py) — уже общий слой, применяется как есть: узел без типа/зоны → not_extracted/requires_human_review, не «удалено».
- Рендер графа `render_graph_for_prompt` (компакт для Stage 02) + `render_graph_etalon_markdown` (8 разделов, дерево+таблицы+секция ТРЕБУЕТ ПРОВЕРКИ) — шаблоны переиспользуются, меняется только состав колонок таблицы на профиль.
- fail-soft контракт `build_*_graph(pdf, vector_text) → None если не наша схема` + честные counters (привязано/всего токенов, пропуски в последовательности) + bbox_page/polygon_page для подсветки области узла.
- Классификатор block_type→profile из graphic_profiles.py (get_profile/PROFILES) — расширить регистр реальными extractor'ами и добавить внутри-профильный саб-классификатор для ОВ (riser/manifold/radiator/ventilation).

## Профили и приоритет

### [1] ЭОМ — `electrical_singleline/grsh (ЭОМ)`  (feasibility=shipped, effort=done)
Однолинейная ГРЩ/ВРУ: X-колонки=фидеры, валидированные params — эталон, уже в проде.
Корпус в `ЭОМ/` подтянут к актуальному Вектографу: 6/6 графов и 6/6 проходов гейта;
включён разнесённый диалект ЭО (`2РП…` + 7 расчётных значений), прогон воспроизводится
через `ЭОМ/run_vectograf.py`.

### [2] ВК — `water_supply_scheme (ВК)`  (feasibility=high, effort=M)
Стояки В/К как X-кластеры × вертикаль по отметкам этажей (Y→elev), арматура/выпуски/диаметры; чистейшая доменная лексика и монотонные отметки.

### [3] ОВ — `hvac_scheme (heating_riser/manifold/radiator + ventilation) (ОВ)`  (feasibility=high, effort=L)
Мультипрофиль ОВ: ИТП→магистраль Т11/Т21→стояк Ст.→этаж→прибор РГ; вертикаль/горизонт/аксонометрия, нужен саб-классификатор.

### [4] СС — `aps_structural + tray_axonometry + terminal_wiring`  (pilot implemented)
Структурная АПС: этаж×адрес-сетка (Y-ряды этажей × X-устройства), ПО→АЛС→этаж→извещатель; APS чистая, tray/СКУД — visual_unverified/отдельный профиль.

## Порядок реализации
- 1. ВК (water_supply_scheme) первым после эталона: feasibility high, лексика максимально регулярная (В2.2-N(6)ø76х3,5 / Оп. К1 / ∅100), а главное — вводит и валидирует НОВЫЙ общий примитив `_levels_by_elevation` (монотонная Y→отметка), который потом переиспользуют ОВ и СС. Один блок-пилот (4VEF-CC3P-P7K) закрывает и X-кластеризацию стояков, и Y-уровни.
- 2. ОВ (hvac_scheme) вторым: наибольшая переносимость с ЭОМ (горизонт-манифольд = 1:1 колонки-фидеры, корень внизу) + уже отлаженные Y-уровни от ВК. Основная новая работа — саб-классификатор riser/manifold/radiator/ventilation, поэтому идёт после того как оба базовых режима (колонки от ЭОМ, уровни от ВК) уже проверены на живых данных.
- 3. СС (low_voltage_fire_alarm_structural) последним: APS-сетка детерминируется отлично, но связность шлейфа (порядок обхода) и tray-аксонометрия требуют вектор-слоя линий get_drawings(), а СКУД — отдельного terminal_wiring профиля. Максимум остаточной неопределённости и профильного разветвления → делать, когда backbone полностью устоялся. Порядок = по возрастанию доли не-детерминируемого (ВК≈0 → ОВ саб-классиф → СС линии/wiring).

## Кросс-дисциплинарные паттерны
- Колоночная иерархия по X (эталонная): ЭОМ фидеры QF → ВК параллельные стояки → СС устройства внутри ряда → ОВ горизонт-манифольд стояки Ст. Один алгоритм `_bind_codes_columnwise` (offset-corrected nearest column + alias δ±spacing).
- Вертикальная иерархия по этажам/отметкам (общая у ОВ/ВК/СС): регулярная Y-сетка уровней. ВК/ОВ — через отметки ±NN,NNN и монотонную Y→elev; СС — через метку 'этаж'+число в левой колонке. Шаг конкретен листу (СС ~103px, ОВ Δ93.6px=3300мм, ВК ~72px=3150мм) → калибровать по медиане, не хардкодить.
- Гибрид «X-колонки × Y-этажи»: ВК (стояки × высота), СС APS (устройства × этажи), ОВ вертикальный стояк (ветви × этажи) — двумерная привязка (x±half, y-полоса ряда) идентична сбору consumer/additional_devices эталона.
- Аксонометрия / 2.5D (СС tray, ОВ ventilation, ВК развёртка): косая проекция ломает монотонность и колонки; рёбра между сегментами в тексте отсутствуют. Общий обработчик — multi-line callout по общей X-колонке + пометка связности visual_unverified.
- Именованные рёбра-магистрали как токены, а не узлы: ОВ Т11/Т21 (подача/обратка), ВК система-код В/К, СС АЛС-шлейф — все раскрываются в рёбра по подписи диапазона (‘АЛС9.2 на 27-30 этажи’, ‘Т11.x/Т21.x пары’).
- Кросс-лист сшивка по имени (общая нерешённая ось): один стояк/шлейф/система появляется на разных листах (Ст.2.1.4 корень в 06 и узел в 03; АЛС на другом фрагменте; ‘см. л.N’/‘далее см. ВжX’/‘к Корпусам 3-6’) — линковка по имени нужна всем четырём для сквозного графа корпуса.

## Риски
- ⚠ Аксонометрия без явных колонок/рядов: СС tray и ОВ ventilation дают косой X при подъёме, трасса вдоль X не монотонна, порядок вдоль ребра ненадёжен. Рёбра сегментов отсутствуют в тексте → детерминированно не восстановимы, только visual_unverified + LLM.
- ⚠ Топология рёбер (стояк↔магистраль↔ввод/выпуск, шлейф между устройствами) НЕ выводима из одних подписей — лежит в векторной графике линий. Нужен разбор page.get_drawings()/vector paths; текущий X-порядок в ряду верен не всегда (шлейф петляет).
- ⚠ Сканы без вектор-слоя: весь подход опирается на CAD-текст-слой (get_text('words'/'dict')). Растровые/сканированные листы → 0 токенов → профиль обязан fail-soft вернуть None и отдать блок в Qwen/LLM, не выдавать пустой граф за истину.
- ⚠ get_text('words') рвёт многословные подписи арматуры ВК на токены; порядок текст-слоя CAD (труба ø76 перед 'Ст.1.1.1' в горизонт-схеме ОВ) не гарантирован → нужна геометрическая верификация близости + fallback, иначе неверная привязка труба↔стояк.
- ⚠ Коллизия X-кластеров при плотной раскладке: ОВ Ст.2.1.1 x=605 vs Ст.2.1.2 x=604 при разном Y — чистая 1D X-кластеризация даёт слипание; нужна (x,y)-кластеризация. То же на границах рядов СС для диапазонных модулей АМ-4 ('...').
- ⚠ page_index блока ≠ реальная PDF-страница (баг эталона) — воспроизведётся во всех дисциплинах; без `_find_page_index` по контенту атрибуты соберутся с чужой страницы.
- ⚠ Профили вне дерева: СС СКУД/СОВ = wiring-diagram (клеммы/провода), не иерархия; попытка уложить в low_voltage-tree даст мусор. Требует отдельного terminal_wiring профиля.
- ⚠ Гидравлические/ёмкостные findings (Q против ø у ОВ, ⌀ против потока у ВК, ёмкость АЛС у СС) выходят за чистую геометрию — нужна нормативная/справочная таблица соответствия, которой пока нет; без неё эти проверки нельзя выдавать детерминированно.

## Детали профилей (по дисциплинам)

### СС (слаботочные системы) — АПС/СОУЭ/АППЗ + аксонометрия кабельных трасс — `low_voltage_fire_alarm_structural (профиль low_voltage/aps_structural + подпрофиль tray_axonometry)` (feas=medium, conf=0.72)
**Актуализация 2026-07-11:** реализован `low_voltage_geometry.py`; полный локальный
корпус АПС — 43/43 прохода гейта, 9628 адресных точек: 16 `aps_structural` с этажной
иерархией и 27 `aps_fragment` с адресным инвентарём без выдуманного этажа. Пилотная
схема: 240/240 адресов привязаны к этажу и типу. Лотки:
точный инвентарь 8+2 с `visual_unverified` топологией; СОВ: 14 компонентов, 111
физических клемм и 3 подтверждённые двухклеммные связи (ещё 2 сложные сети на проверке), 4 типа
кабелей, связи честно заблокированы до трассировки vector paths. Ключевое новое правило:
адрес сам кодирует АЛС (`9A2/9BTM2 → АЛС9.2`, `10A1/10SC1 → АЛС10.1`).

**Корень:** ПО (прибор пожарный ППКП, напр. «ПО №1»…«ПО №7») → далее АЛС-шлейфы (АЛС9.1, АЛС9.2 …). Для TRAY-профиля корень — кросс/точка ввода трассы (в тексте блока обычно не выражен → корень = сам «Узел N.M»).

**Направление:** Вертикаль по этажам: Y-ось = этажи (сверху Кровля вниз до нижнего этажа, шаг ~103px), X-ось = позиция устройства в шлейфе (слева-направо). То есть гибрид «вертикаль по этажам (ряды) × горизонтальные колонки-устройства». АЛС-шлейф связывает диапазон Y-рядов. TRAY — аксонометрия (2.5D), сетка нерегулярная, привязка по близости.

**Узлы:**
- **Извещатель/модуль АПС (адресное устройство)** — Адрес-токен regex ^\d+[A-ZА-Я]+\d+\.\d+(?:\.\.\.\d+)?$ (напр. 9A2.144, 9A2.139...142, 9BTM2.163, 10SC1.53...56) как ЯКОРЬ узла. Тип берётся из ближайшего токена в той же X-колонке с обеих сторон по Y (на кровле тип может быть выше адреса): ^(МДУ-1С|АМ-4|ИЗ|РМ-4|РМ-1С|ШУН/В)$. Диапазон '...' = многоадресный модуль (АМ-4 на 4 адреса).
  примеры: 9A2.144 / МДУ-1С, 9A2.143...146 / АМ-4, 9BTM1.147 / ИЗ / Д, 9A1.180 / ИЗ
- **АЛС-шлейф (loop) — ребро/суб-корень** — ^АЛС\d+\.\d+ ; подпись диапазона этажей — тем же/соседним токеном 'на 27-30 этажи'|'на кровлю'|'на N этаж' → regex АЛС(\d+\.\d+)\s*на\s*(.+?этаж|кровл). Каждый АЛС питает набор floor-rows.
  примеры: АЛС9.1, АЛС9.2 на 27-30 этажи, АЛС10.1 на кровлю, АЛС6.1 на 1-2 этажи
- **ПО / ППКП (прибор) — корень** — ^ПО\s*№?\d+ ; либо ключевые ППКП|С2000|КДЛ|Рубеж|ШУН/В в тексте листа. ПО №N — вершина, от него отходят АЛС.
  примеры: ПО №1, ПО №7, ШУН/В
- **Этаж (floor-row) — организующий контейнер** — Токен 'этаж' + число этажа в левой колонке (x<80): regex ^(2[0-9]|30|Кровля). Y-центр ряда = медиана Y адресов в полосе. Ряды детектируются кластеризацией Y адрес-токенов (пики ~103px).
  примеры: 30 этаж, 27 этаж, Кровля
- **Сегмент кабельного лотка (TRAY-профиль)** — Выноска: строка типа ^(Лестничный|Листовой) лоток\s+(СБ|СПЗ|СЛЗ)(\s+с перегородкой)? + следующая строка \d+х\d+,\s*L=[\d,]+\s*м. Гильзы: ^Гильзы в перекрытии + '\d+ шт. ∅\d+, L=\d+ мм.'
  примеры: Лестничный лоток СБ 300х100, L=1,52 м., Листовой лоток СПЗ с перегородкой 200х100, L=4,88 м., Гильзы: 28 шт. ∅50, L=550 мм.

**Рёбра:** Иерархия ПО(ППКП) → АЛС-шлейф → этаж(floor-row) → устройство. Рёбра строятся геометрически и семантически: (1) АЛС→этажи — по ПОДПИСИ диапазона ('АЛС9.2 на 27-30 этажи' раскрывается в floors {27,28,29,30}); floor-row детектируется по Y-полосе адресов; (2) этаж→устройство — устройство принадлежит ряду, если Y его адрес-якоря в полосе floor-row (|y - y_row| < шаг/2); (3) внутри ряда устройства упорядочены по X (слева-направо = порядок по шлейфу); соседние по X устройства одного АЛС считаются последовательно соединёнными шлейфом (ребро 'шлейф КСПВ'). Для TRAY: рёбра между сегментами лотков в тексте отсутствуют — восстанавливаются только по близости XY выносок (низкая надёжность, помечать visual_unverified).

**Привязка:** АЛГОРИТМ (APS-структурная): 1) Кластеризовать Y всех адрес-токенов → floor-rows (пики через Counter(round(y/10)*10) + разрыв >60px; центр ряда = медиана Y). 2) К каждому ряду привязать метку этажа по левой колонке x<80 (ближайший по Y токен ^(2\\d|30|Кровля)). 3) Внутри ряда: адрес-токены = якоря узлов, отсортировать по X; шаг колонки = медиана Δx. 4) Для каждого якоря (ax,ay) собрать X-колонку |x-ax| < шаг/2 и Y-окно ay-8..ay+70 → device_type (первый тип-токен), subtype/zone (ПД/ДУ/Вж…), флаг Д. **Атрибуты узла:** address, device_type, subtype_zone (тип точки: пожарный/дымоудаление/дверь), floor, loop_als, room_zone, detector_flag, tray_type, tray_size_len, sleeve (гильзы)

### ОВ (Отопление и вентиляция) — `hvac_scheme (подпрофили: heating_riser_vertical / heating_manifold_horizontal / ventilation_axonometric)` (feas=high, conf=0.78)
**Корень:** ИТП (тепловой пункт) для отопления / вентустановка (приточная П# или вытяжная В#/Вж#) для вентиляции. Формально: узел с меткой 'ИТП' или маркером 'от ИТП' (входящий внешний источник), либо нижний кластер РКДМ-П с длиной L#####. Дерево: ИТП → магистраль (Т11/Т21) → стояк (Ст.) → поэтажный отвод → прибор (РГ). Для вентиляции: установка → магистральный воздуховод (РКДМ-П) → поэтажные ответвления → клапан (КПУ)/решётка.

**Направление:** Смешанная, определяется подпрофилем: (а) горизонт — колонки-стояки (ИТП снизу, стояки по X) как в electrical_singleline, но корень внизу; (б) вертикаль по этажам — Y-сетка отметок с постоянным шагом 3300мм (снизу вверх, +отметка растёт вверх); (в) аксонометрия вентиляции — Y-ряды систем у левого края, трасса вдоль X. Направление иерархии: источник(ИТП/установка) → магистраль → стояк → этаж → прибор.

**Узлы:**
- **Источник (ИТП / вентустановка)** — Токен 'ИТП' (обычно единственный, в нижней зоне листа, макс Y — блок 03: x=452 y=1533) ЛИБО текстовый маркер 'от ИТП'/'от ИТП см. л.N' (блок 04). Для вентиляции — нижний кластер РКДМ-П с длиной L##### (блок 05, y≈1534/1608) = приточная/вытяжная установка. Корень с минимальным числом входящих рёбер.
  примеры: ИТП, от ИТП см. л. 9, РКДМ-П 900х450-О L12850
- **Стояк отопления (Ст.)** — regex ^Ст\.\d+(?:\.\d+){0,2} — напр. Ст.1.1.1, Ст.2.1.7. В горизонтальной схеме каждый Ст = отдельная X-позиция (узел-ветвь); в вертикальной — имя в шапке листа (y≈8) = корневой стояк всего листа.
  примеры: Ст.1.1.1, Ст.2.1.4, Ст.2.1
- **Отопительный прибор / регистр (РГ)** — regex ^РГ-\d+-ф\d+x[\d.]+-\d+ (напр. РГ-2-ф108x4-1000, РГ-4-ф89x3.5-1600). Узел-лист. Атрибуты Q=/n= на той же Y-строке справа.
  примеры: РГ-2-ф108x4-1000, РГ-4-ф89x3.5-1800
- **Магистраль/труба (ребро с меткой Т)** — regex ^Т[12]1(?:\.\d+)? — Т11.x подача, Т21.x обратка (первая цифра 1=подача,2=обратка). Часто с диаметром рядом. Это именованные РЁБРА, а не узлы.
  примеры: Т11.1, Т21.5, Т11.2
- **Отметка этажа / уровень** — regex ^[+\-]\d+,\d{3} (напр. +141,880, -0,800) и метка этажа ^L\d+_K\d (L30_K2). В вертикальной схеме образуют Y-сетку с постоянным шагом Δ≈93.6px=3300мм.
  примеры: +101,780, L30_K2, -2,900, +5,810
- **Система вентиляции/дымоудаления** — regex ^(П\d|В\d|Вж\d|ДУ\d|ПД\d)(?:\.\d+)* — П=приток, В=вытяжка, Вж=вытяжка жилая, ДУ=дымоудаление. У левого края листа = Y-ряды-анкеры систем.
  примеры: Вж3.1, ДУ3.1.2, Вж3.4
- **Воздуховод (ребро с сечением)** — regex ^РКДМ-П|СОМ\s?\d+-КАНАЛ, либо сечение \d{3,4}х\d{3,4} (900х450-О, 1000x500). Ребро сети воздуховодов с сечением и длиной L#####.
  примеры: РКДМ-П 900х450-О, 1000x500, 100х100
- **Клапан / арматура вентиляции** — regex ^(КПУ|КВК|КОМ|КДМ) для клапанов (КПУ-1Н противопожарный); для отопления арматура ^(RJIP|MNF-R|BVR-R). Узлы-аппараты на трубе/воздуховоде.
  примеры: КПУ-1Н, RJIP Premium FF DN65, BVR-R Ду 15мм

**Рёбра:** Рёбра = трубопроводы/воздуховоды. Три механизма в зависимости от подпрофиля: (1) ГОРИЗОНТАЛЬНЫЙ манифольд (03/04): ИТП(корень, макс-Y) → стояк Ст. через ближайшую по позиции питающую трубу ø##х#,# (в raw-тексте труба стоит непосредственно ПЕРЕД именем стояка — чередование 'ø76х3,5'\\n'Ст.1.1.1'; ребро = эта пара). Метка Т11/Т21 на ребре задаёт подачу/обратку. (2) ВЕРТИКАЛЬНЫЙ стояк (06): корневой стояк (шапка) → сегменты по этажам, ребро между соседними Y-уровнями этажей (Δ≈93.6px); на каждом сегменте свой диаметр из X-колонки диаметров (x≈406/988). ### ВК (водоснабжение и водоотведение) — `water_supply_scheme` (feas=high, conf=0.72)
**Корень:** Водоснабжение (В): ввод/насосная (низ схемы, max Y) → магистраль → стояки В2.2-N/В2.3-N → этажные врезки/приборы (снизу вверх). Водоотведение (К): приборы/этажные отводы → стояки К1/К13 → магистраль → выпуск 'Оп. К1 -N(6)' → колодец (сверху вниз по потоку). Root = ввод (В) или выпуск (К), т.е. нижняя точка схемы по геометрии.

**Направление:** Гибрид: горизонтальная кластеризация по X даёт ПАРАЛЛЕЛЬНЫЕ СТОЯКИ (как X-колонки=фидеры в эталоне), а иерархия внутри стояка ВЕРТИКАЛЬНА ПО ЭТАЖАМ (ось Y = отметки, монотонна). Общая раскладка — аксонометрия/развёртка: X = разные стояки, Y = высота/этаж. Поток по стрелке: В снизу вверх (ввод→верх), К сверху вниз (приборы→выпуск).

**Узлы:**
- **Стояк** — ^(В|К)\d+(\.\d+)?[нп]?[- ]
  примеры: В2.2-1(6)ø76х3,5, К13н ∅50
- **Выпуск** — ^Оп\.\s*(В|К)
  примеры: Оп. К1 -17(6) ∅100
- **Арматура** — ^(Кран|Клапан|Задвижка|Затвор|Фильтр).*(DN|Ду)
  примеры: Кран шаровой резьбовой BVR-R DN50
- **Оборудование** — ^(Погружной насос|Насос|Узел обвязки|Переходник|Ревизия|Трап)
  примеры: Погружной насос Native NSP 50/400-1,1
- **Уровень/этаж** — ^[+\-]\d+[.,]\d{3}$ или ^Этаж \d+
  примеры: +14.700, Этаж 5

**Рёбра:** Рёбра = участки трубы. Внутри одного X-кластера (стояка) соседние по Y узлы/сегменты соединяются вертикальным ребром 'труба' сверху вниз (по возрастанию Y = сверху этаж → ниже), тип трубы и ⌀ берутся из ближайшего сегментного маркера. Врезки/отводы: узел арматуры или отвод ∅50 в пределах X-полосы стояка присоединяется ребром 'врезка' к ближайшему по Y сегменту стояка. Корневые рёбра: стояк → магистраль/ввод/выпуск определяются по низу схемы (max Y) — стояк соединяется с горизонтальной магистралью, магистраль → 'Оп.' выпуск (канализация) либо стояк → ввод/насосная (водоснабжение). Смена диаметра вдоль стояка (⌀57→⌀76) фиксируется как атрибут ребра, не как разрыв.

**Привязка:** 1) X-кластеризация стояков: собрать x0 всех сегментных маркеров системы (^(В|К)...∅), кластеризовать 1D по X (порог = медианный полушаг между кластерами, аналог spacing в _bind_codes_columnwise) → каждый кластер = один стояк; ID-метка стояка (В2.2-N(6)) назначается кластеру, в чью X-полосу она попадает (nearest-column, offset-corrected как в эталоне). 2) Y-уровневая привязка (замена Y-рядов эталона): построить монотонную функцию Y→отметка по парам (y, +NN.NNN) внутри стояка (в бл.03 линейна: elev = a - b*y); узел/арматура привязывается к этажу по своей Y через эту функцию. 3) Привязка арматуры

**Открытые вопросы:**
- Топология рёбер стояк↔магистраль↔ввод/выпуск не всегда выводима из одних подписей — нужен разбор графических path (fitz page.get_drawings()) для линий труб, а не только words; в эталоне ребро=шина было проще.
- Стаггерированные 'Этаж N' (бл.03) не кластеризуются по X — привязка этажа к стояку только через интерполяцию отметки; надо проверить надёжность монотонной Y→elev при наклонной аксонометрии (изометрия даёт скос X при подъёме).
- Направление потока (В вверх / К вниз) сейчас эвристика по системному коду — нужно подтверждать стрелками/уклонами (i=0,02) из drawings.
- Разные диаметры одного стояка (⌀57/⌀76) — где именно граница смены ⌀ по этажам: нужен nearest-∅ по Y, точность не валидирована на живых данных.
- Привязка арматуры к КОНКРЕТНОЙ точке стояка (до/после насоса) требует Y-упорядочивания группы обвязки — проверено на бл.02 (кран→клапан→насос), но группы у 'Узел обвязки' могут перекрываться по X с соседним узлом.
- Нет валидированной параметрической таблицы (аналог structure_singleline_text даёт физику 100% по коду) — для ВК расходы/напоры берутся из отдельной таблицы расчёта, её ещё надо распарсить и связать по system_code.
