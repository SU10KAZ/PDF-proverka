# Stage 01 — Reusable block: маршрутизация по `document_type`

Этот блок предназначен для копирования в основной Stage 01 prompt И в completeness lens. Hard-rule formulation, без «возможно/желательно».

---

## Декларация

Этот документ имеет `document_type = {DOCUMENT_TYPE}`, одно из:

- `full_rd` — полная рабочая документация раздела
- `audit_comparison` — фрагмент-сравнение разделов / межразделный аудит
- `tz_vs_rd` — сопоставление ТЗ vs реализованный РД
- `specification_only` — спецификация / ведомость / отдельный расчёт

Применяй правила СТРОГО по типу. Любое нарушение → corrector удалит замечание.

---

## `document_type = full_rd`

**Разрешено:**
- Применять весь чек-лист дисциплины.
- Замечания об отсутствии обязательных разделов: `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.
- Документ явно отказывается от обязательного раздела («раздел не предусмотрен», «не выполняется») → `КРИТИЧЕСКОЕ`.
- Замечания об арифметике, нормах, перекрёстной сверке, спецификации vs текст — всё по полной программе.

**Запрещено:**
- Молчание о незначимом разделе чек-листа на `full_rd` — нельзя ставить `КРИТИЧЕСКОЕ` без явной декларации отсутствия. Используй `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.

**Cap completeness lens:** 6 (после исследования FP-аудита на full_rd: cap 14 даёт +114 FP на full_rd-наборе).

---

## `document_type = audit_comparison`

**Назначение:** документ — фрагмент сравнения двух или более разделов (например, ЭОМ vs ОВ нагрузки, КЖ vs АР отверстия). Не претендует на полноту РД.

**Разрешено:**
- Замечания ТОЛЬКО по системам/интерфейсам, которые сравнение явно покрывает.
- Расхождения чисел между разделами в самом фрагменте.
- Нормативные конфликты между разделами, видимые в фрагменте.
- `cross_discipline_with: [...]` обязателен, перечислить участвующие дисциплины.

**Запрещено (STRICT BAN — отбрасывается):**
- «Отсутствует однолинейная схема»
- «Не представлен кабельный журнал»
- «Отсутствует пояснительная записка»
- «Состав раздела неполный»
- «Не приведена спецификация оборудования»
- «Отсутствует план этажа / разрез / узел»
- Любое замечание о полноте раздела, который не предмет сравнения.

**Cap completeness lens:** 10.

---

## `document_type = tz_vs_rd`

**Назначение:** документ сравнивает требования ТЗ с реализованным РД.

**Разрешено:**
- Замечания по позициям, которые ТЗ явно требует И РД заявляет, что решает.
- Прямое противоречие ТЗ ↔ РД → `КРИТИЧЕСКОЕ` с `severity_reasoning` («нарушение ТЗ п. X.Y»).
- Молчание РД по позиции ТЗ → `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.
- Замена производителя без подтверждения эквивалентности → `ЭКОНОМИЧЕСКОЕ` или `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.

**Запрещено (STRICT BAN):**
- Выдумывать дефицит из позиций, которых нет в ТЗ.
- Любые «отсутствует X», если X не в ТЗ.
- Косметические замечания о форме изложения ТЗ или РД (не предмет аудита).

**Cap completeness lens:** 10.

---

## `document_type = specification_only`

**Назначение:** документ — спецификация, ведомость или отдельный расчёт.

**Разрешено:**
- ТОЛЬКО параметровый уровень чек-листа: марки, сечения, мощности, типоразмеры, ёмкости.
- Расхождения внутри самой спецификации.
- Несуществующие в каталогах типоразмеры/марки.
- Применение отменённых норм в обосновании конкретной позиции.

**Запрещено (STRICT BAN):**
- «Отсутствует кабельный журнал», «нет однолинейной схемы», «нет планов» — это не предмет спецификации.
- «Не приведена основа расчёта» — спецификация её и не должна содержать.
- «Состав раздела неполный» — спецификация это не раздел.

**Cap completeness lens:** 10.

## Глобальный STRICT BAN (приоритет над любыми чек-листами)

Если `document_type != full_rd`, НИКОГДА не подавай:

1. «Отсутствует полный комплект РД»
2. «Не представлена пояснительная записка»
3. «Нет однолинейной схемы»
4. «Состав раздела неполный»
5. «Кабельный журнал отсутствует в составе раздела»
6. «Спецификация оборудования отсутствует в составе раздела»
7. «Расчёт нагрузок отсутствует в составе раздела»
8. «Перечень электроприёмников / схема воздуховодов / план водопровода не представлен»

Эти замечания применимы только к `full_rd`. На любом другом типе документа corrector пометит их `out_of_scope` и удалит.

---

## Как использовать в чек-листе completeness lens

Перед каждым пунктом чек-листа сверься:

1. Покрывает ли документ этот тип элемента? (по `document_type` выше)
2. Если нет — пропусти пункт, не ставь `not_applicable` на каждый, просто не подавай finding.
3. Если документ покрывает, но молчит — `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.
4. Если документ покрывает и явно отказывается — `КРИТИЧЕСКОЕ`.
5. Если документ покрывает и есть противоречие — `КРИТИЧЕСКОЕ` (с `severity_reasoning`).

Если **все** пункты чек-листа недоступны для оценки в текущем `document_type` — поставь `applicability: not_applicable` для всей линзы с одной строкой `applicability_reason`.
