## Задача

Прочитай MD-файл ПОЛНОСТЬЮ за один проход и извлеки ВСЕ значимые замечания с привязкой к нормативной базе. Используй 6 обязательных «линз»:

### Линза 1. Параметры проекта (`project_params`)

- Тип объекта, этажность, площади
- Расчётные нагрузки, мощности, расходы
- Основное оборудование, марки, типоразмеры

### Линза 2. Нормативные ссылки (`normative_refs_found`)

- Все упомянутые СП, ГОСТ, ПУЭ, ФЗ
- Проверить актуальность каждой нормы по файлу нормативной базы

### Линза 3. Текстовые замечания (`text_findings`, нумерация T-001, T-002...)

- Несоответствия в расчётах
- Устаревшие нормативные ссылки
- Противоречия между разделами
- Пропущенные обязательные данные

### Линза 4. Арифметическая сверка таблиц (ОБЯЗАТЕЛЬНО)

- Пересчитай суммы строк и столбцов в КАЖДОЙ таблице нагрузок
- Пересчитай расчётные величины по формулам дисциплины (см. чек-лист ниже)
- Проверь площади и мощности на реалистичность
- Сверь суммарные мощности/расходы оборудования с каталожными данными

### Линза 5. Перекрёстная сверка (ОБЯЗАТЕЛЬНО)

- ПЗ vs таблицы нагрузок — совпадают ли числа?
- Спецификация vs текст ПЗ — марки, количества, типоразмеры
- Расхождения между разными местами документа → замечание
- Стандартные типоразмеры — проверь что указанные размеры существуют в ГОСТ-сортаменте

### Линза 6. Диапазоны и характеристики оборудования (ОБЯЗАТЕЛЬНО)

- Диапазон измерительных приборов должен соответствовать рабочим параметрам
- Типоразмеры — существуют ли в каталогах?
- Мощности — совпадают ли с каталожными?
- Сверка спецификации с `[IMAGE]`: оборудование на чертеже, которого нет в спецификации → замечание; позиция в спецификации, которая не встречается ни на одном чертеже → замечание

## Жёсткие правила (НАРУШЕНИЕ → ЗАМЕЧАНИЕ БУДЕТ ОТКЛОНЕНО)

1. **Evidence rule.** Каждое замечание ОБЯЗАНО содержать `evidence_quote` — verbatim-подстроку из MD-файла. Пустая цитата → замечание отбрасывается.
2. **Class rule.** Каждое замечание ОБЯЗАНО содержать `problem_class` (короткий идентификатор класса дефекта) и `affected_system` (короткое именное описание объекта).
3. **Dup rule.** Два замечания с одинаковой парой `(problem_class, affected_system)` — дубликаты. Оставь одно (с самой высокой `confidence`).
4. **Speculation rule.** Запрещены формулировки «уточнить X», «проверить Y», «требуется проверка» без конкретного дефекта. Либо есть конкретное нарушение с цитатой, либо замечание не подаётся.
5. **Norm rule.** Не выдумывай номера пунктов. Если не уверен — оставь `norm: ""`, `norm_confidence: 0`, `norm_quote: null`.
6. **Severity calibration:**
   - `КРИТИЧЕСКОЕ` — здание непостроимо как описано ИЛИ есть прямая угроза жизни/безопасности. Требуется `severity_reasoning` ≤ 120 символов с конкретным дефектом.
   - `ЭКОНОМИЧЕСКОЕ` — количественное расхождение деньги/объёмы.
   - `ЭКСПЛУАТАЦИОННОЕ` — деградация эксплуатации после сдачи ИЛИ нарушение хорошей инженерной практики с названным последствием.
   - `РЕКОМЕНДАТЕЛЬНОЕ` — только косметика, опечатки, наименования.
   - `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ` — нужны данные другой дисциплины (см. критерии ниже).
7. **Beyond-GT useful.** Если нашёл существенное инженерное замечание, не являющееся прямым нарушением нормы (например «выключатель C-кривая допустим, но D-кривая предпочтительнее для прямого пуска АД»), пометь его `is_beyond_gt_useful: true`. Категория такого замечания — `РЕКОМЕНДАТЕЛЬНОЕ` или `ЭКСПЛУАТАЦИОННОЕ`.
8. **Cap.** Не более 14 замечаний всего. Приоритет — инженерная значимость, не покрытие.
9. **Confidence:**
   - `0.95+` — `evidence_quote` прямо содержит дефект.
   - `0.80–0.94` — цитата подразумевает дефект через 1 шаг рассуждений.
   - `0.60–0.79` — нужно 2+ шага рассуждений.
   - `< 0.60` — не сообщай.
10. **Категории** — РОВНО одно из: `КРИТИЧЕСКОЕ` / `ЭКОНОМИЧЕСКОЕ` / `ЭКСПЛУАТАЦИОННОЕ` / `РЕКОМЕНДАТЕЛЬНОЕ` / `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`.

## Маршрутизация по `document_type` (HARD RULE)

Этот документ имеет `document_type = {DOCUMENT_TYPE}`. Применяй правила СТРОГО по типу:

- **`full_rd`** — полная рабочая документация. Применяй ВЕСЬ чек-лист. Отсутствие обязательного раздела → `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`. Документ явно отказывается от обязательного раздела («раздел не предусмотрен») → `КРИТИЧЕСКОЕ`.

- **`audit_comparison`** — фрагмент-сравнение разделов. Замечания о полноте ТОЛЬКО по системам/интерфейсам, которые сравнение явно покрывает. ЗАПРЕЩЕНО писать «отсутствует однолинейная схема» / «нет кабельного журнала» / «нет пояснительной записки» — это не предмет audit_comparison.

- **`tz_vs_rd`** — сравнение задания и реализованного проекта. Замечания только по позициям, которые ТЗ явно требует И РД заявляет, что решает. Прямое противоречие ТЗ ↔ РД → `КРИТИЧЕСКОЕ`. Молчание РД по позиции ТЗ → `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ`. ЗАПРЕЩЕНО выдумывать дефицит из пунктов, которых нет в ТЗ.

- **`specification_only`** — спецификация / ведомость / отдельный расчёт. Применяй ТОЛЬКО параметровый уровень чек-листа. ЗАПРЕЩЕНО писать про отсутствие разделов (кабельный журнал, однолинейная, основа расчёта) — это не предмет спецификации.

**СТРОГИЙ ЗАПРЕТ:** если `document_type != full_rd`, никогда не пиши замечания вида:
- «отсутствует полный комплект РД»
- «не представлена пояснительная записка»
- «нет однолинейной схемы»
- «состав раздела неполный»

Такие замечания применимы только к `full_rd`. На non-`full_rd` они будут отброшены corrector'ом как `out_of_scope`.

### Cap по `document_type`

- `full_rd` — до **14** замечаний (но лимит линзы completeness — 6).
- `audit_comparison` / `tz_vs_rd` / `specification_only` — до **14** замечаний (лимит completeness — 10).

## Критерии для «ПРОВЕРИТЬ_ПО_СМЕЖНЫМ»

Категория `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ` — это НЕ «упоминается другой раздел». Стандартные межразделные интерфейсы (ТЗ смежникам, указание мощностей для ЭОМ, указание расходов для ВК) — нормальная проектная практика, а не ошибка.

### СТАВИТЬ только когда:

1. **Числовое противоречие внутри раздела**, разрешимое только через смежный — например, высота подъёмника 5400 мм не стыкуется с разницей отметок ~2650 мм (нужны данные АР/КР).
2. **Нормативный конфликт** — категория помещения, класс огнестойкости или класс зоны в текущем разделе может не соответствовать смежному разделу (ПБ, АР).
3. **Физическая несовместимость** — оборудование не помещается, проёмы не совпадают, трассы пересекаются (видно из размеров в текущем разделе).
4. **Обязательный элемент, отсутствующий в ЭТОМ разделе** — например, раздел обязан показать узел примыкания к конструкции, но его нет (только для `full_rd`).

### НЕ СТАВИТЬ когда:

1. **Стандартное ТЗ смежникам** — «предусмотреть подвод ХВС/ГВС», «обеспечить электропитание 380В», «передать нагрузки в КР» — это нормальная координация.
2. **Простое упоминание чужой дисциплины** — факт что в ТХ написано про электричество не значит «проверять по ЭОМ».
3. **Общие пожелания без противоречия** — «согласовать с генпланом», «уточнить по АР» без конкретного расхождения данных.

## Нормативная точность (`norm_quote`)

Для КАЖДОГО замечания с полем `norm`:
- `norm_quote` — точная цитата текста пункта нормы (1-2 предложения). `null` если не помнишь точно.
- `norm_confidence` — `0.0–1.0`.
- Все цитаты будут проверены на этапе верификации норм (этап 04) независимо от уверенности.

## Правила записи

1. Прочитай MD-файл ПОЛНОСТЬЮ — не пропускай секции.
2. `text_findings[]` — только по текстовым данным (не по чертежам).
3. `severity` — ТОЛЬКО одно из 5 значений (точное написание прописными буквами с подчёркиваниями).
4. `evidence_quote` — verbatim из MD. Если не можешь привести подстроку — не подавай.
5. Пиши JSON через Write — НЕ выводи в чат.
6. После записи выведи краткий итог (число findings, разбивка по severity).
