# Stages: ПД vs РД vs КМД vs ПОС — implications for completeness

**Дата:** 2026-05-21

## Зачем это в completeness research

Текущие backend-чек-листы **не различают стадии**. Это создаёт системный
FP-риск: один и тот же checklist item применяется к ПД, РД, КМД,
обмерным чертежам и т.д. — но **состав документов на этих стадиях
принципиально разный**.

Phase 1 completeness-валидатор должен научиться различать стадии и
применять разный пресет mandatory-items на каждой.

## Основные стадии в РФ

| Стадия | Шифр | Кем регулируется | Что внутри |
|---|---|---|---|
| **Эскизный проект** | Эс | Договорная, без госнорм | Концепция, объёмно-планировочные решения |
| **Проектная документация** | П (ПД) | ПП РФ 87 | Раздельные тома по разделам ПП РФ 87 |
| **Рабочая документация** | Р (РД) | ГОСТ Р 21.101-2020, дисциплинарные СПДС | Марки (АР, КЖ, КМ, ЭМ, ОВ, ВК, СС…); детальные чертежи и спецификации |
| **Конструктивные металл. деталировочные** | КМД | ГОСТ 21.502-2016 | Деталировка КМ для завода металлоконструкций |
| **Проект организации строительства** | ПОС | ПП РФ 87, раздел 6 | Часть ПД, отдельный том |
| **Авторский надзор** | АН | СП 246.1325800.2016 | Журнал АН, не самостоятельный документ |
| **Сметная документация** | СМ | ПП РФ 87, раздел 11 | Часть ПД |

## Где в проекте видна стадия

1. **Шифр документа** (в штампе и в имени файла), пример:
   - `13АВ-РД-ЭМ-К3` — стадия РД, марка ЭМ
   - `13АВ-П-ЭОМ-К3` — стадия П (ПД)
   - `13АВ-КМД-К1` — стадия КМД
2. **Поле «Стадия»** в основной надписи (форма 3 / 4 / 6 ГОСТ Р 21.101-2020).
3. **`project_info.json`** проекта — поле `section` или новое поле
   `stage` (если будет введено).

## Как стадия меняет состав mandatory items

### ПД (стадия П) — раздел 5 ПП РФ 87, инженерные системы

| Item | Mandatory в ПД? | Источник |
|---|---|---|
| Пояснительная записка к разделу | да | ПП РФ 87, раздел 5 |
| Принципиальные схемы | да | |
| Сводная электробаланс / сводная тепловая нагрузка | да | |
| Детальный кабельный журнал | НЕТ — это уровень РД | ГОСТ 21.613-2014 |
| Спецификация оборудования | да (укрупнённо) | |
| Расстановка оборудования на планах этажей | да (схематично) | |

### РД (стадия Р) — марка (например, ЭМ-К3)

| Item | Mandatory в РД? | Источник |
|---|---|---|
| Общие данные марки | да | ГОСТ 21.613-2014, п. 4.1 |
| Однолинейная схема | да | |
| Кабельный журнал | да | |
| Планы этажей с трассировкой | да | |
| Расчёт нагрузок (электробаланс) | **может ссылаться на ПД** | Не обязан повторяться в каждой марке |
| Спецификация оборудования | да | |
| Сводный перечень ВСЕХ марок проекта | **НЕТ** | Это атрибут проекта в целом, а не марки |

**Важная импликация:** многие текущие checklist items (например, «Общие
данные раздела ОВ: климатические параметры, температурный график») —
формально это атрибуты ПД (раздел 5.3 ПП РФ 87), и в марке РД ОВ-К3
могут отсутствовать как «уже описанные в томе ПД». Флагать их в РД
как missing — **системная ошибка**.

### КМД — деталировка

КМД — это другой жанр. В нём:
- НЕТ пояснительной записки
- НЕТ расчётов
- ЕСТЬ только деталировочные чертежи и ведомости

Применять к КМД мерки из backend/KM.md нельзя.

### Specification_only

Применима только тем, что spec — это spec:
- Спецификация оборудования / ведомость материалов
- Возможно — единичная схема расположения

НЕЛЬЗЯ требовать в specification_only:
- Пояснительной записки
- Расчётов
- Принципиальных схем
- Координации с другими разделами

## Связь со `section` в project_info.json

Текущий `project_info.json` хранит `section` (АР / ЭОМ / ОВ / …), но
не `stage`. Это значит:

- detector умеет различить дисциплину
- detector НЕ умеет различить ПД ↔ РД ↔ КМД

**Рекомендация для Phase 1 implementation (НЕ делается в этом research'е):**
расширить detector чтобы он возвращал не только `document_type`, но и
`stage` (П / Р / КМД). До тех пор completeness-валидатор должен
ИСПОЛЬЗОВАТЬ КОНСЕРВАТИВНУЮ ПОЛИТИКУ: считать «отсутствие пояснительной
записки», «отсутствие расчёта нагрузок» и т.п. как **НЕ КРИТИЧЕСКОЕ**
а как `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ` с гипотезой «возможно, в томе ПД».

## Practical checklist (для completeness-валидатора)

Перед тем как сгенерировать missing finding, валидатор должен пройти:

1. Знаем ли мы стадию? Если нет → понизить severity до
   `ПРОВЕРИТЬ_ПО_СМЕЖНЫМ` для всех ПД-only items.
2. Применима ли норма на этой стадии? Если нет → не флагать.
3. Применима ли норма для текущего `document_type`? Если нет → не флагать.
4. Есть ли явная декларация отсутствия в MD («не разрабатывается»,
   «вне объёма этой марки»)? Если да → не флагать.
