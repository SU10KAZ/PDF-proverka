# Prompt rules update — what to add to the completeness lens prompt

**Дата:** 2026-05-21
**Контекст:** `prompts/pipeline/ru/phase1/completeness_lens_production_prompt.md`
уже содержит частичную логику классов проблем, severity-mapping и
anti-patterns. Этот документ — **добавки**, которые обязательно нужно
внести в lens prompt **до** запуска runner'а на production.

## Что добавить в системную часть lens prompt

### 1. Стадия документа (stage gate)

Добавить блок в начало системной инструкции:

```markdown
## Стадия документа — критически важно

Перед тем как генерировать missing finding, определи стадию документа:

- **ПД (П)** — проектная документация по ПП РФ 87 (тома 1-12).
  Шифр содержит «П» (не «РД», не «КМД»). В штампе стадия «П».
- **РД (Р)** — рабочая документация, конкретная марка (АР-К3, ЭМ-К3, …).
  Шифр содержит «РД» или «Р». В штампе стадия «Р».
- **КМД** — деталировочные чертежи металлоконструкций. В штампе «КМД».

Если стадия неоднозначна:
- НЕ генерируй missing findings о ПЗ/ТЭП/общем электробалансе/общих данных
  (они могут быть атрибутом другого тома проекта).
- Понижай severity таких потенциальных findings до **ПРОВЕРИТЬ_ПО_СМЕЖНЫМ**
  с явной пометкой «стадия документа не определена; возможно, атрибут
  тома ПД».
```

### 2. Document_type gate

Дополнить существующий блок:

```markdown
## Применимость по document_type

document_type = `audit_comparison`:
- НЕ требуй mandatory разделы РД (пояснительная записка, расчёты, схемы).
- Можешь требовать формальные атрибуты: штамп, шифр сравниваемого
  документа, стадия, дата, сводная ведомость замечаний с статусом.

document_type = `tz_vs_rd`:
- Mandatory: на каждое требование ТЗ — ссылка на пункт РД; явные
  отклонения с согласованием.
- НЕ требуй mandatory разделов РД из дисциплинарных чек-листов.

document_type = `specification_only`:
- Mandatory только спецификационные атрибуты: позиция, наименование,
  тип, количество, единицы, ключевые параметры по дисциплине.
- НЕ требуй ПЗ, расчётов, схем, координации.

document_type = `full_rd`:
- Применять дисциплинарный чек-лист в полном объёме С УЧЁТОМ stage gate
  и object_signal gates.
```

### 3. Coordination-as-missing запрет

```markdown
## Запрет на флагание coordination как missing

Координация между разделами (закладные, отверстия, передача
электроприёмников, алгоритмы управления АПС↔ОВ) часто оформляется
**отдельным заданием смежнику** в виде письма или протокола, которые
**не попадают в марку дисциплины**.

Запрещено генерировать missing finding на:

- «Отсутствует координация с разделом X» — если в MD нет явных
  отверстий/закладных без размеров, это процесс-артефакт, не нарушение.
- «Отсутствует передача в ЭОМ перечня электроприёмников ОВ» — это
  задание смежнику.
- «Отсутствует координация АПС с ОВ для управления ПДВ» — алгоритм
  обычно в разделе АПС/СС, не в OV.

Можешь генерировать finding на координацию ТОЛЬКО при явном противоречии:
например, «на плане АР показано отверстие 200×200 без указания
размеров для задания смежнику», «насос упомянут в ВК, но без P_уст».
```

### 4. Cross-section запрет (для одного MD)

```markdown
## Запрет на cross-section flagging при одном MD

Pipeline аудитирует один MD-документ за раз. Запрещено генерировать
missing finding на:

- «Параметры в ЭОМ не совпадают с ОВ» — мы видим только один из них.
- «Отсутствует ЭОМ как раздел» — другой раздел может быть в отдельном MD.
- «Сводный перечень разделов проекта отсутствует» — атрибут проекта в
  целом, не одной марки.

Cross-section проверки — задача отдельного pipeline'а; в этом lens —
запрещены.
```

### 5. Stage- и object-signal gates для конкретных items

```markdown
## Условные items — требуют сигнала в тексте MD

Не генерируй missing finding для следующих items без явного сигнала в MD:

### AR
- Расчёт инсоляции (AR-08), КЕО (AR-21) — требуют сигнала
  «жилое назначение» / «квартиры» / «МКД» в MD.
- Узлы кровли (AR-13), план кровли (AR-23) — сигнал «эксплуатируемая
  кровля» / «кровля с выходом».
- Узлы витражей (AR-22) — сигнал «витраж» / «СПФ» / «навесной фасад».

### EOM

  «I-особая».
- Молниезащита (EOM-22) — сигнал «молниезащита» / «высота … м» /
  «категория по СО-153».
- Компенсация реактивной мощности (EOM-20) — сигнал «двигатели» /
  «cos φ» / «промышленные нагрузки».
- УЗО (EOM-24) — сигнал «розеточная группа» / «санузел» / «ванная».

### KJ
- Ветровые пульсации (KJ-23) — сигнал «≥ 75 м» / «высотное».
- Сейсмика (KJ-24) — сигнал «сейсмо» / «балл» / «карта ОСР».
- Гидроизоляция подземной части (KJ-25) — сигнал «подвал» / «подземная

- Закладные (KJ-14) — сигнал «сварные стыки».

### KM
- Огнезащита (KM-03) — сигнал «требуемый предел огнестойкости» / «R 15»

- Болты (KM-11, 15) — сигнал «болтовое соединение» / «фрикционное».
- АКЗ расширенный (KM-23) — сигнал «агрессивная среда».

- Устойчивость поясов фермы (KM-25) — сигнал «ферма» / «покрытие из

### OV
- Противодымная вентиляция (OV-04) — сигнал «МКД ≥ 28 м» / «общественное

- Ведомость воздуховодов (OV-11), узлы ОЗК (OV-13) — сигнал
  «воздуховод» / «вентустановка».
- АХЗ/ИТП (OV-24) — сигнал «АХЗ» / «ИТП» / «теплоноситель».

### VK
- ГВС Т3/Т4 (VK-03) — сигнал «ГВС» / «горячее водоснабжение» / «ИТП».
- Параметры насосов (VK-13, 14) — сигнал «насос» / «насосная».
- Повысительная насосная (VK-22), бак ГВС (VK-23) — соответствующие

- ВПВ (VK-24) — сигнал «ВПВ» / «внутренний пожарный водопровод».

### SS
- АПС (SS-02) — сигнал «МКД ≥ 28 м» / «число квартир ≥ N» / «класс

- Расчёт извещателей (SS-06) — то же.
- Акустический расчёт СОУЭ (SS-07) — сигнал «речевая СОУЭ» / «3-5 тип».
- Домофония/СКУД (SS-23) — сигнал «домофон» / «СКУД».
- СОТС/CO (SS-25) — сигнал «подземная автостоянка».
```

### 6. Severity calibration update

Существующий severity-block прописан правильно, но добавить:

```markdown
## Severity для условных items

Если условный item не имеет сигнала в MD:
- Severity = НЕ генерировать finding (drop).

Если условный item имеет сигнал в MD и пункт явно отсутствует:
- Severity по таблице базовых severity дисциплинарного чек-листа.

Если сигнал в MD есть, но пункт частично присутствует:
- Severity = РЕКОМЕНДАТЕЛЬНОЕ + finding с фразой «дополнить».
```

### 7. Phantom-clause guard

```markdown
## Запрет на фантомные номера пунктов норм

При формулировке finding'а: если ты не можешь точно процитировать пункт
нормы (с конкретной цифрой), НЕ указывай вымышленный номер. Лучше:

✅ «СП 256.1325800.2016, раздел 6 (расчётные нагрузки)»
✅ «СП 256.1325800.2016 (ред. 29.01.2024)»

❌ «СП 256.1325800.2016, п. 6.4» — если ты не уверен в подпунктовке
❌ «ГОСТ Р 21.1101-2013» — этот ГОСТ заменён на ГОСТ Р 21.101-2020
```

### 8. ПУЭ-7 обязательная параллель

```markdown
## ПУЭ-7 — добровольное применение

При ссылке на ПУЭ-7 в finding'е ОБЯЗАТЕЛЬНО указывай параллельную
ссылку на действующий СП:

- ПУЭ-7 гл. 1.7 → + СП 437.1325800.2018 / ГОСТ Р 50571.5.54
- ПУЭ-7 разд. 7 → + СП 256.1325800.2016 разд. 7
- ПУЭ-7 п. 1.2 → + СП 256.1325800.2016 разд. 5

Без параллельной ссылки СП — отбраковать finding в самопроверке.
```

## Что добавить в anti-pattern блок lens prompt

Дополнить существующий anti-pattern блок:

```markdown
## Дополнительные anti-patterns

- Флаг «отсутствует ПЗ / общие данные / ТЭП» в одной РД-марке
  (например, ЭМ-К3, АР-К3) — это атрибут раздела ПД-тома, не марки. Drop.
- Флаг «отсутствует ПБ / ОДИ / ЭЭ» внутри инженерной марки — это
  отдельные разделы 9/10/10.1 ПП РФ 87. Drop.
- Флаг «отсутствует расчёт нагрузок» в РД-марке без проверки наличия
  ссылки «по данным ПД» — Drop.
- Флаг «отсутствует [coordination_artifact] с [discipline]» — coordination
  обычно письмо-задание, не часть марки. Drop.
- Флаг «параметры разных разделов не совпадают» при наличии только
  одной марки в MD — cross-section требует cross-MD pipeline'а. Drop.
- Флаг «ГОСТ Р 21.1101-2013» в финдинге — этот ГОСТ заменён; использовать
  ГОСТ Р 21.101-2020.
- Условные items без сигнала в MD (см. таблицу сигналов в §5) — Drop.
```

## Where to plug this in

Эти добавки идут в **самостоятельный prompt-постфикс** или в обновлённую
версию `completeness_lens_production_prompt.md`. Подход:

1. Сейчас (research only) — оставить prompt-файл в backend нетронутым.
2. На future sub-task wiring: либо
   (а) применить эти добавки к копии в
   `prompts/pipeline/ru/phase1/completeness_lens_production_prompt.md` (создав
   `completeness_lens_production_prompt_v2.md` или вставив в текущий через
   prompt_loader), либо
   (б) загружать эти rules как отдельный prompt-блок и склеивать в
   runner'e.

Решение по (а) vs (б) — отдельный proposal, не часть этой research.
