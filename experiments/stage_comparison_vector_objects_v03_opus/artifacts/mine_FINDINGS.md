# mine — БЕНЧМАРК трудных пар подготовленных графических блоков (VECTOR 0.3, Opus)

Зонд `mine`. Задача: собрать 20–30 **специально трудных** пар РЕАЛЬНЫХ подготовленных
графических блоков (`block_type == "image"` из `result.json`), пометить их классами и
описать по-русски, что именно изменилось.

Всё чтение блоков — через `probes/v03_foundation.py`. Синтетических bbox нет.
Пар «файл сам с собой» нет: sha256 обоих PDF сверены для каждой пары.

Итого в файле **33 пары**: 15 `GRAPHIC_CHANGE`, 14 `NO_GRAPHIC_CHANGE`, 2 `NOT_COMPARABLE`
(разъехались границы блоков) и 2 `UNCERTAIN`. Как эталон «изменилось / не изменилось»
пригодны 29.

Дополнительно в наборе есть классы, которых не было в задании, но которые корпус навязывает:
`bbox_boundary_artifact` (3 пары — «изменение» есть только на границе кропа),
`block_scope_change` (2 — сторона A целиком вложена в сторону B),
`occluding_fill` (1 — весь вид закрыт чёрной заливкой при том же числе сегментов),
`hatch_noise` (1 — сдвиг фазы штриховки создаёт шум по всей площади),
`block_match_failure` (1 — сопоставлены разные чертежи).

## Как устроен отбор (детерминированная часть)

1. `mine_pairs_index.py` — 99 документов с ≥2 версиями, 122 версионные пары, sha256 обоих PDF.
2. `mine_pagematch_eval.py` — сопоставление страниц и **измерение точности** правил (M3).
3. `mine_screen.py` + `mine_screen_run.py` — сопоставление блоков (жадный IoU по `coords_norm`)
   и дешёвые растровые сигналы; по одному процессу на версионную пару с жёстким таймаутом
   (одиночный `get_pixmap` на плотном листе изнутри Python не прерывается).
4. `mine_align.py` (кадр = bbox блока) и `mine_align2.py` (кадр = равный физический масштаб) —
   FFT-регистрация и разложение невязки на связные компоненты (M4).
5. `mine_shortlist.py` → уроки первого прохода → `mine_shortlist2.py` (фильтр границы кропа,
   исключение штампов из «объектных» классов).
6. `mine_extract.py` — сегменты/текст/растр через `v03_foundation.extract_block` (849 пар).
7. `mine_render_pair.py`, `mine_zoom_component.py` — картинки для глаз.
8. `mine_build_benchmark.py`, `mine_corpus_md.py` — сборка `mine_pairs.json` / `mine_corpus.md`
   с проверками «не тот же файл» и «блок действительно есть среди подготовленных».

## Gaps / not measured

* **Разметка одним размечающим.** Все `human_expected_ru` и вердикты поставлены одним
  наблюдателем (этим зондом) по трёхпанельным картинкам. Согласия второго размечающего нет,
  каппы нет. Две пары, где я не смог сказать, что изменилось, помечены `uncertain`.
* **Нет ни одной пары П↔РД.** Ось набора — только кросс-ревизионная (соседние версии одного
  документа). Причина — в корпусе (см. `pd_block_pairs.json`), а не в методе.
* **Скрининг не исчерпывающий**: кап 70 пар на версионную пару отбросил 405 кандидатов
  (случайная выборка с seed 20260823); версии сравнивались только соседние (v001→v002,
  v002→v003), «через версию» не проверялось.
* **Разбор вектора/текста посчитан на 849 парах из 3 940** — классы `dense_block`,
  `no_labels`, `different_packaging`, `raster_graphics` оценены по этой подвыборке.
* **Не измерено**, какая доля внутренней невязки приходится на текст, а какая на геометрию:
  компоненты не пересекались с bbox текстовых строк. Это следующий очевидный шаг и он прямо
  влияет на класс `text_only_change`.
* **Порог краски фиксирован** (серый < 200 при рендере). Полутоновая графика и очень светлые
  линии могут не попадать в «краску»; чувствительность к порогу не измерялась.
* **Ожидаемое число объектов** (`expected_changed_objects`) — оценка глазами и для составных
  правок (штриховка в ~15 помещениях, слой осей ~30 марок) заведомо приблизительная.
  Пары, где оно указано с `label_confidence: medium`, для метрики «ровно тот объект»
  использовать нельзя.
* Пары `EOM-1db297d2` и `GP-6bc1c029` оставлены в файле намеренно как `uncertain`
  (отказ сопоставления и нечитаемая на уровне блока разница) — считать по ним точность нельзя.
