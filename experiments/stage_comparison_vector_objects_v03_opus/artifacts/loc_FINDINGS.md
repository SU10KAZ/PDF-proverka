# `loc` — маленькое изменение в большом блоке (§10) и «counts те же, конфигурация другая» (§12)

Зонд `loc`, трек VECTOR 0.3 (Opus). Построен **компаратор уровня объектов** —
`probes/loc_common.py::ledger(exA, exB)` — и рядом с ним две базовые линии, которые он
обязан обыграть: `scalar_verdict()` (одно глобальное число похожести, линия v0.1) и
`counts_verdict()` (счётчики примитивов и объектов — прямая проверка «а не построили ли мы
очередной счётчик»).

Геометрия читается **только** через `probes/v03_foundation.py`, объекты — только через
`probes/v03_objects.py`, подмены — только через `probes/v03_counterfactual.py`.
Своего извлечения нет.

Числа из контрфактов помечены **[CF]**, из реальных пар — **[REAL]**. Пар П↔РД в корпусе
нет (зонд `pd`: точность поля `stamp_data.stage` на «П» = 0.133, у двух настоящих
П‑документов нет ни одного `document.pdf`), поэтому **все реальные пары здесь —
кросс‑ревизионные**, и слова «П↔РД» в отчёте нет ни разу.

> **Все [CF]-числа — нижняя граница.** По ходу работы в собственном измерителе нашлись два
> дефекта (DEFECT‑1, DEFECT‑2 ниже), оба исправления **монотонны** — могут только
> превратить «не нашёл» в «нашёл». Переигран 1 315 прогонов из 1 612, которые могли
> измениться; **424 строки класса C остались посчитанными старым измерителем**
> (`loc_sensitivity.json → provenance`), и полный перепрогон даст числа не хуже.

## Что построено: компаратор, который называет объект, но ищет не объектами

`probes/loc_common.py`:

```python
led = ledger(exA, exB, off=(dx, dy), LA=LA, LB=LB, meta=meta)
led["records"]   # [{type, bbox_pt, len_lost, len_new, change_len, at_boundary,
                 #   objects_a: [{object_id, cls, label, share_of_object}], objects_b: [...]}]
led["scalar"]    # базовая линия v0.1: одно число похожести
led["counts"]    # базовая линия «счётчик»: примитивы и объекты
```

Четыре решения, каждое вынуждено ИЗМЕРЕНИЕМ предыдущего зонда, а не вкусом:

1. **Всё в точках PDF.** v0.2: допуски в долях блока бессмысленны, потому что bbox
   версий физически разные (у 47 % пар ширина отличается >2 %, `mine` M4).
2. **Масштаб S общий для двух сторон** (`S = max(S_a, S_b)`). `grp` G2‑2: на
   `EOM-7fef43a3` собственный S дал 1 635 объектов против 200 на одинаковой геометрии;
   общий S чинит это на 4 парах из 19 и не портит ни одной.
3. **Реестр строится по НЕСОВПАВШЕЙ КРАСКЕ, а не сопоставлением объекта с объектом.**
   `grp` G2‑3: выше 15 000 сегментов на блок границы объектов переживают перезапись лишь
   у 0.51 краски, а это **28.6 % корпуса** (`fnd_GATEFIX`). Объекты нужны, чтобы
   **назвать** изменение, а не чтобы его найти.
4. **У каждой записи есть флаг `at_boundary`.** `mine` M5: у 36.5 % реальных пар с
   ненулевой невязкой ВСЕ крупные компоненты разницы лежат на границе кропа.

Решение №3 проверено не рассуждением, а **прогоном конкурирующего компаратора**
`object_ledger()` на тех же данных: на парах без изменений он выдаёт медианой 62 ложные
записи против 0 у реестра по краске (раздел «Фальсификация основного решения»).

### Уровни попадания (как считается «поймал»)

| уровень | что требуется |
|---|---|
| `L1` | есть хоть одна запись |
| `L2` | есть запись, чей bbox перекрывается с эталонным bbox подмены (≥0.30 по меньшей площади, с полем 1 pt) |
| `L3` | ...и её тип совместим с ожидаемым (`REMOVED_OBJECT` ↔ `CHANGED_OBJECT` и т. п.) |
| `L4` | ...и в `objects_a`/`objects_b` назван ТОТ объект, который тронул контрфакт |

`L4` — самое строгое: это ответ на вопрос «реестр указал ровно на тот объект».

## C1. Кривая чувствительности [CF]

Носители: 59 реальных подготовленных блоков (12 дисциплин, 121–59 575 сегментов,
4 полосы плотности зонда `cf`). Подмены — C1 (удалить объект), C2 (добавить), C3
(сдвинуть на 0.25/0.5/1/5 % диагонали), C6 (деформировать) и одиночные C4/C5/C7–C10.
Сторона B дополнительно прогоняется через один из режимов шума перезаписи, чтобы
положительные и контрольные прогоны отличались ровно одной вещью.

|---|---|---|---|
| sparse (<500 сегм.) | L2 0.83 / L4 0.81 (n=48) | 0.90 / 0.88 (60) | 0.93 / 0.93 (54) |
| medium (0.5–5 тыс.) | 0.91 / 0.68 (119) | **1.00 / 0.97** (119) | 1.00 / 1.00 (93) |
| dense (5–50 тыс.) | 0.86 / 0.64 (132) | 0.98 / 0.92 (130) | 0.99 / 0.97 (115) |

Плотность блока **не** определяющая: разброс L2 по столбцу `tiny` — 0.83…0.91, по
столбцу `small` — 0.90…1.00. Определяет размер тронутого объекта, и в столбце `tiny`
падает не столько L2 (место найдено), сколько **L4 (объект назван)**: 0.64–0.81 против
0.88–1.00 у `small`. Это ровно тот отказ, который `grp` измерил как нестабильность границ
объекта в плотной графике: место найдено, но краска изменения приписана соседнему объекту.

### Скаляр этой зоны не видит

Сравнение устроено так, чтобы скаляр был в лучшем положении: он считается по ТОЙ ЖЕ
несовпавшей краске, что и реестр, то есть это не «плохой» скаляр, а верхняя граница того,
что одно число может дать.

| порог скаляра | подмен в «слепой зоне» | доля всех подмен | реестр L2 в зоне | реестр L4 в зоне | медиана тронутой краски |
|---|---|---|---|---|---|
| 0.999 | 986 | 34.3 % | **0.69** | 0.50 | 1.5e‑4 от краски блока |
| 0.9995 | 780 | 27.1 % | 0.61 | 0.42 | 8.6e‑5 |
| 0.9999 | 479 | 16.7 % | 0.41 | 0.20 | 4.5e‑5 |

Читать так: **на трети настоящих изменений скаляр отвечает «NEAR_IDENTICAL», и на 69 % из
них реестр всё равно показывает конкретное место.** Ровно эта ситуация описана в v0.1:
«удалённая стена → 0.992 и строка `Число примитивов: 814 → 815`».

Обратное тоже честно: в самой глубокой зоне (0.9999) реестр теряет 59 % — но там
изменение отсутствует и на картинке (ниже).

## C5. Цена ложных записей: где ставить порог

Ложные записи меряются на шести «тихих» популяциях, потому что ни одна из них сама по
себе не честна:

| популяция | что это | записей на пару (медиана / максимум) |
|---|---|---|
| [CF] контроль без подмены, шум `none` / `jitter03` | побитно та же геометрия | **0 / 0** |
| [CF] контроль, перепаковка путей (A1) | другой экспортёр «в лоб» | **0 / 0** |
| [CF] контроль, другая плотность хорд (A3) | реальная перепаковка кривых | **0 / 24** |
| [CF] контроль, округление 0.25 pt | перезапись координат | 0 (плотные — 1) / 117 |
| [CF] контроль, узловое дрожание 1.0 pt | стресс‑тест | 6–16 / 385 |
| [REAL] 14 тихих пар бенчмарка | настоящая пара ревизий | **0 внутренних** / 207 |

Чем ближе контроль к «побитно та же геометрия», тем меньше он говорит: сторона B там
получается из стороны A детерминированной перезаписью, а не другим экспортом. Поэтому
основная оценка ложных берётся с реальных пар, а контрфактные контроли служат шкалой
«сколько шума добавляет та или иная перезапись».

### Гибридная ROC: recall из [CF], ложные из [REAL]

Обе половины меряют одну и ту же величину — длину краски в одной записи (точки PDF), —
поэтому их можно совместить; выборки при этом разные, и это указано прямо.

| порог T, pt | recall мелких подмен [CF] | ложных внутренних записей на тихую пару [REAL], среднее | доля тихих пар хоть с одной записью |

| 0 | 0.78 | 15.07 | 0.29 |

(«мелкие подмены» = tiny + small, 821 инстанс, шум 0.25 pt; на всех подменах recall выше:

**Рабочая точка.** Порог сам по себе — плохой инструмент: чтобы обнулить ложные, нужно

## Фальсификация основного решения: реестр по краске против реестра по объектам

Главное архитектурное решение зонда — искать изменение по несовпавшей краске, а объекты
использовать только для именования. Проверка сделана не рассуждением, а вторым,
конкурирующим компаратором: `loc_common.object_ledger()` сопоставляет объект с объектом
(гейт по расстоянию 3·S, по длине краски ±30 %, по дескриптору ≤0.30) и объявляет
несопоставленные объекты добавленными/удалёнными. 36 носителей, 9 дисциплин, 204 прогона.

| прогон | шум | реестр по краске: записей (медиана) | реестр по объектам: записей (медиана / максимум) |
|---|---|---|---|
| изменения нет | none | **0** | 0 / 0 |
| изменения нет | округление 0.25 pt | **0** (хоть одна запись — у 36 %) | **62 / 2 441** (хоть одна — у **97 %**) |
| удалён объект (small) | none | 1 | 1 / 11 |
| удалён объект (small) | округление 0.25 pt | **1** | **49 / 2 449** |
| сдвинут объект (small, 1 %) | округление 0.25 pt | **1** | 51 / 2 494 |

При реалистичной перезаписи координат компаратор «объект↔объект» на паре, где **ничего не
менялось**, выдаёт десятки (в пределе — две с половиной тысячи) ложных «добавлен/удалён
объект» — ровно как предсказывало измерение `grp` G2‑3 (границы объектов переживают
перезапись у 0.51 краски на плотных блоках). Реестр по краске в тех же прогонах даёт
медиану 0.

Это и есть ответ на вопрос «почему объекты не используются для поиска»: **они не
переносятся между экспортами, а краска переносится.**

* **перепаковка путей реестру безразлична по построению** — он работает со списком
  сегментов, а не путей; 10 из 10 контролей дали ровно ноль записей (носителей 10 при
  2 дисциплинах — правило «15 носителей и 5 дисциплин» не выполнено, число
  иллюстративное);
* **пересэмплировка кривых — настоящий тест, и реестр проходит его лучше обеих базовых
  линий**: медиана записей 0 (у 53 % носителей ровно ноль), при этом счётчик примитивов
  объявляет изменение у **65 %** тех же контролей, а скаляр — у 41 %. Появляющиеся записи
  коротки: медиана 4.4 pt, порог T = 20 pt оставляет их лишь у 2 носителей из 12;
* **окружность, выведенная пятью хордами, — уже другая картинка** (похожесть 0.941), и
  записи здесь не ложные: пятиугольник вместо круга видно глазом. Режим включён, чтобы
  показать границу: «другая упаковка» перестаёт быть безобидной, когда меняется видимая
  форма.

## Дефекты, найденные по дороге

### DEFECT‑1 (мой, исправлен): предикат перекрытия рамок врал на вырожденной рамке

Проверка «легла ли запись на подмену» считала отношение площадей пересечения. У изменения,
которое есть **одна прямая линия** (добавленная ветвь C9, закрытый проём C10, разрыв
полилинии C7), bbox имеет нулевую высоту или ширину, площадь пересечения обнуляется, и
запись, чей bbox **совпадал с эталонным до третьего знака**, объявлялась «не найденной»:

```
C9_add_branch  exp_bbox [951.36, 1178.976, 1006.143, 1178.976]
               rec      ADDED_OBJECT [951.36, 1178.976, 1006.143, 1178.976] 54.8 pt
               L2 = False
```

Это тот же класс дефекта, из‑за которого основание выбрасывало 45 % геометрии
(`fnd_GATEFIX`: `fitz.Rect.intersects()` ложен на прямоугольнике нулевой площади).
Исправление: обе рамки дополнительно измеряются раздутыми на 1 pt и берётся максимум из
двух значений (правка монотонна — может только превратить «не нашёл» в «нашёл»).

Цена дефекта (шум `none`, до → после): C9 **0.20 → 0.91**, C10 0.23 → 0.71,
C7 0.25 → 0.44, C8 0.78 → 0.81.

**Урок из `fnd_GATEFIX` применён дважды.** Первый раз — при постройке (реестр меряется и по
recall, и по ложным). Второй раз дефект всё равно проскочил в измерителе, и поймать его
удалось только потому, что провал был сконцентрирован ровно на классах «изменение = одна
линия», а не размазан по всем. Правило «смотри, ГДЕ именно метрика проваливается» —
рабочее.

### DEFECT‑2 (мой, исправлен): двух ожидаемых типов не было в словаре

`ADDED_BRANCH` (C9) и `REMOVED_OPENING` (C10) не были перечислены в таблице соответствия
типов, поэтому уровни L3/L4 для этих подмен были равны **0.000** независимо от поведения
компаратора. Ноль, полученный из отсутствия ключа в словаре, выглядит точно так же, как
ноль, полученный из провала алгоритма, — и это единственная причина, по которой такие
таблицы нужно читать по строкам, а не по средним.

### DEFECT‑3 (в `probes/v03_objects.py`, НЕ исправлен мной): дескриптор формы не инвариантен к переносу

Дескриптор из 25 чисел (`shape_descriptor`) обязан быть одинаковым у двух объектов с
одинаковой краской. Измерено на реальных блоках: внутри одного блока берутся группы
объектов с **точно совпадающим** множеством сегментов после переноса в начало координат
(повторяющиеся мотивы в CAD — обычное дело), и считается расстояние между их дескрипторами.

| величина | значение |
|---|---|
| блоков измерено / из них с конгруэнтными парами | 30 / 26 |
| пар точно конгруэнтных объектов | **5 323** |
| доля пар с ненулевым расстоянием | **0.45** |
| доля пар с расстоянием >0.30 | **0.0725** |
| максимум расстояния (теоретический ноль) | **2.00** |

Причина видна в коде: компоненты 8…23 — сетка занятости 4×4 внутри собственного bbox
объекта, ячейка выбирается как `int((mx - bb[0]) / w * 4)`. Штрих, чья середина попадает
ровно на границу ячейки, уходит то в одну, то в другую ячейку в зависимости от последнего
бита координаты. У симметричных мотивов таких штрихов много, поэтому перенос объекта на
28.32 pt даёт расстояние 0.557 между двумя **тождественными** символами:

```
объекты 8c784f1959d1 и 8a146ed06e8d, блок 669G-L37Y-E47 (AR)
краска совпадает точно после сдвига (28.32, 0.00), 16 сегментов, длина 82.692 у обоих
компоненты 17 и 18 (ячейки сетки): 0.0753 / 0.6993 против 0.3539 / 0.4207
descriptor_distance = 0.5573
```

Что это меняет у соседей: `grp` G7 («сопоставление только по дескриптору даёт медиану
0.700») измерял в том числе этот дефект, а не только неразличимость мотивов; `cf` отбирает
пары для C4/C5 по порогу расстояния дескрипторов ≥0.05 — а такое расстояние между
тождественными объектами достигается легко (45 % пар ненулевые), поэтому в C4 попадали
пары, различающиеся на 0.6 pt (см. C3). **Реестра это не касается: он сопоставляет краску,
а не дескрипторы** — что и было целью такого устройства.

Лечится сглаживанием (билинейное размазывание штриха по соседним ячейкам) либо отказом от
сетки в пользу инвариантов; здесь не правится, потому что модуль чужой.

## Стоимость

Одно сравнение = два слоя объектов + двустороннее сопоставление краски + кластеризация
областей изменения. Время — на нагруженной машине (параллельно шли чужие прогоны), один
процесс на сравнение.

| сегментов в блоке | прогонов | медиана, с | p90, с | максимум, с |
|---|---|---|---|---|
| <500 | 1 200 | 0.02 | 0.10 | 6.2 |
| 500–2 000 | 2 114 | 0.22 | 0.80 | 7.3 |
| 2 000–5 000 | 475 | 1.81 | 4.05 | 8.8 |
| 5 000–15 000 | 886 | 3.84 | 8.86 | 110 |
| 15 000–50 000 | 2 030 | 22.3 | 50.3 | 281 |
| >50 000 | 594 | 30.7 | 49.0 | 221 |

Фит: **t ≈ 1.99·10⁻⁵ · n^1.334** (n — сегментов в блоке). Экстраполяция: 10 тыс. — 4.3 с,
50 тыс. — 37 с, 200 тыс. — 3.9 мин, максимум корпуса (817 732 сегмента, `fnd_GATEFIX`) —
**≈26 минут на одну пару блоков**. Требование брифа «никакой квадратичности» выполнено
(показатель 1.33), но хвост корпуса всё равно неприемлем без отдельного решения:
28.6 % блоков имеют ≥10 000 сегментов.

## Gaps / not measured

1. **Пар П↔РД нет** — ось «стадия» не измерена вообще (ограничение корпуса, не метода).
   Всё [REAL] — соседние ревизии одного документа.
2. **[CF]-числа — нижняя граница**: 424 строки класса C остались посчитанными измерителем
   с DEFECT‑1/2 (`loc_sensitivity.json → provenance`). Правки монотонны, поэтому полный
   перепрогон может числа только поднять; переигран самый дешёвый и самый информативный
   слой (все режимы у 59 носителей, плюс адресно `none`/`round025`).
3. **Разметка бенчмарка — один наблюдатель** (`mine` M7), и одну её ошибку этот зонд нашёл
   (`EOM-7fef43a3`). Значит, в оставшихся 27 парах ошибки тоже возможны, и числа [REAL]
   имеют неснимаемую неопределённость ±1 пара ≈ ±7 п.п.
4. **Ложные записи на реальных парах измерены на 14 тихих парах.** Это мало: одна пара
   (`EOM-0c86dfde`) делает всё среднее. Правило границы настроено на этих же 14 парах —
   как настройка непубликуемо, только как порядок величины.
5. **Полный список записей реальных пар не сохранён**: прогон, который писал все записи с
   геометрией, был убит нехваткой памяти на машине. Сохранены 12 самых длинных записей на
   пару, поэтому сводка по границе точна при T ≥ 20 pt и занижает число ложных при T → 0.
6. **Порог сопоставления 0.8 pt не свипировался.** Он взят один на всё; кривая
   «чувствительность против допуска» не построена, хотя именно допуск задаёт нижнюю
   границу чувствительности (C3).
7. **Режимы «перепаковка путей» и «окружность → 5 хорд» прогнаны на 10 носителях двух
   дисциплин** — правило «15 носителей, 5 дисциплин» для них не выполнено (для режима
   «другая плотность хорд» выполнено: 17 / 5).

9. **Растровые блоки исключены** (2 пары бенчмарка из 33): компаратор работает только по
