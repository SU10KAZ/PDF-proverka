## 00. Главное за одну минуту

### Корневая причина

**Из 1720 вопросов CHANGE 1584 (92 %) построены на парах листов, которые
доказуемо неверны.** Конвейер сравнил «Корпуса 1, 2. План 2 этажа» с «План 4
этажа», «Корпуса 3, 3.1. План 1 этажа» с планом подземного этажа, «Корпуса 1, 2.
План 4 этажа» с «План 3 этажа». Оставшиеся 136 вопросов пришли с трёх верных пар
кровель, где на правой стороне вообще не оказалось подготовленного текста, — то
есть это тоже артефакт, а не изменение проекта.

Осмысленных инженерных вопросов среди 1720 **нет ни одного**.

### Решение стоит 1,3 секунды и ноль токенов

Строка вида `Корпуса 1, 2. План 3 этажа` лежит в текстовом слое **обоих**
документов пары в прямо сопоставимом виде. Регулярное выражение по блокам
страницы даёт **19 пар из 19**, ноль неоднозначностей, ноль непокрытых страниц
справа — за 1,33 с и без единого обращения к модели.

Продовый матчер эту строку не читает: он кладёт номер листа из штампа в запись и
больше к нему не обращается, а сигнал `title` заполняет названием тома —
«Часть 1. Архитектурные решения. Планы», одинаковым у 20 из 21 левой страницы.

### Что даёт ИИ-слой

Пока сопоставление листов не подтверждено, все сильные модели честно отказываются
разрешать атомы: 0 % `AI_RESOLVED`, 75–97 % ответов с причиной
`SHEET_RELATION_WRONG`. Они независимо ставят тот же диагноз, что и я по штампам.

Стоит подставить в пакет доказательств подтверждённое отношение листов — и
**ничего больше не меняя** — Codex `gpt-5.6-sol` разрешает **92 %** при 100 %
прохождении детерминированного верификатора. Claude в тех же условиях — 17 %.

> **Порядок работ неотменяем: сначала штамп, потом ИИ.** ИИ-слой, поставленный
> над сломанным сопоставлением листов, честно ответит «не могу» 1720 раз.

Алиасы `opus` / `sonnet` / `haiku` / `fable` разворачиваются в них же. Контроль
ошибки: несуществующая модель даёт `[claude-code:unrecognized_model]` **перед**
JSON в stdout.

**Уровни рассуждения** — `--effort low|medium|high|xhigh|max`. Замер на одной
задаче: low 10 с, high 110 с, max 204 с.

**Структурированный вывод** — `--json-schema` реализован принудительным
инструментом `StructuredOutput` (виден в init-сообщении даже при `--tools ""`),
поэтому enum держит движок, а не уговоры промпта. Провокация «верни
MATERIAL_PROPERTY» не сработала: модель осталась в enum и написала об этом в
свободном поле. Ответ приходит в двух местах: `result` — строкой, а
`structured_output` — уже распарсенным объектом (брать надо его).

**Зрение** — настоящий vision-вход есть только через `--input-format stream-json`
с base64-блоком. Работает при `--tools ""`, то есть без инструментов вообще. Путь
«дай путь к файлу, модель прочитает Read» при отключённых инструментах не просто
не работает — модель начинает выдумывать содержимое. Флаг `--file` для локальных
файлов непригоден (это загрузка облачных `file_id`).

**Сессии** — `--session-id` / `--resume` / `--fork-session` работают, контекст
переносится (двухшаговый тест пройден). Но `--resume` **дороже**: он переигрывает
историю — 6865 входных токенов против 237 у одиночного вызова.

### Codex CLI 0.150.0-alpha.12.2

Авторизация — ChatGPT-подписка (`~/.codex/auth.json`, mode=chatgpt). Бинарь
поставляется внутри расширения VS Code:
`~/.vscode-server/extensions/openai.chatgpt-26.825.32147-linux-x64/bin/linux-x86_64/codex`

**Модели** — девять, все подтверждены прогоном:

`gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-reserve`, `gpt-5.5`,
`gpt-5.4`, `gpt-5.4-mini`, `gpt-5.3-codex-spark`, `codex-auto-review`

Отдельно проверено, чего **нет**: `gpt-5.6`, `gpt-5.6-codex`, `gpt-5.5-codex`,
`gpt-5-codex`, `o3` — API отвечает «not supported when using Codex with a ChatGPT
account».

**Уровни рассуждения** — семь: `none`, `low`, `medium`, `high`, `xhigh`, `max`,
`ultra`. Значение `minimal` недостижимо ни на одной модели этой сборки.
`max` / `ultra` доступны только на части моделей.

**Структурированный вывод** — `--output-schema` уходит в Responses API строгим
`response_format`; это ограниченное декодирование, выйти за enum физически
нельзя. Ограничения схемы жёсткие:

- `additionalProperties: false` обязателен на **каждом** уровне объекта;
- `required` обязан перечислять **все** ключи `properties` (опциональных полей
  нет);
- `oneOf` запрещён, `anyOf` разрешён;
- корень схемы — только `type: object`;
- nullable работает через список типов: `{"type": ["string", "null"]}`;
- при **любой** ошибке схемы файл `-o` не создаётся вовсе — проверять надо
  существование файла, а не его содержимое.

**Зрение** — `-i FILE...` работает и комбинируется со схемой. Проверено на
реальных листах: модель прочитала штампы «Корпус 1,2. План 3 этажа. М 1:200».
Три изображения за один вызов распознаются в правильном порядке.

**Сессии** — `codex exec resume` / `fork`, id берётся из первого события
`thread.started` при `--json`. У `resume` нет флагов `-s` и `-C` — песочница
задаётся через `-c sandbox_mode=read-only`. `--ephemeral` не пишет роллаут, и
такая сессия невоспроизводима.

### Ловушки, которые ломают пакетный разбор

- Без `< /dev/null` Claude CLI ждёт stdin три секунды и печатает предупреждение
  **в поток**.
- `2>&1` у Claude запрещён: предупреждения о wildcard-правилах permissions
  попадают в stdout перед JSON и роняют разбор. Только раздельные потоки.
- Флаг Codex `-i` объявлен как `<FILE>...` — позиционный промпт после него
  проглатывается как ещё один файл. При картинках промпт обязан идти через stdin
  с аргументом `-`. Этот дефект пойман в собственном шлюзе и исправлен.
- `--json-schema` несовместим с `--input-format stream-json` при
  `--output-format json`; для картинок со схемой обязателен
  `--output-format stream-json --verbose`.

## 04. Сопоставление листов: где именно теряется истина

Продовый матчер `production-sheet-matcher.v2` двухпроходный: первый проход
отбирает пять кандидатов по дешёвым признакам, второй считает полный набор.

- Порог HIGH — score ≥ 0,70 **и** минимум два сильных сигнала (≥ 0,6).
- Порог POSSIBLE — **0,27**.
- Финальное назначение 1:1 — жадное, по возрастанию номера левой страницы.
  Глобального назначения нет, хотя венгерский алгоритм в проекте есть

по возрастанию номера левой страницы. Самый уверенный сигнал в прогоне не был ни
использован, ни показан человеку.

## 05. Stage 5 и Stage 7: одна работа, сделанная дважды

**Дублирование доказано по данным.** Множество `review_evidence_id` в вопросах
Stage 5 и множество `target_id` в решениях Stage 7 совпадают на **100 %**:
только Stage 5 — 0, только Stage 7 — 0. На 1720 объектов приходится **3440**
действий человека.

### Что делает эту пару вопросов неотвечаемой

- **Вопрос Stage 5 не показывает содержания.** Промпт — «Подтвердить изменение
  `ureview_56c5372d…` (UNKNOWN_DIMENSION)?». Карточка в интерфейсе показывает
  промпт, id, статус, селект и пустые типизированные поля. Ни `before_value`, ни
  `after_value`, ни страниц, ни перехода к доказательству — хотя эндпойнт
  `/changes/{target_id}/evidence` умеет открывать доказательство именно по этому
  id.

- **Простое «Да» запрещено.** `generic_yes_allowed: false`, обязательные поля —
  `dimension`, `project_entity_ref`, `outcome`. Человек обязан выбрать измерение
  из девяти, выбрать результат и **вписать строку** `project_entity_ref` в
  свободное поле, которое ни с чем не сверяется.

- **Решение Stage 7 по этой строке физически невозможно.** Бэкенд бросает
  «review evidence must be resolved into an atomic change before approval»,
  кнопка в интерфейсе задизейблена.

- **После ответа человек решает второй раз.** Идентичность меняется с `ureview_`
  на `uchg_`, старая строка уходит в историю, и по тому же содержимому создаётся
  новая строка PENDING_REVIEW.

- **78,8 % от 5,5 МБ** файла решений — это копии `finding_snapshot` внутри пустых
  PENDING-строк.

### Целевая семантика

**Stage 5 — разрешение исключений.** Только те вопросы, без ответа на которые
система не может построить осмысленную находку. Кандидаты по итогам исследования
— вопросы уровня листа и группы, а не уровня атома:

- неоднозначный ключ штампа (несколько правых листов с одинаковым ключом);
- лист без пары, где нужен вердикт «удалён» против «переименован»;
- доказанное противоречие между текстом и графикой.

**Stage 7 — проверка инженером готовых изменений.** Строка вида «Объект · Листы ·
Изменение · Было · Стало · Источник · Уверенность · Доказательство» и два
действия: подтвердить или отклонить.

Обычная находка не имеет права порождать и вопрос «это изменение?», и решение
«подтвердить изменение». Одно изменение — одно касание человека.

### Точка врезки уже существует

Production-путь разрешения — это не прямая генерация изменения, а типизированный
ответ на вопрос очереди по контракту `change-typed-resolution.v1`. Оркестратор сам
переписывает поля атома, ставит `review_status=CONFIRMED` и пересобирает синтез, а
`_assert_change_resolutions_materialized` fail-closed проверяет, что ответ
действительно материализовался.

Значит ИИ-слой подключается как **второй источник ответов** рядом с человеческим —
ровно по той схеме, по которой сегодня накладываются ответы инженера.

### Что ИИ возвращать не имеет права

`project_entity_ref` — это `stable_id`-хеш, а не текст. Модель, вернувшая его,
вернёт выдумку. Правильно: ИИ возвращает **подпись объекта на языке проекта**
(«помещение 24.5», «кровля К5»), а детерминированный шаг чеканит из неё реф той же
функцией, которой пользуется продюсер фактов.

Сегодня в интерфейсе это поле — свободная строка, которая ни с чем не сверяется.
Это надо закрыть независимо от ИИ.

### Шлюз сессий

Оркестратор не должен запускать CLI сам. Между ними — шлюз, отвечающий за выбор
модели, уровень рассуждения, изоляцию, таймаут, повтор, разбор структурированного
вывода и журнал.

Значительная часть уже написана и пригодна как есть:

- `run_codex_json_messages` — JSON-режим со схемой;
- `_run_codex_with_transient_retry` — классификация транзиентных отказов, backoff
  с джиттером;
- `resource_budget.slot` — глобальные лимиты конкурентности;
- `process_runner.run_command` — таймаут, чистка окружения, реестр процессов.

### Изоляция: точные команды

```bash
# Claude — ни одного инструмента, ни одной чужой настройки, 240 токенов накладных
claude -p "$PROMPT" --model claude-sonnet-5 --output-format json \
  --json-schema "$SCHEMA" \
  --tools "" --setting-sources "" --strict-mcp-config \
  --system-prompt "..." --no-session-persistence < /dev/null > out.json 2> out.err

# Codex — песочница только на чтение плюс снятие самих инструментов
codex exec -m gpt-5.6-sol -c model_reasoning_effort=low \
  -s read-only --skip-git-repo-check --ephemeral -C "$EMPTY_TMPDIR" \
  --ignore-user-config --ignore-rules \
  --disable shell_tool --disable unified_exec --disable view_image \
  --output-schema schema.json -o out.json "$PROMPT" < /dev/null
```

> Существующий `AUDIT_CODEX_SANDBOX=danger-full-access` для этого слоя не
> используется и не должен. Проверено: `-s read-only` сам по себе оставляет модели
> чтение файлов — инструменты надо снимать отдельными флагами `--disable`.

### Кэш, лимиты, режимы

**Кэш** — ключ `evidence_digest + семейство модели + версия модели + уровень
рассуждения + версия промпта + версия схемы`. Готовый образец в коде:
`text_semantic_validation` переиспользуется по паре подписей
`stage3_signature` + `text_fact_production_signature`.

**Лимиты** — `MAX_AI_ITEMS`, `MAX_AI_BATCHES`, `MAX_RETRIES`,
`MAX_CRITIC_PASSES`, `MAX_VISION_ITEMS`, `MAX_SESSION_DURATION`. При исчерпании
остаток переводится в HUMAN_REQUIRED, конвейер не падает.

**Режимы запуска:**

| Режим | Состав | Ориентировочное время |
|---|---|---|
| БЫСТРО | только детерминированный конвейер + матчер по штампу | ~25 с |
| СТАНДАРТ | + аналитик `gpt-5.6-sol/low` + верификатор | +14 с на элемент |
| ГЛУБОКО | + критик Claude Opus 5 + резерв зрения на спорном | +30–45 с на спорный элемент |

Режим по умолчанию определить после перезамера на исправленном сопоставлении
листов — сейчас данных для этого нет.

## 09. План по этапам

1. **Матчер по штампу.** Первичный ключ листа из строки штампа, неоднозначность —
   в вопрос. Ноль моделей, ноль токенов. Отдельно снять дефект жадного назначения
   и потерю статуса HIGH в очереди. *Наибольший рычаг.*

2. **Развести Stage 5 и Stage 7.** Убрать автоматическое создание вопроса на
   каждый review-элемент. Показать в карточке вопроса before/after, страницы и
   ссылку на доказательство — данные уже есть, эндпойнт уже есть. *Без моделей.*

3. **Перемерить целевую пару** после шагов 1–2. Только эти числа имеют право стать
   базой для оценки выигрыша ИИ.

4. **Эталонная разметка.** 50–100 случаев, размеченных инженером один раз:
   измерение, объект, изменение или нет, было/стало. Без неё говорить о точности
   нельзя. *Нужен человек.*

5. **Шлюз сессий и верификатор** в бэкенде, на базе существующих `codex_runner` и
   `process_runner`. Артефакт `ai_resolution.json` как второй источник ответов.

6. **Аналитик за флагом**, режимы БЫСТРО / СТАНДАРТ / ГЛУБОКО, кэш и лимиты (см.
   §07).

## 11. Простыми словами

### Как это будет работать, когда пользователь нажмёт «Запустить полный анализ»

Система откроет оба комплекта чертежей и первым делом прочитает у каждого листа
штамп в правом нижнем углу — ту самую строку «Корпус 1, 2. План 3 этажа». По ней
она сложит листы в пары: третий этаж с третьим, кровлю с кровлей, корпус с тем же
корпусом. Если у какого-то листа пары нет или их несколько, система не станет
угадывать — отложит его в короткий список вопросов.

Дальше по каждой паре листов она сравнит текст и графику так же, как делает это
сейчас, и получит список отличий. Те отличия, которые она умеет разобрать сама по
правилам, станут готовыми изменениями сразу.

Остальные она отдаст ИИ — по одному, вместе с окружающим текстом обеих сторон и
указанием, какие листы сравниваются. ИИ скажет, что именно изменилось, было и
стало, и насколько это существенно. После него каждое утверждение проверит обычная
программа: она убедится, что все названные числа и слова действительно есть в
документах, что стороны не перепутаны и что вывод не противоречит найденному
ранее. Что не прошло проверку — уйдёт на второй круг или к человеку. Спорное
дополнительно посмотрит вторая модель другого разработчика.

Инженер в итоге увидит не поток технических вопросов, а готовый список изменений:
объект, листы, было, стало, доказательство. Его дело — подтвердить или отклонить.
Вопросы ему зададут только там, где без человека действительно нельзя.

### Сколько вопросов из нынешних 1732 должно остаться человеку

**Из нынешних 1720 вопросов CHANGE — ни одного.** Это установлено: 1584 стоят на
доказуемо неверных парах листов, оставшиеся 136 — на трёх верных парах кровель,
где справа не оказалось подготовленного текста. Ни один из них не является
инженерным вопросом.

**Итоговое число назвать нельзя, и я не буду его выдумывать.** Правильное
сравнение пойдёт по девятнадцати парам листов вместо двенадцати — то есть покроет
заметно больше содержания, чем нынешний прогон. Сколько там окажется настоящих
расхождений, покажет только перезапуск после исправления сопоставления листов.

Что измерено твёрдо:

- при подтверждённом сопоставлении листов ИИ-слой с детерминированной проверкой
  закрывает **92 %** остаточных элементов, которые сегодня уходят человеку;
- развод Stage 5 и Stage 7 убирает **ровно половину** действий человека — 3440
  касаний на 1720 объектов сегодня, 1720 после.
