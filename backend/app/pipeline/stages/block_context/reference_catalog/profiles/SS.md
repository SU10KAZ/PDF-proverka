Корпус состоит из 14 разных графических грамматик. Все профили используют только
векторный текст, координаты и CAD paths. Состояние связи всегда показывает, чем она
подтверждена; визуально правдоподобная связь без опоры не становится ребром.

## Пять общих семейств

### Этажная шина

СОТ, СОУЭ, АСКУВТ и связь МГН используют этажные или пространственные полосы.
Оборудование сохраняет контейнеры корпуса и этажа. У СОТ связь камеры с ОСПД
подтверждается совпадением кодов `ВКb.d.* → ОСПДb.d`; у СОУЭ помещения группируются
с подписанной линией `Vn (P, L)` по одному геометрическому ряду.

### Системная магистраль

ВОК, АК и АСУД описывают инфраструктурный backbone. Разные цвета не смешиваются в
одно электрическое ребро. ВОК хранит сегменты `L1…L9`; АК — локальные шкафы и
интеграционные узлы; АСУД — шахты, этажи, переговорные устройства и повторители.

### Портовая связь

Коммутация шкафа трассирует цветные CAD-компоненты между физическими позициями SONAR.
Внешние подключения материализуют колоночную связь «полевое устройство → ХТ → ШАУВ».
Многоаппаратный цветной путь хранится как шина без выдуманных пар.

### Технологический процесс

Функциональная схема хранит поток воздуха, датчики, исполнительные механизмы и
геометрический порядок. Это не этажная иерархия и не клеммная схема.

### Физическое размещение

Компоновка шкафа и организация ниш отвечают на вопрос «что где находится».
Физический порядок и containment не преобразуются в электрические связи.

## Состояния доказательности

- `semantic_confirmed` — связь подтверждена кодами двух устройств;
- `same_row_geometry` — помещение/оконечник привязан к подписанному ряду линии;
- `nearest_same_building_geometry` — соседние уровни иерархии связаны по близости внутри корпуса;
- `blue_path_component` / `colored_path_confirmed` — оба узла касаются одной CAD-компоненты;
- `multi_device_bus` — CAD-компонента задевает более двух аппаратов и не разбивается на пары;
- `physical_layout` / `physical_containment` — только размещение;
- `x_order_geometry` / `column_alignment` — геометрический порядок, не электрическое подтверждение.

## Граница доказательности

- планы содержат сетку осей и граф цветных трасс; чистое X-пересечение без path-конца
  по-прежнему не считается соединением, а контуры помещений не выдумываются;
- схемы подключения дают `path_confirmed` только для двух клемм одной CAD-компоненты;
  многоклеммные цепи остаются `multi_terminal_review`;
- принципиальные схемы исключают внутреннюю графику корпусов из внешней цепи, привязывают
  порты к `QF/X/A/G/БП/UPS` и хранят многоаппаратную шину как гиперсеть, а не набор ложных пар;
- монтажные узлы и щиты описывают физическую сборку, а не электрическую топологию;
- точка доступа хранит виды и позиционные выноски, не смешивая их с кабельным графом.

## Результат

- 19/19 crop-файлов содержат текст и CAD paths;
- 19/19 проходят минимальные гейты распознавания/извлечения;

- Stage 02 получает структурированный Markdown через `block_source_router`.

Строгий статус полноты отделён от минимального гейта. После трассировки планов и электрических
схем 19/19 блоков имеют `complete`. Статус означает полноту для целевой грамматики блока; он не отменяет

# Структуры логического описания структурных схем СОВ/СКУД

## Общая граница

Три PDF используют один технический способ чтения — векторный текст, рамки и цветные
paths, — но результат у них разный. Общим остаётся только внешний конверт:

```json
{
  "profile_id": "...",
  "source": {"pdf_file": "...", "page_index": 0, "block_id": "..."},
  "containers": [],
  "nodes": [],
  "networks": [],
  "edges": [],
  "external_references": [],
  "validation": {},
  "warnings": []
}
```

`containers` отвечают на вопрос «где находится оборудование», `networks` — «какая
линия показана», `edges` — «какие узлы она соединяет». Геометрическое соседство само
по себе не создаёт связь.

## 1. СОВ К1–К2 — `sov_structural_tower_pair`

Источник: `Структурная схема СОВ — К1-К2 — 6X4P-4EGH-VJ9.pdf`.

### Особенность грамматики

Два однотипных корпуса расположены рядом. Каждый корпус разбит на фиксированные
горизонтальные диапазоны: `-1 этаж`, `1 этаж`, `2–11`, `12`, `13–20`, `21–39`,
`Кровля`. Диапазоны без оборудования являются частью проектного смысла и не должны
исчезать из результата.

### Целевая структура

```text
document
├── building 1
│   ├── control zone / ПО №...
│   ├── floor bands (включая shown_empty)
│   │   ├── rooms
│   │   └── equipment
│   └── territory
└── building 2
    └── ...
```

```json
{
  "profile_id": "sov_structural_tower_pair",
  "buildings": [
    {
      "id": "building-1",
      "name": "1 Корпус",
      "control_zones": [
        {"id": "building-1/po-1", "label": "ПО №1", "floor_band_ids": []}
      ],
      "floor_bands": [
        {
          "id": "building-1/floor:-1",
          "scope": {"kind": "single", "value": -1},
          "display_state": "present",
          "rooms": [],
          "equipment_ids": []
        },
        {
          "id": "building-1/floors:2-11",
          "scope": {"kind": "range", "from": 2, "to": 11},
          "display_state": "shown_empty",
          "rooms": [],
          "equipment_ids": []
        }
      ],
      "territory": {"locations": [], "equipment_ids": []}
    }
  ],
  "nodes": [],
  "networks": [],
  "edges": []
}
```

Типы узлов пилота:

- 6 шкафов `ОСПД`;
- 6 сетевых контроллеров `К`;
- 33 модуля доступа `STR`;
- 2 монитора консьержа `DP`;
- 10 вызывных панелей `VP`.

Уникальный ID всегда включает корпус. Одинаковые подписи `ПО №1` в двух колонках не
являются одним узлом.

### Сети

- `optical_backbone` — оранжевая вертикальная магистраль между ОСПД;
- `rs485` — пурпурная линия `К → STR → STR`;
- `ethernet` — синяя линия `DP/VP → ОСПД`;
- `access_peripherals` — зелёная комбинированная линия локальных устройств;
- `power` — чёрная линия, если присутствует в конкретном фрагменте.

### Гейт

- найдены ровно два корпуса;
- все семь этажных полос каждого корпуса сохранены, включая пустые;
- ≥95% оборудования привязано к корпусу и этажной полосе;
- связь выдаётся только при подтверждённых path-концах;
- пустой диапазон не считается ошибкой и имеет `display_state=shown_empty`.

## 2. СОВ К3–К6 — `sov_structural_multitower`

Источник: `Структурная схема СОВ — К3-К6 — 6F7E-TCVU-KYW.pdf`.

### Особенность грамматики

Четыре корпуса имеют разные высотные схемы и неодинаковый состав оборудования.
Присутствуют несколько ОСПД в одном корпусе, верхние этажные контроллеры, АРМ СКУД,
источник питания и ссылки на смежные комплекты. Поэтому корнем связи является не
только этаж, но и `control_domain` конкретного ПО/ОСПД/контроллера.

### Целевая структура

```text
document
├── building 3
│   ├── floor bands
│   ├── rooms
│   └── control domains
│       └── ПО → ОСПД → К → RS-485 chain STR
├── building 4
├── building 5
├── building 6
└── shared nodes / АРМ СКУД
```

```json
{
  "profile_id": "sov_structural_multitower",
  "buildings": [
    {
      "id": "building-3",
      "floor_bands": [],
      "rooms": [],
      "control_domains": [
        {
          "id": "building-3/domain-1",
          "po_labels": ["ПО №1", "ПО №7"],
          "cabinet_ids": ["ОСПД3.1"],
          "controller_ids": ["К3.1.-1.1"],
          "rs485_chains": [
            {"controller_id": "К3.1.-1.1", "member_ids": [], "path_state": "present"}
          ]
        }
      ]
    }
  ],
  "shared_nodes": [],
  "nodes": [],
  "networks": [],
  "edges": [],
  "external_references": []
}
```

Типы узлов пилота:

- 8 шкафов `ОСПД`;
- 6 контроллеров `К`;
- 46 модулей `STR`;
- 3 монитора `DP`;
- 9 панелей `ТД`;
- 6 панелей `VP`;
- `UG1` и `АРМ СКУД` как специальные узлы.

Семантика цветов совпадает с К1–К2, потому что на листе присутствует та же таблица
условных обозначений кабельных линий. Внешние ссылки на комплекты ОСПД, ЭМ и АПС
сохраняются в `external_references`, а не превращаются в отсутствующие узлы.

### Гейт

- найдены корпуса 3, 4, 5 и 6;
- этажные диапазоны определяются отдельно для каждого корпуса;
- ≥95% `STR/К/ОСПД/DP/ТД/VP` имеют корпус и этажную полосу;
- каждый `control_domain` содержит хотя бы ОСПД либо контроллер;
- RS-485 и Ethernet не объединяются в одну сеть даже при геометрическом пересечении;
- ссылки за пределы листа получают `edge_state=external_reference`.

## 3. Аналог СКУД — `skud_structural_site`

Источник: `Аналог — Структурная схема СКУД — 9AJM-YHWM-CV9.pdf`.

### Почему это отдельная структура

Здесь нет набора одинаковых колонок-корпусов. Лист описывает участок: жилой дом,
два павильона, въезд в паркинг и территорию. Пожарные отсеки пересекают этажи и
сооружения, поэтому они являются `overlays`, а не родителями в дереве.

### Целевая структура

```text
site
├── structures
│   ├── жилой дом
│   ├── общественный павильон
│   ├── административный павильон
│   └── въезд в паркинг
├── territory locations
├── floor bands
├── locations
│   └── access points
│       └── controller + reader + lock + contact + button
├── infrastructure (ОСПД / SW / UG / STR)
└── overlays (пожарные отсеки 1…4)
```

```json
{
  "profile_id": "skud_structural_site",
  "site": {"id": "site-1", "structure_ids": [], "territory_location_ids": []},
  "structures": [],
  "floor_bands": [],
  "locations": [],
  "access_points": [
    {
      "id": "access-point-1",
      "location_id": null,
      "controller_id": null,
      "device_ids": [],
      "assembly_state": "present"
    }
  ],
  "infrastructure_nodes": [],
  "overlays": [
    {"id": "fire-compartment-1", "kind": "fire_compartment", "member_ids": []}
  ],
  "networks": [],
  "edges": []
}
```

Якоря инфраструктуры пилота: `ОСПД.М.1`, `ОСПД.S.4`, `ОСПД_S.2`, `SW.2.2`,
`SW.2.6`, `STR1.1`, `STR1.2`, `STR2.1`, `UG1.1…UG1.3`. Повторяющиеся внутри
дверного комплекта подписи `К1/К3/К4/К5` являются клеммами/портами, а не отдельными
сетевыми контроллерами верхнего уровня.

Цветовую легенду СОВ к этому профилю применять нельзя. Тип сети определяется по
позиционной подписи линии и локальной легенде СКУД; цвет используется как
дополнительный геометрический признак.

### Гейт

- обнаружен корень `site` и минимум две структуры/территориальные зоны;
- ≥90% дверных комплектов привязаны к location;
- пожарные отсеки сохранены как overlays и не ломают дерево размещения;
- клеммы `К1/К3/К4/К5` не попадают в инвентарь оборудования;
- межузловое ребро имеет path, подпись линии либо состояние `requires_review`.

## Порядок реализации

1. `sov_structural_tower_pair`: самая регулярная сетка, эталон геометрии этажных полос.
2. `sov_structural_multitower`: тот же backbone плюс control domains и внешние ссылки.
3. `skud_structural_site`: отдельный адаптер сооружений, access points и overlays.

Сначала строится точная иерархия размещения. Цветная топология добавляется вторым
гейтом и не должна блокировать использование уже подтверждённого инвентаря.
