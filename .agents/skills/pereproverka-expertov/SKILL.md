# Перепроверка решений экспертов

Работать как специализированный агент `pereproverka_expertov`. Использовать
`gpt-5.6-sol` с `model_reasoning_effort=high`. Не создавать кастомных Luna-агентов,
не запускать Luna, DeepSeek, OpenRouter или иной гибрид вместо Codex Sol. Результаты
экспериментов с альтернативными моделями считать архивными и не включать в рабочий
аудит.

Стабильное имя профиля агента: `pereproverka_expertov`. Явный вызов навыка:
`$pereproverka-expertov`.

Каждый finding оценивать как самостоятельный кейс. Не переносить доказательства,
комментарий инженера или вывод соседнего замечания без собственной точной привязки.
Раздельно устанавливать `factual_verdict`, `report_value`, `decision_effect`,
`rejection_basis` и `practical_impact`; не подменять ответ на одну ось ответом на
другую. Визуально-чувствительный вывод подтверждать растром, а связанный документ
оформлять отдельным источником с кодом, версией и страницей.

Запускать готовый CLI из корня репозитория. Не реализовывать параллельный обход данных и не подменять его глобальным логом решений.

## Соблюдать границы

- Использовать `backend/scripts/audit_rejected_findings_codex.py` как единственную точку запуска.
- Читать решения только из canonical `projects_v2/**/versions/*/04_review/expert_review.json`; CLI сам связывает решение с finding той же версии.
- Не использовать `knowledge_base/decisions_log.json` как источник выборки: он не version-aware и содержит исторические дубли.
- Не изменять `projects_v2`, `expert_review.json`, findings, базу знаний или исходные PDF. Писать только отчётные артефакты в `comparison/rejected_findings_audit/<month>/` либо в явно заданный `--output-dir`.
- По умолчанию проверять только ручные `rejected` findings. Добавлять `--include-carried-over` или `--include-optimizations` только по прямому запросу пользователя.
- Для «всех за июль» не задавать фильтры объектов и дисциплин. Если год не указан и текущая задача относится к июлю 2026, использовать `--month 2026-07`.
- Считать месяц в `Europe/Moscow`, если пользователь не указал другой часовой пояс. Помнить: timestamp решения — время последнего пакетного сохранения, а не гарантированная дата первого решения эксперта.
- Не запускать платный API или локальную vision-модель как fallback. Если Codex CLI не авторизован либо достигнут subscription/rate limit, остановиться и продолжить той же командой после восстановления подписочной сессии.
- Если пользователь задаёт порог остатка недельного лимита, останавливаться до его пересечения. Отчитываться о прогрессе с указанным пользователем интервалом; без заданного интервала сообщать после пилота, при остановке и в конце.
- Перед любым `run` явно сообщить пользователю, что выбранные findings, OCR/текстовые фрагменты и изображения будут переданы внешнему подписочному Codex, получить подтверждение и только после него добавлять `--confirm-external-codex`.

Перед оценкой результатов полностью прочитать [references/verdict-contract.md](references/verdict-contract.md). Опираться на нормализованный `verdict` и `guard_adjustments`, а не на `raw_verdict`.

## 1. Подготовить замороженную выборку

Запустить:

```bash
python3 backend/scripts/audit_rejected_findings_codex.py prepare --month 2026-07
```

Для нестандартного каталога результатов добавлять один и тот же `--output-dir` ко всем последующим командам.

Проверить `inventory.json` и `summary.json`:

- `selected_cases` больше нуля;
- интервалы `from` / `to_exclusive` соответствуют месяцу;
- учтены `source_item_found`, `source_item_missing`, `missing_expert_reason`, `suspected_carryover_reason` и распределение `by_route`;
- `manifest.jsonl` создан и содержит version-specific snapshot каждого кейса.

Зафиксировать найденные пробелы данных в итоговом отчёте. Не считать отсутствие finding или причины доказательством ошибки эксперта.

После подготовки использовать `--reuse-manifest`, чтобы пилот и полный прогон работали на одном замороженном наборе. Не пересобирать manifest посреди прогона. Для намеренного нового среза выбрать новый `--output-dir`.

## 2. Выполнить обязательный пилот

Сначала обработать небольшую выборку:

```bash
python3 backend/scripts/audit_rejected_findings_codex.py run --month 2026-07 --reuse-manifest --confirm-external-codex --limit 8 --batch-size 2 --max-batch-images 4 --model codex/gpt-5.6-sol --reasoning-effort high

python3 backend/scripts/audit_rejected_findings_codex.py report --month 2026-07
```

Просмотреть все пилотные строки в `results.jsonl` или `results.csv`. Переходить к полному прогону только если:

- нет систематических `status=error` и `halted_reason`;
- каждый `expert_correct` имеет проверенное внешнее evidence;
- каждый `expert_may_be_wrong` имеет проверенное внешнее evidence либо строго доказанный конфликт привязки;
- `image_index`, `block_id`, locator и quote относятся к тому же `case_id`;
- визуально-чувствительный вывод не основан только на OCR и не скрывает конфликт text layer/растра;
- evidence связанного документа имеет отдельный `source_id`, код, версию и страницу и не проходит через поверхность основного тома;
- `decision_effect=reason_only` не создаёт ручного кандидата, если отклонение оправдано и `report_value=remove`;
- подозрительные ответы были понижены guards до `insufficient_evidence`.

Считать `insufficient_evidence` нормальным безопасным исходом. Не ослаблять guards ради увеличения числа определённых вердиктов.

## 2.1. Автономно добрать недостающий контекст

После отчёта не оставлять `insufficient_evidence` без попытки восстановления, если результат содержит `missing_context`. Сразу запускать локальный preflight второго прохода:

```bash
python3 backend/scripts/audit_rejected_findings_codex.py auto-retry \
  --month 2026-07 \
  --source-output-dir comparison/rejected_findings_audit/<исходный-прогон> \
  --model codex/gpt-5.6-sol \
  --reasoning-effort high
```

Если `--output-dir` не указан, CLI сам возобновляет последний совместимый `auto-retry-vN`; при смене retrieval/disclosure-контракта создаёт следующую версию и не перезаписывает историю.

`auto-retry` самостоятельно:

1. выбирает только актуальные успешные `insufficient_evidence` с точной привязкой, ручным решением и источником той же версии;
2. закрепляет exact source-блоки замечания и не позволяет похожим найденным блокам вытеснить их;
3. восстанавливает старые `blk_...` и новые block ID из same-version JSON, локальных PNG, vector graph и сохранённых crop URL; если штатный crop удалён, ищет точный block ID в локальном архиве экспериментов и принимает его только при единственном согласованном SHA-256 всех найденных копий;
4. если `missing_context` уже перечисляет точные block ID, не расходует image slots на похожих соседей; иначе ранжирует отдельные смысловые цели и добавляет не более двух соседних блоков;
5. восстанавливает crop из канонического PDF по странице и `coords_px/coords_norm`, добирая размеры страницы из `document_graph`; если спор зависит от взаимного расположения, штампа или полноты листа, рендерит полный лист, а при отсутствии PDF собирает spatial composite;
6. при запросе спецификации, ведомости, экспликации или таблицы отдельно сканирует последние 12 страниц того же документа, выбирает до трёх наиболее вероятных листов и приоритетно рендерит их вместе со страницами недоступных блоков;
7. копирует все изображения в отдельный `context_assets/`, удаляет битые/stale пути, пересчитывает `input_hash` и создаёт новый frozen manifest;
8. сохраняет все закреплённые source-блоки до защитного потолка 32 изображения и автоматически поднимает фактический batch image cap до максимума замороженного кейса, чтобы набор не был тихо усечён;
9. ограничивает автоматический повтор одним уровнем: третий проход не создаётся.

Разрешены только HTTPS crop URL из уже сохранённых артефактов той же версии: `vibe.cloud-ip.cc` и точные `pub-*.r2.dev` пути. Redirect, неожиданный host, несовпадающий block ID, не-PDF и файл сверх лимита отклоняются. Применять лимиты 25 МБ на ответ, 96 МБ на кейс и 512 МБ на локальную сборку, проверять свободное место и PDF magic даже при cache hit. Скачанные файлы и рендеры хранить только внутри каталога сравнения; CLI обязан отклонять `--output-dir` внутри `projects_v2`, его предка или путь через symlink.

Первый вызов `auto-retry` не обращается к модели. Он печатает case ID, объём OCR/текста, список изображений, путь к `external_codex_disclosure.json` и его SHA-256, после чего останавливается. Показать эти данные пользователю. Непосредственно перед внешним вызовом CLI обязан заново проверить SHA manifest/inventory, размер и SHA каждого изображения, отсутствие symlink и точное совпадение фактического image alignment с disclosure; любое изменение после подтверждения блокирует запуск. Только после явного подтверждения выполнить ту же команду с:

```bash
--confirm-external-codex --confirm-disclosure-sha256 <показанный-SHA-256>
```

Для автоматического повтора использовать только `codex/gpt-5.6-sol` с `reasoning-effort=high`. Кастомного Luna-агента и Luna-потоки в этом workflow не создавать и не использовать.

## 2.2. Глубокое восстановление оставшихся `Недостаточно данных`

Если после объединённого auto-retry остаются `insufficient_evidence`, не повторять
тот же ограниченный поиск. Запустить отдельный recovery-проход над финальным
замороженным manifest/results:

```bash
norms/tools/venv/bin/python backend/scripts/audit_rejected_findings_codex.py recover \
  --month 2026-07 \
  --source-output-dir comparison/rejected_findings_audit/<финальный-объединённый-прогон> \
  --model codex/gpt-5.6-sol \
  --reasoning-effort high
```

`recover` является отдельным расширенным этапом, а не рекурсивным третьим
`auto-retry`. Он автономно:

1. рассматривает все актуальные `insufficient_evidence`, в том числе с пустым `missing_context`;
2. увеличивает поиск по всему `document_graph`, сохраняет релевантный текст и при запросе спецификации обязательно проверяет последние 12 страниц;
3. рендерит до восьми приоритетных страниц канонического PDF: сначала все явно запрошенные одиночные листы, списки и диапазоны, затем страницы недоступных source-блоков, страницу finding, найденные спецификации и другие релевантные страницы; при отсутствии PDF строит проверяемый композит по координатам блоков;
4. повторно извлекает все ссылки и диапазоны пунктов и таблиц норм из finding, причины эксперта и предыдущего аудита, связывает каждый локатор только с ближайшим кодом нормы и получает буквальные тексты и статусы из локального authoritative corpus; дополнительно выполняет семантический поиск внутри каждого указанного документа, передавая результаты только как кандидатов, а не готовый вывод;
5. ищет ограниченный контекст в явно связанных документах того же объекта, ранжирует ПЗ, ПЗУ, ИОС, ППР, ЭОМ и пожарные разделы по типу запрошенного документа и всегда сохраняет код, раздел, версию и путь источника;
6. не считает текущую редакцию связанного документа доказательством редакции на дату решения, если временная привязка не подтверждена;
7. создаёт `recovery_classification.json` для всех рассмотренных недостаточных кейсов и не отправляет модели случаи с ненадёжной версией, нечеловеческим origin или конфликтом binding;
8. включает во внешний frozen manifest только кейсы, где найден новый проверяемый материал;
9. если объединённый текст ошибочно связал локатор с соседней процитированной нормой, проверяет тот же точный локатор во всех уже процитированных нормах и меняет привязку только при единственном буквальном совпадении;
10. раскрывает составные диапазоны вроде `5.18.7–5.18.10`, не переносит локаторы через `;`, границу предложения или отдельный смысловой абзац;
11. различает буквальный текст, точный локатор, отсутствующий во всей локальной копии, и норматив, отсутствующий в authoritative corpus; сначала обязательно обращается к локальному Norms MCP/API, найденный локально текст не заменяет внешним и переходит во внешний поиск нормы только после сохранённого `not_found`/`not_in_index`, затем добавляет официальную публикацию в Norms vault с URL и фиксированным SHA-256.

Первый вызов `recover`, как и `auto-retry`, является только локальным preflight.
Он показывает число кейсов/изображений/символов, путь к disclosure и SHA-256.
После явного подтверждения пользователя повторить ту же команду с:

```bash
--confirm-external-codex --confirm-disclosure-sha256 <показанный-SHA-256>
```

Обычный `recover` не повторять над собственным результатом. Если после первого
глубокого прохода модель сформулировала новый точный `missing_context`, разрешён
ровно один дополнительный локальный evidence-exhaustion preflight над frozen
результатом `recover`: сохранить прежние evidence, извлечь новые явно названные
листы/блоки, снова обратиться сначала к локальному Norms MCP/API и искать только
новые смежные документы. Во внешний manifest включать кейс лишь при фактическом
material delta. Третий рекурсивный уровень CLI обязан отклонить. После завершения
объединить результат с предыдущим полным отчётом по canonical `case_id`, сохранив
неперепроверенные и безопасно классифицированные строки.

## 3. Запустить полный возобновляемый аудит

После успешного пилота убрать `--limit` и продолжить по тому же manifest:

```bash
python3 backend/scripts/audit_rejected_findings_codex.py run --month 2026-07 --reuse-manifest --confirm-external-codex --batch-size 4 --max-batch-images 6 --delay 0.5 --model codex/gpt-5.6-sol --reasoning-effort high
```

Повторять эту же команду после безопасного прерывания. CLI пропускает успешный результат только при совпадающем `case_id` и `input_hash`; ошибки остаются доступными для повторной обработки. При необходимости ограничивать отдельный сеанс через `--max-calls`, не меняя manifest.

Не удалять и не переписывать `results.jsonl`: это append-only checkpoint. При `subscription_or_rate_limit` не запускать альтернативную модель; сообщить о паузе и затем возобновить.

Для точечного повтора использовать один или несколько `--case-id RF-...`. Фильтры `--objects` и `--disciplines` применять только при подготовке отдельного явно ограниченного среза.

## 4. Сформировать и проверить отчёт

После каждого этапа и в конце запускать:

```bash
python3 backend/scripts/audit_rejected_findings_codex.py report --month 2026-07
```

Проверить:

- `summary.json` — полноту, ошибки и распределение нормализованных verdicts;
- `results.csv` — текущую строку каждого кейса и все независимые оси оценки, включая влияние на решение, практическую значимость, сверку OCR/растра и статус связанного контекста;
- `candidates.json` — только кандидатов с `recommended_action=manual_recheck`;
- `report.md` — краткую сводку для человека;
- `results.jsonl` — первичный checkpoint и `guard_adjustments`.

Завершать работу только после полного прогона либо явной остановки по лимиту/недоступной подписочной сессии. Сообщать пользователю:

- период, timezone и число выбранных/проверенных/оставшихся кейсов;
- распределение итоговых verdicts и число `manual_recheck`;
- число ошибок привязки, отсутствующих причин и недостающего контекста;
- пути к отчёту и кандидатам;
- что исходные экспертные решения не менялись;
- что `expert_may_be_wrong` означает кандидатуру на ручную перепроверку, а не автоматическую отмену решения.

Экспортировать читаемый русский Excel командой:

```bash
python3 scripts/export_rejected_findings_excel.py <audit-dir> --output <report.xlsx>
```

Если полный базовый прогон и успешный повторный проход находятся в разных каталогах,
объединять их только по `case_id`: успешный актуальный retry заменяет базовый результат,
а остальные базовые кейсы сохраняются. Проверять неизменность объекта, раздела,
документа, версии, ID замечания, текста finding и причины эксперта. Использовать:

```bash
python3 scripts/merge_rejected_audit_runs.py \
  --base-dir <complete-base-dir> \
  --overlay-dir <retry-dir> \
  --output-dir <new-merged-dir>
```

Затем экспортировать объединённый каталог через `export_rejected_findings_excel.py`.
Не перезаписывать исходные отчёты и каталоги прогонов.
