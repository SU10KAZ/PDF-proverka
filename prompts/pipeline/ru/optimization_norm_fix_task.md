# ПЕРЕСМОТР ОПТИМИЗАЦИЙ С УЧЁТОМ АКТУАЛЬНЫХ НОРМ — MCP-режим

## Режим работы

Работай АВТОНОМНО. Не задавай вопросов.

### Запрещено

- `WebSearch`, `WebFetch`, любые интернет-запросы
- Использовать `norms/norms_db.json` как источник истины — он больше не authoritative
- Придумывать замену норме, если MCP её не вернул
- **УДАЛЯТЬ предложения.** Даже если норма отменена, а предложение потеряло смысл —
  оставь его с пометкой. Решение принимает эксперт, а не ты.

### Обязательно

- Использовать MCP-инструменты сервера `norms`:
  - `mcp__norms__get_norm_status(code)` — authoritative статус нормы
  - `mcp__norms__get_paragraph_json(code, paragraph)` — текст пункта нового документа
  - `mcp__norms__semantic_search_json(query, top, code_filter)` — найти аналог пункта в замене
- Если замена не найдена — честно пометить `norm_status: "warning"` и описать причину

## Задача

Это НЕ правка ссылки. Норма, на которую опиралось предложение, изменилась — значит
могло измениться и само предложение. Для КАЖДОГО предложения из списка выше:

1. Прочитай текущую формулировку из `optimization.json` (`current`, `proposed`, `norm`).
2. Найди в `norm_checks.json` запись `checks[]` со своим `id` в `affected_optimizations`:
   - `status = cancelled` → норма отменена. Если `replacement_doc` заполнен — проверь через
     MCP `get_norm_status(replacement_doc)`. Если замены нет — `norm_status: "warning"`,
     в `revision_reason`: «норма отменена без замены».
   - `status = replaced` → используй `replacement_doc`. Вызови
     `get_paragraph_json(replacement_doc, <номер пункта>)`, чтобы найти аналогичный пункт.
     Если его нет — `semantic_search_json(query=<требование>, code_filter=<replacement_doc>)`.
   - `status = outdated_edition` → документ действует, указана устаревшая редакция.
     Обнови номер редакции, проверь текст пункта через MCP.
   - `status = not_found` → нормы нет в Norms-main. НЕ угадывай — `norm_status: "warning"`,
     в `revision_reason`: «норма отсутствует в Norms-main, см. missing_norms_queue.json».

3. **Переосмысли предложение** в свете актуальной нормы и выбери ОДИН исход:
   - `still_valid` — суть предложения не зависела от изменившейся нормы (замена аналога,
     унификация, укрупнение узлов). Обнови только ссылку в `norm`.
   - `revised` — новая норма меняет содержание: другой порог, другой сортамент, иные
     условия применения. Перепиши `proposed` (и при необходимости `savings_pct`,
     `risks`) под актуальное требование.
   - `obsolete` — новая норма делает предложение бессмысленным или запрещает его
     (например, предлагался отказ от того, что теперь обязательно). НЕ удаляй:
     поставь `requires_review: true`, `savings_pct: 0` и объясни в `revision_reason`.

4. Если предложение лишь повторяло требование отменённой нормы — это `obsolete`.

## Выходной файл

ЗАПИСАТЬ: `{OUTPUT_PATH}/optimization.json`

Прочитай текущий файл, обнови ТОЛЬКО предложения из списка выше, запиши обратно.

Для каждого обновлённого предложения добавь поля:
- `"norm_verified": true`
- `"norm_status": "revised" | "warning"` (warning — если замена не найдена)
- `"norm_outcome": "still_valid" | "revised" | "obsolete"`
- `"norm_revision": {{"original_norm": "...", "revised_norm": "...", "revision_reason": "..."}}`

Для остальных (не в списке): `"norm_verified": true, "norm_status": "ok"`.

## Правила

1. НЕ удаляй и НЕ добавляй предложения — только обновляй существующие.
2. Сохрани ВСЕ оригинальные поля каждого предложения, включая `id`.
3. Не меняй `id` — по нему предложение связано с решениями эксперта.
4. Если MCP не вернул замену — не выдумывай номер пункта. Пометь warning.
5. Пиши JSON через Write — не выводи в чат.
6. После записи выведи краткий итог: сколько still_valid / revised / obsolete, сколько warning-ов.
