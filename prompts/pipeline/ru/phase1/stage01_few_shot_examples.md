# Stage 01 — Few-shot примеры (Russian)

Набор worked-примеров для калибровки Stage 01 prompt. Каждый пример: фрагмент MD → ожидаемый JSON → пояснение. Категория примера:

- **GOOD** — корректное замечание (правильная схема, verbatim evidence).
- **BAD (spec)** — спекулятивное замечание (запрещено, демонстрация чего НЕ делать).
- **DO-NOT-REPORT** — косметика на non-`full_rd`, или silent-absent на non-`full_rd`.
- **DUP COLLAPSE** — два замечания с одинаковой парой `(problem_class, affected_system)` → схлопнуть в одно.

## Пример 1 — EOM — GOOD (КРИТИЧЕСКОЕ, кабель)

**document_type:** `full_rd`

**MD:**
```

Кабель ввода: АВВГ 4×95, Iдоп 220 А. Расчётный ток 302 А, коэффициент использования 0,9.
Автомат ввода: ВА57-35 250 А.
```

**Finding:**
```json
{
  "id": "T-001",
  "problem_class": "cable_undersized",
  "affected_system": "Кабель ввода ВРУ-1",
  "severity": "КРИТИЧЕСКОЕ",
  "severity_reasoning": "Iдоп 220 А < Iрасч 302 А — пожар при нагрузке",
  "category": "Критическое",
  "problem": "Iдоп кабеля АВВГ 4×95 (220 А) меньше расчётного тока 302 А",
  "description": "Кабель ввода АВВГ 4×95 имеет Iдоп = 220 А, расчётный ток ввода составляет 302 А. Кабель будет работать в режиме длительной перегрузки.",
  "norm": "ПУЭ-7, п. 1.3.10",
  "norm_quote": "Длительно допустимые токовые нагрузки на провода и кабели приведены в таблицах 1.3.4–1.3.31.",
  "norm_confidence": 0.9,
  "recommendation": "Заменить на АВВГ 4×185 (Iдоп ≥ 320 А).",
  "risk": "Тепловой пробой изоляции, возгорание ВРУ.",
  "evidence_quote": "Кабель ввода: АВВГ 4×95, Iдоп 220 А. Расчётный ток 302 А",
  "md_excerpt": "Раздел 4. Кабельные сети. Кабель ввода: АВВГ 4×95, Iдоп 220 А. Расчётный ток 302 А, коэффициент использования 0,9.",
  "discipline": "EOM",

```

**Пояснение:** дефект конкретный, `evidence_quote` — verbatim, `severity_reasoning` ≤ 120 символов и называет последствие. Это эталон.

## Пример 2 — EOM — BAD (spec)

**MD:** тот же, что в примере 1.

**Anti-pattern (НЕ ПОДАВАТЬ):**
```json
{
  "id": "T-002",
  "problem_class": "verify_cable",
  "affected_system": "Кабель ввода",
  "severity": "ЭКСПЛУАТАЦИОННОЕ",
  "problem": "Проверить корректность подбора кабеля по табл. ПУЭ",
  "description": "Рекомендуется уточнить корректность подбора сечения кабеля.",
  "evidence_quote": "Кабель ввода: АВВГ 4×95",
  "confidence": 0.5
}
```

**Почему BAD:** «проверить», «уточнить», «рекомендуется» — спекуляция. Нет конкретного дефекта. Корректное замечание уже сформулировано в Примере 1 (это просто рыхлая версия того же дефекта).

## Пример 4 — ВК — DO-NOT-REPORT (silent-absent на `audit_comparison`)

**document_type:** `audit_comparison`

**MD:**
```
Сравнение ВРУ-1 (ЭОМ) и потребителей ИТП (ОВ).
Расчётная нагрузка по ЭОМ: 12,0 кВт.
Заявленная мощность ИТП по ОВ: 18,5 кВт.
```

**Anti-pattern (НЕ ПОДАВАТЬ):**
```json
{
  "problem_class": "missing_mandatory_schedule",
  "affected_system": "Кабельный журнал",
  "severity": "ЭКСПЛУАТАЦИОННОЕ",
  "problem": "В разделе отсутствует кабельный журнал.",
  "evidence_quote": ""
}
```

**Почему DO-NOT-REPORT:** `document_type = audit_comparison` — фрагмент сравнения. Кабельный журнал не предмет сравнения. Запрет из «STRICT BAN» в правилах prompt'а.

**Что подавать вместо этого:** корректное замечание — расхождение нагрузок 12,0 vs 18,5 кВт между ЭОМ и ОВ (КРИТИЧЕСКОЕ, `cross_discipline_with: ["EOM", "OV"]`).

## Пример 6 — КЖ — DUP COLLAPSE

**document_type:** `full_rd`

**MD:** тот же, что в примере 5.

**Anti-pattern (НЕ ПОДАВАТЬ две штуки):**

Finding A:
```json
{
  "id": "T-001",
  "problem_class": "concrete_class_below_min_for_environment",
  "affected_system": "Несущие стены",
  "severity": "КРИТИЧЕСКОЕ",
  "problem": "B15 не подходит для XC3"
}
```

Finding B:
```json
{
  "id": "T-002",
  "problem_class": "concrete_class_below_min_for_environment",
  "affected_system": "Несущие стены",
  "severity": "ЭКСПЛУАТАЦИОННОЕ",
  "problem": "Класс бетона низок для условий эксплуатации"
}
```

**Почему DUP:** одинаковая пара `(problem_class, affected_system)`. Оставить ОДНО с самой высокой `confidence` (в данном случае — Finding A).

## Пример 10 — ВК — DO-NOT-REPORT (specification_only)

**document_type:** `specification_only`

**MD:**
```
Поз. 1 — Насос Wilo MHIE 403 — 1 шт.
Поз. 2 — Бак мембранный 80 л — 1 шт.
```

**Anti-pattern (НЕ ПОДАВАТЬ):**
```json
{
  "problem_class": "missing_calculation_basis",
  "affected_system": "Расчёт системы",
  "severity": "КРИТИЧЕСКОЕ",
  "problem": "Расчёт водопотребления не приведён в составе раздела.",
  "evidence_quote": ""
}
```

**Почему DO-NOT-REPORT:** `document_type = specification_only`. Спецификация не должна содержать расчёт. Запрет из STRICT BAN. Также нет `evidence_quote`.

## Сводка по anti-patterns

| Pattern | Что не делать | Что делать |
|---|---|---|
| «Проверить X», «уточнить Y» | spec, отбрасывается | сформулировать конкретный дефект с числом и evidence_quote |
| КРИТИЧЕСКОЕ для опечатки | wrong_severity, → РЕКОМЕНДАТЕЛЬНОЕ | оставить КРИТИЧЕСКОЕ только для unbuildable / life-safety |
| Отсутствие раздела на `audit_comparison` | STRICT BAN, отбрасывается | подавать только то, что предмет сравнения |
| Два finding с одинаковой парой `(problem_class, affected_system)` | DUP, оставить ОДНО | объединить, оставить с max confidence |
| Пустой evidence_quote | отбрасывается | привести verbatim подстроку MD |
| Норма без пункта | norm_confidence=0 допустимо, но лучше не подавать как норматив | искать конкретный пункт или оставлять `norm: ""` |
