# Идентичность листа по штампу и разделение Stage 5 / Stage 7

Документ описывает две связанные правки в конвейере сравнения документации,
сделанные 28.08.2026, и новую базу чисел, от которой считается всё дальнейшее.

Предыстория и диагноз — `experiments/ai_supervisor_v1/REPORT.md`.

---

## 1. Идентичность листа

**Модуль:** `backend/app/services/stage_comparison/sheet_identity.py`
(`stamp-sheet-identity.v1`).

Лист называет себя в штампе: «Корпуса 1, 2. План 3 этажа». Эта строка есть в
текстовом слое обоих документов пары в прямо сопоставимом виде. Номер страницы
PDF такой строкой **не является** — стр. 28 старого комплекта и стр. 28 нового
это несвязанные факты, и в контракте номер страницы остаётся только слабым
вспомогательным сигналом (`page_proximity`, вес 0,01).

### Контракт `SheetIdentity`

| Поле | Смысл |
|---|---|
| `page` | страница PDF, на которой прочитан штамп |
| `stamp_key` | канонический ключ точного сравнения: `B=<корпуса>\|K=<тип>\|F=<этажи>[\|L=<подземный ярус>][\|A=<ось разреза>]` |
| `sheet_kind` | `PLAN` / `ROOF` / `BASEMENT` / `TECHNICAL_SPACE` / `TYPICAL_PLAN` / `SECTION` / `FACADE` — только по буквальному ключевому слову |
| `buildings` | номера корпусов, нормализованные и отсортированные |
| `floors`, `floor_range` | множество этажей и сам диапазон |
| `basement_ordinal` | «первого/второго подземного» |
| `elevation` | отметка, нормализована (стороны пишут «-6,000» и «-6.000») |
| `sheet_designation` | обозначение документа из штампа, гомоглифы свёрнуты |
| `raw_stamp_text` | строка целиком, как её читает инженер |
| `confidence`, `evidence` | доля зоны штампа, поворот страницы, происхождение |

### Почему извлечение привязано к геометрии

Те же слова стоят в **содержании того же документа**, левой колонкой, списком
на весь том. Регулярка по всей странице читает лист содержания как двадцать
разных листов — на целевой паре она принимала «План первого подземного этажа»
из перечня на стр. 3 за штамп, и настоящий подземный план (стр. 25) оставался
без пары.

Идентичность несёт только ячейка штампа: `y0 ≥ 0.85`, `x1 ≥ 0.55` от
**отображаемой** страницы. Отображаемой — потому что блоки текста PyMuPDF
приходят в неповёрнутых координатах, и без `page.rotation_matrix` штамп
повёрнутого на 90° листа «уезжает» в середину страницы. У правого документа
целевой пары повёрнуты **все** листы.

Эмпирика на целевой паре: все штампы лежат при `y0 ≥ 0.93`, все строки
содержания — при `y0 ≤ 0.61`.

Страница, давшая два **разных** ключа, не даёт идентичности вовсе. Это честный
ответ, а не догадка; контентные сигналы для неё продолжают работать.

### Стоимость

1,7 с на пару (45 + 24 страницы), ноль токенов, ноль вызовов моделей, офлайн.
Работает только по текстовому слою: у скана штамп не прочитается, и лист
просто останется без идентичности.

## 2. Штамп в сопоставителе листов

**Модуль:** `sheet_matcher.py`, `production-sheet-matcher.v3`.

Порядок проходов:

1. **`STAMP_EXACT`** — ключ совпал, и на каждой стороне ровно одна страница с
   этим ключом → `MATCHED`, `HIGH`, `confidence 1.0`.
2. **Неоднозначность штампа** — один ключ на нескольких страницах одной стороны
   → `UNCERTAIN`, `automatic_scope: false`, `reason_codes: [stamp_key_ambiguous]`
   → вопрос инженеру. Первый кандидат не берётся никогда.
3. **`STAMP_GROUP`** — «План 3-15 этажей» покрывает «План 7 этажа» тех же
   корпусов: это не одна и та же страница, а кандидат в `MERGED`/`SPLIT` по
   существующему контракту 1→N / N→1, статус `POSSIBLE`. Требуется единственный
   контейнер и различные этажи у участников, иначе группа не строится.
4. **Существующие проходы** — явная группа и агрегатное доказательство
   кардинальности — без изменений.
5. **`CONTENT`** — глобальное назначение 1:1 (венгерский алгоритм из
   `document_matching.maximum_weight_assignment`).

### Противоречие штампов

Если обе стороны имеют доказанный ключ и ключи **различны** (и ни один не
покрывает другой по этажам), пара отвергается: `status = NO_MATCH`,
`reason_codes: [stamp_key_conflict]`. Сколько бы общих названий комнат ни было
у третьего и четвёртого этажа, «План 3 этажа» — это не «План 4 этажа».
На целевой паре так отвергнуто 77 пар-кандидатов.

### Конец жадного назначения

Прежний финальный проход шёл по возрастанию номера ЛЕВОЙ страницы и отдавал
каждой странице лучшего свободного кандидата. Из-за этого пара `L34 → R3`
(0,5314) забирала правую стр. 3, и единственное за прогон отношение `HIGH`
`L41 → R3` (0,7089) исчезало без следа.

Теперь назначение глобальное. Сильный кандидат, потерявший страницу, не
пропадает: он попадает в `conflicting_evidence` победившего отношения, в
`diagnostics.displaced_high_candidates` и остаётся отдельным отношением с
`reason_codes: [high_candidate_displaced]` — то есть становится вопросом.

### Что осталось нетронутым

- Все семь контентных признаков (`functional`, `entities`, `topology`,
  `graphic`, `sheet_type`, `title`, `page_proximity`) — они работают там, где
  штамп не разобран, и служат для выявления противоречий.
- **PAGE-режим**: выбор страниц делает человек, сопоставитель там совещательный
  (`sheet_matcher_is_gate: false`), штамп в этом режиме не читается вовсе.
- `USER_SELECTED`, MODE 1 / MODE 2, прямое сравнение страниц, семантика
  APPROVED/REJECTED, «в итоговый отчёт только подтверждённое».

## 3. Stage 5 ≠ Stage 7

**Модуль:** `review_presentation.py` (`review-presentation.v1`).

Оба этапа работали над одними и теми же объектами: каждый review-элемент
становился и вопросом Stage 5, и строкой решения Stage 7. Множества
`review_evidence_id` и `target_id` совпадали на 100 % — на 1720 объектов
приходилось 3440 действий человека.

Разделяет их **пригодность к показу**:

```
есть значение (before или after) И есть страница
    → находка: строка Stage 7, инженер подтверждает или отклоняет
иначе
    → исключение: вопрос Stage 5
```

Находка с неизвестным измерением остаётся находкой: «EI 60 → EI 90,
классификация не определена, источник TEXT, требует проверки» — вполне
решаемая строка. Stage 7 принимает по ней `APPROVED`, а подтверждённая находка
попадает в итоговый отчёт отдельным списком `approved_review_findings`;
контракт `approved_atomic_changes` и признак «только подтверждённое» не
тронуты.

Вопрос Stage 5 остаётся там, где без ответа находки не построить:
неоднозначность листов, неоднозначность объекта, противоречие изменений
(`contested_groups`), отсутствие значения или расположения.

### `project_entity_ref` больше не спрашивают

Это `stable_id`-хеш. В интерфейсе он был свободной строкой, не сверявшейся ни с
чем. Теперь человек называет объект на языке проекта (`object_label` —
«помещение 24.5», «кровля К5»), а оба внутренних рефа чеканит бэкенд
(`review_queue.mint_project_entity_ref`) той же функцией-семейством, что и
продюсер фактов. Поле принимается из старых ответов ради совместимости, но не
предлагается и не требуется.

scratch, боевые артефакты не тронуты). Моделей не вызывалось.

## 5. Что осталось нерешённым

**Дисциплинарный разрыв.** `text_fact_producer` закрывает ЭОМ и не закрывает
АР: три правила, все электрические. После исправления сопоставителя АР даёт
1437 доказанных расхождений и по-прежнему **0 фактов** — то есть 1411
показуемых, но неклассифицированных находок. Это следующая по величине задача,
и теперь она измеряется на чистой базе, а не поверх неверных пар листов.

**ИИ не подключён и флага не заведено.** Мёртвая настройка, которая ничего не
делает, вводит в заблуждение сильнее, чем её отсутствие. Точка врезки
существует и без неё: ответ на вопрос очереди по контракту
`change-typed-resolution.v1` — тот же путь, которым сегодня накладываются
ответы инженера. Когда слой появится, он встанет вторым источником ответов
рядом с человеческим, и флаг заводится тогда же.

Порядок будущего потока:

```
детерминированный конвейер
    → review_items
    → слой ИИ-разрешения (не существует)
    → материализованные находки
    → Stage 5: исключения
    → Stage 7: проверка инженером
```
