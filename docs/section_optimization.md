# Оптимизация на уровне раздела

## Зачем нужен отдельный уровень

Проекты одного раздела часто являются частями одной системы: корпуса, паркинг,
надземная часть, стилобат, наружные сети. Оптимизация отдельного PDF не видит
общий закупочный объём, повторяющуюся номенклатуру и решения, которые можно
унифицировать между комплектами.

Сводка раздела не заменяет проекты и не создаёт обезличенную «общую
спецификацию». Каждая строка обязана сохранять:

- объект и раздел;
- `project_id` и версию;
- страницу PDF и лист;
- исходную позицию и строку таблицы;
- связь с экспертным решением или графическим доказательством.

Без этой адресации объединение опасно: одинаковое название в двух корпусах
может относиться к разным условиям эксплуатации или расчётным параметрам.

## Модель данных

Срез раздела состоит из трёх независимых слоёв.

1. `specification_rows` — исходные строки спецификаций актуальных версий.
2. `accepted_optimizations` — только решения со статусом `accepted` в
   `expert_review.json`. Непроверенные предложения сюда не попадают.
3. `signals` — кандидаты на анализ уровня раздела. Сигнал не является принятой
   оптимизацией и не может автоматически менять проект.

Сейчас детерминированно создаётся один доказательный вид сигнала:

- принятое экспертом решение сопоставляется со спецификациями остальных
  проектов; кандидат появляется только там, где найдена аналогичная позиция,
  но это решение ещё не принято. Пожарное исполнение и степень IP при
  сопоставлении не смешиваются.

Одинаковые закупочные позиции остаются в сводной спецификации, но кандидатами
на оптимизацию не считаются.

Для количества допустимо автоматическое суммирование только при одинаковой
единице измерения и однозначно числовых значениях. Иначе в сигнале остаются
исходные количества без ложного итога.

## Полный механизм анализа

### 1. Снимок

Фиксируются актуальные версии всех проектов раздела. Результат анализа должен
хранить этот набор версий; появление новой версии делает снимок устаревшим, но
не уничтожает его.

Данные сохраняются постоянно по адресу
`backend/app/data/section_optimization/<object_id>/<section>/`:

- `snapshot.json` — последний успешно сформированный снимок, который читается
  при каждом открытии карточки без повторного анализа проектов;
- `pipeline.json` — состояние последнего пересчёта;
- `history/*.snapshot.json` — предыдущие снимки по идентификаторам запусков;
- `replications/*.json` — отдельные процессы тиражирования принятых решений.

Во время пересчёта интерфейс продолжает читать предыдущий `snapshot.json`.
Новый снимок атомарно становится текущим только после успешного синтеза.

### 2. Нормализация

Строки приводятся к общей структуре: позиция, наименование и техническая
характеристика, тип/марка/обозначение документа, код, завод-изготовитель,
единица измерения, количество, масса единицы и примечание. Исходные значения сохраняются,
нормализованное представление используется только для сопоставления.

### 3. Пересмотр принятых решений

Алгоритм группирует похожие принятые оптимизации и проверяет:

- можно ли заменить несколько локальных решений одним решением раздела;
- нет ли конфликтующих ограничений между корпусами;
- не посчитан ли один экономический эффект несколько раз;
- применимо ли принятое решение к проектам, где оно раньше не предлагалось.

### 4. Новый поиск по полной картине

Анализ выполняется не как сумма старых `optimization.json`: принятые решения
заново сопоставляются с общей спецификацией, чтобы найти проекты для безопасного
тиражирования с сохранением технических ограничений.

### 5. Графика по запросу

Vision нельзя запускать по всем блокам всех PDF: это дорого и добавляет шум.
Сначала табличный анализ формирует короткий список спорных кандидатов. Затем
для каждого кандидата выбираются только связанные листы и блоки, например:

- схема для проверки совместимости аппарата;
- план для проверки повторяемости монтажного решения;
- узел для проверки возможности унификации;
- графическая спецификация, плохо распознанная в Markdown.

Графический вывод обязан ссылаться на `project_id`, лист, страницу и `block_id`.
Если графика не подтверждает кандидат, он остаётся на ручной проверке или
отклоняется.

### 6. Critic и эксперт

Перед показом итогового предложения отдельный критик проверяет техническую
эквивалентность, нормативные ограничения, двойной счёт эффекта и полноту
источников. Только эксперт может принять оптимизацию уровня раздела.

## Процесс тиражирования

Одна кнопка запускает подготовку сразу всех ещё не обработанных кандидатов
раздела. Уже подготовленные процессы не создаются повторно, а ошибочные или
прерванные можно перезапустить этой же общей кнопкой.

Кнопка запуска не копирует решение прямо в проекты. Для каждого кандидата
создаётся отдельное сохраняемое досье, в котором фиксируются:

- снимок раздела и исходные принятые решения;
- выбранные целевые проекты и конкретные строки спецификаций;
- технические ограничения и необходимость графической проверки;
- статусы проверки кандидата, подготовки досье, графики и эксперта.

После подготовки досье запускается умный агент на оптимизационной модели Codex
(`gpt-5.6-sol` по текущей конфигурации). Агент работает
через подписочный CLI, поэтому не использует платный OpenRouter. Он получает
все целевые проекты одного кандидата за один вызов и для каждого возвращает:

- `applicable` — решение можно тиражировать;
- `applicable_with_conditions` — можно при сохранении перечисленных условий;
- `needs_graphics` — нужен конкретный лист или графический блок;
- `needs_data` — текстовых данных недостаточно;
- `reject` — решение не следует переносить в этот проект.

Агенту запрещено искать ошибки вместо оптимизации, превращать кандидатов в
общую закупку, придумывать отсутствующие характеристики и унифицировать
индивидуально изготовленные щиты только по сходству наименований. Все ссылки
на проекты, строки и страницы фильтруются по исходному досье. Заключения
обрабатываются последовательно с ограничением конкурентности, чтобы массовый
запуск не создавал десятки одновременных агентских сессий.

После заключения агента процесс переходит в `awaiting_graphics` либо
`awaiting_expert`. Исходные PDF, спецификации и экспертные решения проектов на
этом этапе не изменяются. Это защищает систему от автоматического переноса
решения в проект с другими условиями применения.

## Реализованный первый этап

Карточка «Оптимизация» на странице раздела уже предоставляет read-only срез:

- общую таблицу спецификаций в девяти графах формы 7
  (`10/65/30/18/22/10/10/12/20`: позиция, наименование и техническая
  характеристика, тип/марка/обозначение, код, завод-изготовитель, единица
  измерения, количество, масса единицы и примечание), с горизонтальными строками разделов, фильтром по
  проекту и поиском;
- принятые экспертами оптимизации;
- кандидаты на тиражирование принятых решений в проекты с аналогичными
  позициями спецификации;
- основание и оценку сходства каждой группы с раскрытием исходных решений по
  корпусам;
- количество доступных графических блоков;
- предупреждения о проектах с неполными источниками.

Предварительный табличный фильтр графики сохраняется, но окончательный запрос
конкретных страниц формирует умный агент. Targeted vision и сохранение
экспертного решения уровня раздела остаются отдельными следующими этапами: они
должны использовать сохранённое досье, а не повторно извлекать данные.
