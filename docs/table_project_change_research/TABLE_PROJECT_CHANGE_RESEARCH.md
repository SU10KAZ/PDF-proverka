# TABLE → ProjectChange: подготовительное исследование

Дата: 2026-09-13. Статус: исследовательские требования, без реализации и калибровки.

Крупное изменение следует строить вокруг **сопоставленной инженерной сущности, области действия и одного события**. Ячейки, строки и таблицы — источники доказательств. Замена модели одной установки с изменением двадцати характеристик должна давать одно `EQUIPMENT_REPLACED` с двадцатью доступными фактами. Совпадение модели у двадцати установок само по себе не позволяет объединить их в одно событие.

## Границы работы

Прочитаны код и контракты Table V3, опубликованные отчёты DEV, сохранённые `tables.json`/`ledger.json` и выбранные исходные табличные строки. Для покрытия шести запрошенных семейств использованы источники из DEV и source-only conservation corpus. Это анализ структур и требований; пары редакций с размеченными ProjectChange не исследовались. Примеры «было → стало» в остальных файлах — явно условные сценарии, а не найденные изменения проектов.

Не запускались Table V3, оценивание, подбор правил, OCR, модели или production pipeline. Ответы holdout не читались. Исходные документы, Table V3, Foundation и общий ProjectChange schema не изменялись. TEXT/GRAPHIC-решения и выводы старого Stage 5.3 не использовались для TABLE-решений. Общий контракт TEXT-сессии прочитан только для анализа интерфейсных разрывов.

Важные ограничения:

1. V3 собирает логические таблицы **внутри версии документа**, не сопоставляет инженерные сущности между версиями. `SAME`/`NEW` означают продолжение/новую таблицу, а не сохранение/появление оборудования.
2. `TableKey` включает `document_version`, семантическую структуру и локальное вхождение. `row_key` включает fingerprint содержимого. Изменённая модель изменит fingerprint строки. Ни один из этих ключей не заменяет межверсионную identity сущности.
3. `REVIEW` останавливает автоматическое объединение компонентов и сохраняет `candidate_relations`. Отсутствие строки в одном компоненте не доказывает отсутствие в логической спецификации.
4. Сохраняются все содержательные строки: заголовки, повторения, пустые строки, `DATA_LIKE`. Роль `DATA` не гарантирует, что строка является оборудованием: в ней может быть группа, итог или параметр.
5. `row_values` даёт исходные ячейки и ссылки на ledger. `semantic_structure.schema` — структурные роли, иногда `UNRESOLVED`; это ещё не доказанный инженерный путь многоуровневого заголовка и единицы измерения.
6. В опубликованном DEV: 44 случая границ, 13 PROVEN, 31 REVIEW; точность на PROVEN 13/13, покрытие 29,55%. Допущены только `EDGE_ORDINAL_FLOW@CROSS_PAGE_HEADERED` и `SEMANTIC_CONTRACT_CHANGE@CROSS_PAGE`. Эти числа **не измеряют качество TABLE → ProjectChange** и не дают допуска на collapse.

У S3 дополнительные строки паспорта MD 4673/4676, ledger 3539/3542, стр. 100 имеют `kind=EXCLUDED`, `owner=EXCLUDED`, коды `CONTENTS`, `FRONT_MATTER_EXCLUDED`. Сам факт обнаружения табличного Markdown не разрешает переопределять владельца или забирать данные из TEXT/GRAPHIC/SHEET. Нужен отдельный будущий анализ покрытия producer-а. Здесь зафиксирован пробел; по этим строкам не делается TABLE-вывод. Отсутствие данных из-за маршрутизации никогда не является `EQUIPMENT_REMOVED`.

## Предлагаемая последовательность рассуждения

1. Установить сопоставимый объём: объект, корпус, система, документ/редакция, режим, полный комплект или явно ограниченная область таблиц. П ↔ РД может увеличивать детализацию без изменения проекта.
2. Разрешить заголовки и роли записей: сущность, группа, параметр, итог, рабочая точка, повтор шапки. Сохранить неразрешённые роли.
3. Сопоставить инженерный слот/группу независимо от изменяемых характеристик. Сохранить конкурирующих кандидатов и основания связи.
4. Получить состояния и атомарные факты с адресуемыми табличными доказательствами обеих сторон. Отличать отсутствие, неизвестность, неприменимость и ноль.
5. Применить правила события и collapse, сохранив исходные факты. Противоречие и неподтверждённая причинность не исчезают при сворачивании.
6. Разделить проектные события, оформление/реструктурирование, детализацию, неизвестность и проблемы источника. Не каждое различие обязано стать ProjectChange.
7. Передать общий контракт только в согласованной форме; разрывы интерфейса оставить явными.

Все шаги — предложение будущего TABLE-потребителя, не новая функциональность V3.
