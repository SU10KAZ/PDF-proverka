# Правила сворачивания параметров в TABLE-события

Статус: исследовательская спецификация условий, не реализация и не допуск к автоматической обработке корпуса. «Автоматически допустимо» ниже означает, что перечисленные доказательства позволяют сформулировать безопасное правило; его практическая точность ещё не измерена. Основание: [исследование](TABLE_PROJECT_CHANGE_RESEARCH.md), [identity](TABLE_ENTITY_IDENTITY.md), [таксономия](TABLE_CHANGE_TAXONOMY.md).

## Что именно сворачивается

Сохраняются три уровня: исходные ячейки/строки; нормализованные факты изменения; крупные события. Collapse уменьшает число самостоятельных событий, сохраняя доступ ко всем фактам и источникам. Нельзя обрезать параметры до первых N или удалять «незначимые» изменения ради красивого количества ProjectChange.

Один факт имеет один основной учёт в событиях; он может поддерживать связанные выводы по ссылке. Одна ячейка может содержать несколько разных фактов. Одинаковое значение в нескольких ячейках может быть одним повторно представленным фактом. Числа «ячейки / факты / события» поэтому считаются отдельно.

## Общие условия

До collapse должны быть установлены:

1. Межверсионная identity предмета или явно однородной группы.
2. Область: система/корпус/зона, границы рассматриваемого состава, редакции и стадия документации.
3. Семантический адрес значения: предмет, свойство, единица, режим, рабочая точка, база «на единицу/на комплект/всего», роль «требуемое/выбранное/фактическое/расчётное».
4. Читаемость old/new и прямые ссылки на TABLE evidence, включая шапку и применимую группу.
5. Единый смысл события либо доказанная зависимость фактов; простая одновременность не доказывает причину.
6. Отсутствие неразрешённого противоречия, влияющего на утверждение. Неизвестность сохраняется явно.

Универсальное правило «одна строка = одно событие» запрещено: S3 имеет параметры по строкам, S9 — рабочие точки, S5 — строки групп и итогов. Правило «вся таблица = одно событие» также запрещено.

## Правила

| ID | Условие | Результат collapse | Стоп-условие |
|---|---|---|---|
| C01 — замена | Для одного слота доказаны old/new модели; параметры относятся к выбранным изделиям того же слота и режима | Одно `EQUIPMENT_REPLACED`; масса, габариты, мощность, расход, напор — supporting facts | Необоснованная принадлежность паспортов, нескольких установок/вариантов или отдельных секций |
| C02 — количество | Доказана одна однородная группа; смысл количества совпадает | Одно `EQUIPMENT_COUNT_CHANGED` независимо от представления одной/несколькими строками | Перепутаны штуки/метры/комплекты; количество на единицу и итог; дубли не разрешены |
| C03 — набор производительности | Один предмет и режим; несколько показателей описывают одну производительность | Одно `CAPACITY_CHANGED`, например расход и соответствующий напор | Номинальная мощность двигателя и требуемая мощность потребителя принадлежат разным смыслам; режимы не совпадают |
| C04 — состав системы | Явно установлен один переход состава/рабочей конфигурации системы | Одно `SYSTEM_CONFIGURATION_CHANGED`; состав, количества и связанные замены — факты/дочерние изменения без двойного счёта | Общий заголовок системы — единственная причина объединения; изменения независимы либо старый комплект не раскрыт |
| C05 — производные значения | Табличная формула/явная зависимость связывает изменённый вход и результаты; арифметика воспроизводима | Результаты входят evidence того же события; не создаются события для каждого P/Q/S/I | Связь предположена по инженерной привычке или похожему проценту изменения; округление/режим не установлены |
| C06 — повторное представление | Один и тот же предмет, свойство, режим, сторона и значение повторены в нескольких TABLE-источниках | Один факт с несколькими provenance refs | Повтор может быть ещё одним экземпляром; значения конфликтуют; разные уровни агрегирования |
| C07 — реструктурирование | Существует доказанное соответствие записей/групп, сохраняющее состав, кратность и смысл параметров | Ноль инженерных событий для эквивалентной части; сохраняется structural observation | Одинаковый общий итог скрывает смену состава или перераспределение по системам |
| C08 — комплект → компоненты | Таблично подтверждён старый и новый состав комплекта и база количества | Нейтральная детализация при эквивалентности; одно изменение комплектации при доказанном отличии | Название «комплект» не раскрыто; новые аксессуары могли существовать раньше |
| C09 — набор свойств без модели | Один предмет и один согласованный набор решения; replacement не доказан | Одно изменение набора характеристик с узким summary | Набор включает независимые требования, другую entity или разные режимы; при таком составе разделить либо REVIEW |

Для C01 изменение характеристик подтверждает различие выбранных изделий, но причинную фразу «масса изменилась из-за замены» писать только при доказанной связи. Достаточная безопасная формулировка: «П1: модель A заменена на B; связанные характеристики: …». Collapse не доказывает причину проектного решения.

## Приоритет смысла без потери независимых событий

Это не цепочка first-match-wins: сначала рассматриваются все правдоподобные события и противоречия.

- Доказанная замена поглощает характеристики той же замены; она не становится одновременно отдельным событием массы, размеров и мощности.
- Изменение количества 2 → 3 не считается автоматическим следствием A → B. По умолчанию это второе связанное событие, если сопоставление группы позволяет доказать оба. При явно заданном переходе состава допустим один родительский configuration event.
- Добавление/удаление группы целиком не дублируется событием количества 0 → N/N → 0. Для существующей однородной группы N → M остаётся count event.
- Родительское событие состава и дочерние подтверждённые факты не учитываются дважды как независимые ProjectChange. Сохраняется возможность отдельно проверить факт замены/количества.
- Смена внешнего требования к системе может быть независима от замены установки; общий entity не даёт права поглотить требование заменой.
- Массовая замена A → B у разных марок не объединяется по модели или проценту изменений. Допустима группа отображения, которая не меняет самостоятельность событий. Один group event требует доказанной групповой области решения.
- Если сводное значение системы изменилось вследствие нескольких уже учтённых фактов, оно может поддерживать родителя по ссылке. При неизвестной зависимости хранится отдельный факт без утверждения причины и без принудительного слияния.

## Нормализация и арифметика

| Случай | Безопасная обработка | Что запрещено |
|---|---|---|
| Пробелы, перенос внутри ячейки, формат Markdown | Сохранить raw; сравнивать однозначное семантическое значение | Удалять значимые дефисы, суффиксы, знаки ±, <, >, диапазоны |
| Числа 1,5 и 1.5 | Эквивалентны при однозначном числовом контексте | Превратить код/артикул `1.5` в число |
| 1 кВт ↔ 1000 Вт | Эквивалентность при том же свойстве, режиме и базе; зафиксировать преобразование | Считать близкие числа эквивалентными по произвольному допуску |
| 1000 ↔ 999,6 при разной точности | Сохранить различие; если точность/округление явно задана, оценить представление по ней | Ввести универсальный tolerance без основания; тюнинг не выполняется |
| Пусто, «—», «не применяется», «не указано», 0 | Различные состояния значения; значение прочерка требует контекста | Свести всё к нулю или отсутствию оборудования |
| 3×(5×120), «кол., число и сечение жил» | Сохранить сырой состав и разбор только при однозначной семантике шапки/записи | Считать первую цифру числом кабелей или выводить параллельность из умолчания |
| Сумма количества по строкам | Только по уникальным членам доказанной группы, в одной единице и области | Складывать строку «комплект» с его компонентами; складывать итоги и слагаемые |
| Мощность группы | Указать, это паспортная сумма, установленная, расчётная или рабочая мощность | Умножать мощность на количество и называть результат рабочей производительностью при неизвестном резерве |
| Серия/типоразмер/артикул | Консервативное сравнение с сохранением сырого написания | Склеивать разные изделия удалением букв/суффиксов как «форматирование» |

В S5 имеются коэффициенты и итоги; это основание сохранять уровни расчёта, но не доказательство конкретной формулы. В S8 два одинаково озаглавленных итога принадлежат разным компонентам. В S9 давление — координата рабочей точки; изменение числа точек может быть изменением представления характеристики, а не состава оборудования.

## Барьеры от чрезмерного объединения

Collapse запрещён без отдельного доказательства связи через:

- разные корпуса/системы/независимые марки;
- разные режимы или сценарии расчёта;
- разные смысловые величины одной единицы: электрическая и тепловая мощность, требуемый и выбранный расход;
- различающиеся составы группы при совпадении общей суммы;
- две конкурирующие identity;
- неразрешённый переход «комплект ↔ компоненты»;
- конфликтующие TABLE-значения одной стороны;
- REVIEW-границу, от которой зависит владелец параметра или полный состав.

Поглощение не может повысить доказанность факта. Если модельная замена доказана, а масса сомнительна, узкий вывод о замене может быть доказан при независимых основаниях; масса остаётся неразрешённым supporting fact. Нельзя объявить всю карточку полностью PROVEN без представления частичного статуса evidence. Если общий контракт этого ещё не поддерживает, нужен явный интерфейсный REVIEW, см. [mapping](TABLE_TO_PROJECTCHANGE_MAPPING.md).

## Аудит collapse

Будущий результат должен позволять ответить для каждого исходного различия:

| Что сохранить | Назначение |
|---|---|
| ID атомарного факта, old/new refs и исходные значения | Восстановить утверждение до ячейки |
| ID основного события или причина отсутствия события | Проверить, куда делось различие |
| Правило C01…C09, версия правила, основания entity/scope | Объяснить сворачивание |
| Роль факта: самостоятельный, supporting, зависимый, агрегат, дубликат представления, unresolved | Предотвратить повторный счёт и скрытую потерю |
| Связи факт → родитель и входы производного результата | Проверить причинную/расчётную связь |
| Structural/detail observation отдельно от инженерных событий | Не путать отсутствие ProjectChange с отсутствием diff |
| Явные конфликты и нерешённые кандидаты | Не потерять REVIEW в сводке |

Инварианты будущей проверки: каждый изменённый факт учтён ровно в одном основном disposition; каждый summary подтверждён evidence; нет необъяснённых пропусков и двойного счёта; перестановка строк/страниц не меняет смысловые события; отдельные entity сохраняются отдельными без доказанной групповой связи. Коэффициент сжатия — описательная метрика, не цель оптимизации.
