# TABLE evidence → общий ProjectChange: mapping и требования

Дата: 2026-09-13. Этот документ — входные требования от TABLE-route. Он **не определяет новую общую схему**, не изменяет enum/валидатор и не фиксирует решения за параллельную TEXT-сессию. Имена текущих полей относятся к [прочитанному снимку](TABLE_PROJECT_CHANGE_RESEARCH.md#зафиксированное-состояние-реализации). Предлагаемые смысловые элементы можно согласовать как поля, расширение route evidence или связанный артефакт; выбор реализации здесь не сделан.

## Происхождение TABLE-решения

Будущий TABLE-потребитель читает сохранённые таблицы, их строки, исходные TABLE-ячейки, доказательства границ и source receipts. Он не меняет ledger ownership и решения V3. `SAME` не означает «сущность та же», а `NEW` не означает «оборудование добавлено».

Для самостоятельного TABLE-решения список routes содержит только TABLE. Марка, функция, модель и scope, необходимые для инженерного вывода, должны иметь табличные свидетельства. Контейнер/заголовок раздела из Foundation можно сохранить как locator и гипотезу поиска; внешний TEXT-заголовок не становится доказательством identity оборудования. Неустранённая TABLE-неоднозначность не снимается TEXT/GRAPHIC-выводом.

Растр самого табличного региона может в будущем служить проверкой чтения TABLE-ячейки с тем же provenance; это не заимствование GRAPHIC-решения. В этом исследовании такая проверка не выполнялась. Если region принадлежит другому route или EXCLUDED, потребитель не захватывает его самостоятельно (примеры S3/S6).

## Что передавать

| Смысловой блок | Обязательное содержание | Основание в текущем V3 / недостающая часть |
|---|---|---|
| `entity` | Вид предмета; slot/group identity; область; old/new идентификаторы; основания match; разрешение неоднозначности; конкурирующие кандидаты; связь комплект/члены при использовании | TableKey/row_key/ячейки доступны. Инженерная entity и межверсионный match в V3 не произведены |
| `old_state`, `new_state` | Наблюдаемое состояние выбора/состава/количества/производительности; режим; единицы и база; presence/unknown; полнота состояния | Raw cells доступны; typed state и полнота инженерного предмета не следуют из списка строк |
| `changed_parameters` | Имя и смысл свойства; old/new raw и нормализованное значение; единица/размерность; режим; база; статус; evidence с каждой стороны; роль supporting/independent/derived | Смысловой аналог `supporting_fact_changes`; название нового поля не требуется. Нужны договорённости о typed values, неизвестности и зависимости |
| Table provenance | Версия документа, source hashes, артефакт V3/producer, TableKey, сегменты, row_key, ledger line, исходные колонки/шапки/группа, страница/блок, границы и их статус | Большинство ссылок разрешается из tables+ledger; семантический путь колонки и статус факта требуют будущего анализа |
| Решение и аудит | Тип/subject/scope, основания события и collapse, статус события отдельно от фактов/границ, конфликты, связанные события и основной учёт фактов | V3 boundary evidence — только один из входов, не финальный ProjectChange status |

В состоянии существующей сущности отсутствие модели — неизвестная модель, а не отсутствующая сущность. В добавлении/удалении отсутствующая сторона содержит доказательство полноты поиска или явного исключения, а не выдуманную строку с нулём.

### Адресуемость evidence

Каждый утверждаемый изменённый параметр должен восстанавливаться по цепочке:

`comparison scope → сторона/DocumentVersion → receipts → tables/ledger → TableKey/segment → row_key/line → исходная ячейка → шапка/группа/режим → утверждение`.

Необходимые детали:

- `document_version`, читаемый код документа, версия/редакция и сторона old/new; их различие не выводится из номера страницы.
- `work_md`, `blocks`, `pdf` с SHA-256; для исходного факта — hash строки или эквивалентный проверяемый receipt. Недоступный PDF receipt нельзя выдумывать.
- Ссылка на сохранённый V3 artifact и producer version/policy receipt. TableKey старой и новой стороны обычно различны и хранятся оба.
- Сегмент, row_key, ledger line ID (0-based), исходная Markdown line (1-based), block_id, within_block_line (0-based), page (1-based).
- Колонка в исходном массиве ячеек (предлагается явно 0-based) и семантический путь шапки, например «Расчётная мощность → Активная → кВт». Для вертикальной таблицы — ячейка названия параметра и ячейка значения; для merged/multirow — весь набор исходных опор, без фиктивной единственной ячейки.
- Исходная цитата, raw value/unit; нормализованное значение с основанием преобразования. Знак, диапазон, «на единицу/всего» и «по проекту/проложен» не теряются.
- Заголовки групп и область их действия с refs; пустая ячейка сама по себе не разрешает forward-fill системы или модели через REVIEW-границу.
- Все relevant boundary refs: `decision`, `basis`, candidate JOIN/SPLIT, conflict, witnesses, rule strata; отдельно — почему они влияют/не влияют на событие.
- Bbox/crop при наличии — дополнительный locator. Координаты не заменяют версии/строки; если есть только рамка блока, её нельзя назвать рамкой ячейки.

Неизменённые значения, необходимые для identity, режима и базы, также передаются как context evidence. `changed_parameters` содержит изменения, а не все контекстные ячейки подряд.

## REVIEW: зависимость конкретного утверждения от неопределённости

В V3 фактические состояния границы: `decision=SAME/NEW/REVIEW`, `basis=PROVEN/CONFLICT/NO_EVIDENCE`. Последнее может включать наблюдаемые, но не допущенные к автоматическому решению правила. Это не статус истинности оборудования или параметра.

Предлагаемый критерий: **если допустимые разрешения неопределённой границы меняют identity, значение, область или полноту, от которых зависит утверждение, это утверждение остаётся REVIEW**. Если граница не влияет на полностью доказанный локальный факт, она может остаться REVIEW при самостоятельном узком выводе. Это будущая проверка зависимости, не обход правила V3: автоматического JOIN через REVIEW не происходит.

| REVIEW / ограничение | Что блокирует | Что потенциально можно сделать независимо |
|---|---|---|
| Межстраничный разрыв внутри записи: модель слева, количество справа | Сборку состояния, assignment параметра, replacement/count этой записи | Другую полную запись с явной identity и шапкой, если её scope доказан отдельно |
| Неясно, к какой системе/группе относится продолжение | Membership, группировку, итоги, отсутствие, count по группе | Локальное значение с явным собственным scope в строке; нельзя наследовать спорный заголовок |
| JOIN/SPLIT conflict затрагивает выбранные строки | Любой вывод, меняющийся при выборе JOIN или SPLIT | Только утверждения, независимость которых явно доказана; общий conflict не исчезает |
| Недопущенный `SPECIFICATION_ITEM_FLOW` | Полноту всей спецификации и суммы через границу | Модельную замену полностью заполненного, однозначно сопоставленного слота внутри компонента; не полное удаление из спецификации |
| Headerless/nonadjacent continuation | Объединение зависимых фрагментов, интерпретацию унаследованной шапки | Сравнение полных записей, каждая из которых имеет свои явные шапку и scope |
| Внешняя граница паспорта/соседней таблицы REVIEW | Утверждение, что все паспортные таблицы принадлежат одной установке | Полный локальный набор с собственной табличной identity. Одинакового внешнего названия недостаточно (S3) |
| Неполный scope, пропущенная страница, маршрут EXCLUDED | Added/removed по отсутствию, полный состав, агрегаты и сравнение общего числа | Явные положительные old/new факты в доступных TABLE-регионах, если их identity и смысл независимы |
| Неоднозначный row match/повтор марки | Событие конкретного экземпляра | Групповой count при отдельно доказанных однородности, полноте и кратности; иначе REVIEW |
| Неясная шапка/единица/режим | Соответствующий параметр и события, зависящие от него | Доказанная модельная замена может сохраниться при отдельном статусе проблемного параметра |
| Неопределённость другого параметра/другой сущности | Только зависящие от неё утверждения | Независимое событие остаётся доступно; глобального «вся таблица REVIEW» не требуется |
| Перестановка/перенумерация/пагинация | Ничего при доказанном сохранении смысла | Служебное наблюдение; существующие REVIEW не обязаны закрываться ради ProjectChange |
| `UNRESOLVED` table schema | Не даёт автоматической инженерной интерпретации колонок | Может остаться таким, если конкретный факт имеет независимо прочитанную TABLE-шапку и доказанный смысл; это не promotion схемы V3 |

Не нужно сначала закрывать все 31 DEV REVIEW. Приоритет — неопределённости, влияющие на identity, role/unit, completeness и grouping выбранного события. Число реально блокирующих ProjectChange REVIEW здесь не измерено: DEV содержит границы одной версии, не пары инженерных событий.

### Наличие и полнота

Для автоматического `ADDED`/`REMOVED` по отсутствию нужна проверяемая закрытая область:

1. Обе стороны описывают сопоставимые назначение, комплектность, стадию/редакцию и охват документации.
2. Доступны все TABLE-регионы заявленной области, включая продолжения и возможные перенесённые записи; нет relevant coverage gaps.
3. Сущность не обнаружена под другой маркой/в другой группе/в составе комплекта; альтернативы сопоставления разрешены.
4. Различие не является новым раскрытием ранее недетализированного комплекта.
5. Сохранён отрицательный результат поиска с перечнем обследованных таблиц, критериями entity и ограничениями. Это coverage witness, не цитата несуществующей ячейки.

Пустая таблица справа сама по себе не доказывает пункты 1–4. Альтернативное достаточное основание — явная табличная запись об исключении/включении конкретной entity между указанными редакциями, если смысл изменения однозначен. Число 0 считается явным нулём только при доказанной роли колонки, а не автоматически удалением.

## Сопоставление с прочитанным общим контрактом

| TABLE-потребность | Что уже есть в снимке | Разрыв / требование к обсуждению |
|---|---|---|
| Entity | `engineering_subject`, `entity_id`, `system`, `mark`, old/new model, `identity_basis`, `resolution`, `scope_key` | Представить slot отдельно от product; group membership и one-to-many; old/new system при изменении принадлежности; subject для кабеля, материала, помещения, расчётной группы |
| Состояния | `old_state`, `new_state` — string/null | Нужна проверяемая структура или связанные facts для typed state; null не должен смешивать отсутствие с неизвестностью |
| Параметры | `supporting_fact_changes`: property, old/new VALUE, evidence IDs | В VALUE строка value/quote и unit; отсутствуют явные dimension, режим/база, неизвестность, fact status и зависимости. Нельзя изобразить missing произвольной фиктивной строкой |
| Provenance | `evidence_old/new`, route TABLE разрешён enum; source_refs, receipts, local_unit_id, locator | Договориться о TABLE locator: table/row/column/header/boundary refs. Нельзя заявлять поддержку TABLE только по наличию enum |
| Отрицательное evidence | Сторонние evidence arrays есть | Нужен тип свидетельства полноты/отсутствия. Снимок требует обе цитируемые стороны каждого FACT и old+new evidence для PROVEN; это не выражает отсутствие строки обычным FACT |
| Независимость route | `routes`, enum TEXT/TABLE/GRAPHIC | Уточнить общий и route-specific validators. Параметр `text_only=False` в прочитанном коде не снимает все безусловные проверки двухсторонних цитат и PROVEN; это не готовый TABLE-вход |
| Классификация | Replacement, count, capacity, configuration и другие типы уже есть | Не вводить `SYSTEM_COMPOSITION_CHANGED` как обязательный новый enum: сначала согласовать смысл с configuration. Restructuring/detail/no-change должны иметь место вне инженерного enum |
| Статусы | Event `PROVEN/REVIEW`, confidence, reasons | Нужны отдельно boundary/fact/entity/coverage/event status и зависимость claim от review. Confidence не заменяет полноту |
| Конфликт | `conflicts`, тип `CROSS_SOURCE_CONFLICT` | Выразить также конфликт TABLE-источников одной стороны, identity/units и неразрешённую границу; смысл не следует упаковывать в неверный тип |
| Collapse | event_key, supporting facts | Нужны trace «факт → основное событие», причины поглощения, связанные/родительские события и правила счёта; стабильность смыслового event при переносе страниц |
| Значимость | `MATERIAL/UNASSESSED` | Не объявлять MATERIAL из количества ячеек; при отсутствии инженерного основания оставлять UNASSESSED |

Прочитанный `EVIDENCE` также требует `text_purity_basis`: TABLE не должен сочинять TEXT-доказательство. Следует согласовать нейтральное представление route ownership/допустимости либо явную неприменимость этого поля. В текущей задаче ничего в контракт не дописывается.

## Условные evidence-пакеты для обсуждения

Это смысловые карточки, не JSON и не объекты, уже принятые валидатором.

| Блок | Замена П1 | Удаление П1 | Реструктурирование спецификации |
|---|---|---|---|
| Entity | Тот же slot П1 в явно указанной системе/корпусе; old/new mark refs | П1 с однозначной областью поиска | Доказанное соответствие состава в старой и новой структуре |
| Old/new state | Модель A → B, 1 → 1 шт., один режим | PRESENT(A) → ABSENT с coverage witness | Те же изделия/числа/параметры в иной группировке |
| Changed parameters | Модель — основной факт; расход/масса/размеры — supporting | Состояние существующей стороны; не fake old/new нулевые параметры | Только изменения представления; содержательные факты неизменны |
| Provenance | Две версии, таблицы/строки/ячейки/шапки, доказательства match | Old entity refs + new examined scope, receipts и resolved alternatives | Все соответствующие строки, группа/база учёта и сохранённая кратность |
| REVIEW | Неясный параметр остаётся отдельно; влияющий на identity блокирует событие | Любой relevant gap блокирует PROVEN removal | Неизвестная комплектность блокирует вывод об эквивалентности |
| Выход | 1 replacement, не N параметрических ProjectChange | 1 removal после достаточного доказательства | Structural/detail observation; 0 инженерных ProjectChange |

## Минимальные требования к согласованию contract

1. Двухсторонние typed observations и явные PRESENT/ABSENT/UNKNOWN/NOT_APPLICABLE либо эквивалентная семантика без фиктивных значений.
2. Identity entity отделена от product choice и version-local table/row keys; предусмотрены группы и изменяемые membership.
3. Параметры адресуемы, имеют единицу, режим, базу и статус; зависимые факты/агрегаты сохраняют происхождение.
4. TABLE provenance включает шапку/группу/границы и source receipts; scope completeness имеет собственные проверяемые свидетельства.
5. Есть различение структурной неопределённости и неопределённости конкретного claim; REVIEW не повышается collapse-ом.
6. События и supporting facts не учитываются повторно; аудит объясняет каждое сворачивание и каждое исключение из ProjectChange.
7. Route ownership и validators позволяют TABLE доказательства без TEXT/GRAPHIC-подсказок и без изменения замороженного V3.
8. Representation/detail/no-change имеют явный выход вне ProjectChange; contract не вынуждает называть их инженерными изменениями.

До согласования этих пунктов нельзя утверждать, что TABLE producer совместим с разрабатываемой схемой. Это основание для следующего обсуждения, а не задание на её изменение в этой сессии.
