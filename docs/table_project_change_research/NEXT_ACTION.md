# Следующее действие после TABLE-исследования

Дата: 2026-09-13. Текущее подготовительное исследование завершено. Реализация, tuning, push и deploy не входят в выполненную работу.

## Что передать владельцу общего ProjectChange contract

Передать для согласования [mapping](TABLE_TO_PROJECTCHANGE_MAPPING.md) и [таксономию](TABLE_CHANGE_TAXONOMY.md), прежде всего:

1. Slot identity отдельно от модели изделия, группы и one-to-many membership.
2. Typed facts с единицами, режимом, базой значения и явной неизвестностью.
3. Evidence отсутствия через полноту TABLE-scope, а не искусственные цитаты/нули.
4. Provenance до ячейки/шапки/группы и отдельный статус влияющих V3 REVIEW.
5. Представление supporting/derived facts и родительских событий без двойного счёта.
6. Отдельный результат для restructuring/detail/no-change и корректные subjects для кабелей, материалов, помещений, расчётных объектов.

Это документ для передачи пользователем/следующей сессией. Сообщения владельцам внешними средствами не отправлялись; общий schema не редактировался. Имена полей и окончательный enum остаются решением общей контрактной работы.

## Рекомендуемый следующий исследовательский шаг

Подготовить независимый набор **реальных пар TABLE-редакций** с ручной разметкой identity, событий и provenance. Нынешние 44 DEV случая V3 размечают границы внутри версии и не заменяют такую разметку. Приведённые T01–T14 — проект сценариев для обсуждения, не обучающий набор и не результаты эксперимента.

До какой-либо реализации зафиксировать для каждой пары:

- обе DocumentVersion, состав сравниваемых документов, стадии/редакции и ограничения scope;
- immutable TABLE/ledger/source receipts и доступность нужных таблиц;
- entity correspondence, включая неоднозначные и групповые соответствия;
- old/new state, независимые и зависимые факты, исходные ячейки и шапки;
- ожидаемые тип, число и смысл событий; structural/detail/unresolved dispositions;
- какие REVIEW действительно влияют на утверждения и какие могут остаться открытыми.

Не использовать TEXT/GRAPHIC для назначения правильного TABLE-ответа. Если TABLE недостаточен, ожидаемый ответ — REVIEW с точной причиной. Непокрытые route-регионы учитывать как coverage gap, не добавлять вручную в V3.

## Матрица будущей ручной проверки

| Семейство/риск | Нужные положительные примеры | Обязательный контрпример |
|---|---|---|
| Замена оборудования | Та же марка, новая модель, много характеристик; вертикальная и широкая таблица | Изменились только свойства; та же модель у разных установок; переименование |
| Количество | Однородная группа в одной строке и в нескольких | Метры/комплекты вместо штук; основной/резервный; повтор строки |
| Added/removed | Полная сопоставимая область; явное включение/исключение | Пропущенное продолжение; перенос таблицы; П ↔ РД с разной детализацией |
| Состав системы | Явный переход состава/резерва | «Комплект» раскрыли компонентами; тот же итог, но разные члены |
| Кабельный журнал | Та же линия, изменена марка/сечение/длина/оконечная связь | Дубли маркировки; проект/проложен; длина не доказывает геометрический маршрут |
| Воздухообмен | Тот же room/zone и режим, изменён расход/система | Дубли номера помещения; приток против вытяжки; перенос строк |
| Расчёт | Именованные входы/выходы и явная зависимость | Общая корреляция без формулы; subtotal плюс total; иной сценарий |
| Параметры/паспорт | Один набор параметров одного предмета | Несколько установок одинаковой серии; разные рабочие точки; неизвестные единицы |
| Структура | Перестановка, перенумерация, page split, column reorder, group split/merge | Одновременно реальный count change; неэквивалентный старый комплект |
| REVIEW | Локальное доказанное событие при нерелевантной границе | Та же граница определяет владельца параметра или отсутствие объекта |

Нужна независимая разметка по документам и проектам, отдельные development/holdout наборы без утечки источников и повторов одной пары. Численные пороги допуска и объём выборки в этом исследовании не устанавливаются: их надо определить до будущего эксперимента и проверять по семействам/типам событий, отдельно от V3 boundary gates.

## Что измерять в будущем

| Метрика | Что проверяет |
|---|---|
| Precision/recall крупных событий по типам | Правильный смысл, не только наличие diff |
| Entity matching accuracy и ambiguous coverage | Не перепутаны слоты, группы, корпуса, режимы |
| Over-merge / over-fragmentation | Независимые решения не склеены; параметры одной замены не размножены |
| False added/removed | Отсутствие не выведено из неполноты/переноса/детализации |
| Fact/evidence conservation | Все различия объяснимо учтены, refs разрешаются, повторного счёта нет |
| Статусы фактов/событий и REVIEW dependence | Подтверждённые локальные факты не блокируются нерелевантными REVIEW; влияющие не повышены |
| Formatting/restructuring invariance | Пагинация, порядок, эквивалентные единицы не меняют инженерный результат |
| Route purity и scope completeness | Решение основано на допустимом TABLE-evidence; coverage gaps видны |

Количество ячеек на событие сообщать как характеристику данных. Не оптимизировать его как целевую функцию: искусственное уменьшение числа событий создаёт over-merge.
