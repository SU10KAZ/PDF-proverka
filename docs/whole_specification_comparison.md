# Сравнение полной спецификации между версиями

Дата: 18.10.2026. Статус: механизм и подключение готовых результатов к MD-сводке
реализованы в коде; выпуск на production не выполнен.

## Задача и принцип

При вставке листа или строки таблицы спецификация перераспределяется по страницам.
Сопоставление «лист A ↔ лист B» перестаёт соответствовать составу таблицы.
Единица нового сравнения — **полная спецификация в выбранной версии**.
Номер страницы используется для ссылки на доказательство, а не как ключ позиции.

В существующем `version_comparison/spec.py` уже есть сборка позиций через страницы,
но её вход строится из PDF. Текущая кнопка «Сводка изменений (MD)» использует
`version_comparison_ai/sheet_changes/series_summary.py` и собирает готовые
описания листов. Она не является источником полной спецификации.

Новый механизм получает подготовленный `_results.md` каждой версии. TEXT
авторитетен: ни повторного PDF-извлечения, ни OCR, ни исправления текста по растру.
Версии и полная область спецификации задаются явно. Нельзя передавать только
изменённые или успешно сопоставленные листы.

## Последовательность

1. Канонический парсер `common/results_md.py` читает все выбранные страницы/блоки
   каждой версии. Сохраняются SHA-256 исходного MD, абсолютные строки, страницы,
   `block_id` и исходные цитаты. Проверяются пропуски, дубликаты и неподдерживаемые
   типы блоков. Пустая или повреждённая область не означает пустую спецификацию.
2. Одна сессия Codex Luna получает **всю спецификацию одной версии**. Она
   возвращает позиции с разделом, родителем и девятью полями: позиция,
   наименование, марка, код, поставщик, единица, количество, масса, примечание.
   Позиция может ссылаться на несколько блоков/страниц. Повторы сохраняются.
3. Программа проверяет ответ: точный состав блоков, покрытие непустых строк,
   цитаты и значения полей. Неподтверждённое значение или потерянная строка
   делает сторону неполной. Содержательные примечания нельзя скрывать в ignored.
4. После сборки обеих полных сторон сравниваются реестры. Сначала взаимно
   погашаются одинаковые записи с сохранением кратности. Затем используются
   однозначные признаки внутри раздела/родителя: код, наименование с маркой,
   наименование. Спорные соответствия остаются отдельными группами для проверки.
   Близость количества, порядок строк и номер страницы не решают неоднозначность.
5. Изменение количества/марки/наименования и других содержательных полей
   записывается как «было → стало». Новые и исчезнувшие позиции имеют источники;
   при неполном входе добавления и удаления не публикуются в MD.
6. Записываются `report.json` и `report.md`. MD содержит только содержательные
   изменения: лист и физическую страницу каждой версии, позицию, «было → стало».
   Продолжение позиции на нескольких страницах даёт одну запись со всеми листами.
   Неизменившиеся позиции, переносы и перенумерация без изменения содержания,
   цитаты, хеши и техническая статистика остаются в JSON, а не в итоговом MD.
   При неготовом/неоднозначном сравнении остаётся краткая отметка неполноты.

Полнота покрытия текста не доказывает безошибочность смысловой разметки модели.
Прототип не определяет автоматически границы нескольких спецификаций в одном
документе, их соответствие между версиями и правильность выбранной области.
Эти решения задаются явно для каждого запуска.

## Исполнение и параллельность

Исполнитель — существующий `CodexExecDescriber`: `codex exec`, модель
**`gpt-6-luna`**, усилие `high`, авторизация Codex. Модель зафиксирована,
подмены и OpenRouter нет. CLI запускается в read-only sandbox, с отключёнными
инструментами, без пользовательского конфига, с JSON Schema.
Применение `codex exec` и структурированного вывода описано в
[официальной документации](https://developers.openai.com/codex/noninteractive/).

Предел — **50 одновременных сессий**, по умолчанию. Параллелятся целые
спецификации/версии; внутри одной спецификации страницы не разрезаются на
независимые задания. Для одной пары нужны две сессии, для 25 различных пар —
до 50. Фактический пик и число обращений записываются в JSON-отчёт.

Планировщик запускает следующую задачу при освобождении места. Автоматических
повторов нет. Ошибка квоты/входа останавливает выдачу новых задач и отменяет
незавершённые сессии; отчёт отмечает неполноту. Успешные ответы сохраняются и
при повторном явном запуске проходят проверку заново. Ключ кэша учитывает
вход, промпт, схему, модель, effort и CLI runtime.

## Локальный запуск

Вход — JSON manifest с одной или несколькими парами. Пути к MD считаются от
каталога manifest. Одна сторона сейчас соответствует одному подготовленному MD.
Для привязки результата к существующему прогону каждой стороне дополнительно
передаётся `pdf_sha256` — хеш её PDF из `run.json`; он не вычисляется из MD.

```json
{
  "schema": "whole-specification-input/v1",
  "pairs": [{
    "id": "spec-1",
    "title": "Спецификация оборудования",
    "old": {"path": "old_results.md", "label": "V11", "pages": [79, 80, 81]},
    "new": {"path": "new_results.md", "label": "V12", "pages": [81, 82, 83, 84]}
  }]
}
```

Для самостоятельного анализа можно вместо `pages` передать `block_ids`.
В общую сводку допускаются только целые страницы (`pages`) или весь документ
(`all_blocks`): отдельный блок не доказывает покрытие остальных блоков страницы.
Для MD, который целиком является
одной спецификацией, требуется явное `"all_blocks": true`. Номера страниц
физические, начиная с 1, и у старой и новой версии могут полностью различаться.

Подготовка пакетов без вызовов модели:

```bash
python scripts/compare_whole_specifications.py manifest.json output_directory
```

Запуск через Codex:

```bash
python scripts/compare_whole_specifications.py manifest.json output_directory \
  --run-codex --parallel 50 \
  --codex-bin /home/coder/auditmanager/shared/codex-cli/codex-0.162.0-alpha.17.2/codex
```

В `plan.json` фиксируются область, размер и пригодность каждого пакета.
В `calls/<hash>/` сохраняются `prompt.md`, `schema.json`, `source.json`, ответ,
проверенный реестр, метаданные вызова и события CLI. Реальные исходные документы
и артефакты прогонов не следует добавлять в git.

При превышении 140 000 символов полного пакета задача возвращается как неполная.
Механизм не обрезает хвост и не делит её по страницам. Автоматическое выделение
самостоятельных разделов большой спецификации — следующий этап разработки.
IMAGE/GRAPHIC требуют отдельного пути с изображениями; текстовое описание
графического блока не считается прочитанной таблицей.

## Подключение к итоговому MD без повторов

Готовый JSON привязывается к существующему прогону локальной командой:

```bash
python scripts/publish_whole_specifications.py output_directory/report.json OBJECT_ID RUN_ID
```

Проверяются `pdf_sha256` и имя документа обеих версий, полнота и область
спецификации. Результат сохраняется в `runs/<run_id>/whole_specification.json`.
Неполный результат, чужие версии, конфликтующие пересечения областей и страницы
чертежей отвергаются. Повторный идентичный результат учитывается один раз.
Исходный `spec.json` движка не изменяется. Команда не вызывает модели.

`sheet_changes/series_summary.py` читает этот результат при формировании
существующей «Сводки изменений (MD)». Для спецификаций это единственный источник:
постраничные ИИ-описания, включая добавленные, удалённые, несопоставленные
и неописанные листы СО, в MD не добавляются. Сопоставление и просмотр листов
продолжают работать. Остальные листы экспортируются прежним способом.

Спецификации определяются по уже сохранённым профилям/метаданным. Название
чертежа в штампе имеет приоритет перед геометрическим признаком таблицы:
план с небольшой спецификацией не исключается целиком. При отсутствии профиля
допускается однозначное название отдельного листа спецификации.

Каждая позиция экспортируется один раз для перехода версий, с перечислением
всех её листов. Одинаковые материалы на разных позициях/страницах не схлопываются.
Отсутствие готового результата или покрытия всех листов СО явно отмечается как
«Спецификация не описана полностью». Это состояние также распознаёт последующий
анализатор MD; оно не превращается в «изменений нет». Новые API-вызовы при
скачивании MD не выполняются. Автоматический выбор границ спецификации и запуск
полного анализа из интерфейса остаются отдельной задачей.

## Вся история проекта и структурный режим Luna

`prepare_cached_specification_pilot.py` по умолчанию готовит **все** версии
явно указанного проекта и пары V1→V2 … V(n−1)→Vn. Каждая версия имеет один MD;
соседние переходы ссылаются на тот же файл. `--latest-pair` оставлен только для
диагностического примера. Этот подготовщик предназначен для случая, когда готового
авторитетного MD ещё нет: он использует сохранённые слова страниц и векторную
сетку таблицы, сохраняет учёт каждого слова, не извлекает текст PDF и не читает
растр. Существующий каталог входных MD не перезаписывается.

Для канонических таблиц добавлен `--structure`: Luna видит всю спецификацию,
но возвращает номера строк разделов, групп и продолжений. Ячейки и цитаты
копируются программно; существующая строгая проверка извлечения сохранена.
Нельзя склеить несколько непустых количеств, марок или кодов, скрыть строку
данных либо пропустить обычную строку. Секции и родители продолжаются через
границы страниц.

Идентичные полные разделы разных версий получают согласованную структуру:
пропущенные связи можно дополнить из другой версии только при точном совпадении
всего текста раздела и схемы колонок. Противоречащие связи останавливают результат.
Заголовок, разнесённый по ячейкам, распознаётся только при точном совпадении
с явным заголовком другого входа и отсутствии позиции, единиц, количества,
массы и примечания. Его исходные ячейки остаются в реестре доказательств.
`answer.json` сохраняет исходный ответ; `reconciled.json` — дополнения,
их происхождение и повторно проверенный реестр. Заголовки групп не публикуются
как добавленные или удалённые материалы.

```bash
python scripts/prepare_cached_specification_pilot.py \
  --object-dir /path/to/vc/objects/OBJECT_ID \
  --project PROJECT_CODE --output /path/to/new/input

python scripts/compare_whole_specifications.py \
  /path/to/new/input/manifest.json /path/to/run \
  --structure --run-codex --parallel 50 --codex-bin /path/to/codex

VERSION_COMPARISON_ROOT=/path/to/vc \
python scripts/publish_whole_specifications.py \
  /path/to/run/report.json OBJECT_ID --series-id SERIES_ID \
  --input-manifest /path/to/new/input/manifest.json
```

Публикация сначала проверяет все переходы: отпечаток входного manifest,
version_id, SHA PDF, имя документа, завершённый run и единый MD общей версии.
Только затем записываются результаты в прогоны. Кнопка «Сводка изменений (MD)»
становится доступна и без листового ИИ-задания, если готовы все переходы
спецификации. Сводка берёт полный список переходов из серии; полистовые
описания СО исключаются, остальные описания сохраняются. Когда описания других
листов не запускались, это явно указано в файле.

Проверка на стенде 18.10.2026 по прямому выбору пользователя: Мосфильмовская,
`133/23-ГК-ЭМ1`, восемь версий, 45 страниц спецификаций суммарно, семь переходов.
Выполнено восемь реальных вызовов Codex `gpt-6-luna`, пик одновременности 8 при
лимите 50. Повторные сборки использовали все восемь сохранённых ответов и не
вызывали модель. Все входы прошли проверку строк/ячеек; проверены привязки
публикации, отсутствие повторов и скачиваемый MD через HTTP. V1→V2 и V5→V6
не содержат изменений; V7→V8 содержит пять изменений на СО л.1 (PDF 14→15).
Это проверка выбранной серии Version Comparison, а не валидация ProjectChange
на объекте 272. Счётчики отражают события сравнения подготовленного текста;
без однозначного признака замена может быть представлена отдельными добавлением
и удалением. Независимая инженерная оценка всех выводов не проводилась.

Артефакты проверки хранятся вне отслеживаемого кода:
`experiments/whole_specification_prototype/results/em1_history_20261018/` —
`input/`, `run/calls/`, `run/report.json`, скачанная сводка и `validation.json`.
MD на стенде обслуживает существующий адрес
`/api/version-comparison/objects/0b540226/series/bs4fa454474e7c7b678763bf0e/ai-sheet-changes/summary.md`.
MD-файл не требует отдельной страницы-примера. Проверка браузерного клика
в этом прогоне не завершена: расширение отключилось; HTTP-скачивание и
синтаксис frontend проверены.

## Изменения отдельного листа в окне пары

`specification_view.py` читает опубликованный `whole_specification.json` и
передаёт события в существующую панель «Изменения в листе». Событие относится
к открытой паре, если его старая строка находится на странице A **или** новая
строка находится на странице B. Номера страниц сопоставляются только внутри
своей версии. Если позиция с изменением переехала на другой лист, событие
доступно в окнах обоих затронутых листов с полными ссылками «старая / новая».
Внутри одного окна событие показывается один раз; общая MD-сводка по-прежнему
содержит его один раз на переход. Чистый перенос или перенумерация не выводятся.

Панель показывает каждое изменившееся поле «Было → Стало»; кнопка «MD листа»
выгружает ту же выборку. Для спецификаций готовое полистовое ИИ-описание и
старый список «Спецификация по позициям» больше не служат вторым источником.
Неоднозначные позиции также фильтруются по открытым страницам. Отсутствующий,
неполный или привязанный к другим версиям результат явно отмечается как
недоступный; это не состояние «без изменений». Обычные чертежи сохраняют
прежнюю панель. Чтение панели не запускает модель, задания или извлечение PDF.

## Единый последовательный запуск

POST `objects/{id}/ai-sheet-match` теперь ставит проект (или выбранные проекты)
в одну очередь: `luna → series → ai → specifications → summary`.
Та же цепочка добавляется при выборе этапа «Луна» в очереди проектов.
Обычные этапы сравнения используют существующих исполнителей и их настройки;
полная спецификация использует Codex `gpt-6-luna/high`, до 50 версий одновременно
внутри своего этапа. Между этапами параллельного выполнения нет. PDF-отчёт
остаётся отдельным необязательным этапом.

Чертёж или СО решает полный текст штампа (`spec.drawing_stamp`): профиль хранит
только нижнюю строку названия («ЩУАХП» от «Монтажная схема ЩУАХП»), поэтому
план/схема/разрез/узел ищутся во всех словах штампа; «спецификац» в штампе — СО.
Полное сравнение берёт только переходы, где у обеих версий СО с текстовым слоем
(перечень `spec_so3` нашёл шапку; `specification_export.text_spec`). Версия, где
СО только в кривых или её нет, в подготовку не входит; листы СО таких переходов —
обычные листы листового ИИ, а публикация серии отмечает переход `skipped:
no_text_spec`. Если после переклассификации в готовых ИИ-заданиях не хватает
листов (`series_ai.missing`), очередь запускает задания заново — описанные листы
берутся из кэша, модель вызывается только для недостающих.

Самостоятельные листы спецификаций отсекаются до построения вопросов Луны
(включая обратные кандидаты), до оценки/создания листовых ИИ-заданий и перед
обработкой старого возобновлённого задания. Чертёж с встроенной таблицей
остаётся обычным листом. Первичная подготовка MD вынесена из CLI в
`specification_prepare.py`: используются сохранённые слова и геометрия таблиц;
подготовленный MD не перезаписывается. `whole_specifications.py` хранит входы
и ответы с привязкой к версиям, публикует только полный результат и
переиспользует подходящий опубликованный результат даже после нового
сопоставления тех же PDF. Неподдерживаемый/неполный источник останавливает этап
с причиной, а не считается пустой спецификацией.

Последний этап собирает обычные листовые описания и полные спецификации через
существующий `series_summary.build` в `series/<id>/summary.md`. Скачивание общей
сводки во время активной или незавершённой цепочки возвращает 409 с текущим
этапом; кнопка ждёт завершения цепочки. Панель листа продолжает показывать свою
выборку. Пауза доводит начатые запросы и блокирует следующие этапы; продолжение
сохраняет охват проектов. Неполный листовой результат блокирует MD; неполный —
это лист с ошибкой ИИ / не отправленный или с записями, которые модель не отнесла
ни к изменениям, ни к вопросам, ни к исключённым (`coverage.not_reviewed`).
Состояние «Частично» из-за одних пометок движка (дубль листа, надписи без
текстового слоя, сопоставление с низкой уверенностью) при полном разборе
записей неполнотой не считается и цепочку не останавливает (`series_ai.incomplete`).
Записи без решения модель сначала доразбирает внутри листа: одно обращение с
перечнем пропущенных записей в пределах трёх запусков; такой ответ берётся,
если пропусков стало меньше. Ответ с оставшимися пропусками в кэш не попадает.
Если после этапа неполные листы остались, очередь один раз заново описывает
только их мимо кэша (`series_ai.retry_incomplete`); не помогло — этап «ошибка»,
и «Продолжить очередь» повторяет доразбор тех же листов, а не берёт кэш.
Прерванный этап восстанавливается один раз, повторный сбой останавливает очередь.
Межпроцессная блокировка не позволяет двум диспетчерам начать один этап.

Проверки цепочки: `tests/test_whole_specification_workflow.py`,
`tests/test_version_comparison_stage_queue.py` и
`node --test tests/frontend/test_comparison_workflow.cjs`.
Все модельные ответы в этих тестах подменные; OpenRouter не используется.

На стенде `127.0.0.1:8103` установлена эта последовательность; существующая
очередь сохранена и продолжена после обновления. Через HTTP проверены загрузка
новых frontend-файлов, доступность семи переходов ЭМ1 и 331 события в общей
сводке, а также сохранённые результаты отдельных листов. Кнопки ИИ стенда
по-прежнему используют подменный исполнитель; сохранённые спецификации ЭМ1
получены ранее настоящим Codex Luna. Новый полный запуск с реальными модельными
запросами при этом обновлении не выполнялся. Проверки Vue и маршрутов API
используют тестовых исполнителей; клики в живом браузере не проверялись.
