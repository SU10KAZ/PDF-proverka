# Остаток лимита Claude из локального кеша Claude Code (12J)

Как на карточке VPS появляется «Claude — 84 % осталось», если у Claude Code нет
ни команды про лимит, ни разрешения спрашивать его запросом к модели.

## Задача

До 12J карточка воркера показывала «Claude · Остаток недоступен» и «Дата сброса
недоступна». Это было не сбоем связи и не разлогином: снимок приходил с
`installed` + `logged_in`, но `quota_state=unknown`, `source=unavailable`,
`remaining=NULL`. Так был написан адаптер, и написан правильно:

* `claude --help` (проверено на 2.1.220, 2.1.226 и 2.1.233) не содержит ни
  `usage`, ни `limits`, ни `quota`;
* `/usage`, `/cost`, `/status` живут только в интерактивном сеансе;
* OpenTelemetry-экспорт отдаёт РАСХОД, а не остаток;
* официальные `rate_limits.five_hour.*` публикуются только скрипту статусной
  строки и только ПОСЛЕ первого ответа API в сеансе.

То есть опросить остаток можно лишь ценой запроса к модели — а тратить
подписку на телеметрию запрещено (§17 задания 11).

## Что изменилось

Claude Code по ходу ОБЫЧНОЙ работы сам сохраняет последнюю известную
утилизацию в свой конфигурационный файл, в ключ `cachedUsageUtilization`:

```json
{
  "cachedUsageUtilization": {
    "fetchedAtMs": 1787124588457,
    "utilization": {
      "five_hour": {"utilization": 16, "resets_at": "2026-08-19T09:10:00+00:00"},
      "seven_day": {"utilization": 12, "resets_at": "2026-08-24T04:00:00+00:00"}
    }
  }
}
```

Чтение этого файла — открытие локального файла: **0 запросов к провайдеру,
0 токенов, 0 сетевых обращений**. Запрет на опрос остаётся в силе и не
нарушается, потому что опроса нет.

## Ключевые решения

| Решение | Почему так |
|---------|-----------|
| `source = local_usage_statistics`, `stability = undocumented`, `confidence = medium` | Число сообщил сам CLI, но недокументированным полем и с задержкой кеша. `high` (как у Codex с его структурным RPC) было бы завышением, `official_*` — прямой ложью |
| `remaining = 100 − utilization` | `utilization` — это ИСПОЛЬЗОВАНО. Перепутать значит показать «осталось 16 %» там, где осталось 84 % |
| Главное число — по САМОМУ ОГРАНИЧИВАЮЩЕМУ окну | Пятичасовое окно бывает свободно при почти выбранном недельном, и «осталось 84 %» в этом случае неправда |
| Дата сброса — того же окна, что и процент | Иначе процент от одного лимита подписан датой другого |
| `observed_at` = `fetchedAtMs`, а не момент чтения | Иначе кеш восьмичасовой давности выглядел бы снятым только что, и весь механизм `stale_after` стал бы декорацией |
| Нет `fetchedAtMs` → снимок не принимается | Без метки снимка возраст неизвестен, а значит свежесть недоказуема |
| Отсутствие кеша НЕ делает провайдера недоступным | Установка, вход и квота — независимые поля. Закрывается только квота |
| Планировщик этих чисел не использует | Источник недокументирован; допуск его в автоматический выбор воркера — отдельное решение (12K) |

## Раскладка файлов

Порядок проверки задан `claude_local_usage.candidate_paths()`:

1. `<CLAUDE_CONFIG_DIR>/.claude.json` — воркер задаёт `CLAUDE_CONFIG_DIR`
   всегда (`ClaudeProviderAdapter.provider_env`), и именно эта конфигурация
   относится к процессу, чью квоту мы показываем;
2. `<HOME процесса CLI>/.claude.json` — обычная установка без переопределения.

В ambient-режиме (`auth_mode = ambient_user`) HOME процесса CLI — личный
каталог пользователя VPS, поэтому пути берутся у `ProviderHome`, а не через
`os.path.expanduser`: у процесса воркера собственный HOME, и «домашний
каталог» без уточнения указал бы не туда.

## Граница безопасности

Конфигурационный файл соседствует с учётными данными. Разбор устроен как
**явный список разрешённого**:

* наружу выходят только `utilization` и `resets_at` окон `five_hour` и
  `seven_day` плюс `fetchedAtMs`;
* окно с незнакомым именем (`nimbus_quill`, `tangelo`, `extra_usage`, …) не
  разбирается вовсе;
* поля `limit_dollars` / `used_dollars` / `remaining_dollars` / `scope` не
  читаются;
* ни один неизвестный ключ не логируется, не пересылается и не сохраняется;
* файл никогда не сериализуется целиком, не копируется на центр и не попадает
  в evidence;
* при неожиданной форме — `local_cache_schema_unsupported`, а не догадка.

Тест `tests/test_claude_local_quota_12j.py` кладёт в фикстуру приманки
(`accessToken`, `refreshToken`, `sessionId`, `cookie`, `apiKey`, `accountUuid`,
`organizationUuid`, адрес почты) и проверяет, что ни одно значение не
появляется ни в снимке воркера, ни после санитайзера центра.

## Коды причины

Оператор должен понимать, ПОЧЕМУ остатка нет. Свободный текст с воркера в
браузер не идёт — идёт код, который центр разворачивает в предложение:

| Код | Когда | Что видит оператор |
|-----|-------|--------------------|
| `local_cache_available` | кеш прочитан | «Локальные данные Claude Code. Официального машиночитаемого остатка у Claude Code нет…» |
| `local_cache_stale` | снимок старше `stale_after` | «…показано последнее известное значение, а не текущее» |
| `local_cache_missing` | файла нет либо ключа нет | «Локальные данные об использовании Claude пока не появились…» |
| `local_cache_schema_unsupported` | JSON битый, форма незнакома, нет метки времени | «Формат локальных данных Claude Code не распознан…» |
| `no_safe_supported_source` | центр не может отличить два предыдущих случая | «Claude Code не сообщает остаток лимита без обращения к модели…» |

## Ограничение проводного контракта

`ProviderCapabilitySnapshot` (contracts/agent_stream/v1) несёт **один**
остаток и **одну** дату сброса: `remaining_pct_milli` и `next_reset_at`. Полей
под список окон и под код причины в нём нет.

Из этого следует:

* по gRPC-пути (боевой воркер 11l → шлюз → центр) доезжает ТОЛЬКО главное
  окно — самое ограничивающее. Второе окно на экран не попадает;
* код причины по этому пути тоже не доезжает, поэтому центр выводит его сам из
  состояния снимка (`_quota_reason`) — консервативно: где нельзя отличить «нет
  кеша» от «незнакомая форма», говорится общее `no_safe_supported_source`;
* HTTP-путь heartbeat (`/api/.../heartbeat` → `sanitize_provider_snapshot`)
  провозит и окна, и код причины полностью — там снимок едет как JSON.

Приёмная сторона (санитайзер центра, модель API, интерфейс) уже умеет оба
окна и код причины: как только контракт расширят, данные пойдут без правок
центра. **Расширение proto требует перекатки шлюза и в 12J не делалось.**

## Эксплуатация

* Кеша нет — это НОРМАЛЬНОЕ состояние: он появляется только после реальных
  обращений к модели под пользователем воркера. На 19.08.2026 у боевого
  `auditworker_11l` его не было ни по одному из путей.
* Наполнять кеш запуском Claude «ради телеметрии» запрещено.
* Интервал перечитывания — `AUDIT_WORKER_PROVIDER_QUOTA_PROBE_INTERVAL_SEC`
  (по умолчанию 900 с). Изменение кеша меняет `provider_status_digest`, и центр
  получает ровно одно `CapabilitiesChanged` — без переподключения; одинаковый
  кеш событий не порождает.
* Порог `low` — `quota_low_threshold_pct` центра / `low_threshold_pct` адаптера.
* Срок годности снимка — `stale_after_sec` адаптера (по умолчанию 900 с) и
  `quota_stale_sec` центра (3600 с).
