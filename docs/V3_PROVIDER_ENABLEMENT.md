# ProjectChange V3 — включение живого inference

Статус на 2026-09-19: **inference выключен.** В окружении прод-сервиса
(`/home/coder/.config/auditmanager/backend.phaseb.env`, `backend.secrets.env`)
нет ни одной переменной `PROJECT_COMPARISON_*`, поэтому действуют значения по
умолчанию: движок `v3`, живой вызов запрещён. Любой запуск сравнения пары
заканчивается состоянием `FAILED` с `reason_code = v3_inference_kill_switch`.
В этом режиме CLI не опрашивается, модель не вызывается, legacy не запускается.

Источник истины — код [provider_gate.py](../backend/app/services/project_change_v3/provider_gate.py)
и [engine.py](../backend/app/services/project_change_v3/engine.py). Других
переключателей нет.

## Условия допуска живого прогона

Прогон пары допускается, только если выполнены **все** условия:

| # | Условие | Значение по умолчанию |
|---|---------|-----------------------|
| 1 | `PROJECT_COMPARISON_ENGINE` ∈ {`v3`, `projectchange_v3`, `project_change_v3`} | `v3` |
| 2 | `PROJECT_COMPARISON_V3_FORCE_UNAVAILABLE` ≠ `1` | `0` |
| 3 | `PROJECT_COMPARISON_V3_ALLOW_INFERENCE` = `1` (строго) | `0` → выключатель закрыт |
| 4 | `PROJECT_COMPARISON_V3_PROVIDER_READY` = `1` **или** офлайн-проверка `gateway.validate_runtime(require_vision=True, deep=False, require_json_events=True)` вернула `ok` | `0` + проверка |

Что проверяет пункт 4 (без единого запроса к провайдеру): у codex CLI есть
`--output-schema`, `--sandbox`, `--ignore-user-config`, `--disable`, `--config`,
`--image`, `--json`; `features list` подтверждает, что shell/view_image/browser/computer
use/hooks/plugins выключены; в окружение сессии не попали секреты.
`PROJECT_COMPARISON_V3_PROVIDER_READY=1` пропускает эту проверку, поэтому
использовать его стоит только осознанно.

Бинарь codex находится по обычным правилам шлюза сравнения:
`STAGE_COMPARISON_AI_CODEX_BIN`, затем `codex` в `PATH`, затем расширение VS
Code. Это не переключатель V3, а общая настройка шлюза.

`PROJECT_COMPARISON_ENGINE=legacy` — только ручной откат на старый конвейер.
Автоматического перехода на legacy при ошибке, квоте или отказе проверки нет:
V3 закрывается в `FAILED`.

## Как включить (когда появится квота)

1. Проверить, что в очереди нет живых задач. Рестарт бэкенда прерывает их.
2. Дописать в `/home/coder/.config/auditmanager/backend.phaseb.env`:
   ```
   PROJECT_COMPARISON_V3_ALLOW_INFERENCE=1
   ```
3. `systemctl --user restart auditmanager-backend.service` и проверить
   `systemctl --user is-active auditmanager-backend.service`.
4. Выключение: удалить строку (или поставить `0`) и перезапустить; либо
   аварийно `PROJECT_COMPARISON_V3_FORCE_UNAVAILABLE=1`.

больше не выбирается (`get_provider()` возвращает только
`ClaudeOpusProvider`, переключателя на другую модель нет), код оставлен ради
собственных тестов.

| Что | Значение |

| Модель | `claude-opus-5` (точный идентификатор из таблицы моделей самого CLI и из `modelUsage` канарейки) |
| Рассуждение | адаптивное, `--effort xhigh` (у CLI по умолчанию `high`) |

| Транспорт | `projectchange_v3_claude_cli_transport/1`, `claude_cli_stream_json_single_user_message` |

Что НЕ менялось: промпты (sha256 те же `324696ce…`, `7837a504…`, `b31304ff…`),
схемы, упаковка источников `projectchange_v3_source_pack/2`, отбор
доказательств, правила дедупликации и уверенности. Видимый модели текст —
тот же `build_codex_payload`, байт в байт; его sha256 стоит в квитанции
вызова и сравним с квитанциями прежнего движка.

**Замороженные промпты по-прежнему начинаются словами «… gpt-6-astra/xhigh.»**
Это текст промпта, а не конфигурация: менять его — значит менять промпт.
Провенанс результата называет модель верно (`claude-opus-5`).

### Большие вызовы

Предела «один ход ≤ 1 048 576 символов» у этого транспорта нет: вся полезная
нагрузка — одно сообщение пользователя, её принимает родной контекст модели.
Кусков, истории и `cyberAccessProgram` нет. Ввод `stream-json` читается
потоком; предел 10 МБ у CLI относится только к текстовому stdin.

### Конверт изображений (прочитан в CLI 2.1.270, в документации его нет)

- Больше 100 изображений в запросе или больше 25 165 824 байт base64 —
  CLI **молча вырезает** самые старые изображения. `transport.plan_claude`
  отказывает такому вызову ДО обращения к провайдеру (`transport_integrity`).
- Сторона больше 2000 px — CLI уменьшает изображение. Тоже отказ до вызова
  (подготовка источников режет кропы до 1800 px, так что в проде недостижимо).
- Файл тяжелее 512 000 байт CLI перекодирует в JPEG (размер в пикселях не
  меняется). Снаружи это не отключается; квитанция вызова называет такие
  изображения поимённо (`images_reencoded_by_provider_cli_sha256`). На паре
  ИОС2.1 это 34 файла из 158.
- Изображения идут в порядке меток полезной нагрузки, перед каждым — его
  порядковый номер «Image N:» (тот же N, что в метке `"image": N`).

### Что транспорт проверяет после вызова

- Ответ дала запрошенная модель: у CLI есть собственный переход на другую
  модель после отказа (`refusal_fallback`). Поле `model` каждого ответа и
  ключи `modelUsage` сверяются; чужая модель → `provider_model_mismatch`,
  ответ не принимается. `--fallback-model` не передаётся никогда.
- У сессии нет инструментов, кроме `StructuredOutput`, и нет MCP
  (`provider_isolation_breach`).
- CLI не проигнорировал `--effort` (незнакомый уровень он молча заменяет
  уровнем по умолчанию) — `provider_effort_ignored`; сам уровень проверяется
  ещё до запуска.
- Все вызовы прогона выполнены одной конфигурацией (провайдер, модель,
  уровень) — иначе `v3_model_mixing`, результат не сохраняется.

### Побочный запрос CLI к малой модели

Канарейка 2026-09-20 показала в `modelUsage` вторую модель:
`claude-haiku-4-5-20251001`, 1161 входной токен, 19 выходных. Это не ответ
V3 (все ответы дал `claude-opus-5`), а собственная служебная просьба CLI:

чтобы придумать сессии заголовок (текст не обрезается, отказ «слишком длинно»
глотается молча). Заголовок никому не нужен, а доказательства должна видеть
одна модель, поэтому транспорт ставит `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` —
условие пропуска прочитано в том же месте CLI. Второй живой вызов ради
проверки не делался (канарейка одна): признак — пустой список
`wire.auxiliary_models` в квитанции первого же реального вызова. Вызов из-за
побочной модели НЕ отклоняется: ответ принимается только по модели ответа.

## Модель и транспорт (прежний провайдер: gpt-6-astra, до engine 3.4.x)

- Модель `gpt-6-astra`, reasoning `xhigh`; промпты — замороженные
  `MAPPER_PROMPT.txt` / `MINER_PROMPT.txt` / `DEDUPE_PROMPT.txt`
  (sha256 `324696ce…`, `7837a504…`, `b31304ff…`), совпадают с исследованием V3.
- Транспорт версионирован: `provider_transport_version =
  projectchange_v3_codex_transport/1`
  ([transport.py](../backend/app/services/project_change_v3/transport.py)).
  - Полезная нагрузка ≤ 1 048 576 символов: `gateway.call_codex` →
    `codex exec -m gpt-6-astra -s read-only --ephemeral --ignore-user-config
    --ignore-rules --json --output-schema … -i <картинки> -`, `retries=0`,
    таймаут 3600 с на вызов. `--json` (engine 3.4.0) нужен только для
    квитанции: расход токенов берётся из события `turn.completed`, как в
    исследовании; ответ читается только из `-o`, поток событий как ответ не
    разбирается.
  - Полезная нагрузка > 1 048 576 символов (один ход Codex больше не
    принимает, `input_too_large`): `gateway.call_codex_app_server` →
    `codex app-server --stdio`, эфемерный тред. Точные куски по 800 000
    символов, кроме последнего, уходят в видимую модели историю
    (`thread/inject_items`); последний кусок вместе с картинками и
    `outputSchema` запускает ход (`cyberAccessProgram: standard`). Ничего не
    обрезается. Текст собирается обратно из уже сериализованных строк
    JSON-RPC и сверяется по sha256 до запуска процесса и ещё раз перед
    отправкой. При любом расхождении, инструменте в ответе или сбое хода
    результат `FAILED`, повтора нет.
- У каждого вызова в `provenance.transport_calls` есть квитанция:
  `provider_transport_version`, `transport`, `oversize_transport_used`,
  `model_visible_payload_sha256`, `model_visible_payload_size` (символы),
  `model_visible_payload_bytes`, размеры и sha256 кусков, sha256 картинок.
  У oversize-пути дополнительно есть `wire.wire_text_sha256`. С engine 3.4.0
  в квитанции есть `usage` (`input_tokens`, `cached_input_tokens`,
  `output_tokens`, `reasoning_output_tokens`) для обоих путей и
  `provider_ok`, а `provenance.usage_total` — фактический расход по всем
  вызовам прогона, повторы включены. Квитанция пишется и для вызова, который
  упал.
- Перед обращением к модели провайдер проверяет, что `jsonschema`
  импортируется: ответ перепроверяется по схеме. Если пакета нет, вызов
  отклоняется кодом `schema_validator_unavailable` без обращения к модели.
  Эта защита остаётся и после установки пакета.
- Число вызовов на пару: 1 Mapper + по одному Miner на семантический регион
  (+ не больше одного повтора на регион, см. ниже) + 1 Dedupe (если
  изменений ноль, Dedupe не вызывается).

## Повтор майнера после отказа проверки провенанса (engine 3.4.0)

Решение пользователя от 2026-09-19: **один ограниченный повтор.** В
исследовании A-R017 полный оплаченный ответ был отвергнут проверкой
доказательств (`Untraceable evidence: PCA-A-R017-C001`), а следующий вызов с
тем же модельно-видимым входом принят.

- Повторяется только ответ, отвергнутый проверкой трассируемости
  доказательств (`validate.EvidenceTraceabilityError`: неизвестный блок, тип
  или bbox; чужой crop графики). Всего попыток — 2 (`MINER_MAX_ATTEMPTS`).
- Повтор — тот же вызов: тот же промпт, данные, картинки, схема, модель,
  reasoning и семантический регион. Перед повтором отпечаток входа
  пересчитывается; если он не совпал с первой попыткой, повтор не
  отправляется (`miner_retry_input_drift`). Никакой правки промпта или
  доказательств.
- Вторая неудача — `FAILED` с `reason_code = miner_provenance_rejected`.
- Не повторяются: квота и прочие отказы провайдера, целостность транспорта,
  отсутствие валидатора схемы, несоответствие схеме, неверный пакет
  источников, сохранение, ошибки путей и безопасности, отмена, все остальные
  проверки майнера. Общего цикла повторов нет.
- Квитанции обеих попыток — `provenance.miner_attempts`: номер попытки,
  `call_id` (`<pair>_<region>` и `<pair>_<region>_RETRY_1`), sha
  модельно-видимой нагрузки (у обеих одинаковый), транспорт, usage, причина
  отказа, принят/отвергнут. Политика — `provenance.miner_retry_policy`.
- Полезная нагрузка побайтово равна замороженной (`SOURCE_PACKAGING_PARITY.json`:
  A — 25/25, B — 13/13 точных промптов майнера; промпт Mapper совпадает).

## Видимость прогона и остановка (engine 3.4.1)

Найдено живой приёмкой 2026-09-20 (первое реальное сравнение V3, пара ИОС2.1
объекта `4f3e5916`). Модельно-видимый вход и поля результата не менялись.

- **Этап виден.** Состояние `RUNNING` переписывается на каждой границе этапа:
  `V3: семантическое сопоставление OLD↔NEW (Mapper)` → `V3: поиск изменений,
  регион i из n (Miner)` → `V3: поиск дублей (Dedupe)`; в состоянии есть
  `current_stage` (`MAPPING`/`MINING`/`DEDUPE`), `processed`/`total`/`unit`,
  `current_item` (регион) и `model_calls` на этот момент. Раньше весь
  многочасовой прогон висело `V3: подготовка источников`. Если запись прогресса
  не сохранилась, прогон останавливается в `FAILED`
  (`state_persistence_failed`), а не продолжается вслепую.
- **Прогон можно остановить.** Ветка V3 регистрирует тот же run control, что и
  legacy, с `run_id` самого прогона. `POST …/production/cancel` отвечает
  `cancelled: true` и взводит токен: между вызовами прогон останавливается на
  ближайшей границе этапа, внутри вызова шлюз убивает CLI-сессию (≤ 0,2 с).
  Итог — `FAILED`, `reason_code = v3_cancelled`; результат не публикуется,
  убитый вызов попадает в `transport_calls` без `usage`. Отказ провайдера без
  отмены этого прогона сохраняет свой код. Раньше ответом было
  `run_not_owned_by_this_process`, и кнопка «Остановить анализ» не делала ничего.
- **Состояние видно на вкладке «Изменения проекта».** Панель прогона legacy в
  оболочке ProjectChange скрыта (`pcDebug`), а карточки V3 появляются только
  в конце, поэтому идущий и упавший прогон выглядели как «изменений нет».
  Над списком теперь плашка: идёт анализ (этап, минуты, обращения к модели,
  кнопка «Остановить анализ»), анализ не выполнен (сообщение и `reason_code`),
  анализ прерван (процесса больше нет), Human Mapping не опубликован. Для
  опубликованного прогона и для legacy плашки нет. Логика —
  `ProjectChangeView.runBanner` (`frontend/static/js/project-change-view.js`).

## Известные расхождения транспорта с исследованием — решить ДО включения

Упаковку источников они не затрагивают (сверка полная), но от них зависит, дойдёт
ли живой прогон до результата. Во всех случаях прод закрывается в `FAILED`, а не
выдаёт ложные изменения.

1. **Промпты длиннее 1 048 576 символов — РЕШЕНО (engine 3.3.0).** В паре A это
   регионы A-R003, A-R011 и A-R022 (у A-R003 ≈ 1,65 млн символов). В проде
   реализован тот же способ, что и в исследовании
   (`experiments/project_change_272/ai_first_semantic_mapping_projectchange_v3_pair_a_recover.py`):
   история треда плюс последний кусок. Проверки без вызова модели: синтетика
   > 1 048 576 символов (sha восстановленного текста = sha исходного) и
   предпроверка трёх регионов пары A. Прод-упаковка равна замороженному
   промпту, разбиение на куски побайтно равно исследовательскому. Квитанции:
   `OVERSIZE_TRANSPORT_AUDIT.json`, `OVERSIZE_TRANSPORT_TEST.json`,
   `PAIR_A_OVERSIZE_PREFLIGHT.json` в архиве передачи
   `claude_handoff_v3_preinference_ready_*`; скрипт
   `scripts/audit_projectchange_v3_oversize_transport.py`.
2. **Повтор после отказа проверки доказательств — РЕШЕНО (engine 3.4.0).**
   Один повтор с тем же входом, см. раздел выше. Исследование допускало до
   трёх попыток; прод — две.
3. **ИЗВЕСТНЫЙ ТЕХНИЧЕСКИЙ РИСК: явная «стандартная» обработка на обычном
   пути.** Для A-R017 исследование после отказа автоматической обработки
   запрашивало `cyberAccessProgram: standard` через App Server. Прод передаёт
   этот параметр только на oversize-пути (app-server); у `codex exec`
   аналога нет, поэтому такой отказ на обычном пути даёт `FAILED` (повтор
   провенанса на него не распространяется: это отказ провайдера, а не
   проверки доказательств). Сознательно не лечится заранее, без
   воспроизведения. После включения inference независимая проверка прода
   (Fable) проверяет реальный путь провайдера и вправе исправить такой
   технический сбой транспорта, если он воспроизведётся.
4. **Флаги CLI.** Исследование ставило `service_tier=priority`,
   `web_search="disabled"`, `mcp_servers={}`, `project_doc_max_bytes=0`,
   изоляцию bubblewrap и `--disable memories`. Прод выключает более широкий
   набор возможностей (включая `view_image` и `standalone_web_search`),
   использует `--ignore-user-config` и пустой временный `cwd`, но
   `service_tier` и `web_search` явно не задаёт.
5. Проверка гранулярности (`GRANULARITY_AUDIT`) в исследовании была
   диагностической, на карту не влияла; в проде её нет.
6. **`jsonschema` в прод-venv — РЕШЕНО.** Сборщик релиза клонирует venv без
   `pip install`, поэтому пакет ставится отдельным документированным шагом
   сборки: `scripts/install_release_runtime_deps.py` по
   `requirements-projectchange-v3-runtime.lock.txt` (`jsonschema==4.23.0` +
   `attrs 26.1.0`, `jsonschema-specifications 2025.9.1`, `referencing 0.37.0`,
   `rpds-py 2026.6.3` — версии и файлы исследовательского рантайма V3), только

## Запечатанный снимок АР1/ИОС4.2 и живой V3

Объект `4f3e5916` отдаёт 121 запечатанную карточку на **реальных парах своих
сессий сравнения**. Пара снимка и реальная пара считаются одной, если оба
исходных PDF побайтно одинаковы: `source_sha256` снимка совпадает с sha256
PDF реальной пары. Код документа только сужает круг файлов, которые нужно
хешировать. Каждая такая реальная пара получает свои карточки: 84 у АР1,
37 у ИОС4.2, на других парах их нет. Интерфейс остаётся в реальной сессии
объекта, моста просмотра нет. Как прошла привязка, видно в поле ответа
`snapshot_binding` (`bound` / `unbound` / `skipped_live_v3` /
`cards_without_real_pair`). Если у реальной пары есть опубликованный живой
прогон V3, карточки снимка к ней не привязываются: показывается живой
результат.

## Human Mapping с реальной пары

Страница HM реальной пары показывает данные в таком порядке: опубликованный
живой V3 этой пары → (только для объекта фикстур) псевдоним `A`/`B` → посев
запечатанной фикстурой → 404. Посев допускается, только если sha256 левого
PDF пары равен OLD, а правого — NEW одной одобренной фикстуры
(`backend/app/data/human_mapping_fixture_sources.json`, строится и
сверяется `scripts/build_hm_fixture_source_identity.py`). Имена, дисциплина,
код документа, число страниц и метка не решают. Так АР1 (`p11ad4a09d9`)
открывает 25 регионов, ИОС4.2 (`p7b37b4e31b`) — 13. Идентичность в ответе и
странице — реальная (объект, сессия, пара), квитанция в поле `seed`.
Решения человека (CONFIRM/REJECT/UNCERTAIN, ADD/DELETE/REASSIGN BlockLink)
пишутся только под реальную пару; файлы фикстур только читаются. Если позже
у пары появится опубликованный живой V3, его данные HM важнее посева.

## Проверка после включения (сначала на одной паре)

- `GET /api/stage-comparison/sessions/{sid}/pairs/{pid}/production/state` →
  `engine=projectchange_v3`, `status` ∈ {COMPLETED, REVIEW}, `model_calls` > 0,
  `legacy_invoked=false`.
- `GET /api/stage-comparison/objects/{object}/project-changes` → карточки пары
  в `project-change-view/1`.
- `GET /human-mapping/?object={object}&comparison={pid}` → регионы именно этой
  пары.
