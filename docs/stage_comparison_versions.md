# Версии сравнения в разделе «Сравнение стадий»

С 18.11.2026 у одного проекта (объекта реестра) может быть несколько
независимых сравнений — «Версия 1», «Версия 2» и т.д. У каждой версии своя
пара комплектов документов (слева и справа) и свой результат. Старые версии
остаются рабочими, к ним можно вернуться из списка версий.

## Что видит инженер

- В строке вкладок раздела — «Версия сравнения: [список] ✎ [+ Новая версия]».
  - В списке у каждой версии видны название, дата и число документов слева и
    справа.
  - Выбор запоминается в браузере отдельно для каждого объекта. Без
    запомненного открывается самая новая версия.
- Все четыре вкладки показывают выбранную версию: загрузку, сопоставление
  листов, изменения проекта и отчёт.
- «✎» переименовывает версию. Название — от 1 до 100 символов, совпадать с
  другой версией объекта нельзя (регистр не учитывается).
- «+ Новая версия» открывает окно выбора комплектов. Для каждой стороны
  («Слева — исходная редакция», «Справа — новая редакция»):
  - **«Уже загруженный комплект»** — любая сторона любой версии этого
    объекта. Одинаковые комплекты разных версий показываются одной строкой.
    Повторная загрузка не нужна.
  - **«Загрузить новый комплект»** — сторона создаётся пустой. После
    создания сразу открывается «Загрузить проекты» для этой стороны.
- Один и тот же комплект слева и справа выбрать нельзя.
- Новая версия начинается с пустой раскладки пар: «Сопоставить
  автоматически», группы собираются заново.
  - Раскладка и группы из прежней версии не переносятся — решение
    18.11.2026.
  - Результаты прежней версии тоже не переносятся: новая версия сравнивает
    заново.
- В окне «Загрузить проекты» видно, в какую версию идёт загрузка.
- Загрузка в любую версию меняет только её копию комплекта. Можно взять
  комплект из прежней версии и догрузить в него изменённые тома: документ с
  тем же кодом получит новую версию документа только в этой версии
  сравнения.
- Шапка Excel-отчёта для версий, кроме первой, содержит название версии:
  «<объект> · <название версии>».
- Создавать и переименовывать версии может только администратор. Viewer
  переключает версии и смотрит результаты.

## Как устроено

```
projects_v2/objects/<объект>/comparison/          ← Версия 1 (cv001)
    stage_1/  stage_2/  document_groups.json  assemblies/
    comparison_versions.json                     ← реестр версий
    versions/cv002/                              ← Версия 2
        object.json  stage_1/  stage_2/  document_groups.json  assemblies/
```

- **Версия 1** — прежняя папка `comparison/`. Её ничего не переносит:
  `session.json` хранит абсолютные пути к PDF. Без реестра «Версия 1»
  синтезируется на чтении; файл появляется при первом создании или
  переименовании.
- **Реестр** `comparison_versions.json` (схема
  `stage_comparison_versions/1`). Хранит номер (`cvNNN`), название, автора,
  дату создания и переименования, а также источники сторон:
  `{"kind": "existing", "comparison_version", "stage", "documents", "set_key"}`
  или `{"kind": "new"}`.
  - Изменения идут через `common/atomic_json.load_modify_save`: межпроцессная
    блокировка, параллельное создание даёт разные номера.
  - Папка версии без записи в реестре не видна. Её номер повторно не
    выдаётся.
- **Номер версии** `cv001…cv999` — отдельный формат, чтобы не путать его с
  версиями документов (`v001`), версиями сборок (`v005`) и разделом
  «Сравнение версий». В API это параметр `comparison_version`.
- **Копия комплекта** — `shutil.copytree` стороны-источника в рабочую папку
  новой версии.
  - PDF — жёсткой ссылкой: после импорта их никто не переписывает, а это
    ≈95 % объёма. На Stories 1,82 из 1,93 ГБ.
  - Остальные файлы копируются: `stage_storage` пишет JSON на месте, и
    жёсткая ссылка разнесла бы правку по версиям.
  - `stage.json` копии исправляется на имя новой стороны.
  - Копия идёт под общей блокировкой стороны (`stage_lock`). Загрузка берёт
    ту же блокировку эксклюзивно на время подмены папки стадии.
  - Сборки и группы источника не копируются: вложения сборок живут в
    `assemblies/attachments.json`, а не в папке стадии.
- **`set_key`** — sha256 по `(код, версия документа, sha256 input_manifest.json)`
  текущих документов стороны. У копии комплекта он тот же: по нему список
  выбора склеивает одинаковые комплекты, а создание отказывает «один и тот
  же комплект».
- **Сессии, раскладка, прогоны, решения, отчёты** различаются по путям папок
  стадий. Поэтому у каждой версии они свои без отдельной доработки:
  - сессия — по `_source_signature` с путями стадий;
  - доска — `boards/<sha(путей)>`;
  - прогоны V3, «Сведение дублей», ИТ-отчёты, пакет запусков — внутри
    `sessions/<sid>/pairs/<pid>`;
  - решения эксперта — по прогону.

  Прогоны Версии 1 на доску новой версии не подтягиваются:
  `store._comparison_runs` сравнивает корни.

### Область версии `<object_id>@cvNNN`

Группы документов и сборки передают версию строкой области
(`comparison_versions.scope_id`):
- для Версии 1 область совпадает с `object_id`, поэтому прежнее поведение и
  тесты не меняются;
- `stage_upload.resolve_object_dir` превращает область в рабочую папку
  версии;
- область доходит до отдельного процесса сборки аргументом командной строки
  `project_assemblies.worker`;
- область записывается в ссылки на источники сборки и в карту
  происхождения, поэтому ZIP-отчёт (`report_bundle.side_documents`) находит
  файлы участников сборки своей версии.

Место, которое об областях не знает, получит «объект не найден». Записать
молча в Версию 1 оно не может. В JSON групп и в ответах API пишется чистый
`object_id`.

### Где версия выводится из пути стадии

Все проверки «сессия ↔ объект» понимают обе раскладки
(`comparison_versions.parse_stage_path`):
- `core/object_scope._session_belongs` — без этого каждый запрос Версии 2
  получал бы 404 `session_not_in_object` при включённой авторизации;
- `project_change_v3/scope.py`:
  - `object_id_for_session` ищет владельца по всем версиям;
  - `sessions_for_object(object_id, comparison_version=None)`: `None` — все
    версии (проверки владения), значение — одна версия (общие виды);
- `store.assert_path_in_allowlist` — стадии зарегистрированных версий;
- `project_assemblies.scope_for_stage_path` и `object_id_for_stage_path` —
  вложения сборок в сессии, группы по пути стадии, удаление группы с доски;
- шапка отчёта `_report_labels`.

Общая блокировка сборок (`objects/_system/project_assemblies.lock`)
считается от папки Версии 1 — сборки всех версий идут по одной.

## API

Новые маршруты (`/api/stage-comparison/objects/{object_id}`):

| Метод | Путь | Права | Что делает |
|---|---|---|---|
| GET | `/comparison-versions` | просмотр | список версий по номеру, стороны с числом документов и `set_key` (viewer — без путей), `latest` |
| POST | `/comparison-versions` | admin | `{label?, stage_1, stage_2}`; сторона — `{source: "existing", comparison_version, stage}` или `{source: "new"}` |
| PATCH | `/comparison-versions/{comparison_version}` | admin | `{label}` |

Ошибки создания и переименования:

| Код ответа | Коды ошибки |
|---|---|
| 400 | `BAD_SOURCE`, `BAD_COMPARISON_VERSION`, `LABEL_REQUIRED`, `LABEL_TOO_LONG`, `LABEL_INVALID` |
| 404 | `unknown_comparison_version` |
| 409 | `SAME_SET`, `EMPTY_SET`, `SOURCE_NOT_VERSIONED`, `LABEL_TAKEN`, `VERSION_LIMIT` |

Параметр `comparison_version` (query, `^cv\d{3}$`) есть у объектных маршрутов:
- `GET /objects?object_id=`;
- пять маршрутов `document-groups`;
- `upload` и `upload-folder`;
- `GET /objects/{id}/session` (viewer);
- `GET /objects/{id}/project-changes`;
- `GET /api/project-comparison/catalog` и `/progress`.

Как обрабатывается параметр:
- нет параметра — Версия 1: вкладки, открытые до выкатки, работают как раньше;
- неизвестная версия — 404 `unknown_comparison_version` до любой записи;
- маршруты по `session_id` параметра не принимают: версия следует из сессии.

Ответы `POST /sessions` и `GET /sessions/{id}` несут поле
`comparison_version`. Оно вычисляется по пути стадии, реестр не читается.

Каталог результатов:
- у записей есть поле `comparison_version`;
- `pair_group_key` включает версию для `cv≠cv001`, чтобы одинаковые пары
  разных версий не сливались в одну «основную»;
- ключи Версии 1 прежние.

Запечатанный снимок объекта привязывается только к парам Версии 1.

## Не входит

- Удаление версий.
- Перенос раскладки пар и групп между версиями (решение 18.11.2026).
- Перенос результатов из прежней версии в новую.
- Жёсткие ссылки в обычной загрузке: `copytree` при каждой загрузке
  по-прежнему копирует сторону целиком, и первая загрузка в повторно взятую
  сторону разводит её PDF в отдельные копии.

## Откат

Откат на релиз до версий безопасен. Версия 1 лежит там же, где и раньше.
Папки `versions/` и файл `comparison_versions.json` прежний код не видит,
сессии версий для него «чужие» (404). Данные версий остаются на диске и снова
видны после возврата на релиз с версиями.

  Прогон V3 идёт на тестовом провайдере; у каждой версии своя пара и свой
  результат, результат Версии 1 после прогона Версии 2 не меняется.
