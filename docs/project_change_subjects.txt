Экспериментальный режим ProjectChange «По инженерным предметам»
Версия движка 3.29.0; метод projectchange_subjects/2.

Коротко для пользователя

Перед сравнением выбирается метод: «Стандартный» или «По инженерным предметам».
Новый метод доступен и для больших, и для маленьких пар. Он сначала читает
документы и составляет каталог предметов, ищет соответствия по назначению,
добирает связанные листы и передаёт полные источники существующему поиску изменений.
Результат каждого запуска сохраняется отдельно. В каталоге можно открыть любой
готовый вариант; подпись показывает метод и модель. По умолчанию выбран стандартный.

Что реализовано

1. Односторонний каталог по полному MD, таблицам и графическим кропам.
   Блок должен иметь наблюдение либо явное объяснение его исключения из каталога.
   У наблюдения есть функция, зоны, обозначения, роль источника, параметры с
   основанием и режимом, ссылки. Физическое/рабочее/резервное количество — разные
   nullable поля. Покрытие блоков не доказывает полноту извлечённых смыслов.
2. Семантический поиск по карточкам обеих стадий. При необходимости карточки
   разбиваются на порции с покрытием OLD×NEW КАТАЛОГА. Это не линейный алгоритм
   в худшем случае. Основной выигрыш ожидается от уменьшения повторной передачи
   полных источников; числа вызовов и качество нужно измерять.
3. Кандидатные группы образуют явные связи наблюдений. Общая страница сама по
   себе не объединяет предметы. Модель читает полные страницы группы и может
   запросить другие страницы по марке, функции, зоне или оборудованию.
   Поиск локальный, по всему корпусу, в обоих направлениях. Нормализация
   регистра, пунктуации и сходных латинских/кириллических знаков применяется
   только к индексу, не к MD и не к результатам.
4. Ограничения добора: до двух раундов на группу, до 12 запросов за раунд,
   до 12 найденных страниц на запрос. Нулевые результаты, обрезанные списки
   и исчерпание бюджета записываются в gaps, не превращаются в доказанное удаление.
   Поиск по изображению без текста опирается на первичный визуальный каталог.
5. Подробный Mapper получает оригиналы выбранных страниц и все их кропы.
   Большая группа делится существующим проверенным планировщиком. Карта имеет
   прежнюю схему. Miner получает оригинальные источники каждой подтверждённой
   области. Строгая трассируемость доказательств и запрет односторонних изменений
   сохраняются. Дополнительные правила учитывают режимы, резерв и графы давления.
6. Проверка параметров добирает источники связанной группы и ищет контрдоказательства
   по обозначениям во всём корпусе, включая другие документы той же стадии.
   Читает оригиналы; слишком большой запрос не обрезается, его проверка остаётся
   незавершённой. Поиск и его ограничения сохраняются.
7. Принятые ответы каталога, маршрутизации, добора и подробного Mapper сохраняются
   сразу. При явном продолжении остановленного поиска проверяются источники,
   кропы, модель, промпты, схемы и состав каждого запроса. Изменение методики или
   модели без явной политики remaining_stages при продолжении поиска запрещено.
   Эта политика позволяет выбрать Sol 6.1 (профиль sol61) для новых запросов:
   старые ответы повторно проверяются и сохраняют исходные квитанции Astra,
   новые ключи связываются с исходными через reused_from_key/identity. Все
   сохранённые ответы текущего пакета проверяются до первого нового вызова;
   последующая остановка на Sol не заставляет повторять принятые ответы Astra.
   В provenance.model_handoff отмечена передача частично выполненного поиска,
   а прежний usage остаётся отдельно в subject_recovery. У Miner и последующих этапов остаётся
   собственный механизм сохранения/продолжения.
   Независимые запросы исполняются с выбранным параллелизмом 5 или 10; после
   ошибки новые запросы не запускаются, уже идущие ответы сохраняются.
   Результаты собираются в детерминированном порядке, независимо от порядка ответа.

API и артефакты

POST .../production/run: comparison_mode = standard | subjects.
Без выбора свежий запуск стандартный, продолжение наследует метод донора.
Поле не связано с ai_mode или model_profile. Очередь пар сохраняет метод запуска.
GET /api/stage-comparison/production/ai-modes возвращает comparison_modes.
Профиль sol61 должен быть явно включён в PROJECT_COMPARISON_V3_MODEL_CHOICES.
Для смены модели: остановить запуск, затем POST .../production/run с
resume_from_run_id, model_profile=sol61 и resume_model_policy=remaining_stages.
Профиль по умолчанию не меняется. Все новые этапы продолжения используют Sol 6.1/xhigh.

project_change_v3_subject_search.json: источники и их хеши/происхождение,
каталог, связи, кандидатные группы, запросы, пробелы, подробные пакеты,
покрытие пар страниц и сводные счётчики.
project_change_v3_subject_checkpoint.json: проверенная идентичность запуска,
принятые ответы по ключу фактического запроса и попытки.
provenance: comparison_mode, subject_method_version, subject_contract_sha256,
subject_search, subject_recovery; реальные квитанции и usage остаются отдельно
от оценок планировщика. При продолжении поиска предыдущий расход обозначен
отдельно, новые квитанции не выдаются за повторно выполненные старые вызовы.

Гарантии и границы первой версии

Стандартный режим продолжает использовать полное покрытие сочетаний страниц.
Новый режим использует кандидатов. Его результат всегда требует проверки;
страница без найденной связи остаётся предварительно несопоставленной. Журнал
отдельно показывает нерассмотренные сочетания и незакрытые запросы. Ни отсутствие
gaps, ни покрытие всех блоков не доказывает отсутствие пропущенного изменения.
Нельзя объявлять новый режим лучшим по одному числу карточек или по экономии.

Каталог — вспомогательное наблюдение модели, не эталон инженерных фактов.
TEXT берётся только из подготовленного MD. Повторного извлечения PDF-текста нет.
Внутристоронние противоречия сохраняются. Механического расширения объединённых
областей до общего OLD×NEW между разными заданиями Miner нет.
Качество моделей и экономия на настоящих проектах этой реализацией ещё не измерены.
OpenRouter не используется; разрешительные шлюзы существующих провайдеров не меняются.

Порядок пилота

Использовать только допущенные DEV пары объекта 272, stage_1 → stage_2,
логическая v002, через experiments/project_change_272/policy.py.
Выбрать малую, среднюю и самую большую допустимую пару. Пара с embargo_pages
не допускается к такому полному запуску без отдельного разрешённого протокола.
Проверку split/версий/хешей выполнить до чтения исходников. Архивный объект 256
не является основанием для настройки, оценки качества или замены стандарта.

Сравнивать два метода на одинаковых источниках и модели. Фиксировать время,
вызовы, фактический usage, принятые/непринятые ответы, покрытие и пробелы.
Инженерная оценка должна независимо установить подтверждённые изменения,
пропуски, ложные изменения/объединения, правильность ссылок, чисел и конфликтов.
Стандартный результат не считать эталоном автоматически. Известные случаи не
обозначать слепой проверкой. До доступа к VALIDATION/FINAL_HOLDOUT требуется
заморозка кандидата; нельзя использовать резерв для настройки.

В каталоге результатов показаны число вызовов, известный фактический расход
входных/выходных токенов и длительность. Для сохранённого локального отчёта:
python scripts/compare_projectchange_modes.py --dev-pair НОМЕР \
  --standard-run ПАПКА_СТАНДАРТНОГО_ПРОГОНА --subjects-run ПАПКА_НОВОГО_ПРОГОНА \
  --output /tmp/projectchange-mode-comparison.json
Команда сначала проверяет допуск DEV, затем привязку к документам, сохранность
артефактов и совпадение MD/графики. Числа сами по себе не назначают победителя.
Для чистого сравнения расходов нужны два свежих запуска: продолжение имеет
отдельную историю расходов и явно помечается как ограничение сравнения.

Решение о замене стандартного режима принимается после такого пилота.
Разработка и синтетические тесты не запускают анализ в production и не тратят
подписку на модели. Для применения нового кода нужен обычный релиз проекта.
