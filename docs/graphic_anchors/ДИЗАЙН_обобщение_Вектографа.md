# Обобщение Вектографа: якорные точки для всех графических блоков

**Статус: утверждённый дизайн (2026-07-29), код не написан.**
Собран двухфазным multi-agent разбором: 9 читателей (полный разбор кода block_grounding,
галереи 1133 эталонов, инфраструктуры) → 8 проектировщиков с обязательной эмпирикой на
реальных PDF корпуса → критик полноты. Полные отчёты — в `отчёты/`, воспроизводимые
python-пробы с числами — в `пробы/`. Этот файл — канонический синтез: разрешает все
конфликты между дизайнами и фиксирует порядок реализации.

**Цель** (задача Андрея Ивановича): для каждого уникального типа графического блока каждой
дисциплины придумать якорные точки и правила связывания текстовых значений между собой и с
элементами чертежа (размер → выносные линии/полочка → элемент; толщина → слой; позиция →
выноска → стержень), чтобы скрипты пайплайна описывали блоки с очень высокой точностью и
граф подавался в LLM вместе с картинкой — как Вектограф делает для однолинеек ЭОМ.

---

## 1. Главный вывод разбора

Схемные дисциплины уже имеют настоящие графы: **ЭОМ** (Вектограф + electrical_geometry —
эталон), **ГП** (сети «подпись↔CAD-компонента»), **СС** (богатейший набор из 20+ грамматик с
provenance-шкалой), **ОВ/ВК** (union-find трасс, `levels_by_elevation`). А вот строительные —
нет: на 510 графов АР/КЖ/КМ/ГП/ТХ всего **172 ребра, и все — «порядок слоёв»**. Размеры (935
dimension-узлов только в АР), отметки, позиции, марки лежат плоскими реестрами.

**Механики «размер→полочка→элемент» нет нигде.** Слой `vector_path_graph.py` читает только
отрезки `"l"`, выбрасывает заливки (где живут стрелки и junction-точки), не разворачивает
`re`/`qu`/Безье, не использует `width`. Ни один модуль не детектирует размерные линии,
засечки, полочки выносок, осевые кружки. Warning в `structural_geometry.py:82` прямо
называет выноску отсутствующим механизмом.

Эмпирика проектировщиков (60+ PDF, 8 наборов проб) доказала: **всё это детектируемо
детерминированно** — засечки, полочки, кружки осей, флажки отметок, стрелки уклонов, сетки
таблиц имеют стабильные геометрические сигнатуры в вектор-слое, а масштаб листа
восстанавливается по парам «число ↔ расстояние между засечками» с точностью 0.1–1.5%.

## 2. Механика Вектографа — что переносится (выжимка)

Полный каталог: `отчёты/разбор_vectograf-core.md`. Три яруса:

- **Ярус A (берётся как есть):** клипы fail-closed (`_clip_words_to_bbox/_polygon`),
  `_filter_text_lines_to_region` (порядок строк pdfplumber сохраняется!), `_find_page_index`
  по needle-токенам (лечит баг page_index), `_near`/`_near_xy`/`_median`,
  `cluster_by_gap` (3 инлайн-копии → общий helper).
- **Ярус B (универсальный алгоритм, параметры = профиль):** `_bind_codes_columnwise`
  (offset-corrected nearest column + алиасы δ±шаг + GEOMETRY_CONFLICT), `_split_codes_by_y_rows`
  (ярусность подписей), «вычесть известное → остаток = подпись» (`_extract_consumer_geo`),
  «якорь-с-единицей + вертикальный сбор» (`_extract_lighting_runs`), «атрибут по Y-строке
  хозяина» (`_pole_for_breaker`), восстановление разорванных CAD-токенов «число+единица»,
  `semantic_facts` (реестр фактов без рёбер), счётчики честности + гейт.
- **Ярус C (ЭОМ-специфика):** регэкспы сущностей, физика P=√3·U·I·cosφ,
  `_deterministic_protection_check` (идея «пересчёт домена → готовые факты в промпт»
  переносится), хардкоды (`_extract_power` «ВА-305…», `_extract_service_elements`,
  `_TT_ANCHOR_RE`) — **вычищаются в конфиг** (§7.2).

Сквозные принципы, обязательные для всех новых детекторов: (1) допуски в долях медианного
шага якорей, не в px; (2) fail-closed для областей, fail-soft послойно; (3) конфликт →
явная заметка GEOMETRY_CONFLICT, никогда молчаливый выбор; (4) непривязанное не теряется —
уходит в semantic_ledger; (5) гейт качества перед подачей в LLM («слабый граф хуже честного
„нет графа“»); (6) анти-boilerplate инструкции в рендере.

## 5. Единая схема графа v2 и provenance

Конверт — аддитивный к schema_version=1 (`дизайн_integration-design.md` §2.1): новое поле
`graph_schema_version: 2` + опциональные слои `graphic_anchors[]`, `dimensions[]`,
`dimension_chains[]`, `leaders[]`, `axis_grid`, `tables[]` + аддитивные счётчики validation.
Связь «размер→элемент» — сущность `dimension` с evidence-ссылками на graphic_anchors, ПЛЮС
обычные рёбра `measures|annotates|located_on_axis` для существующих потребителей.
`SCHEMA_VERSION` пакета остаётся 6 (граф — opaque dict).

Канонический реестр provenance — иерархия tier 5…0 из integration-design §2.2 (семантика
кода > текстовая аннотация пары > подтверждённая CAD-геометрия > близость/порядок >
инвентарь > not_extracted). Существующие коды не переименовываются; добавляются
`dimension_line_confirmed`, `leader_polyline_confirmed`, `axis_circle_confirmed`,
`table_grid_cell`, `text_cluster_only`, `ocr_from_vector_glyphs`, `dimension_break_confirmed`,
`axis_ring_confirmed`. Словарь quality.py примитивов отображается в этот реестр (не свой).
Ортогональная ось — physics_check (замыкание цепочек, монотонность ⌀, Δh=i·L).

Правило промоции против ложных детекций: текстовый кластер осей получает tier 3 только при
подтверждении кружком/штрих-цепочкой; dimension без размерной линии остаётся плоским узлом.
Анти-паттерны findings: размер со «*» (не в масштабе) исключается из scale-чеков; «N ряд»
кладки — не размер; «фр.20-40мм» — не толщина слоя.

## 7. Владение таблицами и конфиги

**7.1 Таблицы (снимает конфликт пяти реализаций):** движок `tables.py` — библиотека.
Дисциплинарный профиль, у которого таблица — часть предметной области (ведомость дверей →
`ar_opening_drawing`, ведомость отделки → `ar_finish_plan`, спецификации КЖ/КМ → новые
`kj_steel_schedule`/`km_element_schedule` внутри structural_geometry), вызывает движок сам —
profile_id сохраняется, сигнатуры каталога стабильны. Router-ветка **`table_structured`** —
только fallback для табличных блоков без дисциплинарного профиля (кабельные журналы,
экспликации, generic) и для text-блоков (большинство спецификаций ЭОМ/СС — `block_type:
"text"`, в image-роутер не попадают: их обсчитывает пост-стадия по bbox из result.json).
Карточки подтипов (12 форм ГОСТ с ожидаемыми колонками и findings) — в
`дизайн_tables-design.md` §2. Findings-карты дверей/отделки/спецификаций живут в одном
месте (tables-design), АР/КЖ ссылаются.

**7.2 Конфиги:** `reference_catalog/profile_rules/<DISC>.json` (loader по образцу
`loader.py`, lru+валидация): ярус C ЭОМ (модели, `_TT_ANCHOR_RE`, service-каталог,
стоп-маркеры нот), `_ID_HINTS` (37 ОВ + ~50 ВК + 19 СС) как **project-scoped** секции
(`object_scope: 214_Alia_ASTERUS`), `_GATE_RULES` ALIA, цвет→тип сети, needle-регэкспы,
гейт-пороги (в коде остаются default'ы), render_budget, пресеты засечек/полочек per-disc.
Грамматики сущностей (регэкспы `_QF_RE`, `_ADDRESS_RE`, PATTERNS) остаются в коде.

## 8. Кросс-блочный реестр (новая пост-стадия)

Нужен четырём дизайнам (сечения план↔разрез КЖ, «Линия N.N» план↔профиль ГП, марка насоса
кривая↔схема ОВ/ВК, позиции таблица↔чертёж). **Решение критика принято:** отдельная
пост-стадия `table_cross_reference`/`cross_block_registry` ПОСЛЕ сборки пакетов, пишет
СВОЙ артефакт `_output/cross_block_registry.json` — **пакеты не мутируются** (иначе
ломается иммутабельность hard-link sidecar-графов галереи). Findings из реестра идут в
merge с `related_block_ids`; инвалидация — при пересборке любого блока версии. Валюты
связи: `Поз. N`, `Д-N`, `М-N`, коды цепей, марки Стм/Пм, «Линия N.N», марки насосов,
имена сечений «1-1». Прод-порт доказанной связки `experiments/crosssheet_valuejoin`.

## 9. Интеграция в пайплайн

- **Каскад роутера не трогается до влития ветки feature/block-vector-graphs** (незакоммичено:
  СС CTX-профили + normalize_low_voltage_graph + sidecar). Затем — табличная fallback-ветка.
- Точки встраивания не меняются: `resolve_block_package` → `user_text` → Stage 02.
  Апгрейды лотков/клемм обязаны обновлять normalize-проекцию СС, иначе CTX-окно не увидит.
- **Prepared-reuse:** Stage 02 сейчас вызывает `resolve_block_package(prefer_prepared=False)`
  — с тяжёлыми детекторами это удвоение стоимости. Ввести config-hash/mtime-гейт: prepared
  переиспользуется, если конфиг примитивов и result.json не менялись.
- **Промпт-бюджет:** ~5–6К токенов у строительных (однолинейка при своих 10–12К). Приоритет
  рендера: шапка+гейт → готовые детерминированные факты (полностью) → связанные сущности
  компактно (цепочка = одна строка; cap ~60 строк + счётчик излишка; row-cap таблиц) →
  непривязанное только счётчиками → анти-boilerplate («непривязанность — ограничение
  разметки, НЕ дефект»). Provenance печатается только при tier<3.
- **Обвязка, которую нельзя забыть:** `localize_profiled_block_graphs.py` (новые рендер-секции),
  фронтенд `profiled_graph_display` (отображение слоёв dimensions/leaders в панели «Граф
  схемы»), словари `profiled_graph_localization.py` (новые kind/edge_type/профили; сверить
  PROFILE_LABELS с фактическими профилями water_geometry), `build_catalog.py` (bump
  catalog_version — новые `*_total` попадут в сигнатуры).
- Двойной маршрут findings: детерминированные факты по умолчанию идут «в промпт» (паттерн
  `_deterministic_protection_check`); «детектор-инжект в merge» — только для кросс-блочного
  реестра (Stage 02 одного блока их не видит). Дедуп с LLM-findings — на merge по
  fingerprint значения+листа.

## 11. Измерение качества без разметки

1. **Замыкание цепочек**: Σ сегментов = габарит (допуск 1 мм·n) — прокси точности; расхождение
   кратно соседнему размеру = алиас привязки (наша ошибка), иначе — finding проекта.
2. **Согласованность масштаба**: остатки >5% от медианы вида = подозрительная связь.
3. **Физика per-discipline**: Δh=i·L (ГП), монотонность ⌀ (ВК, дописать К-ветку),
   шаг×кол-во≈зона (КЖ), n_ступеней×подступёнок=Δотметок (АР-лестницы).
4. **GEOMETRY_CONFLICT-rate** ≤15% (унаследовано от гейта однолинейки).
5. Ручная выборка единожды: 5 блоков × 5 профилей, CSV-вердикты, precision ≥0.95 на
   связанных; recall не гейтится (непривязанное честно в ledger).
