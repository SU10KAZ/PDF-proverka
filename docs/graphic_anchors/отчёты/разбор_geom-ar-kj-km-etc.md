# Отчёт: дисциплинарные геометрии АР/КЖ/КМ/ГП/ТХ + electrical_geometry + block_text_clustering

## 0. Общий фундамент (важно для всех модулей)

Все пять дисциплинарных модулей — тонкие обёртки над общими хелперами из `hvac_geometry.py` (не входил в задание, но прочитан точечно, т.к. в нём вся механика):

- `_node` (hvac_geometry.py:129), `_unique` (136) — узел-факт: текст + bbox + центр + `source_label` (полная исходная строка).
- `_segments` (hvac_geometry.py:153-167) — линии из `page.get_drawings()` (только items типа `"l"`, фильтры по цвету vivid/neutral).
- `_components` (hvac_geometry.py:170-195) — union-find по совпадению **конечных точек** сегментов (квантование `round(p/tolerance)`), считает `branch_points` (степень ≥3) и `endpoint_count`. Это ядро «CAD-непрерывности»: пересечение линий без общей конечной точки соединением НЕ считается.
- `_attach` (hvac_geometry.py:198-207) — привязка узла к ближайшему сегменту (точка→отрезок, проекция) с порогом `limit`; узел получает `route_id` компоненты.
- `_axes` (hvac_geometry.py:219-234) — оси А/Б/1/2: короткий токен (`^[A-ZА-Я]{1,3}|\d+$`), повторённый ≥2 раз и выстроенный в вертикаль/горизонталь → ось с позицией.
- `_bind_nearest_axes` (hvac_geometry.py:237-242) — проставляет узлам `nearest_vertical_axis`/`nearest_horizontal_axis` (вызывается ТОЛЬКО в ЭОМ, см. ниже).
- `_views` (hvac_geometry.py:464-470) — «виды» по regex подписи (`Разрез|Вид|Узел|N-N`); `_assign_nodes_to_views` (473-479) — членство по **ближайшему якорю подписи**, НЕ по вхождению в bbox вида (слабое место: узел прилипает к ближайшей подписи, а не к своему виду).
- `_preferred_parent` (hvac_geometry.py:210-216) — родитель: сначала кандидат из той же CAD-компоненты (`same_cad_component`), иначе ближайший по расстоянию (`nearest_geometry`).
- `_base` (hvac_geometry.py:245-270) — каркас графа `{nodes, containers, networks, edges, validation, warnings}` + **`semantic_ledger`**: полный координатный реестр ВСЕХ строк текст-слоя (id, text, bbox_page, x, y) — страховка от потери надписей, не вошедших в словари паттернов.

Все модули имеют по два входа: `build_*_graph(pdf)` (одностраничный блок-PDF) и `build_*_graph_from_source(pdf, page_index, bbox_norm, polygon_norm)` (кроп из исходника с derotation + опциональный полигон-клип `_clip_copied_page`).

## 1. architecture_geometry.py (АР, 230 строк)

**(а) Типы блоков.** 21 профиль (строки 8-19): кладочный план/узел, лестница, ограждение, разрез, план отверстий, фасад, узел, маркировочный план, эскиз проёма, план этажа, кровля (план/узел), отделка, фундамент под оборудование, развёртка стены, потолок, полы, интерьерная электрика, мебель, узел примыкания пола/стены. Классификатор — `classify_ar_profile` (architecture_geometry.py:25-74), чисто по ключевым словам текста с приоритетами (комментарий 30-32: развёртка перед проёмами, иначе теряются размерные цепочки стен — реальный кейс АИ2 «580+580 против 1155 мм»). Деление на `PLAN_PROFILES` / `ELEVATION_PROFILES` / `DETAIL_PROFILES` (20-23).

**(б) Якорные точки.** 17 regex-паттернов `PATTERNS` (76-93): room, opening (ДПМ/ДО/ОК-марки), **elevation** (`[+-]N,NNN`), **dimension** (`AxB`, `R=`, `N мм`), material, construction_element, layer_count, installation_requirement, finish_mark, furniture, furniture_mark, electrical_fixture, roof_element, stair_or_railing, fire_rating (EI/REI), fastener. Извлечение — `_facts` (103-111) по строкам `_lines` (95-102). Спец-правило: **голые числа 2-5 цифр как dimension** только для профилей FLOOR_WALL_JUNCTION и WALL_ELEVATION (109-110). Растровые области — `_raster_nodes` (124-131). Оси — `_axes`, но кладутся в `graph["grid"]` (139) и к узлам НЕ привязываются (`_bind_nearest_axes` не вызывается).

**(в) Приёмы связывания.**
1. `_nearest_room` (118-123): каждому узлу — метка ближайшего помещения, если расстояние < 20% диагонали; честно помечено `room_binding_state="пространственно ближайшая подпись"` (не полигон комнаты).
2. `_architectural_views` (112-117): контейнеры-виды по regex подписей («Развертка|Фасад|Сечение|Фрагмент|Схема устройства/примыкания») + членство по ближайшему якорю.
3. **Единственный тип рёбер**: в `_view_graph` (140-155) для профиля ROOF_DETAIL — «порядок слоёв» (144-147): узлы-material сортируются по (y,x), соседние соединяются, если |Δx| < 40% ширины. Всё.
4. В `_plan` (132-139) рёбер нет вовсе — только счётчики + `_inside_segments` как число.

**(г) Валидация.** Счётчики по типам (axes/rooms/openings/materials/…, 134-137), `physical_line_segments_total`, `topology_state`. Гейт `evaluate_ar_gate` (186-191): use = есть узлы или сегменты; complete = есть текст-слой; `description_depth` — только `semantic_hierarchy` (планы) или `physical_hierarchy` (виды/узлы), уровень `engineering_graph` для АР **недостижим в принципе**. Рендер — `render_ar_markdown` (205-230).

**(д) Непокрытое / зрелость.** РАЗМЕРЫ: ловятся как узлы-факты с координатами и считаются, но **ни одной связи размер→элемент нет**: нет детекции размерных линий, засечек, выносных линий, размерных цепочек, суммирования цепочки. ВЫНОСКИ (полочки): **не детектируются вообще** — ни в одном модуле нет анализа leader-линий (полочка = короткий сегмент от текста к элементу; `_inside_segments` их видит, но никто не связывает текст с концом линии). ПРИВЯЗКА К ОСЯМ: оси найдены, но узлам не проставлены. УЗЛЫ/РАЗРЕЗЫ: только контейнер «вид» по подписи + nearest-anchor членство; исключение — порядок слоёв кровельного узла.
**Оценка: продвинутая кластеризация фактов (инвентарь с координатами + nearest-room + 1 эвристика слоёв). НЕ граф со связями «размер→полочка→элемент».**

## 2. structural_geometry.py (КЖ + КМ, 132 строки)

**(а) Типы блоков.** КЖ: опалубочный план, план армирования, сечение армирования, маркировочная схема, закладные, ж/б узел (строка 7). КМ: монтажная схема, чертёж элемента, узел соединения, стремянка, фасадная система (схема/узел), мокап (строка 9). Классификаторы `classify_kj_profile` (28-38), `classify_km_profile` (39-49) — ключевые слова.

**(б) Якорные точки.** 14 паттернов `PATTERNS` (12-27): structural_mark (Стм/Км/Пм/Бм…), **rebar** (Ø12 А500С и вариации), **position** («поз. №N» — это и есть текст выноски-позиции!), **spacing** («шаг 200»), **elevation**, **dimension** (`AxBxC`, `N мм`), concrete (В25 W6 F150), **cover** («защитный слой…»), embedded, section_mark («разрез 1-1»), steel_profile (L/HEA/Швеллер…), bolt (М16), weld (катет), plate. `_facts` (58-68) + растровые области. КМ-фолбэк: если текста нет, но есть вектор — один узел `vector_geometry_region` на весь лист (71-73).

**(в) Приёмы связывания.** Фактически **нет**. `_dispatch` (69-83): узлы + оси (в `grid`, без привязки) + счётчик сегментов (`_inside_segments`, для km_ отключён — 74) + виды для не-плановых профилей (nearest-anchor). **Рёбра не строятся никогда** — в модуле нет ни одной ветки, создающей `edges`. Модуль сам это декларирует в warning (82): *«арматурные марки и позиции сохраняются по координатам; попарная связь не создаётся без выноски или отдельного правила»* — прямое признание, что механика выносок не реализована.

**(г) Валидация.** Счётчики (77-81): marks/rebar/positions/spacings/elevations/dimensions/embedded + `vector_geometry_state` (для КМ «preserved_not_expanded»). Гейт `evaluate_structural_gate` (114-118) — тот же паттерн, глубина только semantic/physical_hierarchy. Рендер `render_structural_markdown` (124-132).

**(д) Непокрытое / зрелость.** Ключевое для КЖ: связка «позиция → выноска → стержень», «шаг → зона армирования», «Ø/класс → позиция», размерные цепочки опалубки, привязки к осям — **ничего из этого нет**. Для КМ: связка «профиль → элемент», «болт/шов → узел» — нет. Даже порядка слоёв (как в АР-кровле) нет.
**Оценка: чистая кластеризация/инвентарь фактов. Самый честный из «заглушек»: словарь паттернов богатый и предметный, но нулевая топология.**

## 3. technology_geometry.py (ТХ, 80 строк)

**(а) Типы блоков.** 8 профилей (строка 7): план/узел автостоянки, план/разрез/оборудование/задание лифта, план/узел мусороудаления. `classify_tx_profile` (15-28).

**(б) Якорные точки.** 12 паттернов (9-14): lift (Л1.1П), parking_space (м/м №N), accessibility (МГН), parking_device, shaft, lift_device, capacity (кг/чел), speed (м/с), elevation, dimension, fire_rating, waste_device. `_facts` (36-44) + растр.

**(в) Приёмы связывания.** **Нет вообще.** `_dispatch` (45-48): узлы + оси (grid) + счётчик сегментов + виды для не-плановых. Не вызывается даже `_attach` — узлы не привязываются к CAD-компонентам; рёбер и сетей нет.

**(г) Валидация.** Счётчики lifts/parking_spaces/lift_devices/… + `topology_state="technology_plan_or_views"` (48). Гейт `evaluate_tx_gate` (67-71). Рендер `render_tx_markdown` (74-80).

**(д) Непокрытое / зрелость.** Габариты машиномест → разметка, кабина → шахта, грузоподъёмность → конкретный лифт — ничего не связано.
**Оценка: заглушка-инвентарь (самый слабый модуль из пяти; даже route-attach отсутствует).**

## 4. general_plan_geometry.py (ГП, 271 строка)

**(а) Типы блоков.** 13 профилей (11-18): оси, генплан, разбивочный, рельеф (+узел), земляные массы, покрытия, дорожная одежда, раскладка, МАФ, водоотвод (план/профиль/узел). `classify_gp_profile` (24-43). Деление: `PLAN_PROFILES` (сети) / `PHYSICAL_PROFILES` (слои/виды) (19-21).

**(б) Якорные точки.** 12 паттернов (46-59): building (корпус №/К1-7), floor_count, **elevation** (в т.ч. без знака `NN.NN`), **coordinate** (X=/Y= — геодезия!), radius, **slope** (i=… и ‰), dimension (мм/см/м), area_or_volume (м²/м³), surface, small_form, drainage (DN…), earthwork. Плюс **производные узлы**: `building_footprint` — контур здания восстанавливается по позиции подписи этажности (`_plan`:124-126, `field_state="confirmed_by_floor_count_position"`); `earthwork_cell` — ячейка сетки земляных масс из знаковой отметки Δ (128-131).

**(в) Приёмы связывания.** Самые настоящие среди «строительных» модулей:
1. Собственный `_inside_segments` (82-103) — сегменты с клипом по границам страницы и цветовой логикой (vivid → фолбэк на все, если <15), **этот хелпер импортируют АР/КЖ/ТХ**.
2. Собственный `_attach` (106-116) — проекция точки на отрезок, порог 25-30, узел получает `route_id` компоненты.
3. `_plan` (119-151): `_components(tolerance=3)` + `_attach` → **сети** `site_geometry_component` (133-140): CAD-компонента + подписанные ей узлы (label из building/small_form/drainage/surface/earthwork). Это граф уровня «подпись ↔ непрерывная CAD-линия».
4. `_physical` (153-178): для PROFILE_ROAD — **рёбра порядка слоёв дорожной одежды** (165-169, сортировка surface по y, |Δx|<50% ширины); штриховки честно не разворачиваются (159, комментарий 155-158: >120 тыс. hatch-путей).

**(г) Валидация.** Счётчики + route_segments/components/branches + `nodes_route_attached` (141-147); warnings о том, что назначение линии определяется только подписью и что пересечение ≠ соединение (147-149). Гейт `evaluate_gp_gate` (218-226): для плановых профилей глубина **`engineering_graph`**, если хоть одна сеть имеет endpoint_ids — единственный «строительный» модуль, способный достичь этого уровня. `render_gp_markdown` (249-271).

**(д) Непокрытое / зрелость.** Уклон→конкретный участок лотка, отметка→конкретная точка профиля, размерные привязки разбивочного плана (X=/Y= ловятся, но не связываются с объектом) — не реализовано; выносок нет.
**Оценка: настоящий граф «подпись↔CAD-компонента» для планов + рёбра слоёв для дорожной одежды; между «кластеризацией» и «инженерным графом» — ближе ко второму, но без размеров-связей.**

## 5. electrical_geometry.py (ЭОМ вне Вектографа, 469 строк)

**(а) Типы блоков.** 12 профилей (17-31): singleline (уходит в Вектограф), схема щита, план силовых сетей, освещение, кабельные трассы, молниезащита/заземление, СУП, ОЗДС, монтажный узел, чертёж оборудования, светотехнический расчёт, площадочная схема. `classify_electrical_profile` (34-54) — в т.ч. эвристика «≥3 вхождений QF → panel» (45).

**(б) Якорные точки.** Базовые regex (57-64): `_PANEL_RE` (ВРУ/ГРЩ/ЩР/…), `_DEVICE_RE` (QF/УЗО/АВДТ…), `_CIRCUIT_RE` (Гр.N, K1.2.3, L1/N/PE/PEN), `_CABLE_RE` (ВВГнг…), `_ELEV_RE`, `_SIZE_RE` (AxB, мм²), `_POWER_RE` (кВт/А/В/лк), `_FIRE_RE` + per-builder extra-паттерны. Ключевая особенность `_line_fact_nodes` (67-97): **тройной источник строк** — склеенные `_lines` + объединённые spans PDF-линии + каждый span отдельно (74-89, комментарий: вертикальные марки групп вдоль трасс под 90° не должны исчезать). Анти-шум: N/PE/PEN в строке >40 символов отбрасывается (94).

**(в) Приёмы связывания.** Наиболее богатый набор:
1. `_build_plan` (134-162): **единственное место, где вызывается `_bind_nearest_axes`** (142) — узлы получают ближайшие оси; nearest-room в радиусе 22% (144-148); `_route_geometry` (113-117, cap 60000) + `_attach(limit=28)` → сети `_networks` (120-131) типов lighting_route/cable_route/power_route с label из имён привязанных узлов.
2. `_build_panel` (165-189): **подтверждённые рёбра** — если на одной CAD-компоненте ровно 2 «мажорных» узла (panel/device/meter/bus/load) → edge `electrical_connection` / `path_confirmed` (177-178); ≥3 → сеть `multi_device_bus` без выдуманного порядка (174-176, warning 188).
3. `_build_lightning` (192-213): рёбра «заземление/СУП» через `_preferred_parent` — `same_cad_component` приоритетнее `nearest_geometry` (200-204), в валидации отдельно считаются `cad_confirmed_edges_total` (210).
4. `_build_ozds` (216-227): только сети.
5. `_build_physical` (230-266) для узлов/оборудования: rule-based классификация каждой строки в kind (`_physical_nodes`:230-245 — elevation/dimension/route_part/fastener/support/equipment/grounding/construction/assembly), `_geometry_parts` для EQUIPMENT (250-253), виды.
6. `_build_illuminance` (269-283): изолинии как `uncalibrated_vector_field` — честный отказ придумывать матрицу значений (warning 283).
7. `_build_site` (286-294).

**(г) Валидация.** Пер-профильный гейт `evaluate_electrical_gate` (347-367): лестница глубин — `engineering_graph` (планы с endpoint-сетями; щит с confirmed_pairs; молниезащита с cad_confirmed_edges) / `semantic_hierarchy` / `physical_hierarchy` / `geometry_inventory` / `analytical_geometry`; флаг `vectograph_level` = достигнут engineering_graph (366). Профильные complete-причины (353, 356). Рендер `render_electrical_markdown` (427-469) + словарь 40+ русских сабтайпов `_SUBTYPE_RU` (398-422).

**(д) Непокрытое / зрелость.** Размеры/сечения ловятся как узлы, но связь «сечение → конкретный кабель» и «размер → габарит шкафа» не строится; для монтажных узлов — та же беда, что у АР/КЖ (dimension без адресата).
**Оценка: настоящий граф со связями (наиболее зрелый после Вектографа): CAD-сети + подтверждённые пары + приоритет общей компоненты над близостью.** Это фактический образец того, куда надо дотянуть АР/КЖ/КМ.

## 6. block_text_clustering.py (214 строк)

**(а) Назначение.** Не дисциплинарный: универсальная геометрическая кластеризация текста вектор-слоя блока в «группы с началом и концом» — упрощённый родственник Вектографа без доменной модели (docstring 1-19). Лечит «кашу» плоской Y-склейки `md_mirror_reconcile._block_text`.

**(б) Якоря/атомы.** `line_atoms` (68-90): PyMuPDF words → атомы-строки (агрегация по (block_no,line_no), bbox + текст в порядке word_no,x).

**(в) Связывание.** `cluster_atoms` (93-129): union-find по двум правилам в масштабе медианной высоты строки (пороги TV=2.0/TH=0.8/OV=0.3, строки 25-27): вертикальный стек (зазор ≤2h И X-перекрытие ≥0.3) ИЛИ та же строка (Y-пересечение И гориз. зазор ≤0.8h). Соседние колонки принципиально НЕ сливаются (docstring 11). Сортировка групп: колонки по левому краю (банды ~4h), затем сверху вниз (127-128).

**(г) Валидация/контракт.** Fail-soft всюду (18, 164, 213-214). `compute_text_groups` (145-214): bbox нормируется к региону блока `coords_norm`, клип слов по bbox/полигону через хелперы `singleline_graph_geometry` (168-172); документирована гоча: `result.json.page_index` бывает +1 к fitz-индексу (158-161, пример блока 9Q9M-YM9X-AHA). `render_grouped_text` (132-138) — текст с разделителями «━━━ группа N ━━━» для LLM.

**(д) Зрелость.** **Кластеризация by design** — это и заявлено; связей между группами нет и не планируется. Полезен как подложка для будущих правил «текст↔линия».

**Итоговая шкала зрелости** (заглушка / кластеризация / настоящий граф):

- **ТХ — заглушка-инвентарь** (нет даже route-attach).
- **КЖ/КМ — кластеризация** (богатый предметный словарь, нулевая топология; сам модуль декларирует отсутствие правила выносок).
- **АР — кластеризация+** (nearest-room, контейнеры видов, один тип рёбер для кровельного узла).
- **ГП — настоящий граф для плановых профилей** (сети «подпись↔CAD-компонента», endpoint-непрерывность, может достигать `engineering_graph`), physical-профили — кластеризация + слои дорожной одежды.
- **ЭОМ — настоящий граф** (сети + подтверждённые пары + same_cad_component-приоритет + привязка к осям), эталон для переноса.
- **block_text_clustering — кластеризация by design** (вспомогательный слой).

**Главный разрыв для цели пользователя:** нигде нет механики leader/выносок и размерных линий — короткие сегменты с полочкой от текста к геометрии присутствуют в `get_drawings()` (их видят `_segments`/`_inside_segments`), но ни один модуль не связывает конец такого сегмента с текстом и элементом. Готовые строительные блоки для этого уже есть: проекция точка→отрезок (`_attach`, hvac_geometry.py:198 и general_plan_geometry.py:106), endpoint-union-find (`_components`, hvac_geometry.py:170), полный координатный реестр строк (`semantic_ledger`, hvac_geometry.py:253-261) и текстовые кластеры (`cluster_atoms`, block_text_clustering.py:93). Не хватает правила: «текст, чей bbox касается конца сегмента-полочки → элемент/линия на другом конце», и правила размерной линии (пара выносных + размерная с засечками → привязка числа к паре точек).
