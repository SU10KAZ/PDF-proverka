### (в) Геометрические приёмы связывания

1. **Rotation-aware координаты**: `_point`/`_bbox` (:88-99) через `rotation_matrix`; multi-line подписи через `page.get_text("dict")` в `_lines` (:110-119); слова — `_words` (:122-126).
2. **Цветовая сепарация трасс** `_segments` (:153-167): из `page.get_drawings()` берутся только отрезки `l`, fill отбрасывается; **chroma-фильтр** — на планах `vivid_only=True` (chroma≥.16 = цветные инженерные трассы, стены-нейтраль отсекаются), на схемах нейтрально-серый (chroma<.08 и яркость>.12) отбрасывается, чисто-чёрный остаётся.
3. **Union-find по совпадающим концам** `_components` (:170-195): ключевой принцип модуля (докстринг :1-6) — «X-пересечение линий не образует связь», компонент = отрезки с общими квантованными концами (tolerance 0.8/2.0/4.0 по профилю); считаются `branch_points` (степень≥3) и `endpoint_count` (степень 1).
4. **Привязка узла к трассе** `_attach` (:198-207): ближайший сегмент через `point_segment_distance` (импорт из `vector_path_graph`:15), порог limit 20-28 pt по профилю → `route_id`+`route_distance`.
5. **Доказательный выбор родителя** `_preferred_parent` (:210-215): сперва кандидаты в той же CAD-компоненте (`same_cad_component`), иначе ближайший (`nearest_geometry`) — состояние пишется в ребро.
6. **Иерархия отопления** `_build_heating` (:322-356): каскад источник→система→стояк→прибор/отметка с fallback-родителями (`parents=systems or sources`:335, `risers or systems or sources`:338); отсутствующий ИТП **синтезируется** с `field_state="inferred_from_system_scheme"` (:326-328).
7. **Группировка повторных марок вентсистем** (:380-395): вхождения одной марки (В1 подписана 5 раз) сливаются в одну сеть; аппарат дедуплицируется по id (:386); ребро — от ближайшего вхождения марки (:393); порог пространственной привязки 45% листа (:378).
8. **Гидравлика без домыслов** (:418-433): ребро создаётся только для CAD-компоненты ровно с 2 аппаратами (`confirmed_pair`), ≥3 — общая сеть `multi_apparatus_hydronic_path`, ничего нет — `spatial_inventory`.
9. **Контейнеры-виды** `_assign_nodes_to_views` (:473-479): узел — к ближайшему якорю вида.
10. **Физические группы оборудования** `_geometry_parts` (:514-524, прямоугольники 20 pt²…18% листа) + `_equipment_groups` (:527-546, X-кластеризация с разрывом >8% ширины).
11. **Кривые графиков** (:574-581): drawing с безье `"c"` или ≥3 итемов = кандидат кривой; крупный растр ≥20%×15% (:583-588) — отдельный узел.
12. **semantic_ledger** в `_base` (:245-270): полный координатный реестр ВСЕХ текстовых строк листа рядом с графом — «обратимо проверяемое» описание без создания неподтверждённых рёбер.

- Control: порядок клемм внутри многоточечной цепи не восстанавливается (:341, честно, но мелко).

## 3. `water_supply_geometry.py` (331 строка) — профиль `water_supply_scheme` (стояковые «лесенки» ВК)

### (а) Тип блока

Один профиль — вертикальная стояковая схема В/К/Т («лесенка» этажей × сегменты труб), прямой аналог Вектографа `electrical_singleline` (докстринг :1-25). Выход — `{"type":"water_riser_diagram","profile_id":"water_supply_scheme",…}` (:275-297). Узел = сегмент стояка на этаже (система+⌀+стенка+этаж/отметка), ребро = вертикальная непрерывность стояка, корень (ввод/насосная) опционален и фактически не строится.

### (б) Якорные точки

- `_SYS_RE` (:34): `^(В\d+\.\d+|К\d+н?|Т\d+н?|Ст\.?\d+)$` — В2.2, К13н, Ст.5.
- `_ELEV_RE` (:35): `^[+\-]?\d{1,2}[.,]\d{3}$` — отметки ±NN,NNN.
- `_DIA_RE` (:36): `^[⌀∅Ø]\s?\d{2,3}[xх]?$` — ⌀57x, ∅100.
- `_WALL_RE` (:37): `^\d[.,]\d$` — стенка 3,5.
- `_FLOOR_KW="Этаж"` (:38); число этажа — токен-сосед справа.
- `_water_distinct_tokens` (:54-63): до 8 редких токенов блока для поиска страницы.

### (в) Геометрические приёмы

1. **Фикс бага page_index** `_find_page_index` (:66-76): страница ищется по попаданиям редких токенов (нужно ≥max(2, N/2)) — вместо доверия к переданному индексу.
2. `_extract_floors` (:127-138): токен «Этаж» + число справа в Y-полосе (|Δy|<8, зазор<90).
3. `_extract_segments` (:141-151): системный токен + ⌀ и стенка в той же Y-полосе (ряд собирается сортировкой по X).
4. **X-кластеры стояков** `_cluster_by_x` (:112-123, tol=30): этаж-токены → «лесенки»; лесенка валидна при ≥3 этажах (:199-201).
5. **`levels_by_elevation`** (:79-109) — заявленный **ОБЩИЙ ПРИМИТИВ** («переиспользуют hvac/low_voltage»): линейная регрессия Y→отметка по парам (y-центр, ±NN,NNN), качество = доля остатков <1,5 м; не хардкодит шаг этажа, устойчив к стаггерированным подписям.
6. **По-стояковая регрессия** (:209-214): отметки берутся только в X-полосе ±55 стояка, потому что на одном листе несколько зданий с разными шкалами отметок — глобальная регрессия их смешивает; fallback на глобальную (:213).
7. Привязка сегментов к стояку по X-полосе ±45 (:222-227); доминирующая система через Counter (:229-231); в рендере диаметр этажа = ближайший сегмент по Y в пределах 60 (:316-321, `render_water_graph_markdown`:300-331).

### (г) Валидация, findings, честность

- **FINDING 1 «разрыв стояка»** (:236-245): пропуск в нумерации этажей флажится **консервативно** — только если лесенка плотная (≥70% диапазона размечено) и пропусков ≤max(2, span//5); текст явно содержит «requires_human_review».
- **FINDING 2 «немонотонность ⌀»** (:246-257): для систем «В» диаметр не должен расти к верхним этажам; формулировка «проверить», не вердикт.
- `validation` (:290-295): floors_detected, segments_detected, risers_with_review, elevation_regression_quality_per_riser; блок `levels` с качеством global/per-riser и elevation_range (:281-288); сводный `review` (:273).
- fail-soft каскад None: нет fitz (:166-168), нет water-токенов — «не водяная схема, блок уходит дальше в LLM» (:169-171), не открылся PDF (:173-175), страница не найдена (:177-179), <3 этажей (:193-194), нет стояков (:269-270).

### (д) Слабые места

- Нет корневого узла ввода/насосной и нет горизонтальных связей между стояками (магистраль не строится) — граф фактически = набор независимых лесенок.
- Проверка монотонности реализована только для «В»; для «К» (диаметр растёт к низу, докстринг :21) кода нет (:255 гейтует на `startswith("В")`).
- Мёртвый код :252-253 — условие с `pass`, никогда ничего не делает.
- Не обрабатывается rotation страницы (сырые `get_text("words")` без `_point`-преобразования, в отличие от hvac/water).
- Узлы без нормализованных bbox (только `x_norm` стояка и сырые y), нет `field_state`/`evidence`-таксономии материнских модулей.
- Коллизия имени `build_water_graph` с water_geometry.py:475 (другая сигнатура).

### (е) Новые примитивы vs эталон ЭОМ

(1) `levels_by_elevation` — монотонная (линейно-регрессионная) функция Y→отметка с метрикой качества, оформленная как переиспользуемый межпрофильный примитив (:79-109); (2) локальная по-стояковая регрессия против смешения шкал нескольких зданий (:209-214); (3) поиск реальной страницы по редким токенам `_find_page_index` (:66-76) — обход известного бага page_index; (4) плотностный гейт пропусков этажей (:236-245) — паттерн «finding только на плотной разметке»; (5) доменная проверка направления потока (монотонность ⌀ по высоте, :246-257); (6) табличный Markdown-рендер «Этаж|Отметка|⌀×стенка» per-стояк (:300-331).

## Сквозные наблюдения для обобщения на другие дисциплины

- **Таксономия доказательности** едина: `same_cad_component` > `path_confirmed/confirmed_pair` > `nearest_*` > `semantic_*` > `spatial_inventory` > `secondary_description_only`; лестница `description_depth` с флагом `vectograph_level` — готовый каркас для АР/КЖ/СС.
- **Три слоя источника** (текст/вектор/растр) полностью разведены только в ВК (`source_layer_state`, raster-узлы, secondary_facts) — в ОВ это долг.
- Главный переносимый инвариант: **связь = совпадающие концы CAD-отрезков (union-find), а не пересечение**; неподтверждённое не домысливается, а фиксируется как inventory + warning.
- Проектная привязка `_ID_HINTS` в обоих модулях — основное препятствие генерализации; текстовые классификаторы (`classify_hvac_profile`:57, `classify_water_profile`:70) — единственный переносимый путь.
