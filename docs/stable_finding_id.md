# Стабильный идентификатор замечания (`uid`) — спека для AuditManager rewrite

Статус: **дизайн** (код не пишем; закладывается в модель данных TS-порта).
Дата: 2026-06-29. Автор контекста: диагностика орфанов БЗ (см. ниже).

## 1. Проблема: `F-NNN` — это номер строки, а не идентичность

Сейчас `id` замечания (`F-001`, `F-002`, …) присваивается **позиционно и заново
на каждом прогоне** в конце этапа `findings_merge`, дважды:

1. `merge_similar_findings` — группирует по `severity||category||нормализованный_текст`
   и перенумеровывает `F-001…F-NNN`
   (`backend/app/pipeline/stages/findings_merge/runner.py`, ~L374–385).
2. `phase0_dedup` — схлопывает дубли и **снова** перенумеровывает
   (там же, ~L254–261).

Оба шага зависят от **порядка и количества** замечаний. На переаудите findings
генерируются заново (LLM выдаёт другой текст/порядок/число) → одна и та же
физическая ошибка попадает на другой `F-NNN`, а данный `F-NNN` начинает указывать
на другую ошибку. В объекте finding **нет ни одного поля**, привязанного к самой
ошибке — только позиция.

### Последствия (подтверждено на данных)

`knowledge_base/decisions_log.json` хранит решения эксперта с ключом
`(source_project, item_id=F-NNN)`. Поля `summary`/`severity` в решении пустые и
**хайдрейтятся на лету** из «последней» версии документа
(`knowledge_base_service._hydrate_kb_entry_from_source → _load_source_item_maps`,
читает `versions/vNNN/.../03_findings.json` latest).

Эталон-кейс **DEC-5453** (объект 214, `13АВ-РД-АР1.2-К3К4`, `F-006`, accepted):
`F-006` был в **v001** (ЭКОНОМИЧЕСКОЕ, нестыковка площадей 14,8 м²), а latest = **v002**
findings перенумеровал (F-005 → F-007, F-006 нет) → источник не найден → пустые
«Суть»/«Критичность» в таблице БЗ.

Масштаб на 2026-06-29: **447 орфанов из 6440 решений (~7%)**.

## 2. Требования к решению

- R1. Идентичность замечания **постоянна** в пределах `(проект, версия)` и
  переживает переаудит той же версии.
- R2. Удаление/добавление/слияние замечаний **не сдвигает** идентичность остальных.
- R3. Решения эксперта / БЗ / обсуждения ключуются на постоянный id, а не на `F-NNN`.
- R4. По id можно однозначно определить **версию** (чтобы хайдрейтинг читал именно
  её, а не latest).
- R5. Недеструктивно к истории: id никогда не переиспользуется и не перенумеровывается.
- R6. `F-NNN` остаётся как **человеко-читаемый порядковый ярлык** (его можно
  перенумеровывать свободно — он косметический).

## 3. Модель: ordinal ⟂ identity

Разделяем два разных понятия, которые сейчас смешаны в одном поле `id`:

| Поле | Назначение | Стабильность |
|------|-----------|--------------|
| `ordinal` (= нынешний `F-NNN`) | порядковый ярлык для людей/отчётов | может меняться |
| `uid` | вечная идентичность замечания | **неизменна, append-only** |

Все внешние привязки (decisions, expert_review, discussions, KB) переходят на `uid`.
`ordinal` остаётся только для отображения.

## 4. Фингерпринт (по дрейф-устойчивым якорям)

`uid` назначается через **tracking по фингерпринту**, а не по полному тексту
(текст дрейфует между прогонами LLM). Фингерпринт считается по якорям, которые
устойчивы к перефразировке:

- `version_id` — проект + дисциплина + документ + версия (обязательно, кодирует
  принадлежность → даёт R4);
- `sheet` и/или `page` — локализация на чертеже;
- `norm` нормализованная — на какой пункт ссылается замечание;
- `category` + `severity`;
- **сигнатура сути**: `normalize_problem_pattern(problem)` **+ ключевые числа**
  из текста. Якорь на числах (например `14,8`) делает фингерпринт устойчивым к
  перефразировке. В текущем коде уже есть основа:
  - `findings_service._normalize_problem_pattern` (`backend/app/services/findings/findings_service.py:1345`);
  - числовые токены извлекаются локально в реализации идентификатора.

Фингерпринт = детерминированный хеш кортежа якорей (canonical-сериализация → SHA-256,
первые N hex). Версия алгоритма фингерпринта хранится рядом (`fp_algo: v1`), чтобы
смену правил можно было мигрировать.

## 5. Реестр идентичности (`finding_identity.json`)

Рядом с версией документа — append-only реестр:

```jsonc
{
  "version_id": "214/AR/13АВ-РД-АР1.2-К3К4/v001",
  "fp_algo": "v1",
  "next_seq": 18,
  "entries": [
    {
      "uid": "214/AR/13АВ-РД-АР1.2-К3К4/v001:U-0006",
      "fingerprint": "a3f1…",      // текущий
      "fingerprints": ["a3f1…"],   // история (для эволюции текста)
      "first_seen_run": "run-2026-06-25T…",
      "last_seen_run": "run-2026-06-28T…",
      "alive": true,                // присутствует ли в последнем прогоне
      "anchors": { "sheet": "Листы 2,3", "norm": "ГОСТ 21.501-2018 п.5.4",
                   "category": "documentation", "severity": "ЭКОНОМИЧЕСКОЕ" }
    }
  ]
}
```

### Алгоритм трекинга (на каждый write `03_findings.json`)

Для каждого finding нового прогона:

1. Посчитать фингерпринт.
2. **Exact**: фингерпринт уже есть в реестре → переиспользовать его `uid`.
3. **Fuzzy**: иначе искать кандидата среди реестра по «мягкому» совпадению —
   тот же `sheet`+`norm` и похожесть сути ≥ порога (машинерия
   `dedup/fuzzy_dedup.py` уже есть). Совпало однозначно → переиспользовать `uid`,
   дописать новый фингерпринт в `fingerprints[]`.
4. **Mint**: иначе выдать новый `uid = <version_id>:U-<next_seq++>`, добавить запись.
5. Проставить finding-у `uid` и `ordinal` (текущий `F-NNN`).

Инварианты:
- `uid` **никогда** не удаляется и не переиспользуется (R5). Исчезло замечание →
  запись остаётся с `alive=false` (старые решения по нему всё ещё резолвятся).
- Реестр идемпотентен: повторный прогон на тех же findings даёт те же `uid`.

## 6. Ключи decisions / expert_review / KB

- `decisions_log` и `expert_review`: ключ `(source_project, uid)` вместо
  `(source_project, F-NNN)`. `uid` уже содержит `version_id` → решение само «знает»
  свою версию.
- Хайдрейтинг БЗ: резолвить источник по **версии из `uid`**, а не «latest». Это
  убивает баг пустых строк независимо от переаудитов.
- `ordinal` можно дополнительно хранить в решении как «снимок для удобства», но он
  **не ключ**.

## 7. Кросс-версия — отдельная ось (не путать)

«То же» замечание в v001 и v002 получают **разные `uid`** (версия в ключе) — ровно
требование «привязка к замечанию ВЕРСИИ и проекта». Связь v001 ↔ v002 — отдельный,
уже частично решённый механизм: `origin_finding_id` / `_stable_migrated_id` /
`linked_finding_id` в `backend/app/services/findings/migrated_findings_service.py`
(L1415 и далее). Его не трогаем — он ортогонален стабильному `uid` внутри версии.

При желании поверх `uid` строится «issue lineage»: `uid(v002)` ←link→ `uid(v001)`
через тот же fuzzy-матчинг, но это надстройка, не часть базовой идентичности.

## 8. Краевые случаи

- **Split** (одно замечание разнесли на два в новом прогоне): один кандидат
  совпадает → берёт старый `uid`; второй минтит новый. Не идеально, но детерминированно.
- **Merge** (два схлопнули в одно): победитель берёт `uid` ближайшего кандидата;
  проигравший помечается `alive=false`. Решения по проигравшему остаются валидны
  (резолвятся в исторический источник).
- **Два равных кандидата при fuzzy**: НЕ матчить (минтим новый `uid`) — precision >
  recall, чтобы не приклеить решение к чужой ошибке. Логировать неоднозначность.
- **Коллизия фингерпринта** (разные ошибки → один хеш): снижается включением
  числовой сигнатуры + sheet; при остаточных коллизиях — `seq` всё равно разводит
  (фингерпринт лишь подсказка матчинга, уникальность даёт `uid`).

## 9. Миграция существующих данных (разово, недеструктивно)

1. Пройти все версии всех документов, посчитать фингерпринты, проставить `uid` и
   собрать реестры. Findings дополняются полем `uid` аддитивно (бэкап `.bak`).
2. Для 447 орфанных решений: перепривязать `F-NNN → uid`, матча против **той версии,
   что реально содержала этот `F-NNN` на момент решения** (выбор версии по
   `expert_date`; если в нескольких — ближайшая по дате). Это разовый
   «version-aware» проход.
3. Решения, не нашедшие источник ни в одной версии (стейл `source_project` с
   суффиксом `…-К1 V1/V2` — см. [[project_decisions_log_not_version_aware]]) —
   в отдельный список «битые», на ручной разбор, не на авто-перепривязку.
4. Все правки — с бэкапом и dry-run-отчётом (политика «никаких деструктивных
   операций на live»).

## 10. Схема для TS-порта (ориентир)

```ts
type FindingUid = string;            // "<versionId>:U-0006"

interface Finding {
  uid: FindingUid;                   // вечная идентичность (R1, R5)
  ordinal: string;                   // "F-006" — косметика (R6)
  versionId: string;
  // …существующие поля (severity, category, sheet, page, norm, problem, …)
}

interface IdentityEntry {
  uid: FindingUid;
  fingerprint: string;
  fingerprints: string[];
  firstSeenRun: string;
  lastSeenRun: string;
  alive: boolean;
  anchors: { sheet?: string; norm?: string; category?: string; severity?: string };
}

interface FindingIdentityRegistry {
  versionId: string;
  fpAlgo: string;                    // "v1"
  nextSeq: number;
  entries: IdentityEntry[];
}

interface ExpertDecision {
  uid: FindingUid;                   // ключ вместо F-NNN
  decision: "accepted" | "rejected" | /* … */;
  // …
}
```

В реляционной БД (PG, целевой стек rewrite): `findings.uid` — natural key с
уникальным индексом `(version_id, uid)`; `decisions.finding_uid` — FK на него;
реестр идентичности можно держать как таблицу `finding_identity` или вывести из
самих findings + истории фингерпринтов.

## 11. Альтернативы (почему не они)

- **Чистый хеш по тексту, без реестра** — ломается от дрейфа формулировок. Хеш
  только по жёстким якорям (sheet+norm+числа) рискует склеить два разных
  замечания. Реестр + fuzzy надёжнее.
- **«Заморозить F-NNN»** — не работает: dedup/merge законно убирают строки; разные
  ошибки всё равно переиспользуют номера.
- **Снапшот сути в решение** — лечит только отображение, но не даёт переаудиту
  понять «эта ошибка ещё открыта». `uid` строго лучше и включает это бесплатно.

## 12. Если нужно облегчение до rewrite (Python-шим, отдельный трек)

Аддитивно, прод не ломает: запись `uid`+реестра в конце `findings_merge`,
dual-write решений на `(uid, F-NNN)`, хайдрейтинг БЗ по `uid → версия`. Не входит
в эту спеку; рассматривать отдельно при необходимости.

## Открытые вопросы

- Порог fuzzy-матчинга и набор якорей — калибровать на реальных парах (объект 214,
  v001↔v002) до фиксации `fp_algo: v1`.
- Формат `uid`: человеко-читаемый `<versionId>:U-NNNN` vs UUID + side-index.
  Читаемый удобнее в логах/БЗ, но длиннее.
- Нужен ли `ordinal` стабильным внутри версии (для печатных отчётов) или допустимо
  его свободное перенумерование между прогонами одной версии.
