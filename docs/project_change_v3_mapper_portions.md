# ProjectChange V3 — Mapper порциями (Claude и Codex)

## Локальный выбор плана полного покрытия (3.27.0)

`mapper_planning.py` собирает настоящий вход Mapper через `build_codex_payload`;
`transport.measure_request` измеряет его без создания провайдера. Оба провайдера
учитывают промпт, данные, все подписи, схему ответа и уникальные изображения.
Для Claude дополнительно считается консервативная оценка размера JSON-запроса
с экранированием и запасом на обрамление. Бюджеты приложения не увеличены.
Идентичный bitmap отправляется один раз, но **все** его привязки OLD/NEW/page/block
сохраняются с тем же номером изображения.

Доступны настройки (для новых запусков):

| Настройка | Значения | По умолчанию |
|---|---|---|
| `PROJECT_COMPARISON_V3_MAPPER_PLANNER` | `legacy`, `shadow`, `balanced` | `balanced` |
| `PROJECT_COMPARISON_V3_MINER_PLANNER` | `legacy`, `shadow`, `balanced` | `balanced` |

`legacy` выполняет прежнее разбиение и записывает его оценку. `shadow` сравнивает
варианты, но выполняет прежний план. `balanced` может выбрать более экономичный
вариант. Неизвестное значение настройки останавливает запуск до вызовов.
Профиль модели выбирается обычным способом; планировщик его не переключает.

Среди кандидатов всегда есть прежний план. Дополнительные кандидаты выделяют
OLD 25, 40, 50, 60 или 75 процентов полезного бюджета. Вес страницы служит только
для выбора границ OLD: NEW упаковывается с проверкой реальных совместных пакетов
и учётом границ томов. Затем проверяются окончательные порции, включая их полные
названия, номера и пояснения. Выбирается вариант с меньшим суммарным оценочным
входом и не большим числом вызовов относительно допустимого прежнего плана.
При отсутствии такого варианта используется прежний. Это ограниченный поиск,
а не доказанный глобальный оптимум. Словарь текста и дедупликация изображений
учитываются при измерении каждого сочетания, а не суммой весов страниц.

Обязательная проверка подтверждает ровно одно включение каждой пары OLD×NEW.
Источники и изображения перечитываются перед отправкой; изменение ключа запроса
останавливает выполнение. Кэш метаданных изображений и ограниченные кэши
локальных измерений существуют только в пределах планирования. Они не являются
хранилищем ответов модели.

Артефакт `project_change_v3_mapper_plan` содержит выбранный и рекомендованный
варианты, стоимость допустимых кандидатов, причины отказа, максимальную порцию,
повторную передачу источников по сторонам, время планирования, состав порций,
ключи окончательных запросов и принятые порции. Ключ зависит от точного текста
запроса, схемы, хешей изображений, профиля, reasoning и версий упаковки. Из-за
путей и пояснений он может измениться даже для тех же страниц; консервативное
несовпадение безопаснее ошибочного повторного использования. Номер `P0001`
сам по себе не идентифицирует вход. Частичный Mapper по-прежнему сохраняет
попытки для диагностики; автоматическое восстановление отдельных попыток
этим изменением не вводится. `complete=true` устанавливается только после
принятия всей карты; отдельная ошибка не закрывает оставшиеся порции.

Существующая досборка сохранённой карты и Miner дополнительно сверяет
`source_payload_version` и `source_compaction_version`. Старые доноры без
совместимой версии не переименовываются в новый формат и будут отклонены до
вызовов. Донорская карта сохраняет свой исходный план независимо от настроек
планировщика оставшихся этапов.

Miner измеряется отдельно через полные `optimized_region_bundle`, включая
растры графических страниц. `project_change_v3_miner_plan` хранит число новых
вызовов и сумму их оценочного входа. Сбалансированный режим переразбивает
**каждую исходную область отдельно** и сохраняет её прямоугольник OLD×NEW;
между независимыми областями новых сравнений не возникает. Принятые области
и старые текстовые окна не переразбиваются. Существующее безопасное объединение
родственных необработанных частей продолжает работать. Точный план Miner
появляется после Mapper: до него в отчёте явно указано `pending_mapping`.

Запуск локального отчёта:

```sh
python scripts/plan_projectchange_v3.py --synthetic --output /tmp/projectchange-plan-demo
python scripts/plan_projectchange_v3.py --dev-pair 5 --profile astra --profile opus55 --output /tmp/projectchange-plan-dev5
```

Вторая команда требует допуска `policy.admitted_pairs('DEV')` по неизменному
реестру объекта 272 / stage_1 → stage_2 / logical v002. Полная пара с embargo
не допускается. `--corpus-root` позволяет указать местоположение того же
замороженного реестра; проверки хешей и принадлежности остаются обязательными.
Validation/final reserve этим инструментом не открываются. На выходе
`planning.json` и `planning.txt`, при отказе — `planning_refusal.json`.
Все числа токенов являются оценками, стоимость подписки в деньги не переводится.

Проверка разработки 25.10.2026: на синтетических 8 OLD / 24 NEW и реальной
локальной формуле Codex число вызовов снизилось с 12 до 8, оценочный вход —
с 2 151 535 до 1 436 172 токенов. Эти числа не являются результатом на проекте.
По штатному пути корпуса отсутствует `SPLIT.sha256`, поэтому измерение полного
DEV и проверка семантического качества не выполнены. По разрешению пользователя
25.10.2026 режимы `balanced` включены по умолчанию для проверки на портале.
Это разрешение на выкатку не является подтверждением качества на корпусе.
Откат на предыдущий релиз возвращает прежнее планирование; в новом релизе
его также можно явно выбрать настройками `legacy` для обоих планировщиков.

Дополнительное компактное представление источников в этот этап не включено:
сохраняется существующий обратимый словарь с проверкой `decode(compact(data))`.
Решение об удалении повторов таблиц или замене путей короткими идентификаторами
требует измерения на допущенных полных источниках. Промпт и `MAP_SCHEMA`
сохраняются. Полное покрытие входами проверяется программно; семантическая
полнота требует отдельных контрольных сравнений. Для подтверждения качества
остаётся восстановить реестр, проверить DEV, зафиксировать кандидата и затем
проверить разрешённый резерв и итоговые затраты Mapper вместе с Miner.

## Claude: бюджет окна контекста (3.24.0)

До 3.24.0 `plan_claude` проверял только медиаконверт CLI (100 изображений,
24 МиБ изображений, 32 МиБ запроса), но не объём входа в токенах. Порция,
которая проходила конверт, могла не поместиться в окно Opus 5.5 (1 000 000
токенов), и API отвечал `Prompt is too long` уже после отправки. 14.10.2026 так
упали все три сборки ИОС4.1 / ИОС4.1(ОВ1) / ИОС4.1(ОВ2) объекта 256: OLD
(235 страниц) уходит в каждую порцию целиком и сам занимает ~0,8 млн токенов.

Теперь `plan_claude` оценивает вход: **байты UTF-8 текста / 2 + (ш × в / 750 +
256) на изображение** и отказывает до отправки, если оценка выше
`CLAUDE_INPUT_BUDGET_TOKENS = 950 000`. Планировщик порций (и дробление
участков Miner) получает отказ заранее и режет мельче, при необходимости — и
сторону OLD. Оценка пишется в квитанцию вызова (`context_budget`).

Калибровка по 17 принятым вызовам Mapper Opus 5.5 (фактический вход из
`usage`): оценка выше факта на 9–20 %; наименьшая оценка среди 14 отклонённых
вызовов — 1,20 млн. Для Miner фит хуже (оценка бывает ниже факта до 9 %) — это
покрывает запас 50 000 до окна, вместе с системным промптом и схемой
StructuredOutput.

## Бюджет Miner и сжатие контекста (3.18.0)

Для Miner на Codex/Astra введена та же локальная политика входа **196 000
оценочных токенов**, что и для Mapper. Версия проверки —
`projectchange_v3_codex_miner_budget/1`. Учитывается весь фактический пакет:
промпт выбранного формата Miner, JSON-схема ответа, данные страниц, подписи,
графические фрагменты и полные растры страниц. Оценка остаётся эвристикой;
лимит приложения не является гарантией вместимости у провайдера.

После Mapper планируются **все** области до первого вызова Miner. Если область
не помещается, сначала делится NEW; при необходимости делится и OLD. Каждое
сочетание OLD×NEW исходной области сохраняется ровно один раз. Важные ссылки
на блоки фильтруются по страницам обеих сторон части; исходные OCR и изображения
не сокращаются. Номер части и пояснение в `scope` учитываются при планировании,
затем все окончательные части проверяются ещё раз. Для Claude сохраняется его
проверка транспорта; теперь и там возможно разбиение OLD внутри области.

Провенанс `miner_region_splits` хранит исходную область, идентификаторы частей
и страницы OLD/NEW каждой части. Умещающаяся область передаётся без изменений.
Перед запуском CLI адаптер Codex повторно проверяет фактический запрос Miner
и сохраняет `context_budget` в квитанции. Если даже две отдельные страницы
не помещаются вместе, возвращается `miner_envelope_exceeded` до первого
вызова Miner. Разбиение внутри листа пока не реализовано.

Событие клиента `contextCompaction` отделено от вызовов инструментов. Оно
приводит к `CONTEXT_COMPACTED` / `provider_context_compacted`: после сжатия
полнота источников не подтверждена. Полученный JSON сохраняется в отклонённой
попытке Miner для диагностики, но не публикуется и не принимается как успешный.
Автоматического повтора нет. Обработка охватывает app-server и структурированные
события `codex exec --json`; обычный текст ответа с таким словом событием не
считается. Квитанция app-server содержит счётчик `context_compactions`.

Проверки выполняются на синтетических документах и подставном CLI без вызовов
моделей: полный бюджет с изображениями и схемой, двухстороннее разбиение,
сквозной проход, отказ до Miner, сохранение отклонённого ответа и отсутствие
повтора/публикации. Завершённые и остановленные боевые запуски не переписываются
и не возобновляются автоматически.

## Разбиение обеих сторон (3.17.0)

Если OLD целиком не помещается даже с одной страницей NEW, планировщик делит
OLD пополам и для каждой части заново планирует **все** страницы NEW. При
необходимости деление OLD повторяется до одной страницы. NEW сохраняет
существующее разбиение по проектам сборки и страницам. Все сочетания страниц
OLD×NEW покрываются ровно один раз; отдельная локальная проверка запрещает
пропуски, повторения и неизвестные страницы до первого обращения к модели.

Порции получают `old_pages` и пояснение, что обе стороны представлены частично.
Артефакты и квитанции сохраняют границы каждой порции; провенанс содержит
`mapper_portioning.version=projectchange_v3_mapper_portions/2` и
`split_sides=["OLD", "NEW"]`. Если достаточно прежнего разбиения NEW, поле
`old_pages` отсутствует, а `split_sides=["NEW"]`.

После проверки каждого ответа страницы **обеих** сторон считаются без пары
только тогда, когда их не сопоставила ни одна порция. Например, NEW 1 может
получить `unmatched_new` при сравнении с OLD 1, а затем сопоставиться с OLD 2:
в общей карте NEW 1 уже не будет без пары. Области сохраняют префиксы порций,
финальная карта проходит существующую проверку покрытия.

Бюджет входа не увеличен; OCR, блоки и изображения не сокращаются. Каждый
окончательный запрос проверяется до начала Mapper. Если не помещается даже
пара отдельных страниц, прогон останавливается до вызовов модели и называет
эти страницы. Для такого случая потребуется дальнейшее разбиение внутри
страницы — текущая версия его не выполняет. Лимит параллельности остаётся 10.

Синтетические тесты проверяют полное покрытие сочетаний, неравные размеры
страниц, слияние частичных сопоставлений, отказ до первого вызова и сквозной
прогон при реальном локальном бюджете Codex. Модели не вызываются; материалы
других объектов и validation/final reserve не используются для проверки.
Повторная передача частей увеличивает число запросов. Контекст, пересекающий
границу частей, по-прежнему может дробиться; эти тесты проверяют транспорт и
покрытие, а не качество семантического сопоставления на реальных документах.

## Параллельное сопоставление (3.15.0)

Подготовленные порции Mapper выполняются одновременно, до **10 сессий на одно
сравнение**. Настройка `PROJECT_COMPARISON_V3_MAPPER_CONCURRENCY` принимает 1–10,
по умолчанию 10. Для семи порций одновременно запустятся максимум семь сессий;
дополнительные порции ради параллельности не создаются. Сопоставление, которое
помещается в один запрос, по-прежнему делает один запрос. Планирование порций,
предварительная проверка всех входов, промпт, схемы и правила слияния сохранены.

Каждая порция имеет свой экземпляр провайдера и квитанцию. Рабочие потоки вызывают
только модель; проверка ответов и запись артефактов идут в потоке оркестратора.
Ответы сохраняются сразу по готовности в `project_change_v3/mapper_attempts/<run_id>/`,
включая отклонённые ответы и ошибки. Это внутренние артефакты без публикации и без
автоматического повторного использования. Их пути и хеши находятся в
`provenance.mapper_attempts`, установленный лимит — в `provenance.mapper_concurrency`.

Для слияния ответы упорядочиваются по исходному номеру порции: скорость ответа не
меняет префиксы регионов и вход Miner. Прогресс показывает число сохранённых и
принятых порций. Miner начинает работу после завершения и проверки всей карты,
также с собственным лимитом 10; два этапа не перекрываются.

При ошибке прекращается выдача новых порций, ответы уже начатых запросов
сохраняются, общая карта и следующий этап не публикуются. Отмена передаётся всем
сессиям через общий токен запуска. Неверный лимит останавливает прогон до вызовов
модели. Изменение действует для новых запусков после установки релиза.

## Codex: общий бюджет контекста (3.13.0)

Mapper теперь планирует отдельные порции и для Codex/Astra, включая обычные
пары без сборки. Текст, разбитый через `thread/inject_items`, остаётся в одном
контексте: транспортное разбиение не уменьшает нагрузку на модель.

Локальная политика `projectchange_v3_codex_mapper_budget/1` ограничивает
**оценку входа 196 000 токенами**. Это бюджет приложения, а не заявленный
лимит API. Метаданные установленного Codex для Astra на момент изменения:
`context_window=272000`, `effective_context_window_percent=95`; остаётся
более 62 тысяч токенов на инструкции среды, обрамление, рассуждение и ответ.
Максимальное окно модели в API не означает, что CLI использует его по умолчанию.

Оценка считается для полного запроса, включая инструкции Mapper, подписи
изображений, данные порции и выходную JSON-схему:

- текст: число UTF-8 байт / 2 с округлением вверх;
- изображения после существующего удаления побайтных дубликатов:
  `ceil(ceil(width/32) × ceil(height/32) × 1.2) + 256` на каждое;
  берутся исходные размеры, без предположения, что CLI уменьшит картинку.

Формула изображений опирается на [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision).
Текстовая оценка — осторожная эвристика для OCR/JSON, **не точный токенизатор
и не гарантия вместимости**. Поэтому отказ провайдера `contextWindowExceeded`
также распознаётся отдельно: `provider_context_window_exceeded`, понятное
сообщение по-русски, без автоматического повтора того же пакета.

Все окончательные порции с их реальными названиями и пояснениями проверяются
до первого вызова. Адаптер Codex повторно проверяет каждый фактический запрос
Mapper перед запуском CLI. Квитанция успешной локальной проверки сохраняет
`context_budget`: версию политики, оценки текста/изображений и бюджет.
С 3.17.0 непоместившаяся OLD тоже делится. Отказ
`assembly_mapper_envelope_exceeded` остаётся для пары отдельных страниц,
которая не помещается, и для не прошедшего проверку окончательного запроса.
Данные не обрезаются.

В 3.13.0 бюджет Codex относился только к Mapper; с 3.18.0 проверяется и Miner
(см. выше). Порции требуют повторной передачи источников, поэтому увеличивают
расход входных токенов.

Проверки изменения используют синтетические документы и подставной CLI,
без вызовов моделей и без материалов validation/final reserve.

## Зачем

Claude Code CLI передаёт в одном запросе не больше **100 изображений** и не
больше **24 МиБ изображений в base64**. Лишнее он молча выбрасывает (старые
изображения первыми), до модели это не доходит, и никто об этом не узнаёт.
Сборка «ИОС2.1 ↔ 9 проектов РД ВК» объекта 256 — это 321 графический фрагмент,
86 МБ. Один вызов Mapper в неё не помещается, и 3.9.0 честно отказывался
(`assembly_mapper_envelope_exceeded`, 0 вызовов).

## Как устроено (`mapper_portions.py`, `engine.py`)

1. **Один вызов, если помещается.** План транспорта (`plan_claude`) или оценка
   контекста Codex (`plan_codex_mapper`)
   строится до первого обращения к модели. Если вызов Mapper проходит, путь
   прежний, байт в байт (страж `test_dev5_mapper_input_unaffected` сверяет
   отпечаток входа на замороженном DEV5).
2. **Mapper порциями.** Сначала OLD идёт **целиком в каждую порцию**. Сторона
   NEW делится по проектам сборки (`assembly_origin.json`): проекты подряд, пока
   порция помещается. Проект, который не помещается сам, режется по страницам;
   без сборки порции — подряд идущие страницы. Каждая порция проверяется
   планом выбранного провайдера. Если OLD целиком не помещается даже с одной
   NEW, включается разбиение обеих сторон, описанное выше.
3. К данным порции добавляется поле `portion` (номер, границы NEW, пояснение:
   «OLD целиком, NEW — только эта часть; OLD без пары в этой порции — в
   unmatched_old»). **Промпт Mapper не меняется.**
4. Ответ каждой порции проверяется так же, как одиночный (`validate_map` на
   страницах порции). Затем порции сливаются:
   - области получают префикс порции `P03.A-R002`;
   - страница любой стороны остаётся без пары, только если её не взяла
     **ни одна** порция.

   Итог проходит схему `MAP_SCHEMA` и ту же финальную проверку покрытия.
   Ответы порций сохраняются отдельно: артефакт `project_change_v3_mapper_portions`.
5. **Области Miner.** Miner отправляет по каждой странице области фрагменты
   **и полный растр страницы**, поэтому крупная область («корпус целиком») может
   не поместиться. До первого вызова Miner каждая область проверяется точным
   планом выбранного провайдера. Не помещающаяся область делится на части
   по страницам NEW, затем при необходимости OLD: `…A-R002.1`, `.2`.
   Части — обычные области: проверка
   ответов, контрольные точки и Dedupe работают без изменений. Провенанс:
   `miner_region_splits`.

Mapper отказывается до вызовов модели, если не помещается даже пара отдельных
страниц (`assembly_mapper_envelope_exceeded`). Для Miner отказ при паре
отдельных страниц называется `miner_envelope_exceeded`.

## Архив: цифры на объекте 256 (не валидация текущего изменения)

- **Порции:** 8, план строится за 1,5 с.
- **Состав:** ВК-1, ВК-2, ВК-3 + ВК-4, ВК-5, ВК-6, ВК-7, ВК-АС (1-я часть),
  ВК-АС (2-я часть) + ВК.НС.
- **Нагрузка на порцию:** 40–73 изображения, 13,7–23,8 МиБ при пределе 24 МиБ.

## Цена и осознанные компромиссы

- Сторона OLD уходит в каждую порцию. Токены OLD оплачиваются N раз
  (на ИОС2.1 это около 50 тыс. токенов на порцию).
- Изменение OLD, которое NEW повторяет в нескольких корпусах, может дать
  карточку в каждой порции. Их сводит Dedupe; межкорпусное дробление — известный
  долг V3, см. консолидатор.
- Если изменение лежит на стыке двух частей области, оно может распасться на
  подсказки в обеих частях.
- Astra (Codex) включает порционирование по общей оценке контекста; ограничение
  Claude в 100 изображений к нему не применяется.
