# «Сравнение документации»: текущий контракт этапов 1–5

Раздел реализует сопоставление PDF-листов стадии П и стадии РД, после
подтверждения связей — детерминированное исключение доказанно одинакового
текста, затем группировку оставшегося текста в `changed / removed / added` и
семантическую ИИ-ревизию всей предварительной классификации. Графика будет
сравниваться отдельным следующим этапом.

## Рабочий поток

```text
MD П ─┐
      ├→ SheetPassport
MD РД ─┘
          ↓
     простые правила
          ↓
   TOP-кандидаты
          ↓
 sheet_match_suggestions.json
          ↓
       человек
          ↓
     sheet_links.json
```

Карта листов строится по оглавлению актуального `ocr.html` (канонической копии
загруженного `_results.html`); краткая семантика из `document.md` используется
только как ограниченный fallback для повторяющихся заголовков. PDF читается
для page count и выдачи страницы через `page-info` / `page-preview` /
`page-tile`.

Автоматика сначала ищет однозначное совпадение `тип + корпус + этаж`,
`тип + корпус + кровля` или `тип + уровень` для подземной части. Затем
используется короткая шкала `корпус 4 / этаж 4 / уровень 3 / тип 2 / Sheet 1 /
порядок 1`. Противоречие корпуса, этажа или типа нельзя перекрыть одинаковым
номером Sheet либо порядком.

## Хранение

- `sheet_match_suggestions.json` — безопасно пересчитываемый автоматический
  результат с primary и не более чем тремя alternatives;
- `sheet_links.json` — принятое пользователем решение;
- `left_pages` и `right_pages` всегда массивы, uniqueness-гейтов нет;
- `unlinked_left_pages` хранит явное ручное решение оставить лист без связи;
- повторная обработка заменяет только suggestions и не изменяет links.

## Интерфейс

- «Обработать» строит предложения для выбранной PDF-пары;
- «Обработать выбранные» выполняет ту же операцию для отмеченных сохранённых
  пар;
- вкладка «Связь блоков» сохраняет прежнее имя, но показывает связь листов;
- доступны «Оставить», «Изменить», «+ Добавить лист РД» и «Удалить связь»;
- связанные правые страницы переключаются в двухпанельном тайловом viewer;
- карта листов показывает ровно 5 строк и прокручивается: высота списка
  считается из `--sc-sheet-map-row`, поэтому «пять» не разъезжается с вёрсткой,
  а активная строка при листании подкручивается внутри самого списка
  (`scRevealActiveSheetMapRow`, не `scrollIntoView` — тот утащил бы страницу);
- видны количества уверенных, требующих проверки, ручных и несопоставленных
  листов.

## Панель миниатюр листов

Кнопка «Миниатюры» открывает слева от просмотрщика полосу пар листов: в строке
мини-кроп П и мини-кроп РД, клик — переход обеих панелей. Панель нужна только
для ориентации — действий над страницами (поворот, печать, удаление) в ней нет.

- растр даёт `page-thumb` (PNG, ширина 64–400 px). Вектор здесь не годится:
  лист A1 после `text_as_path` весит ~6 МБ;
- цена в отрисовке содержимого, а не в размере растра — насыщенный лист A1
  рисуется ~120 мс при любой ширине, лёгкий титульный 3 мс. Поэтому готовые PNG
  лежат в памяти (512 штук ≈ 6 МБ) и отдаются с ETag и суточным Cache-Control,
  а `<img loading="lazy">` тянет только видимые кропы;
- строки полосы строятся из `scSheetMapRows`, чтобы связи не считались второй
  раз и не разъезжались с картой листов; пока карта не построена — из номеров
  страниц, чтобы панель работала сразу после открытия пары;
- активная пара подкручивается в видимую зону при листании
  (`scRevealActiveThumb`, крутится сам список, не страница);
- слева от каждой строки стоит номер пары.

### Перестановка листов

Ctrl/Shift + клик отмечает листы ОДНОЙ стороны (обычный клик остаётся переходом
к паре), перетаскивание переносит всю отметку. У края списка работает
автопрокрутка: `dragover` при неподвижном курсоре не приходит, поэтому список
крутится в своём кадре по последней известной точке.

Строка полосы — это пара, и её положение выводится из связей, а не хранится
отдельно, поэтому перестановка — это переназначение связей
(`scPlanThumbMove` → `scLinksFromThumbRows` → `scPersistLinks`), после которого
карта листов сверху пересобирается сама из тех же данных.

Два правила, которые нельзя терять:

- листы раскладываются по ближайшим СВОБОДНЫМ местам вниз от цели: перестановка
  не должна молча разрывать пару, которую инженер подтвердил раньше;
- явной связью становится только ИЗМЕНЁННАЯ строка, иначе разовая перестановка
  перекрасила бы всю карту в «Ручная» и стёрла уверенность автосопоставления на
  строках, которых никто не трогал. Лист, оставшийся без пары, попадает в
  `unlinked_left_pages` — без явной пометки автосопоставление вернуло бы ему
  прежний правый лист.

## Просмотрщик листов

Инлайновый SVG больше не используется основным интерфейсом: насыщенный A1 давал
около 6 МБ разметки и 30 000 DOM-узлов на страницу, а непрерывный режим держал
сразу несколько таких деревьев на каждой стороне. Теперь страница открывается
как полноформатный PNG-preview шириной 1400 px, а при увеличении поверх него
лениво подставляются только видимые PNG-тайлы 512×512. Уровни 1–64 пикселя на
PDF-point позволяют рассматривать локальный фрагмент при прежнем диапазоне
масштаба 0,1×–100×, не создавая гигантский растр всего A1.

Непрерывный режим использует preview шириной 1000 px и по-прежнему держит окно
не более чем ±2 страницы от текущей. Legacy `page-svg` оставлен серверным
fallback на время проверки нового рендера, но frontend его не запрашивает.

Обе панели ведёт ОДИН видовой порт в нормированных координатах листа
(`cx`/`cy` ∈ [0,1] — точка листа в центре панели, `zoom` = 1 — лист целиком).
Каждая панель переводит их в свои единицы, поэтому один и тот же участок
чертежа стоит в одном месте обеих панелей даже когда слева A4, а справа A1.
Флажок «Синхронный вид» разводит панели на независимые состояния; при
отвязке правая продолжает с текущего места, при возврате подхватывает левую.

Управление: `Ctrl`/`⌘` + колесо — масштаб вокруг курсора, колесо — прокрутка
листа, `Shift` + колесо — горизонтально, перетаскивание — сдвиг, двойной клик —
×2 (с `Alt` — ÷2); кнопки «Вписать» и «1:1».

В шапке каждой панели есть независимый поиск по встроенному текстовому слою
её PDF. Первое нажатие «Найти» открывает первую подходящую страницу, повторные
нажатия переходят по отдельным совпадениям по кругу. Запросы и результаты левой
и правой панели не смешиваются. Все слова найденной фразы выделяются жёлтыми
рамками непосредственно поверх листа; активное совпадение имеет усиленную
обводку. Кнопки `↑`/`↓` рядом с «Найти» циклически переходят между отдельными
совпадениями и выводят выбранный фрагмент в центр панели с читаемым масштабом.
Координаты нормированы относительно страницы, поэтому подсветка остаётся на
месте при pan/zoom и работает как в постраничном, так и в непрерывном режиме.
Для сканов без текстового слоя интерфейс явно показывает «Нет текста»; OCR
этим поиском не запускается.

## Этап 2: исключение одинакового текста

Кнопка «Сравнить текст» запускает отдельный слой после того, как инженер
сохранил связи в `sheet_links.json`. Он не пересчитывает и не меняет карту.

Структура и второй проход берутся из TEXT-блоков текущего `document.md`.
Страница разбивается на заголовки, небольшие абзацы, подписи, нумерованные
пункты, элементы списков и отдельные строки таблиц. Форматирующая канонизация
приводит регистр, `ё`, пробелы, тире, Markdown-разметку и очевидный десятичный
разделитель; цифры и инженерные термины не исправляются.

Геометрия кандидатов первого прохода строится непосредственно из визуальных
строк встроенного текстового слоя двух PDF. Точные строки сопоставляются внутри
принятой связи, поэтому разная нарезка или опечатка распознавания в MD не
оставляет визуально одинаковый текст открытым. Проценты UI рассчитываются по
тому же PDF-слою. Если текстового слоя нет, используется структурированный
MD-результат. LLM для этого не вызывается.

Если совпал весь TEXT-блок целиком, построчные маски внутри него заменяются
одним серым overlay по исходной геометрии загруженного `blocks.json`. Для
прямоугольника используются `coords_norm`, для сложной формы — нормированные
`polygon_points` через CSS `clip-path`. Если внутри блока есть хотя бы одно
текстовое отличие, весь блок не закрывается и остаётся точное построчное
маскирование.

Первый проход ищет точный canonical match только внутри каждой принятой связи,
включая many-to-many. Повторяющиеся фразы связываются только при совместимых
типе и относительном положении; неоднозначные повторы остаются нетронутыми.
Второй проход берёт остатки и ищет точное совпадение на других листах
противоположного документа. Короткие и часто повторяющиеся строки для этого
не используются.

Результат хранится в `text_comparison.json` версии 1:

- исходные минимальные `TextFragment` и устойчивые идентификаторы;
- `same_on_linked_sheet` и `found_on_other_sheet` с фактической страницей;
- остатки `remaining_for_comparison` в виде списков fragment id;
- метрики по фрагментам и символам для каждой связи;
- только рекомендательные `sheet_link_hints`;
- нормированные bbox overlay для обеих панелей.

Одновременно атомарно сохраняется обязательный машинный контракт
`text_exclusions.json`. Это не UI-флаг, а входной барьер для всех следующих
этапов сравнения:

- `downstream_text_input` содержит только строки PDF, которые остались после
  вычитания совпавшего текста;
- `exclusion_masks` фиксирует нормированные прямоугольники и полигоны, которые
  должны вычитаться перед сравнением растра и векторной графики;
- `excluded_fragment_ids` и `excluded_pdf_line_ids` позволяют проверить, что
  уже принятое совпадение не попало в следующий проход повторно;
- `source_signature` привязывает контракт к конкретным PDF, MD, `blocks.json`
  и сохранённой карте листов, а `contract_sha256` защищает его от незаметного
  повреждения.

Каждый следующий backend-этап обязан сначала вызвать
`require_text_exclusions_for_downstream`. Отсутствующий, устаревший или
повреждённый контракт блокирует запуск; использовать исходный полный текст в
обход `downstream_text_input` запрещено.

В MD/HTML координат нет, поэтому bbox извлекаются из встроенного текстового
слоя PDF через PyMuPDF. PDF открывается только на чтение. После Этапа 4
финальные серые области — это DOM-overlay только для подтверждённых ИИ
`SAME/MOVED` в постраничном и непрерывном viewer, а не изменение PDF.
Совпадение на другом листе получает компактный маркер `↗` и tooltip. Подсказка меняет
`sheet_links.json` только после явного нажатия инженером «Добавить связь» или
«Заменить связь»; после изменения карты старый слой помечается устаревшим.

API:

- `POST .../pairs/{pair_id}/text-comparison` — построить/получить тот же
  детерминированный результат для неизменившихся входов;
- `GET .../pairs/{pair_id}/text-comparison` — получить сохранённый UI-слой.
- `GET .../pairs/{pair_id}/text-exclusions` — получить сохранённый контракт
  исключений, его подпись, контрольную сумму и признак актуальности.

В этом этапе нет LLM, Vision, повторного OCR, semantic similarity, embeddings
или сравнения векторной графики. Остаток не создаёт findings.

## Этап 3: фактические текстовые расхождения

`text_differences.json` строится только после проверки актуального и валидного
`text_exclusions.json`. Входом служат исключительно fragment id из
`remaining_for_comparison`; пересечение с `same_on_linked_sheet` или
`found_on_other_sheet` считается нарушением контракта и останавливает запуск.

Production-путь полностью детерминированный. Это решение принято по реальному
benchmark из 11 кейсов и 9 листовых групп: baseline не уступил моделям по
фактическому сопоставлению, ни один модельный вариант стабильно не разрешил
оставшуюся неоднозначность, а один дал два невалидных JSON-ответа. Полный
отчёт и сырые ответы находятся в
`experiments/stage_comparison_text_differences/artifacts/`.

Обработка внутри каждой принятой many-to-many связи выполняется так:

1. безопасная канонизация форматирования и очевидных OCR-confusables;
2. удаление точных эквивалентов;
3. сопоставление уникальных устойчивых ключей строк и марок;
4. консервативное сопоставление по skeleton, идентификаторам и similarity;
5. всё оставшееся сохраняется как `removed` и `added`, а не как сомнительный
   `changed`.

Каждый элемент хранит полный исходный `before`/`after`, fragment ids, страницы
и нормированные bbox-якоря. Краткое summary не является отдельным выводом и
не может потерять provenance. Графические OCR-описания не анализируются.
Строгий model JSON validator покрыт тестами, но в production модель не
вызывается на этом уровне: её отдельный вызов относится к Этапу 4 и не меняет
этот RAW-артефакт.

Вкладка «3. Расхождения» показывает ровно одну строку на принятую группу
листов с колонками «Лист П / Лист РД / Изменилось / Удалено / Добавлено».
Пустые группы скрыты. `details` раскрывает полный исходный текст, а кнопка
источника открывает соответствующую страницу и центрирует viewer на bbox.

API:

- `POST .../pairs/{pair_id}/text-differences` — атомарно построить либо вернуть
  идемпотентный результат для неизменившегося Stage 2 контракта;
- `GET .../pairs/{pair_id}/text-differences` — получить сохранённый результат
  и признак его актуальности.

## Этап 4: семантический AI reviewer

Этап 4 работает поверх неизменяемых `text_exclusions.json` и
`text_differences.json`. Для каждой принятой `sheet_links` group backend заново
собирает точные исходные фрагменты П и РД, их страницы, подписи листов, bbox,
тип источника, табличный ключ и предварительные статусы всех трёх
детерминированных проходов. PDF, растр, изображения, нормы, findings и другие
дисциплины модели не передаются.

Модель возвращает только массивы существующих fragment id, один из статусов
`SAME / MOVED / CHANGED / REMOVED / ADDED / UNCERTAIN`, уверенность и краткое
объяснение. Полные `before`/`after`, страницы, подписи листов и bbox backend
восстанавливает из source fragments. Строгий validator атомарно отклоняет всю
группу при неверной схеме, чужом или конфликтно повторённом id, неполном
покрытии, несовместимой форме статуса или неверной actual page. Выдуманное
число/обозначение и инженерная оценка переводят только затронутое решение в
`UNCERTAIN` с сохранением исходного model explanation для аудита. `SAME/MOVED`
принимаются только с высокой уверенностью; конфликт
`deterministic CHANGED → model SAME` и `MOVED` без фактического выхода за
принятую связь также закрываются в `UNCERTAIN`.

Большие листовые группы транспортно делятся не более чем по 40 preliminary
items. Каждый fragment id попадает ровно в один чанк; решения объединяются
только после успешной строгой проверки всех чанков родительской группы. При
отказе любого чанка вся группа остаётся deterministic fallback без частичных
AI-масок. Завершённые группы переиспользуются при same-model recovery.

Результаты разделены:

- `text_ai_review.json` — трассируемое решение модели по каждой группе,
  переход `deterministic_status → final_status`, ошибки и usage;
- `text_final_comparison.json` — единственный UI-слой с итоговыми
  расхождениями и overlay;
- `text_exclusions.json` и `text_differences.json` остаются RAW evidence и
  никогда не перезаписываются моделью.

Если вызов или validation группы не удался, сохраняется явный `failed/partial`:
таблица продолжает показывать deterministic differences этой группы, но серые
маски для неё не строятся и UI не называет результат «Проверено ИИ». Финальная
серая маска существует только для принятого AI `SAME` или `MOVED`; у `MOVED`
сохраняются actual page/sheet и маркер `↗`. `sheet_links.json` модель не меняет.

API:

- `POST .../pairs/{pair_id}/text-ai-review` — выполнить либо идемпотентно
  вернуть ревизию и финальный слой;
- `GET .../pairs/{pair_id}/text-ai-review` — получить reviewer artifact;
- `GET .../pairs/{pair_id}/text-final-comparison` — получить финальный UI-layer.

Отдельный воспроизводимый benchmark находится в
`experiments/stage_comparison_text_ai_reviewer/`: 27 групп, независимый ground
truth, одинаковая нативная JSON Schema и `medium` effort для трёх Codex и трёх
Claude моделей, режимы с deterministic hint и без него. Production-модель
фиксируется в коде только по итогам этого benchmark; каскада моделей нет.
Текущий победитель и единственный production reviewer — `gpt-5.6-luna` с
`medium` effort и deterministic hint.

## Этап 5: основные изменения проекта

Этап 5 работает только поверх неизменяемого `text_final_comparison.json` и
создаёт отдельный `project_change_summary.json`. Полные MD, PDF, изображения,
растр и графика в модель не передаются. Stage 3/4 artifacts и `sheet_links.json`
слой не изменяет.

Перед ИИ для каждой принятой sheet group выполняется консервативный purpose
precheck по сохранённым названиям листов. Результат `PAIR_OK` допускает
классификацию, `PAIR_REVIEW_REQUIRED` создаёт заметный REVIEW и принудительно
оставляет `project_changes` пустым; связь автоматически не исправляется.

Каждый атомарный CHANGED/REMOVED/ADDED/UNCERTAIN получает устойчивый
`evidence_id`. `gpt-5.6-luna` с `medium` effort возвращает только класс
`PROJECT_CHANGE / SERVICE_STRUCTURE / REVIEW`, категорию, краткий factual title
и группы существующих evidence IDs. Backend сам восстанавливает before/after,
страницы, bbox, считает `count` и формирует заголовки агрегатов. Prompt и JSON
Schema отдельны от Stage 4.

Validator требует точное однократное покрытие всех evidence, запрещает чужие
IDs, неподтверждённые числа/обозначения, инженерные оценки и PROJECT_CHANGE из
заведомо служебного либо UNCERTAIN evidence. Записи из «Справки об изменениях»
без подтверждения фактическим проектным листом остаются REVIEW. При невалидном
ответе вся группа показывается как REVIEW; частичные технические догадки из неё
не публикуются. Успешные группы переиспользуются при retry.

Контракт `project_change_summary.json` хранит source signature, версии prompt и
validator, model/effort, usage, purpose status, три массива агрегатов, полные
atomic details и явные ограничения `stage4_immutable`, `sheet_links_mutated:
false`, `images_sent: false`, `counts_computed_by_backend: true`.

На вкладке «Расхождения» основным слоем являются карточки «Основные изменения
проекта». Детали каждого агрегата раскрывают все atomic evidence и переходы к
листу П/РД. `REVIEW` заметен сразу. «Служебные и структурные изменения» — один
общий блок, закрытый по умолчанию; прежняя таблица доступна в также закрытом
блоке «Показать исходные текстовые различия».

API:

- `POST .../pairs/{pair_id}/text-change-summary` — выполнить агрегацию либо
  переиспользовать актуальные успешные группы;
- `GET .../pairs/{pair_id}/text-change-summary` — получить артефакт и признак
  актуальности.

Инженерные решения, которые нельзя ломать:

- состояние вида НЕ реактивно, `transform` пишется прямо в DOM внутри
  `requestAnimationFrame`; набор тайлов обновляется только через 90 мс после
  паузы pan/zoom;
- preview всегда остаётся под тайлами, поэтому при движении либо смене уровня
  детализации на листе не появляются пустые области;
- серверный кэш preview и тайлов ключуется подписью `mtime+size` исходного PDF,
  ограничен 128 МБ и отдаёт ETag с суточным browser cache;
- разобранная MuPDF display list держится только для двух последних страниц:
  тяжёлый A1 разбирается один раз (~1 с в худшем текущем примере), после чего
  каждый его тайл рендерится примерно за 15–25 мс; одновременно исполняются не
  более двух raster-задач, чтобы непрерывный режим не устроил всплеск памяти;
- URL изображения содержит подпись версии PDF, поэтому браузер не показывает
  устаревший лист после замены файла;
- `will-change: transform` включается только на время сдвига и снимается через
  200 мс покоя либо перед зумом;
- legacy `page-svg` по-прежнему сжимается вне event loop и безопасно
  namespace-ит идентификаторы, пока существует как fallback.

## Границы clean-slate

Здесь нет PreparedDocument, старого sheet matcher/page alignment, affine/ORB,
image fingerprint, block/entities matching, change regions/groups,
старого semantic diff, Pipeline V2, Vision или embeddings. Внешние model calls
ограничены текстовыми Stage 4 reviewer и Stage 5 classifier/aggregator; раздел
не создаёт findings.

Основные точки входа:

- `backend/app/services/stage_comparison/sheet_matching.py`;
- `backend/app/services/stage_comparison/text_differences.py`;
- `backend/app/services/stage_comparison/text_ai_reviewer.py`;
- `backend/app/services/stage_comparison/project_change_summary.py`;
- `backend/app/services/stage_comparison/store.py`;
- `backend/app/api/routers/stage_comparison.py`;
- `frontend/index.html`;
- `frontend/static/js/app.js`.
