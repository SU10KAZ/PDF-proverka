## 1. Причина уточнения

Этап 11 закончился с одним незакрытым узлом: провайдеры установлены и
наблюдаемы, но **вход не выполнен ни у одного** (док 11, §8). Предполагалось,
что оператору достаточно войти в изолированный provider home.

Отдельно в доке 11 §2 стоит самокоррекция: утверждение этапа 10 «`claude` и
`codex` на воркере физически отсутствуют» верно лишь в той форме, в какой оно
проверялось — `command -v` в неинтерактивной сессии. Фактически на машине жили
и `claude`, и личные каталоги `~/.claude`, `~/.codex`.

Отсюда вопрос, который и породил этап 11b: **если у пользователя VPS уже есть
рабочая авторизация, зачем воркеру вторая?** И встречный: **можно ли считать
доказанной авторизацию, которую оператор видит в VS Code?**

Ответ на второй — нет, и это зафиксировано измерением, а не рассуждением
(§6, §7). Ответ на первый — можно, и ради этого введён режим `ambient_user`
(§11, §12).

Чего этап 11b НЕ делает: не выполняет ни одного запроса к модели, не разворачивает
новый релиз на воркере, не входит в учётные записи за оператора.

## 2. Архитектура SSH admin plane

```
ЦЕНТР 176.12.77.128                        ВОРКЕР 176.12.77.31
adm.hlab.kz                                andrewuzun3.hlab.kz

  ssh audit-worker-pilot  ──────────────►  установка, обновление,
  (publickey, BatchMode)                   диагностика, статус юнитов,
```

Что по этому каналу ездит: артефакт релиза (`scp`), скрипт установки
(`ssh ... bash -s`), чтение состояния, `systemctl --user restart`.

Что по нему **не** ездит и не будет: задания, промпты, ответы моделей.
Формально это закреплено тремя способами — статическим тестом по дереву
разбора (§23), шагом смоука (§22) и отсутствием в `deploy_audit_worker.py`
любых ручек вида `--run-claude`/`--run-codex` (проверяется тестом).

Инвариант **C-01/C-02** дока 02 («входящего SSH для обработки заданий нет»,
«SSH — только установка, ремонт, диагностика») этапом 11b не ослаблен.

## 4. Central SSH state

| вопрос | ответ |
|---|---|
| проходит ли `BatchMode=yes` | да, с первой попытки |
| способ | `publickey`, ключ `~/.ssh/id_ed25519` центра |
| запрашивался ли пароль | ни разу |
| хранится ли пароль в проекте | нет; `sshpass` в репозитории отсутствует |
| проверка ключа хоста | штатная, `StrictHostKeyChecking=ask`, запись в `known_hosts` уже была |
| заводился ли новый ключ | **нет** |

Про последнюю строку стоит сказать прямо. Задание разрешало создать выделенный
`~/.ssh/audit_worker_admin_ed25519`, **если подходящего ключа нет**. Ключ
нашёлся и работал. Заводить второй значило бы: сгенерировать ключ, попросить
оператора вручную положить его в `authorized_keys` на живой машине и ради
косметики имени файла на время оставить доступ в промежуточном состоянии.
Выигрыш — только имя; риск — реальный. Поэтому создан **алиас**, а не ключ:

```sshconfig
Host audit-worker-pilot
    HostName 176.12.77.31
    User coder
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 3
```

Приватный ключ не читался, не выводился и в Git не попадал. Прочие записи
`~/.ssh/config` не изменялись. `sshd_config`, `sudoers`, firewall, Plesk/nginx
не трогались.

## 7. Claude discovery

Исходное состояние — и главная находка этапа.

`command -v claude` → `/home/coder/.local/bin/claude`, `claude --version` →
`2.1.218`. Выглядит как установка. Установкой не является:

```bash
#!/bin/bash
CLAUDE_BIN=$(find /home/coder/.vscode-server/extensions /home/coder/.vscode/extensions \
             -name "claude" -type f 2>/dev/null | sort -V | tail -1)
if [ -z "$CLAUDE_BIN" ]; then
    echo "Claude CLI not found in VSCode extensions" >&2
    exit 1
fi
exec "$CLAUDE_BIN" "$@"
```

Это **скрипт-обёртка**, которая ищет бинарь внутри каталогов расширений VS Code.
Три следствия, и каждое дисквалифицирует его как штатный путь для воркера:

1. **Версия выбирается случайностью сортировки строк.** На машине лежали
   2.1.222 (в `~/.vscode-server/extensions`), 2.1.218 и 2.1.217 (в
   `~/.vscode/extensions`). `sort -V` сравнивает пути целиком, а `.vscode-` <
   `.vscode/` по коду символа (`-` = 0x2d, `/` = 0x2f) — поэтому `tail -1`
   выбирал **не новейшую** копию, а ту, что лежит в `~/.vscode/`. Отсюда
   расхождение «в расширении 2.1.222, а CLI отвечает 2.1.218».
2. **Путь исчезает вместе с расширением.** Удаление или обновление расширения
   меняет каталог; обёртка либо начинает указывать в другое место, либо
   печатает «not found».
3. **Приватная раскладка чужого продукта** не является контрактом.

Ровно это задание и запрещает: не делать audit-worker зависимым от внутреннего
layout расширения. `claude auth status` при этом честно отвечал
`{"loggedIn": false, "authMethod": "none", "apiProvider": "firstParty"}` —
то есть IDE-логин действительно **не** давал CLI авторизации.

## 9. CLI installation

Оба — **официальными установщиками, пользовательскими, без `sudo`**. Скрипты
скачивались во временный каталог и читались до запуска (проверялось отсутствие
`sudo`, каталог установки, переменные).

**Codex** — `curl -fsSL https://chatgpt.com/codex/install.sh | sh`
(`CODEX_NON_INTERACTIVE=true`):

```
BIN_DIR="${CODEX_INSTALL_DIR:-$HOME/.local/bin}"
CODEX_HOME_DIR="${CODEX_HOME:-$HOME/.codex}"
STANDALONE_ROOT="$CODEX_HOME_DIR/packages/standalone"
```

Раскладка совпала с той, что `providers/paths.py` описывал **ещё на этапе 11**
в докстринге `default_executable`. Результат:

```
/home/coder/.local/bin/codex → /home/coder/.codex/packages/standalone/current/bin/codex
codex-cli 0.147.0
```

**Claude** — `curl -fsSL https://claude.ai/install.sh | bash stable`. Установщик
отказывается работать под `sudo` (проверка в самом скрипте) и кладёт нативную
сборку в `~/.local/share/claude/versions/`.

Здесь потребовался второй заход, и это стоит записать, а не замолчать: первый
запуск отработал с кодом 0 и напечатал «Location: ~/.local/bin/claude», но
**лаунчер не заменил** — на этом пути лежал посторонний файл (та самая
обёртка), и установщик его не тронул. `install --force` повёл себя так же.
Сработало только освобождение пути:

```bash
cp -p  ~/.local/bin/claude ~/.local/bin/claude.vscode-wrapper.bak-20260809   # копия
mv     ~/.local/bin/claude ~/.local/bin/claude.vscode-wrapper.disabled-20260809
~/.local/share/claude/versions/2.1.220 install --force stable
```

Результат:

```
/home/coder/.local/bin/claude → /home/coder/.local/share/claude/versions/2.1.220
2.1.220 (Claude Code)
```

Обёртка не удалена, а сохранена под двумя именами: откат — одна команда `mv`.
Личные `~/.claude` и `~/.codex` при установке не менялись; `~/.npm-global`
и системный Node не трогались.

## 10. Operator login boundary

Граница простая: **вход выполняет человек**. Скрипты и агент не имеют права
ни выполнить браузерный вход, ни получить одноразовый код, ни попросить его в
чате.

Состояние на момент написания:

| провайдер | состояние | что требуется |
|---|---|---|
| Codex | **вход выполнен** — `Logged in using ChatGPT` | ничего |
| Claude | `{"loggedIn": false}` | вход оператора |

Codex оказался авторизован сразу: свежеустановленный официальный CLI читает
тот же `CODEX_HOME=~/.codex`, где уже лежала личная авторизация пользователя
VPS. Это и есть `ambient_user` в чистом виде — учётные данные не переносились
и не копировались, CLI просто нашёл их там, где они всегда были.

**Про Claude стоит сказать отдельно, потому что это ловушка.** Файл
`~/.claude/.credentials.json` на воркере **существует** (339 байт, `0600`,
владелец `coder`) — и при этом `claude auth status` отвечает
`{"loggedIn": false}`. Содержимое файла не читалось: только `os.stat`. Наличие
файла — не признак действующей авторизации; вероятнее всего там просроченные
данные. Практический вывод для оператора: «файл на месте» и «вход выполнен» —
разные утверждения, и второе даёт только сам CLI. Вход по команде из
Приложения Б перезапишет файл действующими данными.

Права проверены заодно (только `stat`): оба credential-файла `0600`. Каталог
`~/.codex` имеет режим `0775` — шире, чем `~/.claude` (`0700`), — но сам
`/home/coder` закрыт как `0750`, а непривилегированный пользователь на машине
ровно один (`coder`), так что практического доступа это никому не даёт.
Приводить каталог в порядок этап не стал: каталог чужой (§11), а решение
менять права в личном каталоге — за оператором.

Команда для Claude приведена в Приложении Б. Отдельно: там **`claude auth
login --claudeai`, а не `claude setup-token`**. Второй выдаёт долгоживущий
токен для `CLAUDE_CODE_OAUTH_TOKEN`, а эта переменная стоит в
`FORBIDDEN_ENV_NAMES` и до CLI не доедет по построению (док 11, §33). Совет,
который нельзя исполнить, хуже отсутствия совета.

## 11. Ambient user auth

Идея режима в одну строку: **не заводить воркеру вторую учётную запись там,
где у пользователя машины уже есть первая.**

```
процесс конвейера   HOME=<job_dir>/work/home     ← изоляция ДАННЫХ задания
процесс CLI         HOME=/home/coder             ← авторизация ПРОВАЙДЕРА
```

Два разных процесса и два разных вопроса. Изоляция конвейера этапом 11b не
ослаблена ни на шаг (§13) — ambient касается только подпроцесса CLI.

Что режим НЕ делает:

* не копирует `~/.claude` и `~/.codex` ни между машинами, ни внутри машины;
* не читает содержимое `.credentials.json` / `auth.json`;
* не создаёт второй логин в `providers/<p>/home` — изолированные каталоги
  этапа 11 остались на месте нетронутыми как legacy/тестовая инфраструктура и
  автоматически не удаляются;
* не передаёт учётные данные центру ни в каком виде.

Ключевое свойство: в этом режиме домашний каталог считается **чужим**. Воркер
его читает (`os.stat`), но не создаёт и не перенастраивает права.

## 12. ProviderAuthMode

Новый модуль `audit_worker/providers/auth_mode.py`. Три значения:

| значение | смысл | HOME процесса CLI |
|---|---|---|
| `isolated_provider_home` | схема этапа 11, **умолчание** | `<worker_data>/providers/<p>/home` |
| `ambient_user` | личная авторизация пользователя VPS | `/home/coder` |
| `unavailable` | учётных данных здесь нет **по решению оператора** | CLI не запускается вовсе |

Три решения, каждое с причиной:

1. **Умолчание не изменилось.** Воркер, где переменная не задана, работает
   ровно как на этапе 11. Иначе одна правка кода поменяла бы поведение всех
   уже развёрнутых машин.
2. **Настройка попровайдерная, глобальной переменной нет.**
   `AUDIT_WORKER_PROVIDER_CLAUDE_AUTH_MODE`,
   `AUDIT_WORKER_PROVIDER_CODEX_AUTH_MODE`. `ambient_user` — это разрешение CLI
   дотянуться до личного каталога человека; включаться оно обязано на одной
   машине для одного провайдера. В коде это выражено выбором образца:
   `modes.get(name)`, как `account_groups`, а **не** как глобальный
   `inference_allowed`.
3. **Неизвестное значение валит старт** (`SystemExit`), а не откатывается к
   умолчанию. `…_AUTH_MODE=ambient` (без `_user`) при тихом фолбэке означал бы:
   оператор думает про ambient, воркер молча работает в изоляции и честно
   рапортует «вход не выполнен». Искали бы проблему в подписке, а не в букве.

`unavailable` — не синоним аварии. В нём адаптер **не запускает CLI вообще**:
`auth status` на чистой машине способен создать каталоги и файлы состояния в
чужом HOME, а объявленное «не используем» не должно оставлять следов.
Предупреждение оператору тоже отдельное (`provider_<p>_auth_unavailable`), а не
общее «авторизация не выполнена»: настройка обязана читаться как настройка,
иначе она неотличима от поломки и её перестанут читать оба раза.

Режим виден оператору и центру как **значение** — поля `auth_mode` в
`capability_snapshot`, `ProviderIdentity.as_dict` и `as_center_payload`.
`auth_mode` и `auth_method` — разные оси: первая отвечает «где лежат учётные
данные», вторая — «чем вошли» (`claudeai`, `chatgpt`, `apiKey`).

**Как режим доезжает до центра — и почему без миграции схемы.** Санитайзер
центра (`provider_accounts.sanitize_provider_snapshot`) собирает снимок
перечислением полей, поэтому новый ключ верхнего уровня он молча отбрасывает.
Это правильное поведение для совместимости — старый центр не падает от нового
воркера, — но само по себе означало бы, что оператор режима не увидит.
Спасает `capability`: адаптер кладёт `auth_mode` туда, а `capability_json`
сохраняется целиком (ограничение — 40 ключей и 8 КБ, ключи берутся
отсортированными, и `auth_mode` в этом порядке первый). Проверено прогоном
санитайзера и закреплено классом `TestCenterVisibility`.

Отдельная колонка в `worker_provider_states` и элемент интерфейса — **не
сделаны**: это миграция схемы центра, отдельное и более рискованное изменение,
которое этап 11b на себя не берёт.

## 13. Pipeline HOME

**Не изменён.** `audit_runner.isolated_roots` по-прежнему даёт
`HOME=<job_dir>/work/home`, `HOME` отсутствует в `_ENV_WHITELIST`, а
`remote_audit_runner.apply_runtime_paths` по-прежнему падает `SystemExit`, если
значение уводит наружу каталога попытки.

Проверяется тремя тестами класса `TestPipelineIsolationUnchanged`, включая
AST-проверку того, что конвейер не импортирует `audit_worker.providers`.

Отсюда следует важное и неприятное: **авторизованный CLI конвейеру пока
недоступен по построению**. Это тот самый разрыв, который док 11 назвал
развилкой §33, и этап 11b его намеренно не закрывает — см. §26–27.

## 14. Provider subprocess environment

Окружение по-прежнему собирается **с нуля** белым списком (инвариант I-P1).
Ambient добавил ровно две переменные:

| имя | значение | режим |
|---|---|---|
| `PATH` | `/usr/local/bin:/usr/bin:/bin` (константа) | оба |
| `LANG`, `LC_ALL`, `TZ`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `LD_LIBRARY_PATH` | passthrough, если заданы | оба |
| `HOME` | по режиму | оба |
| `TMPDIR` | `<worker_data>/providers/<p>/runtime` — **всегда воркерский** | оба |
| `USER`, `LOGNAME` | имя пользователя из базы учётных записей | **только ambient** |
| `CLAUDE_CONFIG_DIR` / `CODEX_HOME` | свой каталог провайдера | оба |

Три вещи, которые НЕ изменились и не должны:

* **`FORBIDDEN_ENV_NAMES` не ослаблен.** У живого пользователя в окружении
  вполне может лежать `OPENAI_API_KEY` — и он не должен доехать до подпроцесса.
  Тест `test_forbidden_env_names_are_rejected_even_if_added_later` ставит рубеж
  против будущей правки ambient-ветки, а не против текущего кода.
* **`TMPDIR` не переезжает вместе с `HOME`.** Домашний каталог нужен ровно для
  одного — чтобы CLI нашёл свою авторизацию. Всё, что процесс пишет сам,
  остаётся во владении воркера.
* **I-P3 действует и при общем HOME**: Claude не видит `CODEX_HOME`, Codex не
  видит `CLAUDE_CONFIG_DIR`. Общий домашний каталог — самое вероятное место,
  где изоляция переменных могла бы незаметно исчезнуть, поэтому на неё есть
  отдельный тест.

`USER`/`LOGNAME` берутся из `pwd`, а **не** из `os.environ`. Разница
принципиальная: `HOME`/`USER` — обычные переменные, и тот, кто сумеет их
подменить, увёл бы CLI читать учётные данные из подставного каталога, а воркер
отрапортовал бы центру `logged_in`. `pwd` описывает учётную запись, а не
окружение процесса. Переменной-override для домашнего каталога намеренно нет —
она вернула бы ровно ту дыру, ради закрытия которой взят `pwd`.

## 15. Filesystem/tool isolation

**Главный предохранитель режима — `ProviderHome.ensure_dirs`.** В ambient
список управляемых каталогов сокращён до воркерских:

```python
if self.ambient:
    managed = (self.root, self.runtime, self.metadata)
else:
    managed = (self.root, self.home, self.runtime, self.metadata, self.config_dir)
```

Оставь в нём `home` и `config_dir` — и `os.chmod(path, 0o700)` уехал бы на
`/home/coder` и `~/.claude` живого человека: сначала закрыл бы его домашний
каталог от группы (на этой машине под соседними пользователями работает чужой
почтово-веб стек), а `mkdir` вдобавок создал бы `~/.codex` там, где оператор
его, возможно, не заводил. Тест
`test_ensure_dirs_never_touches_the_personal_home` сравнивает режимы каталогов
до и после и специально стартует с «широких» 0755 — то есть поймал бы именно
«наведение порядка».

`cwd` подпроцесса остаётся **пустым каталогом `runtime/`** в обоих режимах.
Это не перестраховка: на этапе 11 `codex app-server`, запущенный с
`cwd=/home/coder`, обнаружил там личный `.codex` как project-local
конфигурацию. Соль отпечатка учётной записи тоже остаётся в `metadata/`
воркера, а не в каталоге человека.

**Что честно назвать неопределённым.** Контрольный запрос Codex идёт с
`--sandbox read-only`. Какой именно объём ЧТЕНИЯ этот режим разрешает в
codex-cli 0.147.0, на этом этапе **установить не удалось**, и утверждать в
любую сторону было бы выдумкой. Что известно точно:

* в `codex --help` есть пример конфигурации
  `-c 'sandbox_permissions=["disk-full-read-access"]'`, а у подкоманды
  `codex sandbox` — параметр `--sandbox-state-readable-root`. Оба намекают, что
  читаемые корни **являются** предметом настройки, а не открыты всегда;
* проверить это без обращения к модели не получилось: подкоманда
  `codex sandbox` требует `--permission-profile` и таблицу `[permissions]` в
  `config.toml`. Дописывать её в личный `~/.codex/config.toml` оператора этап
  не имеет права (каталог чужой, §11), а угадывать недокументированную схему на
  живой машине — плохой размен;
* песочница, которая реально важна, — та, что применяет `codex exec`, а его
  запуск и есть обращение к модели.

Для Claude ситуация лучше по построению: доступ к файлам ограничен `cwd`
(пустой `runtime/`) плюс явно добавленные каталоги, а контрольный запрос идёт с
`--permission-mode dontAsk` и явным списком запрещённых инструментов
(`Bash`, `Read`, `Edit`, `Write`, `Glob`, `Grep`, `WebFetch`, …).

Отсюда — контрольный файл (§20) и требование доказать изоляцию чтением
**измерением, а не рассуждением**, вынесенное в предусловия следующего этапа
(§26, §27). `PROVIDER_FS_READ_ISOLATION = not_determined`.

Первый вариант сохраняет оба свойства разом, второй разменивает изоляцию на
простоту. Решение договорное и принимать его нужно **до** подключения моделей к

## 29. Незапланированный запрос к модели: как это вышло

Прежде чем говорить о контрольных запросах, нужно назвать лишний.

При выяснении, какие флаги принимает `claude` 2.1.220, была выполнена команда
`claude --tools "" doctor`. Опция `--tools` объявлена вариадической
(`<tools...>`), поэтому `doctor` был поглощён как ВТОРОЕ имя инструмента.
Подкоманды не осталось, stdout не терминал — CLI ушёл в print-режим и прочитал
промпт из stdin. А stdin в тот момент был каналом, из которого `bash -s` читал
сам исполняемый скрипт. Модель получила его хвост.

Зафиксировано по записи сессии `~/.claude/projects/-home-coder/490c1344-…jsonl`:

| параметр | значение |
|---|---|
| модель | `claude-opus-5` |
| токены | 4224 cache-creation input + 732 output |
| время | 2026-08-09T13:14:12Z |
| содержимое промпта | хвост тестового скрипта, 636 символов; документов проекта нет |

Оператор был извещён до продолжения работ и подтвердил выполнение
запланированного контрольного запроса, зная, что суммарно по Claude выйдет два
обращения.

Два вывода, оба вошли в код и в тесты:

1. **вариадический флаг съедает соседний токен** — поэтому `--tools=` и
   `--disallowed-tools=` пишутся только в форме с `=`, а промпт стоит
   последним аргументом (`_probe_argv`, тест `TestVariadicArgumentSafety`);
2. **подпроцессу нельзя отдавать унаследованный stdin** — инвариант I-P8,
   `stdin=DEVNULL`, когда своего ввода нет. У `codex exec` это ещё и вопрос
   воспроизводимости: непустой stdin он дописывает к промпту `<stdin>`-блоком.

Замечание о цене ошибки: она обошлась в один запрос по подписке ровно потому,
что случилась ВНЕ провайдерского слоя — в отладочной команде. Через
`ProviderAdapter` она была невозможна: там argv собирается из констант, а stdin
теперь `/dev/null`.

## 31. Разрешение со стороны воркера (закрытие находки 9)

Было: `AUDIT_WORKER_ALLOW_REAL_PROVIDER_PROBE=true` подставлялась в ту же
SSH-команду, что и `--i-confirm-single-real-request`. Два «независимых» голоса
принадлежали одному вызывающему.

Стало: `<worker_root>/config/allow_real_provider_probe` — файл на машине,
`0600`, владелец совпадает с процессом, символьная ссылка отвергается. Его
нельзя приписать к команде: он либо есть, либо нет.

Формат — `<провайдер>=<остаток>`, и это **бюджет, а не булево «можно»**.
Разница не косметическая: «можно» не ограничивает количество, и дальше всё
держится на дисциплине вызывающего — обещании, которое подписка проверить не
может, тогда как счёт расходуется настоящий. Бюджет расходуется машиной:
`consume()` списывает единицу и переписывает файл **до** обращения к модели,
поэтому второй запуск упирается в остаток 0 независимо от намерений и от того,
чем кончился первый. Аварийное завершение работает в безопасную сторону —
попытка засчитана.

Переменная окружения на решение больше не влияет; в отчёте `providers` она
осталась наблюдаемой под именем `inference_probe_env_flag_deprecated`.

**Честно о границе независимости.** Разрешение и подтверждение теперь живут в
разных местах, приходят по разным каналам и списываются однократно. Но в этом
прогоне и файл, и флаг восходят к одному решению одного оператора, отданному в
одном разговоре. Архитектурно голоса разделены; организационно — пока нет, и
называть это «двумя независимыми людьми» было бы неправдой.

  котором модель выполняет команду, а бюджет этапа исчерпан;
* у Claude ситуация структурно лучше и не зависит от ядра: `--tools=`
  отключает встроенный набор целиком, читать файлы попросту нечем.

Итог: `PROVIDER_FS_READ_ISOLATION` = `claude: enforced_by_absence_of_tools`,
`codex: not_enforced_by_os` (механизм песочницы на воркере недоступен).
Контрольный файл не тронут ни разу, но доказывает это факт «не читали», а не
«не смогли бы прочитать».

## 35. Транспорт, следы и утечки

**Транспорт.** Codex: измерено во время самого запроса — установленное
TCP-соединение процесса `codex` на `172.64.155.209:443`. Claude: соединения во
время контрольного запроса **потеряны из-за моей ошибки** (вывод обрезан
`head`, повторить нельзя без второго запроса). Взамен эндпойнт измерен на
операции без обращения к модели: `claude doctor` — процесс `claude`,
`160.79.104.10:443` и `34.149.66.165:443`. То есть 443/TLS у обоих; у Claude
это измерение соседней операции, а не самого probe, и подменять одно другим
нельзя.

**SSH инференсом не был.** Дерево процессов запуска содержало только
`python -m audit_worker provider-probe`, `claude`/`codex` и их потомков —
ни одного `ssh`/`scp`; AST-проход по всем модулям `audit_worker` не нашёл ни
импортов `paramiko`/`fabric`/`pexpect`, ни литералов `ssh`/`scp`/`rsync` в
argv; текст ответа модели по SSH не передавался в принципе.

**Следы в личном каталоге.** Единственный файл сессии Claude за час — тот
самый незапланированный запрос (16:14). Контрольный запрос не оставил ни
одного: `--no-session-persistence` сработал, и это подтверждено сравнением, а
не документацией. Codex с `--ephemeral` не создал файлов сессии, но обновил
собственные базы состояния в `~/.codex` (`state_5.sqlite`, `logs_2.sqlite`,
`queue_1.sqlite`) — ambient-режим означает, что часть следов в чужом каталоге
неизбежна, и это цена, а не дефект. `TMPDIR` при этом остался воркерским: всё,
что процесс писал сам, легло в `providers/<p>/runtime`.

**Скан утечек.** Ищутся не слова, а формы секретов (префикс + тело ≥ 20
символов) И фактические подстроки из настоящих `.credentials.json`, `auth.json`
и токена воркера — иначе «не найдено» значило бы лишь «известные формы не
найдены».

| канал | объём | результат |
|---|---|---|
| argv (во время запросов и живые процессы) | всё дерево | 0 |
| журналы воркера | 3 файла | 0 |
| EventOutbox (`event_journal`, `event_sequences`) | 1414 + 37 строк | 0 |
| `worker.db` целиком | 7 таблиц | 0 |
| heartbeat-payload | 4118 байт | 0; абсолютных путей нет, e-mail нет |
| пакеты и результаты заданий | 1082 файла | 0 |
| `workers.db` центра | **файла нет** | см. ниже |

Про последнюю строку прямо: подсистема распределённых воркеров на центре
выключена (`DISTRIBUTED_WORKERS_ENABLED` в `.env` отсутствует, умолчание
`false`), и базы `workers.db` в окружении центра не существует. Проверка
«учётных данных нет в базе центра» проходит **вырожденно** — проверять нечего.
Записывать это в зелёные — самообман.

**Heartbeat и интерфейс.** Живой снимок воркера прогнан через санитайзер
центра: `auth_mode` верхнего уровня отбрасывается перечислением полей (так и
задумано ради совместимости), но доезжает внутри `capability` —
`capability.auth_mode = ambient_user` у обоих. Туда же добавлен
`inference_probe_grant_remaining`. Экран «Аудит-воркеры» теперь печатает режим
словами и предупреждает, когда воркер способен потратить настоящий запрос.
Доставить снимок в живой центр в этом этапе нельзя: ingress выключен, а
включение — правка `.env` и перезапуск бэкенда центра, то есть отдельное
решение оператора.

## Приложение А. Переменные окружения этапа

| переменная | по умолчанию | назначение |
|---|---|---|
| `AUDIT_WORKER_PROVIDER_CLAUDE_AUTH_MODE` | не задана → `isolated_provider_home` | режим авторизации Claude |
| `AUDIT_WORKER_PROVIDER_CODEX_AUTH_MODE` | не задана → `isolated_provider_home` | режим авторизации Codex |
| `AUDIT_WORKER_ALLOW_REAL_PROVIDER_PROBE` | `false` | **на разрешение больше не влияет** (§31); осталась наблюдаемой в отчёте |

Разрешение на контрольный запрос переменной больше не задаётся. Его место —
файл `<worker_root>/config/allow_real_provider_probe` (`0600`):

```ini
claude=1
codex=1
```

Допустимые значения: `ambient_user`, `isolated_provider_home`, `unavailable`.
Регистр и пробелы нормализуются; **любое другое значение валит старт**.
Глобальной переменной `AUDIT_WORKER_PROVIDER_AUTH_MODE` не существует —
намеренно (§12).

Для пилотного воркера после входа оператора:

```ini
# /home/coder/audit-worker/config/worker.env   (0600)
AUDIT_WORKER_PROVIDER_CLAUDE_AUTH_MODE=ambient_user
AUDIT_WORKER_PROVIDER_CODEX_AUTH_MODE=ambient_user
```
