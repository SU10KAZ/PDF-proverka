## 3. Ответ на критический вопрос §18

### «Claude+GPT+Codex» — может ли воркер воспроизвести сегодня?

**NO.**

Причины, по коду ветки `feat/distributed-audit-workers-codex-real-project-e2e`
(в `main` не влита):

1. Контракт задания несёт **одного** провайдера и **одну** способность
   (`provider_requirement.py`: `provider ∈ {claude, codex}`, `capability = strong_audit`)
   на **все** разрешённые этапы. Разбивки по этапам в контракте нет вообще.
2. Точную модель центр передавать **запрещено** инвариантом I-P5. Модель выбирает
   локальная политика воркера (`audit_worker/providers/model_policy.py`).
   Значит `claude-opus-5` на 02 и `claude-sonnet-5` на C OPT Critic центр заказать не может.
3. Этап 01 на воркере деградирует до **одной** ноги:
   `use_dual = (not use_provider_bridge) and model == STAGE02_DUAL_MODEL_ID`
   (`gemma_findings_only.py:2059`) — мост перекрывает ансамбль. Нет ни GPT-ноги,
   ни третьей ноги, ни судьи, ни gap-search.
4. Этап 05 на воркере — **один** вызов `_run_json_stage_via_provider`, а не две ноги.
   Подтверждено журналом боевого прогона 11F: `optimization: 1`.
5. OpenRouter-нога вообще не предусмотрена: провайдеров всего два, оба CLI-подписки.
6. Способность `strong_audit` — единственная в реестре (`KNOWN_CAPABILITIES`),
   различить «сильная модель для свода» и «дешёвая для критика» нечем.

Фактический замер 11F: `block_analysis` 1 вызов на блок, `text_analysis` 1,
`findings_merge` 1, `optimization` 1, `optimization_critic` 1,
`optimization_corrector` 1 — все на `claude-opus-5`.

### «Full Codex» — может ли воркер воспроизвести сегодня?

**NO.**

Те же шесть причин плюс две своих:

7. Этап 01 в «Full Codex» тоже смешанный (GPT + два Codex) — воркер даст один вызов.
8. Нога `claude-opus-5` на этапе 05 в контракте невыразима: провайдер у задания один.
   Заказав `provider=codex`, центр потеряет Claude-ногу; заказав `claude` — потеряет Codex-ногу.

Дополнительно: страж отсутствия на воркере ходит через тот же мост
(`absence_guard._verify_via_provider_bridge`), то есть на связанного провайдера,
а на центре — всегда на Claude. Даже этот шаг воспроизводится неточно.

## 4. Чего именно не хватает в distributed job contract

| Требуется для воспроизведения | Есть в контракте | Комментарий |
|---|---|---|
| Разбивка «этап → провайдер» | **нет** | один `provider` на всё задание |
| Разбивка «этап → способность» | **нет** | одна `capability` на всё задание |
| Понятие ансамбля (N ног на одну стадию) | **нет** | `allowed_stages` — плоский список имён |
| Роль ноги (детектор / судья / критик / фиксер) | **нет** | — |
| Порядок и параллельность внутри стадии | **нет** | — |
| Второй провайдер в одном задании | **нет** | схема допускает ровно один |
| Reasoning effort (`xhigh` для OPT-Codex, `low` для 01) | **нет** | задаётся `.env` центра |
| Различение «сильная» / «дешёвая» модель | **нет** | `KNOWN_CAPABILITIES = ("strong_audit",)` |
| Бюджет вызовов | **есть** | `graphic_blocks + 6 + max(3, ⌈N×0.10⌉)`, потолок 64 |
| Белый список этапов | **есть** | 7 имён |

Замечание к бюджету: формула считает **один** вызов на графический блок.
Центральный конвейер делает **четыре**. Документ на 40 блоков потребует ≈165 вызовов,
а контракт авторизует максимум 64. Значит контракт сегодня и не рассчитан
на воспроизведение центральной схемы — он описывает упрощённый worker-участок.
