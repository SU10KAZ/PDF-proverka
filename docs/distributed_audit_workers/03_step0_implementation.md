## 1. Что это и чего здесь нет

Проверена **вся инфраструктурная цепочка** распределённого аудита на безопасной тестовой задаче — до какого-либо вмешательства в `PipelineManager`:

```
заявка на регистрацию → одобрение оператором → обмен claim-secret на токен
→ heartbeat с ресурсами → ручная выдача тестового задания → скачивание TAR-пакета
→ sha256 + манифест → безопасная распаковка → фиксированный тестовый процесс
→ события и полные логи → сборка результата → чанкованная загрузка
→ четыре проверки → скачивание оператором
```

**Чего в этом этапе нет и не должно быть** (проверяется тестами, а не обещаниями):

| Не реализовано | Как это гарантировано |
|---|---|
| Реальный аудит, интеграция с `PipelineManager` | `test_pipeline_manager_untouched` — грепом по `manager.py` |
| Вызовы Claude Code / Codex | `test_no_llm_invocation_in_worker_package` |
| Произвольные shell-команды от центра | `test_command_enum_has_no_shell`, `test_only_one_subprocess_spawn_point` |
| Нормативный этап, запись в `decisions_log.json` | подсистема к ним не обращается вовсе |
| Автовыбор воркера, «потратить до сброса», учёт лимитов подписок | не реализовано; поля протокола заложены |
| Автоудаление через 30 дней, команды удаления пакета | `retention_until` передаётся, но чистильщика нет |
| Автообновление воркера | `GET /update/manifest` отвечает `204` — контракт без реализации |
| Операторская кнопка отмены задания | команда `cancel_job` работает, кнопки на экране нет |
| S3, Redis, RabbitMQ, Kubernetes, внешняя БД, постоянный WS центр↔воркер | не введены |

## 2. Быстрый старт (пилот на одной машине)

### 2.1. Центр

```bash
# 1. Секрет регистрации — обязателен, дефолта нет намеренно
python3 -c "import secrets; print(secrets.token_urlsafe(32))"

# 2. В .env центра
DISTRIBUTED_WORKERS_ENABLED=true
DISTRIBUTED_WORKERS_BOOTSTRAP_SECRET=<вставить сгенерированное>

# 3. Запуск как обычно
uvicorn backend.app.main:app --host 0.0.0.0 --port 8081
```

Экран: **`http://<host>:8081/audit-workers`**.

Проверка конфигурации без захода в UI:

```bash
curl -s localhost:8081/api/workers/status | python3 -m json.tool
# enabled: true, config_error: null  → всё готово
# enabled: true, config_error: "...BOOTSTRAP_SECRET не задан..." → секрет не выставлен
```

> `/api/workers/status` живёт в портальном контуре: при `PORTAL_AUTH_ENABLED=true`
> нужен cookie сессии, иначе ответ `401`.

### 2.2. Воркер — регистрация в ДВА этапа

Токен не выдаётся по одному только знанию bootstrap-секрета. Регистрация —
заявка; в ответ приходит **одноразовый claim-secret**, который превращается в
токен лишь после того, как оператор одобрил воркер.

```bash
# На стороннем VPS, под ОТДЕЛЬНЫМ системным пользователем (не root)
python3 -m venv /opt/audit-worker/venv
/opt/audit-worker/venv/bin/pip install -r requirements-worker.txt

export AUDIT_WORKER_DISPATCHER_URL=https://auditmanager.app
export AUDIT_WORKER_ROOT=/var/lib/audit-worker
export AUDIT_WORKER_NAME="VPS-2 Hetzner FSN1"
export AUDIT_WORKER_MAX_SLOTS=1

# Проверка окружения БЕЗ центра: прогнать тестовый процесс локально
python -m audit_worker selftest --steps 3

# Этап 1 — заявка (секрет переносится на VPS по SSH, вне протокола)
python -m audit_worker register --bootstrap-secret '<секрет центра>'
#   → registration_status: pending, файл <root>/claim_secret с правами 0600

# ← здесь оператор нажимает «Одобрить» на экране «Аудит-воркеры»

# Этап 2 — обмен claim-secret на токен. Bootstrap-секрет БОЛЬШЕ НЕ НУЖЕН.
python -m audit_worker register
#   → token_stored: true, файл <root>/token с правами 0600,
#     claim_secret удалён (второй раз он всё равно не сработает)

python -m audit_worker run
```

Файлы состояния в `<root>`: `worker_state.json` (личность), `token` (0600),
`claim_secret` (0600, живёт только между заявкой и одобрением), каталоги
`jobs/`, `runtime/`.

**Транспорт.** Переменной, отключающей проверку TLS-сертификата, не существует
намеренно. `http://` разрешён только к `localhost`/`127.0.0.1` и только при явном
`AUDIT_WORKER_ALLOW_INSECURE_LOCALHOST=true` (dev-режим); `http://` на внешний
хост и любые схемы кроме `http`/`https` отвергаются при старте с внятной ошибкой.

## 3. Ручной smoke-сценарий

Проверяет то же, что автотесты, но руками и на живой связке (два процесса,
настоящий HTTP). Все пункты ниже прогнаны на этой ветке.

| # | Действие | Ожидаемый результат |
|---|---|---|
| 1 | `python -m audit_worker selftest --steps 3` | код 0, создан `_selftest/result/summary.json`; в выводе виден **фиксированный argv** |
| 2 | `AUDIT_WORKER_DISPATCHER_URL=http://example.com … register` | отказ на старте: «HTTP запрещён для внешнего хоста» |
| 3 | `http://127.0.0.1:8081` без `ALLOW_INSECURE_LOCALHOST` | отказ: «HTTP к localhost требует явного …=true» |
| 4 | `register --bootstrap-secret <неверный>` | `HTTP 401`, внятное сообщение без стектрейса |
| 5 | `register --bootstrap-secret <верный>` | `registration_status: pending`, `claim_secret` с правами 600, **токена ещё нет** |
| 6 | Открыть `/audit-workers` | секция «Ожидают одобрения» с карточкой, кнопки «Одобрить» и «Отклонить»; в шапке счётчик «ждут одобрения» |
| 7 | `register` (без секрета) **до** одобрения | `409`: «регистрация не одобрена» |
| 8 | Нажать «Одобрить» → `register` (без секрета) | токен получен, `claim_secret` удалён |
| 9 | Повторить `register` | второй токен не выдаётся; claim одноразовый (`409` при попытке использовать погашенный) |
| 10 | `python -m audit_worker run` | heartbeat проходит; на экране RAM/CPU/диск и слоты с пояснением «ограничивает …» |
| 11 | Форма задания (4 шага × 0,4 с) → «Отправить» | статусы: «Назначено» → «Выполняется» с полосой `k/4` → «Результат принят и проверен» |
| 12 | Кнопка «Логи» | построчный stdout тестового процесса с номерами `seq` |
| 13 | Карточка завершённого задания | SHA-256 пакета, размер, дата приёма, срок хранения |
| 14 | Кнопка «Скачать результат» | `.tar.gz`; внутри `package_manifest.json`, `payload/input/`, `payload/work/` (в т.ч. `completed.marker`), `payload/result/` |
| 15 | Убить агент `kill -9` во время прогона, запустить снова | агент сам сообщает `job_failed{code: process_lost_after_restart}`; центр показывает «Ошибка», **сам провал не объявляет** |
| 16 | Погасить **центр** во время прогона | конвейер на воркере не останавливается; агент дорабатывает и пишет архив на диск |
| 17 | Пункт 16, продолжение | локально `completed_locally` (НЕ `failed`), в журнале нет `job_failed`, в логе «результат готов, но передать не вышло — дошлю позже» |
| 18 | Поднять центр, ничего не трогая руками | агент сам досылает: события, затем архив; состояние доходит до «Результат принят и проверен» |
| 19 | То же, но событие о завершении не дошло вовсе | центр догоняет состояние законными рёбрами (`running → completed_locally → result_uploading → result_received`), а не отвечает `500` |
| 20 | Результат приходит для уже проваленной попытки | принимается **на хранение** без публикации: `superseded_result_received`, файл в `rejected_results/`, `unpublished_reason.json` с `published: false` |
| 21 | `python -m audit_worker status` | список заданий и счётчик `retention_unconfirmed` |
| 22 | Второе задание на **тот же** `project_id`, пока первое активно | `409` — одно активное задание на проект |

**Проверка выключения:** `DISTRIBUTED_WORKERS_ENABLED=false` (или переменная не
задана) + перезапуск центра → из 384 маршрутов приложения к подсистеме относятся
ровно два: `GET /api/workers/status` (отдаёт `enabled:false`) и HTML-страница
`GET /audit-workers` (честно показывает «функция отключена»). Остальные ручки
`/api/workers/*` и весь контур `/api/v1/worker/*` не зарегистрированы, файл
`workers.db` и каталог данных не создаются.

## 5. API

### Контур воркера — `/api/v1/worker/*` (bearer-токен машины)

| Метод | Путь | Назначение | Идемпотентность |
|---|---|---|---|
| POST | `/register` | заявка на регистрацию (bootstrap-секрет) | по `instance_id`; токен НЕ выдаётся |
| POST | `/claim` | обмен одноразового claim-secret на токен | строго один раз; повтор → `409` |
| PUT | `/registration` | обновление возможностей | естественная |
| POST | `/heartbeat` | живость + ресурсы + активные задания | естественная |
| POST | `/resources` | внеочередной снимок ресурсов | естественная |
| POST | `/jobs/next` | long-poll задания; `204` = нет | атомарный claim + `Idempotency-Key` |
| GET | `/jobs/{id}/source` | скачать пакет (`Range` → докачка) | естественная |
| POST | `/jobs/{id}/accept` | подтверждение принятия | `Idempotency-Key`; повтор → тот же ответ |
| POST | `/jobs/{id}/reject` | отказ от задания | по `attempt_id` |
| POST | `/events` | пакет событий | `first_seq` + курсор в одной транзакции |
| POST | `/uploads` | создать сессию загрузки | по `(job, attempt, hash)` + `Idempotency-Key` |
| GET | `/uploads/{id}` | состояние сессии (докачка) | естественная |
| PUT | `/uploads/{id}/chunks/{idx}` | чанк | по `(upload_id, idx, sha256)` |
| POST | `/uploads/{id}/complete` | завершить и провалидировать | повтор → тот же ответ |
| GET | `/commands` | забрать команды | естественная |
| POST | `/commands/{id}/ack` | подтвердить | `noop` при повторе |
| GET | `/update/manifest` | контракт обновления | всегда `204` на этом этапе |
| POST | `/reconcile` | сверка после рестарта | чистое чтение |

`Idempotency-Key` учитывает хэш тела: тот же ключ с **другим** телом — это ошибка
клиента, ответ `409 idempotency_key_reuse`, а не молчаливая подмена.

### Контур оператора — `/api/workers/*` (портальная cookie)

Собственной аутентификации у этого контура нет: он целиком опирается на
`PortalAuthMiddleware`. Поэтому при `PORTAL_AUTH_ENABLED=false` роутер **не
регистрируется вовсе** — иначе `POST /{id}/rotate-token`, отдающий живой токен
воркера открытым текстом, был бы доступен любому, кто дотянулся до порта. Для
локального пилота есть явный выключатель `DISTRIBUTED_WORKERS_ALLOW_INSECURE_ADMIN=true`;
`GET /api/workers/status` в этом случае честно возвращает `admin_api_available: false`
и текст причины.

| Метод | Путь |
|---|---|
| GET | `/status` (работает и при выключенном флаге) |
| GET | `""` (список + сводка, включая счётчик `pending`) |
| GET | `/{id}` |
| POST | `/{id}/approve` · `/{id}/reject` · `/{id}/revoke` · `/{id}/rotate-token` |
| GET | `/jobs/list` |
| POST | `/jobs` |
| GET | `/jobs/{id}` · `/jobs/{id}/events` · `/jobs/{id}/logs` · `/jobs/{id}/result` |

## 6. Безопасность тестового задания

Требование выполнено **конструкцией**, а не проверкой.

| Что центр НЕ передаёт | Почему это невозможно |
|---|---|
| shell-команду | в схеме `TestJobParams` таких полей нет (`extra="forbid"`) |
| имя исполняемого файла | путь берётся из `Path(test_process.__file__)` |
| аргументы | `build_argv()` возвращает ровно 4 элемента фиксированной формы |
| путь | `result_dir` вычисляется от каталога задания на воркере |
| переменные окружения | `build_env()` — белый список: `PATH`, `LANG`, `LC_ALL`, `HOME`, `TMPDIR` |

Разрешённая нагрузка: `label` (только `[A-Za-z0-9._-]`, ≤64), `steps` (1..100),
`step_seconds` (0..10), `result_bytes` (0..8 МиБ), `fail_at_step`.

**Три рубежа зажима**, каждый держит оборону сам:
1. центр — pydantic + проверка суммарной длительности против `DISTRIBUTED_WORKERS_TEST_JOB_MAX_SEC`;
2. воркер — `test_runner.validate_params` (отвергает неизвестные поля, зажимает диапазоны);
3. сам процесс — повторный clamp в `test_process.main`.

## 7. Инварианты и где они закреплены

| Инвариант | Реализация | Тест |
|---|---|---|
| I-01 потеря heartbeat ≠ остановка | конвейер пишет в файловый outbox, сети на его пути нет | `test_offline_run_then_late_delivery` |
| I-01 обрыв **при передаче** ≠ провал | ошибка отправки оставляет `completed_locally`, `job_failed` не порождается | `test_upload_failure_is_not_a_job_failure` |
| I-02 не признавать зомби по локальным сигналам | ребра `running → failed` для роли `center` нет в таблице | `test_center_cannot_fail_running_job`, `test_reconcile_dead_process_is_not_told_to_continue` |
| I-03 нет авто-переназначения | ребра `running → assigned` нет вовсе | `test_no_auto_reassign_edge` |
| I-04 идемпотентность событий | `UNIQUE(job_id, attempt_id, sequence)` + курсор в одной транзакции | `test_event_batch_idempotent` |
| I-05 одно исполнение | частичный уникальный индекс + `execution_token` | `test_double_assignment_blocked_by_index`, `test_execution_token_mismatch_rejected` |
| I-06 нет дубля результата | сессия по хэшу, чанк по `(upload_id, idx)` | `test_upload_session_is_idempotent` |

## 9. Известные ограничения этапа

1. **Ротация токена без grace-периода.** Старый гасится сразу, воркер надо перезапустить с новым. Grace на сутки (§20.3 техпроекта) появится вместе с автообновлением.
2. **`reconcile` при недоступности центра возвращает пустой вердикт** — агент продолжает по локальному состоянию. Это следствие I-01, а не недоделка.
3. **Отмена задания** реализована на стороне агента (`cancel_job` → `terminate_job`), но операторской кнопки на экране нет: команда ставится только через API.
4. **Компрессия — gzip.** `zstandard` в окружении отсутствует; `zstd` объявлен полем манифеста и читается, если пакет установлен.
5. **Исходный пакет синтетический** — описание задания, а не дерево `projects_v2`. Сборка настоящего пакета проекта — шаг 2 из §25 техпроекта.
6. **Слоты считаются по «лёгкому» профилю** (`RAM_PER_JOB_LIGHT = 1 ГБ`): норм-базы на воркере нет. Профиль с норм-этапом (6,5 ГБ) объявлен рядом и включится вместе с ним.
7. **`project_id` задания ограничен ASCII** (`^[A-Za-z0-9._\- ]+$`) — защита от подстановки пути. Реальные идентификаторы проектов кириллические и содержат `/` (`АР/133-23-ГК-АР5`), поэтому **перед шагом с настоящим пакетом проекта потребуется безопасное расширение шаблона** с отдельной проверкой на обход каталога. На этапе 0 не блокирует: `project_id` тестового задания — только метка.
8. **Автоудаления и команд удаления пакета нет** — `retention_until` доезжает до воркера (в heartbeat и в `reconcile`), но чистильщик не написан. Пакеты на воркере накапливаются.
9. **Операторского API управления заданием нет вовсе.** Ни отмены, ни признания попытки потерянной, ни создания повторной попытки: `repositories.enqueue_command` не вызывается ниоткуда, кроме тестов, а роль `operator` в таблице переходов достижима только при создании задания. Практическое следствие: задание, застрявшее в `running` (например, процесс пережил рестарт агента и остался без родителя), выводится из этого состояния только правкой БД. Реализация — следующий этап.
10. **Процесс, переживший рестарт агента, остаётся сиротой.** `survived_processes` его находит и не трогает, но заново подключиться к его stdout/stderr агент не умеет: событий от такого задания больше не будет, а код возврата никто не соберёт. Приемлемо для тестового задания на минуты, недопустимо для реального аудита на часы — закрывается вместе с `ExecutionBackend`.
11. **`RetentionManager` не реализован.** Срок хранения доезжает до воркера тремя путями (ответ на `complete`, heartbeat, сверка) и пишется в `metadata.json`, но по нему ничего не удаляется. Диск воркера растёт неограниченно. Инвариант I-08 при этом соблюдён: удалять просто нечем.
12. **Идентификаторы `worker_id`/`attempt_id`/`command_id`/`package_id` — 32 бита** (`uuid4().hex[:8]`), тогда как `job_id` — полный uuid4. Непоследовательно; угадывание ограничено проверками владельца, но запас стоит увеличить.
13. **Нет ограничения на число заявок регистрации** и на суммарный объём событий, принимаемых центром: знающий bootstrap-секрет может забить таблицу `workers`, а воркер — раздуть журнал. Верхнюю границу одного запроса держит только nginx.
14. **Геометрические тесты не собираются в worktree** — им нужен каталог `projects_v2/` с рабочими данными, которого в worktree нет. К этим изменениям отношения не имеет: в основном дереве те же файлы собираются (164 теста).

## 10. Что делать дальше

Порядок из §25 техпроекта, шаги 1–2:

1. **`ExecutionBackend` без удалённого режима** — ввести абстракцию, ничего не изменив в поведении: `LocalExecutionBackend.run()` = однострочный делегат в `_dispatch_action`. Критерий: `test_execution_backend_local_parity` + суточный прогон реальных аудитов без отличий.
2. **Настоящий пакет проекта** — сборка дерева версии по `is_source_file()`, переписывание абсолютных путей, гидрация кропов офлайн. Критерий: `detect_resume_stage` на распакованном пакете даёт ту же точку, что на исходном дереве. Сюда же входит расширение шаблона `project_id` из §9.7.

**Чего делать НЕ нужно** до этих двух шагов: подключать реальный аудит к удалённому исполнению, трогать `cleanup_zombies`, вводить автовыбор воркера.
