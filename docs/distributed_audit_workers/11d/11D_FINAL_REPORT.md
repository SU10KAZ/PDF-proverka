```

  → конвейер САМ читает (prompt_builder._read_md_file, text_source="md")

  → pipeline_bridge: белый список этапов, потолок вызовов, заявка в журнале
  → ProviderAdapter.structured_inference(model=claude-opus-5)
     --tools=  --disallowed-tools=…  --max-turns 1  --safe-mode
     --setting-sources=  cwd = пустой runtime попытки, env с нуля, промпт в stdin
  → Claude CLI 2.1.220 → подписка владельца .31
  → structured JSON
  → боевая проверка: 13 именованных утверждений
  → guard пути записи
  → КОНВЕЙЕР САМ ПИШЕТ 02_text_analysis.json
  → боевой раннер: validate_and_repair_json, обязательный text_findings, md_prescan
```

## 19. Ограничения

1. **Калибровка severity.** Ноль КРИТИЧЕСКИХ против трёх исторических; одна из
   трёх критических тем не найдена вовсе. Причина не установлена.
2. **Блочный контекст не вкладывается.** Если `01_blocks_for_text.json` уже
   собран, provider-режим **отказывается работать**, а не тихо игнорирует его.
   Для порядка «текст→блоки» это безвредно; для обратного порядка нужен
   отдельный шаг.
3. **Планировщика бюджета промпта нет.** Ветка codex умеет Tier 1/Tier 2
   (снять норм-базу, нарезать по листам), provider-режим — нет. Вместо
   молчаливого усечения стоит потолок 600 000 символов и отказ.
4. **Кастомный промпт проекта не поддерживается** — прогон отказывается, а не
   подменяет промпт стоковым.
5. **Оркестратор этапа подставной.** `PipelineStageContext` в 11D — заглушки
   логирования и учёта. Сам этап настоящий целиком; связка с `PipelineManager`
   и с центральным заданием на воркере не проверялась.
6. **Требование модели ужесточено для всех этапов, включая `provider_selfcheck`.**
   После 11D задание обязано нести `provider_requirement.capability`, иначе
   модель не назначится и вызов не состоится. Синтетический путь 11C без правки
   задания работать перестанет — это осознанное решение, а не побочный эффект.
7. **`~/.claude` владельца трогается** (mtime `sessions/`) — следствие ambient-режима.
8. **Слепое пятно проверки литералов**: если модель ответит прозой, а не JSON,
   сырой текст хранится только отпечатком, и запрещённый литерал в нём проверка
   не увидит. В этом прогоне ответ был валидным JSON.
9. **`--tools=` проверен по argv, не по наблюдению.** Позитивный контроль стоил
   бы второго оплаченного вызова (§22 запрещает).

## 20. Следующий шаг

**Один минимальный этап: `findings_merge` через тот же ProviderAdapter, в том же
изолированном рантайме, на артефактах уже выполненного 11D.**

Почему именно он:

* он следующий по конвейеру и **не требует ни новых источников данных, ни
  графики**: его вход — `02_text_analysis.json`, который 11D уже произвёл;
* его прежний промпт устроен так же, как у `text_analysis` (Read/Write tools),
  то есть проверяется переносимость **метода**, а не единичный случай;
* он даст ответ на главный незакрытый вопрос 11D — воспроизводится ли
  расхождение по severity на следующем этапе или это особенность одного промпта.

Перед ним стоит закрыть ограничение №2: `findings_merge` читает и блочный
контекст, и текстовый, поэтому потребуется решение о вкладывании второго входа
