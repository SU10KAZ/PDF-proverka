# Этап 7 — REMOTE RUNTIME GATE: запуск конвейера на удалённой ноге

**Статус: REMOTE RUNTIME GATE COMPLETE.**

Главный результат: **реальный конвейер впервые прошёл на удалённой ноге целиком
— настоящим исполнителем, настоящим дочерним процессом, настоящими
stage-runner'ами — до границы центральных этапов, и его результат совпал с
локальным.** Предыдущий этап закончился формулировкой «удалённая нога ещё не
запускается»; теперь она запускается и доходит до конца.

## 1. Почему этап отдельный

Отчёт 07 закончился вердиктом **EXECUTION BACKEND PARTIAL** с двумя
подтверждёнными блокерами (Б-3, Б-4) и списком недоказанного. Оба блокера лежат
не в логике аудита, а в стыке процессов: пакет, раскладка, конфигурация, пути
записи. Именно этот класс дефектов не видят юнит-тесты — 477 зелёных тестов
сосуществовали с удалённой ногой, которая не могла стартовать вовсе.

Поэтому этап делался не «доработкой», а сначала ВОСПРОИЗВЕДЕНИЕМ обоих блокеров
прогоном, и только потом исправлением.

## 3. Подтверждённые блокеры — перепроверка прогоном

Отчёту не доверялось: оба блокера воспроизведены до единой правки.

### Б-3. Раскладка пакета несовместима с резолвом проекта

**Как перепроверено:** собран настоящий пакет из фикстуры, распакован как это
делает агент, вызваны оба резолвера в отдельном процессе.

```
[legacy]             resolve_v2_job_paths -> None
[legacy]             resolve_project_dir  -> …/project/01_input/ТЕСТ-РД-АР1-К1.pdf  exists=True
[projects_v2_primary] resolve_v2_job_paths -> None
[projects_v2_primary] resolve_project_dir  -> …/project/01_input/ТЕСТ-РД-АР1-К1.pdf  exists=True
```

Блокер подтверждён — и оказался **хуже, чем описан в отчёте 07**. Там сказано
«такого каталога нет». На деле `resolve_project_dir` доходит до fallback'а по
суффиксу `.pdf` (`_resolve_pdf_suffixed_dir`) и возвращает **ФАЙЛ**, который
существует. Разница практическая: «не найдено» падает сразу, а «найден файл
вместо каталога» уезжает дальше по конвейеру и падает позже и непонятнее.

Дополнительно: `document.json` и `object.json` лежат ВЫШЕ каталога версии, а
сборщик сканирует только `version_dir` — то есть в пакет они не попадали вовсе.
Без `document.json` `ProjectsV2Adapter.list_documents` пропускает документ
МОЛЧА (`projects_v2_adapter.py:156-158`: `if dj is None: continue`).

### Б-4. Запись вне изоляции

`manager.py::_snapshot_output_before_codex_run` пишет снимок в
`BASE_DIR / "comparison" / "classic_codex_ab" / "backups"`, где `BASE_DIR ==
ROOT_DIR` — корень установленного кода. Путь идёт из `_dispatch_action`
(`manager.py:6459`), то есть ровно тем маршрутом, которым работает удалённая
нога, и срабатывает всякий раз, когда любая модель этапа — codex
(`_codex_models_enabled`). Единственный корень без env-override среди всех,
которые трогает конвейер.

**Раскладка версии 1 отвергается** распаковщиком воркера явной ошибкой
(`package_io.require_portable_layout`), а не «не находится».

**Метаданные чистятся от абсолютных путей центра** (`sanitize_metadata_blob`,

Новые поля манифеста: `portable_projects_root`, `object_folder`, `object_id`,

## 7. Runtime configuration snapshot

`backend/app/services/distributed_workers/runtime_config.py`.

Манифест описывает АРХИВ, нагрузка описывает ЗАДАНИЕ. Третьего документа — как
настроен сам процесс — не было, и именно на этом стыке лежало ограничение 4
отчёта 06.

`AuditRuntimeConfigSnapshot`: `extra="forbid"`, `frozen=True`, собственный
SHA-256 по КАНОНИЧЕСКОМУ представлению (сортировка ключей, без пробельного шума
— иначе переупаковка меняла бы хэш).

Поля: `snapshot_version`, `pipeline_revision`, `protocol_version`,
`package_manifest_version`, `execution_profile`, `project_layout_version`,
`projects_v2_write_mode`, `include_norms`, `provider_mode`,
`stage_model_mapping`, `prompt_bundle_hash`, `model_config_hash`,
`feature_flags`, `feature_flags_hash`, `output_schema_versions`,
`path_policy_version`, `environment_policy_version`, `created_at`.

Правила, каждое против конкретного класса дефекта:

* **умолчаний у обязательных полей нет** — умолчание означает «воркер додумал за
  центр», а додумывает он из окружения ЧУЖОЙ машины;
* **неизвестное поле — отказ**, а не игнор;
* **порядок «структура → хэш → совместимость → применение»** — обратный дал бы
  «хэш сошёлся» для документа, который мы не умеем интерпретировать;
* **применённое значение читается ОБРАТНО у фасада** — «мы выставили переменную»
  и «фасад видит то же» это разные утверждения, и evidence обязан содержать
  второе;
* **секретов нет структурно** (`assert_no_secrets` проверяет и имена, и значения).

Хэш — обязательное поле нагрузки `AuditPipelineParams.runtime_snapshot_hash`;
задание без снимка воркер не исполняет. Применённый снимок пишется в
`<attempt>/metadata/applied_runtime_config.json` и в манифест результата.

Закрыто отдельно и доказано прогоном.

## 9. Environment allowlist

`build_env` собирает окружение С НУЛЯ, а не копирует `os.environ` с последующей
чисткой: чистка знает только то, что в неё внесли.

Наследуется четыре имени: `PATH`, `LANG`, `LC_ALL`, `TZ`, плюс при наличии
`LD_LIBRARY_PATH`, `SSL_CERT_FILE`, `SSL_CERT_DIR` (без них интерпретатор на
части VPS не стартует; путей к данным среди них нет).

`HOME` и `TMPDIR` из списка **убраны**: их значения вычисляются от каталога
попытки.

Всё остальное — вычисленные корни (§10). Токенов, адреса центра, ключей
провайдеров и write mode хоста в окружении дочернего процесса физически нет.

## 12. Runtime write guard

Поиск файлов ПОСЛЕ прогона доказывает только то, что файл остался лежать.
Запись во временный путь, запись с последующим удалением и запись в чужой
каталог, который потом подмели, так не ловятся вовсе.

Поэтому запись перехватывается в момент совершения: `sitecustomize.py`
(`tests/distributed_audit_e2e/isolation.py`) патчит `builtins.open`, `os.open`,
`mkdir`, `makedirs`, `rename`, `replace`, `remove`, `unlink`, `rmdir`, `link`,
`symlink`. Запись вне allowlist **убивает процесс кодом 96** — исключение
поймал бы fail-soft `except OSError` конвейера.

Разрешены `/dev`, `/proc`, `/sys` (без них не стартует ни интерпретатор, ни
subprocess) и явные корни прогона.

**Самопроверка обязательна и двусторонняя:** запрещённая запись обязана убить
процесс, разрешённая — пройти. Без второй половины «прогон упал» и «сторож
слишком строг» неразличимы.

Дополнительно корень установленного кода на время прогона переводится в `0555`.

## 13. Executor и дочерний процесс

Граница «исполнитель → дочерний процесс конвейера» не обходится: именно она
ломалась всё предыдущее время.

* исполнитель — настоящий `python -m audit_worker executor --root … --max-jobs 1`
  отдельным процессом (`start_new_session=True`);
* дочерний процесс порождает `audit_runner.run_audit_job` через
  `subprocess.Popen`, `shell=False`, argv фиксирован:
  `[python, "-u", "-m", "backend.app.pipeline.remote_audit_runner", <spec>]`;
* доказательство — запись, которую делает САМ исполнитель в реестре процессов
  (`register_process` из `on_start`): pid, `process_group_id` и отпечаток argv.
  Snapshot `ps` как первичное доказательство не годится: короткий прогон
  успевает закончиться между опросами, и «не поймали» стало бы неотличимо от
  «не было».

Отпечаток сверяется с ожидаемым, вычисленным независимо:

```
[OK] argv дочернего процесса — фиксированный audit_pipeline_v1 entrypoint
```

## 14. Граница этапов на воркере

Разрешённый план профиля задан В КОДЕ воркера
(`remote_audit_runner.WORKER_STAGE_PLAN`), а не приходит JSON'ом от центра:
`crop_blocks`, `block_context`, `block_analysis`, `text_analysis`,
`findings_merge`, `findings_review`, `optimization`, `optimization_review`.

`FORBIDDEN_STAGES` — `norm_verify`, `decision_carryover`, `debt_control`,
`excel`. Запрет стоит теперь в ЧЕТЫРЁХ местах, и четвёртое добавлено этим
этапом:

1. валидатор `retry_stage` в модели задания;
2. `FORBIDDEN_STAGES` в `load_spec` — тоже только для явного `retry_stage`;
3. процессный гейт `AUDIT_PIPELINE_CENTRAL_STAGES_DISABLED` — единственный, что
   останавливает `action="full"`;
4. **`audit_stage_history` — проверка ФАКТИЧЕСКОЙ истории после прогона.**

Четвёртый существен: первые три проверяют, что этап не БУДЕТ запущен; четвёртый
— что он не БЫЛ запущен. Гейт стоит в четырёх местах менеджера, и пятое место,
которое однажды появится, поймает именно эта проверка. Нарушение обрывает
прогон и не даёт собрать пакет.

Фактический прогон:

```
completed_stages       : block_analysis, block_context, crop_blocks,
                         findings_corrector, findings_critic, findings_merge,
                         gemma_enrichment, optimization, optimization_critic,
                         text_analysis
forbidden_stages_not_run: norm_verify, decision_carryover, debt_control, excel
```

## 15. Fake providers

Поддельные CLI — отдельные процессы, соблюдающие фактический контракт обоих
бинарей (разбор argv `-o`/`--output-last-message`, два разных конверта,
эмуляция Write-инструмента). Журнал вызовов пишется внутрь каталога попытки
(`logs/fake_provider_calls.jsonl`) и уезжает в пакет результата.

**Коллекции сделаны НЕПУСТЫМИ.** Первая версия возвращала пустые списки с
доводом «E2E проверяет транспорт, а не качество аудита». Для узкой parity довод
неверен: при нуле замечаний дедуп в `findings_merge`, критик, корректор, подписи
блоков и обогащение листом/страницей не выполняются НИ НА ОДНОЙ стороне, и
совпадение проекции доказывает лишь то, что обе стороны ничего не делали.
Значения детерминированы, поэтому сравнение по-прежнему сравнивает конвейер, а
не случайность. Smoke отдельно проверяет, что набор непустой.

Фактический прогон — 6 вызовов:


## 27. Адверсариальные находки

Четыре независимые проверки, только на чтение, ни одна не правила файлы. Темы:
(1) раскладка пакета и резолвер, (2) runtime-конфигурация и пути, (3)
подлинность живого прогона, (4) пакет результата и parity.

Итог: **они нашли 34 подтверждённых дефекта на ЗЕЛЁНОМ прогоне 53/53**, включая
один, который обесценивал две главные гарантии этапа. Это и есть главный
результат раздела.

### 27.1. Обесценивало заявленные гарантии

**Ни один guard не был взведён в ДОЧЕРНЕМ процессе конвейера** — единственном,
который выполняет аудит. `audit_runner.build_env` собирает окружение с нуля и
ПЕРЕЗАПИСЫВАЕТ `PYTHONPATH` корнем установленного кода, поэтому `sitecustomize`
стенда до него не доезжал. Утверждения «внешних соединений не было» и «записей
вне каталога попытки не было» относились к исполнителю и подделкам, но не к
конвейеру. Закрыто без правки боевого кода: штатная настройка
`AUDIT_WORKER_PIPELINE_PYTHON` + обёртка, восстанавливающая окружение guard'ов и
передающая управление через `execv` (тот же процесс — pid, группа и отпечаток
argv остаются валидными). Добавлена самопроверка ОБОИХ сторожей именно в этом
интерпретаторе: 96 на запись наружу, 97 на внешний адрес.

**Сторож записи не перехватывал `Path.write_text`** — доминирующий примитив
записи в этом репозитории. `pathlib` зовёт `io.open`, а это ОТДЕЛЬНАЯ ссылка на
ту же функцию: патч `builtins.open` её не трогает. Самопроверка проходила,
потому что пробовала ровно тот примитив, который перехвачен. Перекрыты
`io.open`, `Path.open`, `Path.write_text`, `Path.write_bytes`, `Path.mkdir`,
`Path.unlink`.

**Текст в модель брался из установленного кода, а не из сверенного снимка.**
`task_builder._EN_DIR` якорился на `BASE_DIR`; `verify_snapshot` при этом сверял
`prompt_bundle_hash` и рапортовал о совпадении, которого для английской половины
шаблонов не было.

**Снимок пропускал режим записи, при котором раскладка не резолвится вовсе.**
Раскладка 2 работает только в `projects_v2_primary`; в двух других режимах
`resolve_project_dir` возвращает ФАНТОМНЫЙ путь, и прогон падает часами позже
как «нет PDF». Класс дефекта известен и повторялся трижды.

### 27.2. Проверки, которые не могли провалиться

| Проверка | Почему была зелёной по построению |
|---|---|
| «настоящие claude/codex не запускались» | снимала `ps` ПОСЛЕ выхода исполнителя, то есть по пустому множеству |
| «центральные этапы не выполнялись» | принимала ПУСТОЕ поле манифеста как успех и верила самоотчёту |
| «в корне кода не появился comparison/…/backups» | `chmod 0555` на корень не защищает УЖЕ существующий `comparison/` |
| «в окружении нет ключей провайдеров» | имена безусловно вычищались строкой выше |

Все четыре переделаны: живые снимки дерева процессов, точное множество имён плюс
независимая сверка по журналу этапов, заморозка самого каталога + канарейка по
составу.

### 27.3. Функциональные дефекты

* **`pipeline_log.json` накопительный и приезжает в пакете.** У версии, которую
  центр уже аудировал, там лежит `norm_verify: done` с прошлого раза — и
  проверка §14 обвинила бы безупречный многочасовой прогон в том, что сделал
  центр месяцем раньше, на самом последнем шаге. Сравнивается ДЕЛЬТА.
* **Режим провайдеров из снимка не обязывал:** воркер с
  `AUDIT_WORKER_ALLOW_REAL_LLM=true` мог исполнить настоящими моделями задание,
  заказанное как `fake`, а в манифест уехало бы «fake».
* **`allow_real_llm` не попадал в спеку** — `assert_compatible` всегда получал
  False, и настройка воркера не работала ни в одну сторону.
* **Второй, негейтованный `load_dotenv`** в `model_control_service` возвращал
  ключи платных провайдеров одним импортом.
* **`01_blocks_analysis.json` и `02_text_analysis.json` не были обязательными:**
  прогон, где есть только `03_findings.json`, — форма известного инцидента
  «нога провайдера молча отвалилась», и он проходил транспорт как успешный.

### 27.4. Честность манифеста и parity

* `absolute_paths_present: false` утверждалось безусловно, при том что
  СОДЕРЖИМОЕ артефактов несёт абсолютные пути каталога попытки. Поле
  вычисляется, нарушители перечисляются, маркеры выводятся из фактического
  каталога попытки, а не из фиксированного списка шести префиксов.
* `external_network_attempts` было «ноль по умолчанию» — аттестация, которую не
  производит ни одна строка кода. Теперь `None` означает «не измерялось».
* Санитайзер метаданных видел только ПРЯМЫЕ значения словаря: список путей и
  вложенные структуры проходили насквозь при `cleared_absolute_paths: []`.
* Правило parity «ключ на `_s`/`_ms` волатилен» вычищало инженерные величины в
  л/с и м/с — то есть удалённая нога могла посчитать расчётный расход иначе при
  зелёной проверке. Отметки времени распознаются по ЗНАЧЕНИЮ (ISO-8601), ключ
  остаётся.
* `meta` вырезался целиком вместе с атрибуцией по детекторам и сводкой качества.
* Сравнивались 3 артефакта из 6 возвращаемых.
* Symlink в `result/`, `usage/`, `logs/` упаковывался по цели.

### 27.5. Что проверки признали корректным

Настоящий Executor породил настоящий дочерний процесс (запись реестра процессов,
pid, группа, отпечаток argv); настоящие stage-runner'ы прошли разрешённую
последовательность (13 записей журнала с разными длительностями); подделки —
внешняя граница, без подмены LLM-слоя в процессе; самопроверки обоих сторожей
идут ДО прогона и покрывают обе стороны; целостность кода возврата стенда (любой

## 26. Готовность к полному центральному E2E

**Готово.** Удалённая нога проходит целиком, результат воспроизводим и не
зависит от машины, пакет результата валиден и содержит доказательства того, что
применялось.

Следующий этап — центральный контур: приём результата на живом центре, откат
применения, `detect_resume_stage`, нормативный этап и финальная генерация,
полное семантическое сравнение local/remote, usage и `paid_cost`, кнопка на
странице проекта.

**Это НЕ означает** готовности к тестовому VPS: до него остаются §24 п. 1–5, в
первую очередь профили дисциплин (п. 5) и центральный хвост (п. 1).
