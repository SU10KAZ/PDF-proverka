## 1. Цель этапа

Этап 3.5 закончился вердиктом **HARDENING PARTIAL** с двумя пунктами, из-за
которых подключать реальный аудит было нельзя (§29 и §30 отчёта 04):

1. **ролей у операторов нет** — любой аутентифицированный пользователь портала
   мог отменить попытку, признать её потерянной, заказать удаление данных с VPS
   и ротировать worker-token. Журнал фиксировал, кто это сделал, но не
   ограничивал никого;
2. **`max_slots > 1` не проверялся** — исполнитель механически поддерживал
   несколько попыток, но агент вёл ровно одну, и параллельная работа не
   тестировалась. Реальные аудиты идут часами, и однослотовый воркер бесполезен.

Задача этапа — закрыть ровно эти два, ничего не расширяя.

## 5. Исследование portal auth (ответы по фактическому коду)

Читалось: `backend/app/core/portal_auth.py`, `backend/app/api/routers/auth.py`,
`backend/app/main.py`, `frontend/static/js/portal_auth.js`,
`docs/portal_auth.md`.

1. **Есть ли уже ролевая модель?** Нет. `portal_auth` — логин/пароль без БД
   пользователей: `PORTAL_AUTH_USERS` = `имя:pbkdf2-хеш` через запятую. Слова
   «роль» в модуле нет.
2. **Есть ли понятие администратора?** Нет. Все вошедшие равны.
3. **Есть ли стабильный immutable subject?** Да — **username**. Он и ключ в
   `PORTAL_AUTH_USERS`, и полезная нагрузка подписанной сессии (`{"u": …}`).
   Email в системе нет вовсе, отдельного user id — тоже.
4. **Можно ли переиспользовать существующий permission-check?** Нечего
   переиспользовать: проверок прав в портале нет. Поэтому взят третий вариант
   §7 задания — минимальная конфигурация подсистемы поверх СУЩЕСТВУЮЩЕЙ
   аутентификации. Вторая система пользователей не заводилась: пароли, сессии и
   их проверка остались в `core/portal_auth`.
5. **Что пользователь может подделать?** Тело, query, любые заголовки,
   localStorage. Подделать нельзя ровно одно — подпись cookie (HMAC-SHA256 на
   `PORTAL_SESSION_SECRET`). Поэтому субъект берётся ТОЛЬКО оттуда.
6. **Что при `PORTAL_AUTH_ENABLED=false`?** Middleware пропускает всё, а
   `request.state.portal_user` не выставляется — субъекта нет вовсе. На этапе
   3.5 операторский роутер в этом режиме просто не монтировался (кроме явного
   `DISTRIBUTED_WORKERS_ALLOW_INSECURE_ADMIN`). Теперь этого мало: см. §8.
7. **Как определялся actor в журнале?** `audit_workers_admin._actor()` читал
   `request.state.portal_user`, а при его отсутствии писал
   `operator:anonymous` — и действие всё равно выполнялось.

монтируется, и просмотровые ручки дают **404**; при

любое изменение — 503 (см. §8). Ответа «403» эта строка не производит ни при
каком сочетании — обозначение «403/503¹» осталось от общей колонки и означает
«закрыто», а не конкретный код.

**Чем на самом деле является insecure-admin.** Формулировка «читать нечего
опасного» неточна: под правом `view` лежат скачивание пакета результата
(`…/result`), логи выполнения и снимок ресурсов воркера. То есть в этом режиме
любой, кто дотянулся до порта, выкачает результаты аудита. Смягчающее
обстоятельство ровно одно: в этом режиме без аутентификации работает и весь
остальной портал, так что относительно него эскалации нет. Режим предназначен
для локального пилота и на слушающем `0.0.0.0` включаться не должен.

**Настроек retention через API нет** — они задаются переменными окружения на
самом воркере (`AUDIT_WORKER_RETENTION_*`), и включить физическое удаление
удалённо нельзя ни от какой роли. Это не пробел матрицы, а свойство модели:
центр не управляет диском чужого VPS.

Агентский контур (`/api/v1/worker/*`) в матрицу не входит: у него своя
аутентификация bearer-токеном, портальная cookie там не работает и не должна
(`test_portal_session_is_not_accepted_by_worker_api`).

## 8. Fail-closed

Порядок ветвлений в `authorization.require_permission` и есть fail-closed:

| Условие | Ответ | Почему |
|---|---|---|
| `DISTRIBUTED_WORKERS_ENABLED=false` | **404** | маршрута как бы нет |
| `PORTAL_AUTH_ENABLED=false`, изменяющее действие | **503** `portal_auth_disabled` | субъекта нет — проверять право не у кого |
| `PORTAL_AUTH_ENABLED=false`, просмотр, `ALLOW_INSECURE_ADMIN=true` | 200 | читать нечего опасного, режим признан явно |
| нет сессии портала | **401** | |
| конфигурация ролей не разобрана | **503** `role_config_invalid` + диагностика | |
| роли нет / прав нет | **403** `permission_denied` + требуемое право | |

Ключевое изменение против этапа 3.5: `DISTRIBUTED_WORKERS_ALLOW_INSECURE_ADMIN`
**больше не открывает изменяющие ручки**. Раньше он поднимал операторский
роутер целиком, и «локальный пилот» означал «можно всё без входа». Теперь он
даёт только просмотр (`test_real_main_closes_operator_api_without_portal_auth`).

Отказ происходит **до** обращения к БД, создания WorkerCommand, сборки пакета и
выдачи живого токена: право проверяет FastAPI-зависимость, то есть до входа в
тело обработчика. Проверено содержательно, а не по коду:
`test_denied_request_changes_nothing` сверяет состояние попытки, список
WorkerCommand и журнал решений до и после отклонённого запроса.

Пустая конфигурация ролей не даёт прав никому — `test_empty_role_config_grants_nothing`.
Это не сбой, а намерение: «не настроено» ≠ «разрешено всем».

## 9. CSRF

Отдельного слабого механизма для audit-workers не заводилось: используется тот
же рубеж, что и на этапе 3.5, — `SameSite=lax` у портальной cookie плюс
обязательный `X-Requested-With: audit-workers` на всех изменяющих ручках.
Межсайтовый «простой» POST такого заголовка не поставит, а запрос с ним
становится preflight'ным и отбивается CORS (CORS-разрешений в приложении нет).

Что рубеж даёт честно: защиту от межсайтового запроса. Чего не даёт: защиты от
XSS в самой странице — same-origin скрипт выставит любой заголовок. От XSS
защищает то, что экран нигде не собирает HTML из данных (§10, §33).

Проверки: `test_missing_intent_header_is_rejected`,
`test_wrong_intent_header_is_rejected`, `test_correct_csrf_with_permission_passes`.

Worker API портальный CSRF-токен как авторизацию не принимает и портальную
cookie не признаёт: `test_portal_session_is_not_accepted_by_worker_api`,
`test_worker_token_gives_no_operator_rights`.

## 10. UI permissions

`GET /api/workers/me` возвращает только собственные разрешения вызывающего:
`subject`, `role`, `permissions`, флаги `can_view/can_operate/can_admin` и
диагностику, если прав нет. Чужих субъектов и списков в ответе нет
(`test_me_never_leaks_other_subjects`). Ручка отвечает и без прав — иначе экран
не смог бы честно сказать «недостаточно прав».

Оговорка про экран: вызова ротации токена на странице НЕТ (`grep rotate` по
`audit-workers.js` и `audit-workers.html` — ноль совпадений). Ручка доступна
только прямым `POST /api/workers/{id}/rotate-token` и защищена
`require_admin` + гейтом намерения. То есть экран сейчас консервативнее
серверной модели, а не наоборот.

`frontend/static/js/audit-workers.js`:

* наблюдатель видит read-only экран; опасные кнопки отрисованы, но `disabled` и
  с подсказкой «Недостаточно прав для этого действия». Прятать их полностью
  хуже: человек не поймёт, действие исчезло или экран сломался;
* оператор получает действия над заданиями, администратор — над воркерами,
  токенами и сводным журналом;
* роль НЕ хранится в `localStorage`/`sessionStorage` и не отправляется обратно
  в запросе (`test_frontend_reads_permissions_from_server_only`);
* разметка строится `createElement` + `textContent`; `innerHTML`, `outerHTML`,
  `insertAdjacentHTML`, `document.write` отсутствуют
  (`test_frontend_has_no_html_injection_points`);
* worker-token показывается один раз в ответе на ротацию и доступен только
  администратору; bootstrap-secret на экран не попадает никогда.

Отключённая кнопка ничего не защищает — это записано в коде рядом с ней. Сервер
отвечает 401/403 на прямой HTTP-запрос независимо от того, что нарисовано
(`test_viewer_cannot_touch_attempt`, шаг 5 ролевого smoke).

## 11. Operator audit log

Таблица `worker_admin_actions` получила две колонки (миграция 4): `actor_role` и
`permission`. Без них запись отвечает на «кто», но не на «на каком основании».

Полный состав записи разрешённого опасного действия: `actor_id` (из сессии),
`actor_display_name`, `actor_role`, `permission`, `action_type`, `worker_id`,
`job_id`, `attempt_id`, `reason`, `previous_state_json`, `requested_state_json`,

**Отклонённые опасные запросы** пишутся в существующий сквозной журнал

## 12. Конфигурация ролей

```
DISTRIBUTED_WORKERS_VIEWER_SUBJECTS=ivan,petr
DISTRIBUTED_WORKERS_OPERATOR_SUBJECTS=semyon
DISTRIBUTED_WORKERS_ADMIN_SUBJECTS=Андрей
```

Значения — **логины портала** (те же строки, что слева от `:` в
`PORTAL_AUTH_USERS`). Разделители: запятая, точка с запятой, перевод строки.

Правила разбора (`authorization.load_role_config`):

* NFC-нормализация — «й» в двух кодировках не должно давать двух пользователей;
* **регистр учитывается**: «Ivan» с правами «ivan» — тихое расширение прав, а
  не удобство (`test_role_config_parses_lists_and_normalizes_unicode`);
* `*` и `?` запрещены — один символ не должен отключать защиту
  (`test_role_config_rejects_wildcards_and_closes_access`);
* управляющие символы и длина > 200 отвергаются;
* **любая ошибка разбора закрывает доступ ВСЕМ**, а не только виновной строке;
* пустой список прав не даёт; конфигурация читается на каждый запрос — правка
  `.env` + рестарт backend меняет права, кэша инвалидировать не нужно;
* субъект в нескольких списках получает высшую роль — `admin` и так включает
  `operate`, запрещать это бессмысленно (`test_highest_role_wins_for_subject_in_two_lists`).

Списки живут только на сервере: на фронтенд не отдаётся ни одного чужого имени.

## 13. Модель max_slots=2

`backend/app/services/distributed_workers/slots.py` и зеркало
`audit_worker/slots.py`. Дублирование намеренное: пакет воркера ставится на
чужой VPS отдельным комплектом и не имеет ни одного импорта из `backend`.
Совпадение правил закреплено тестом `test_worker_normalization_mirrors_center`.

```
MAX_VERIFIED_SLOTS = 2     # доказано этим этапом
DEFAULT_MAX_SLOTS  = 1     # значение по умолчанию не менялось
```

`normalize_max_slots` (таблица из `test_max_slots_normalization`):

| Вход | Результат | Предупреждение |
|---|---|---|
| не задано, `""` | 1 | нет |
| 1, 2 | как есть | нет |
| 0, −1 | 1 | «значение меньше единицы» |
| 3, 5 | **2** | «доказан максимум 2… поддержка 3–5 НЕ проверялась и не заявляется» |
| `"две"` | 1 | «нечисловое значение» |
| `True` | 1 | «логическое значение вместо числа слотов» |
| 6 и больше | **2** | то же, что для 3–5 |

Предупреждение возвращается в ответе `approve` (`slot_limit_notice`), видно на
карточке VPS и печатается воркером в stderr при старте. Молчаливое зажатие
оставило бы оператора в уверенности, что у него пять слотов.

Границы pydantic в моделях (`le=64`) — санитарный предел против абсурдного
ввода, а не заявление о числе слотов. Единственный потолок системы —
`MAX_VERIFIED_SLOTS`, и он применяется зажимом с объяснением. Раньше в моделях
стояло `le=5`: 3–5 зажималось с предупреждением, а 6 отбивалось голым 422, и
OpenAPI-схема публично обещала пять слотов, которых нет (§30.3, находка 31).

**Где значение обязано стоять.** `AUDIT_WORKER_MAX_SLOTS` ставится в ОБОИХ
systemd-юнитах и в `approve` на центре — три места должны говорить одно и то
же. Центр берёт МИНИМУМ из одобренного оператором и заявленного агентом в
heartbeat, поэтому значение только у исполнителя (или только у агента) даёт
эффективный лимит 1 при внешне верной настройке.

**Где ветка мёртвая.** `slots.worker_max_verified_slots` сначала читает колонку
`max_verified_slots`, которую миграция 4 объявляет `NOT NULL DEFAULT 1`, —
значит запасное чтение из `capabilities` недостижимо (а `capabilities` хранится
строкой JSON, и проверка `isinstance(..., dict)` для неё всё равно ложна).
Колонку пишет только heartbeat. Практическое следствие: между `approve` и
первым ударом сердца центр держит лимит 1. Само-лечится за один интервал
heartbeat; трогать не стали, чтобы не менять схему ради косметики.

Capability `max_verified_slots=2` едет и в `capabilities` при регистрации, и в
heartbeat. Старый воркер поля не пришлёт — для него это 1, и это честный ответ:
доказательств двух слотов у его сборки нет.

## 14. Центральный reservation

`repositories.claim_next_job_for_worker`. Всё — внутри одной транзакции
`BEGIN IMMEDIATE`:

1. выбрать задание воркера в состоянии `assigned` с `attempt_disposition='active'`;
2. посчитать занятость по СВОЕЙ базе (`_attempts_for_slots` + предикаты §16);
3. вычислить эффективный лимит (или взять переданный);
4. понизить его подсказкой воркера (см. ниже);
5. если занято ≥ лимита — `SlotLimitReached`, задание остаётся `assigned`;
6. иначе условный `UPDATE … WHERE execution_state = 'assigned'` и запись
   перехода в `job_state_transitions`.

SQLite сериализует писателей, поэтому два одновременных `/jobs/next` физически
не могут перескочить лимит: проигравший увидит уже обновлённую занятость.
Проверено настоящей гонкой двух потоков —
`test_two_concurrent_jobs_next_never_exceed_limit` (ровно один 200 и один 409).

**Что именно транзакционно свежо, а что нет** (уточнено после независимой
сверки). Внутри транзакции читается ЗАНЯТОСТЬ — на каждой итерации цикла
ожидания. Сам ЛИМИТ вычисляется один раз в роутере ДО входа в цикл и передаётся
во все итерации как `limit_override`, поэтому его возраст доходит до `wait_sec`
(потолок 60 с). Отзыв регистрации, уход воркера в offline или критический диск,
случившиеся внутри этого окна, текущий вызов не увидит — увидит следующий.
Сторона ошибки безопасная в том смысле, что лимит на момент снимка уже прошёл
все обнуляющие проверки; но «лимит проверяется в той же транзакции» было бы
неточной формулировкой (§32.1 п.26).

**Эффективный лимит** (`slots.effective_limit`) — минимум из: настройки
оператора, заявленного воркером `configured_max_slots`, capability
`max_verified_slots`, `MAX_VERIFIED_SLOTS`, состояния регистрации, связи с
агентом, состояния исполнителя, уровня диска и совместимости
`protocol_version`. Любое из них умеет обнулить лимит — правильная сторона
ошибки: невыданный слот стоит ожидания, лишний выданный — второго процесса там,
где его не ждут (`test_effective_limit_is_minimum_of_all_constraints`).

**Центр не верит воркеру.** Заявленный `free_slots` — это «сколько возьму ещё»,
а не лимит; вместе с `busy_slots` из того же снимка он переводится в абсолютный
потолок как `min(лимит центра, занято У ВОРКЕРА + заявленное)` и может лимит
только **понизить** (`test_center_does_not_trust_inflated_free_slots`,
`test_worker_capacity_hint_is_not_anchored_to_center_occupancy`).

**Граница гарантии, названная точно.** Одновременно ВЫПОЛНЯЮЩИХСЯ попыток — и
значит процессов на VPS — не бывает больше двух: в работу уходит только то, что
прошло через `claim_next_job_for_worker`, а он выбирает исключительно `assigned`
и сверяется с лимитом в своей транзакции. Отдельно от этого СЧЁТЧИК занятости
может показать значение выше лимита («3/2») — если оператор отменил задания,
которые воркеру ещё не выдавали: они уходят в `cancel_requested`, а это
состояние слот занимает. Ошибка консервативна (выдача блокируется, третий
процесс невозможен) и подробно разобрана в §32.1 п.24.

> Дефект, найденный на живом прогоне и исправленный здесь же: сначала
> `free_slots` подставлялся как лимит напрямую. Занятость вычиталась дважды —
> воркер с одним заданием сообщал «свободен один», центр понимал это как
> «лимит один», видел одно занятое и отказывал. Второй слот был мёртв, а тесты
> на моках этого не показывали: их поймал smoke на настоящих процессах.

Состояние исполнителя при выдаче берётся из ЗАПРОСА (`executor_status`), если
воркер его прислал, иначе из heartbeat: между ударами проходит до 30 секунд, и
«исполнитель был офлайн полминуты назад» — плохое основание отказать в работе,
которую уже есть кому делать.

## 15. Локальная ёмкость исполнителя

`Executor.local_capacity()` — второй, независимый от центра рубеж (S-16). Берёт
худшее из трёх наблюдений: живые потоки-наблюдатели, попытки в состоянии
`claimed`/`running` локальной очереди и ДОКАЗАННО живые процессы реестра
(pid + тик старта из `/proc`). Критический диск обнуляет ёмкость, но не трогает
идущие процессы.

Проверка ёмкости ушла ВНУТРЬ `local_db.claim_next(capacity_limit=…)`: подсчёт
занятых и захват — одна транзакция. Снаружи между ними было окно, в которое
проскакивал третий захват (`test_two_executors_share_one_capacity_counter`).

**Точная граница транзакционности** (формулировка исправлена после независимой
сверки). Внутри `BEGIN IMMEDIATE` сверяется РОВНО ОДИН из четырёх источников —
счётчик строк очереди в `claimed`/`running` против переданного `capacity_limit`.
Живые потоки, доказанно живые процессы реестра и уровень диска считаются в
`local_capacity` выше по коду и в транзакцию не попадают. Следствие, которое
надо знать: живой процесс, чья строка очереди уже терминальна, транзакционному
счётчику невидим — его ловит только внешняя проверка. Гарантия «два исполнителя
над одной worker.db не превысят лимит» при этом сохраняется, потому что счёт
идёт по таблице, а не по памяти процесса.

Даже если центр ошибётся и выдаст третье задание, третий процесс не стартует
(`test_executor_claims_two_and_refuses_third`). Третья попытка при этом
остаётся `queued` и ждёт слот — в `failed` из-за отсутствия ёмкости она не
переводится никогда.

## 16. Двухслотовая машина состояний

Единственный предикат — `slots.attempt_occupies_execution_slot(attempt)`.
Списки состояний живут в одном модуле и больше нигде.

```
занимает слот  = source_uploading | source_ready | accepted_by_worker
                 | running | cancel_requested          (и disposition = active)
ждёт слот      = assigned
освободил слот = completed_locally | result_uploading | result_received
                 | validating | completed | failed | cancelled
                 | superseded_result_received
```

**`assigned` НЕ занимает слот — и это отход от буквы §16 задания.** Обоснование:
в этой архитектуре назначение делает ОПЕРАТОР при создании задания (ADR-004,
автовыбора нет), поэтому `assigned` означает «лежит в очереди центра», а не
«исполняется на VPS». Если считать его занятым, три созданных задания при
лимите 2 заблокировали бы выдачу даже первого — включая тот случай, когда на
воркере не идёт ничего. Граница проведена по факту передачи работы воркеру.

`cancel_requested` слот занимает до фактического подтверждения: пока воркер не
ответил, процесс может работать (I-06) —
`test_cancel_requested_holds_slot_until_worker_confirms`.

`result_uploading` слот НЕ занимает: процесс уже завершён, а передача архива
ограничивается сетью и диском (`test_result_uploading_does_not_hold_execution_slot`).
Освобождение слота при этом не означает разрешения удалить попытку:
неподтверждённый результат по-прежнему неудаляем (I-08, §19 отчёта 04).

**Политика по `operator_declared_lost`** (§34 задания требует явного решения):

* такая попытка НЕ занимает слот — иначе один mark-lost навсегда съедал бы
  единственный слот воркера, и задание нельзя было бы повторить вообще;
* она попадает в отдельный счётчик `unproven_remote`, который виден в API и на
  карточке VPS как предупреждение «фактических процессов на VPS может быть
  больше». Центр не изображает знание, которого у него нет;
* настоящим рубежом остаётся локальная ёмкость исполнителя (§15);
* новая попытка на воркере, с которым **нет связи**, требует явного
  `accept_capacity_risk=true` — там центр не может ни увидеть чужой процесс, ни
  попросить его остановиться
  (`test_new_attempt_on_offline_worker_requires_risk_acknowledgement`).

## 17. EventOutbox concurrency

Ограничение 17 этапа 3.5: межпроцессный замок счётчика — `flock`, а вне POSIX
он деградирует до потокового. Два процесса выдают двум событиям один номер,
центр дедуплицирует по `(job, attempt, seq)`, и второе теряется молча. На одном
слоте это редкая гонка, на двух — штатный режим.

Решение (миграция 2 `worker.db`):

```sql
event_sequences(job_id, attempt_id, next_seq, updated_at)   PK(job, attempt)
event_journal (job_id, attempt_id, sequence, event_id,
               event_type, allocated_at, written)           PK(job, attempt, sequence)
```

`LocalDB.allocate_event_sequence` под `BEGIN IMMEDIATE` увеличивает счётчик и
вставляет строку журнала ОДНОЙ транзакцией. Дубль невозможен по схеме, а не по
дисциплине кода. Пары «задание+попытка» независимы: своя строка счётчика у
каждой (`test_two_attempts_have_independent_sequences`).

`written` отличает «номер выдан» от «строка легла в сегмент». Разрыв между ними
— доли секунды, но если процесс умрёт именно там, в файлах останется дыра.
Она не прячется: `EventOutbox.heal_allocation_gaps` дописывает на это место
явное событие `events_truncated` с причиной `allocated_but_not_written`.
Потеря видима, а поток событий не встаёт навсегда на ожидании пропавшего
номера (`test_allocation_gap_is_filled_visibly_not_masked`).

Побочно исправлено следствие: `pending_batch` собирал непрерывный диапазон,
обходя строки в порядке ФАЙЛА. Порядок строк больше не равен порядку номеров
(пишут два процесса, а заполнение дыры уходит в конец файла), поэтому пакет
теперь собирается по отображению «номер → событие».

**Нагрузочная проверка** — `test_event_sequence_is_unique_across_processes`:
4 настоящих ПРОЦЕССА (`multiprocessing` spawn, не потоки), две попытки, по 120
событий на писателя, всего 480. Проверяется: ровно 240 записей на попытку, ни
одного дубля, ни одной дыры (`sorted(seqs) == range(1, 241)`), счётчики попыток
независимы. Продолжение после рестарта — `test_sequence_survives_restart`.

## 18. Два параллельных задания

Агент этапа 3.5 выполнял задание в главном цикле: `poll()` → `execute_job()`.
Второй слот при такой конструкции существует только на бумаге.

Теперь цикл получает назначение и отдаёт его отдельному потоку. Контекст
регистрируется в `_active` в ГЛАВНОМ потоке, до старта рабочего: иначе между
«получили назначение» и «поток записался» открывается окно, в котором
`_free_slots` считает слот свободным и агент забирает третье задание.

Опрос команд вынесен в собственный поток. Раньше его делал цикл ожидания
задания: при двух заданиях это два независимых опроса одной очереди и двойное
подтверждение одной команды, а при занятых слотах цикл в опрос не заходил
вовсе — отмена не доезжала, пока слот не освободится.

Досылка результатов пропускает задания, которые ведёт поток прямо сейчас: без
этого один архив уезжал бы дважды.

**Доказательство на настоящих процессах** (`test_two_real_processes_overlap_and_third_waits`
и smoke, шаги 9–13):

| Что | Как доказано |
|---|---|
| два процесса живы ОДНОВРЕМЕННО | `process_registry` + `/proc/<pid>/stat`, два разных PID |
| разные process groups | `os.getpgid(pid)` — два разных значения |
| ни один не в группе агента | сравнение с `os.getpgid(agent.pid)` |
| разные каталоги попыток | `jobs/<job_uuid>/<attempt_uuid>/…` у каждого свой |
| независимые логи | свой растущий `logs/stdout.log` у каждой попытки |
| независимые EventOutbox | свой каталог `events/`, свои счётчики в базе |
| прогресс растёт у обоих | `progress_snapshot.processed` увеличивается у A и B |
| независимые результаты | два архива, два разных sha256 |

Временная диаграмма зелёного прогона (дословно из `evidence.json`):

```
t+0.0s   overlap_start   A pid=3295965 pgid=3295965
                         B pid=3295968 pgid=3295968   ← перекрытие началось
…        прогресс и логи A и B растут независимо
t+6.2s   cancel_a        killpg(3295968) — только своя группа
t+7.4s   c_started       C занял освободившийся слот; снова ровно два: A + C
t+~10s   SIGKILL агенту → оба процесса живы, журналы растут
         агент поднят   → состав процессов не изменился {3295965, 3295995}
t+24.4s  offline_finished — обе работы доделаны при недоступном центре
```

Перекрытие здесь не косвенное: два разных PID в двух разных группах процессов
живы одновременно, и обоим растут прогресс и `stdout.log`. Последовательный
запуск такой картины не даёт.

## 19. Третье ожидающее задание

Третье задание создаётся на центре и остаётся `assigned`. Центр не отдаёт его
сверх лимита, поэтому до локальной очереди воркера оно не доезжает вовсе —
`test_two_real_processes_overlap_and_third_waits` проверяет и состояние на
центре, и отсутствие строки в `execution_queue`.

Ответ на создание честно сообщает, что будет:
`{"will_wait_for_slot": true, "queue_note": "Свободных слотов нет (2 из 2) —
задание встанет в очередь и уйдёт в работу после освобождения слота."}`.
Экран показывает это же и не блокирует кнопку: блокировать значило бы
разойтись с сервером, который возможность даёт.

После завершения A освобождается ровно один слот, C уходит в работу, и снова
одновременно ровно два процесса — B и C (smoke, шаги 19–20).

Отдельно исправлено то, что мешало этому работать: гистерезис расчёта слотов
применялся к числу СВОБОДНЫХ слотов, поэтому освобождение слота считалось
«ростом ресурсов» и ждало две минуты стабильности. Теперь сглаживается ЁМКОСТЬ,
а занятость вычитается после (`test_finished_job_frees_slot_immediately`).

## 20. Отмена одного из двух заданий

Механизм не менялся с этапа 3.5 и именно поэтому проверен заново на двух
процессах: persistent `WorkerCommand` адресован паре (job, attempt), исполнитель
доказывает принадлежность процесса четырьмя совпадениями и шлёт `killpg` ТОЛЬКО

Живая проверка (smoke, шаги 16–18 и pytest):

* оператор с правом `distributed_workers.operate` отменяет A;

## 22. Restart Executor

Механизм `Executor.recover_after_restart` с этапа 3.5 не менялся: pid жив и тик
старта совпал → не трогаем и поднимаем наблюдателя; pid мёртв и есть маркер →
доупаковываем; pid мёртв и маркера нет → `executor_interrupted` без автоповтора.
`completed.marker` обрабатывается отдельно для каждой попытки — маркер лежит в
каталоге попытки.

Дочерние процессы переживают уход исполнителя: они запускаются с
`start_new_session=True`, а systemd-юнит стоит с `KillMode=process`. Это
подтверждено живым прогоном на двух процессах — smoke, шаги 40–43 (перезапуск всех
трёх сторон подряд, после которого состояния заданий восстановлены и лишних
процессов нет).

**Честная граница:** отдельного pytest-сценария «убить исполнителя при ДВУХ
живых процессах и проверить, что новый создаёт два наблюдателя» на этом этапе
нет — есть проверка того же кода на одном процессе (этап 3.5,
`test_two_executors_never_start_two_processes`) плюс двухпроцессный smoke,
который перезапускает исполнителя в шаге 44. Это записано в §32 как
ограничение, а не выдано за проверенное.

## 24. Concurrent upload

Изоляция обеспечена ключом сессии: `upload_sessions` заводится на пару
(job, attempt), `staging_dir` строится из UUID попытки, `expected_hash` свой у
каждой. Чанки хранятся с `PRIMARY KEY(upload_id, idx)`, поэтому индекс одного
upload физически не может задеть другой; повтор чанка A не меняет B; `complete`
адресуется конкретной сессии и захватывает её арендой.

Живая проверка — smoke, шаги 30–36: две сессии, два manifest, два разных
sha256, оба результата скачиваются, множества attempt_id двух заданий не
пересекаются. Перезапуск центра и агента (шаги 40–43) обе сессии переживают.

## 25. Resource gate

Перед вторым запуском проверяются: состояние исполнителя (offline/interrupted
обнуляет лимит центра), уровень диска (critical обнуляет и центральную, и
локальную ёмкость), RAM и swap через `ResourceMonitor` (жёсткий ноль при свопе
> 1 ГБ — профиль обоих известных OOM-инцидентов), LA5 на ядро, и явная
настройка оператора.

`HARD_CAP` расчёта слотов на воркере снижен с 5 до 2: считать пять там, где
проверены два, значило бы обещать неизвестное.

Disk critical **не убивает** текущие задания и не удаляет неподтверждённые
результаты: `test_disk_critical_blocks_new_jobs_but_not_running` и
`test_executor_capacity_zeroes_on_critical_disk`. Причина блокировки
показывается в карточке VPS (`blocked_reason`).

Точную RAM на реальный аудит здесь не выдумывали: профиль остаётся лёгким
(`RAM_PER_JOB_LIGHT_GB`), тяжёлый объявлен рядом и будет измерен при подключении
ExecutionBackend.

## 30. Адверсариальные находки

Четыре независимые проверки читали готовый код против §3 этого документа:
авторизация и роли; слоты и гонки; изоляция процессов и офлайн; регрессия и
документация. Проверяющие ничего не правили — только предъявляли путь, строку и
сценарий. Подтверждённые находки и их закрытие — §30.1–30.4 ниже.

### 30.1 Найдено живым прогоном до адверсариальной проверки

* **Второй слот был мёртв.** `free_slots` воркера подставлялся в центр как
  ЛИМИТ, из-за чего занятость вычиталась дважды (§14). Тесты на моках этого не
  видели: они всегда просили ровно столько, сколько было свободно. Поймал
  двухпроцессный smoke. Закрыто разделением «лимит» и «подсказка воркера»;
* **освобождение слота ждало две минуты.** Гистерезис применялся к числу
  свободных слотов вместо ёмкости (§19). Закрыто, тест
  `test_finished_job_frees_slot_immediately`;
* **`pending_batch` обрывался на первой же перестановке номеров** — обход шёл
  по строкам файла (§17). Закрыто сборкой по номерам;
* **ничья в `binding_constraint`.** После снижения `HARD_CAP` до 2 расчёт
  слотов сообщал «ограничивает LA», хотя ограничивала настройка оператора.
  Закрыто приоритетом при равных значениях.

### 30.2 Дефект smoke этапа 3.5 (не регрессия)

Прогон smoke этапа 3.5 на этой ветке провалил одну проверку — «центральный
пакет результата на месте (I-14)». Разбор:

* инвариант **не нарушен**: центральная копия на диске есть, просто лежит в
  `superseded_results/`, а не в `validated_results/`;
* виновата сама проверка: `confirmed[0]` выбирается по порядку каталогов
  (UUID), и им может оказаться попытка, признанная потерянной, — её результат
  по построению попадает в отдельное хранилище. Проверка же смотрела только в
  `validated_results`;
* **тот же прогон на нетронутом `4cbc29eb` даёт ровно тот же провал** — то есть
  это дефект скрипта этапа 3.5, а не следствие этой работы.

Исправлена проверка (искать в обоих центральных хранилищах), а не поведение:
I-14 звучит как «удаление локальной копии не трогает центральную», а не
«результат обязан быть опубликован».

## 32. Известные ограничения

1. **Доказано ровно 2 слота.** `max_slots=2` не означает готовность к 5.
   Значение больше зажимается с предупреждением — теперь и при регистрации, и
   при одобрении, так что колонка `configured_max_slots` больше не может
   хранить 3-5 (`test_configured_max_slots_column_never_stores_more_than_proven`).
   RAM-профиль реального аудита не измерялся.
2. **Реального аудита по-прежнему нет.** Всё проверено на `test_pipeline_v1` и
   только на нём.
3. **Роли хранятся в переменных окружения.** Изменение состава требует правки
   `.env` и рестарта backend. UI управления ролями нет и на этом этапе не
   планировался.
4. **`admin` — один уровень.** Разделения «может ротировать токен» и «может
   читать журнал» нет; обе операции требуют `admin`.
5. **Отклонённые запросы пишутся только в файловый журнал** (`logs/actions/`),
   не в БД подсистемы. Ротация и хранение — общие для журнала действий портала.
6. **Ограничения частоты регистрации нет** — унаследовано с этапа 0. Готового
   rate limiter в проекте не нашлось (`ActionLogMiddleware` только пишет,
   ограничителя частоты в репозитории нет), а самодельный счётчик в памяти
   одного процесса создаёт ложное ощущение защиты: он не переживает рестарт и не
   работает при нескольких воркерах uvicorn. **Перед выставлением bootstrap-эндпоинта
   наружу это ограничение обязано быть закрыто** — на уровне обратного прокси
   либо отдельным решением.
7. **Общий прогон `tests/` + `backend/tests/`** содержит унаследованные падения,
   не связанные с подсистемой (тесты, требующие боевых данных `projects_v2` и
   внешних сервисов), а девять файлов падают ещё НА СБОРЕ — им нужны корпуса из
   `experiments/`, которых в worktree нет. Состав падений сверялся с базовым
   `4cbc29eb` построчно (§31): 118 строк, совпадение полное. Подсистемные файлы
   зелёные все.
8. **Рестарт исполнителя при двух живых процессах** проверен smoke-прогоном и
   тестами на одном процессе; отдельного pytest-сценария именно на два живых
   процесса нет (§22).
9. **Дыра «номер выдан, событие не записано»** закрывается заполнением, а не
   предотвращается. Само событие теряется — восстановить его нечем; видимость
   потери и есть гарантия.
10. **Агент, перезапущенный при НЕДОСТУПНОМ центре, не стартует.** Найдено на
    живом прогоне этого этапа: `ensure_registered` при старте делает
    `PUT /registration`, и `httpx.ConnectError` уходит наружу — процесс
    завершается с traceback. Под systemd с `Restart=always` это даёт
    крэш-луп до возвращения центра. Уже идущие процессы аудита при этом не
    страдают (их держит исполнитель, I-01/I-02), и результат не теряется — он
    доедет, когда агент поднимется. Поведение унаследовано с этапа 0, к
    двухслотовости отношения не имеет и в границы этого этапа не входило;
    закрывать его следует вместе с ExecutionBackend.
11. **Ограничения этапа 3.5 остаются в силе:** окно идемпотентности в 500
    записей, отсутствие TTL у `idempotency_keys`, аренда сборки архива 30 минут,
    long-poll держит поток обработчика, `mark_lost` не снимает
    `current_attempt_id`, миграции вперёд-только.

### 32.1 Подтверждено состязательной проверкой, но осознанно НЕ исправлено

Каждый пункт подтверждён чтением кода. Не закрыт либо потому, что лежит вне
границ этапа, либо потому, что цена правки выше пользы прямо сейчас. Молчать о
них нельзя — иначе следующий этап примет их за проверенное поведение.

12. **`lease_expires_at` локальной очереди пишется, но НИКОГДА не читается.**
    Аренда продлевается и обнуляется, сравнения со временем нет ни одного.
    Строка в `claimed`, чей исполнитель умер, освобождается только при старте
    следующего исполнителя. Под systemd с `Restart=always` это лечится
    рестартом за секунды, но поле создаёт ложное впечатление работающего
    механизма. Сравните с центральной `ASSEMBLY_LEASE_SEC`, где аренда реально
    проверяется.
13. **`worker_state` не участвует в `effective_limit`.** `draining`/`drained`
    лимит не обнуляют, а `/jobs/next` из `can_receive_jobs` смотрит только на
    диск. Три места решают вопрос «можно ли давать работу» по-разному. Сегодня
    это не эксплуатируется: `draining` никто не выставляет, а `worker_state`
    вообще перезаписывается каждым heartbeat значением от самого воркера. То
    есть механизм «слива» воркера не существует — а не «существует и дыряв».
    Заводить его следует вместе с ExecutionBackend, разом и во всех трёх местах.
14. **`instance_id` не уникален в схеме.** Скомпрометированный одобренный
    воркер может назваться чужим `instance_id` и помешать перерегистрации
    настоящей машины. Кражи токена нет (перевыпуск claim-secret закрыт), остаётся
    отказ в обслуживании. Требует миграции с уникальным индексом и разбора
    легитимных повторов — отдельная работа.
15. **`rotate_token` не смотрит на статус регистрации.** Токен выпускается и
    для `rejected`/`revoked` воркера. Использовать его нельзя (`require_worker`
    пропускает только `approved`), но после «Отозвать» → «Одобрить» доступ
    восстановится по токену, выданному ПОСЛЕ отзыва. Всё в пределах прав
    администратора; дефект гигиены, а не дыра.
16. **NFC-нормализация строже в ролях, чем в аутентификации портала.**
    `authorization` приводит субъекта к NFC, `portal_auth` сверяет логины
    побайтово. Два РАЗНЫХ портальных аккаунта, различающихся только формой
    записи «й», получат одну роль. Чинить надо в портальной аутентификации —
    это чужой слой, и правка там задевает всех пользователей портала.
17. **Битый JSON даёт 422 раньше 403.** FastAPI парсит тело до разрешения
    зависимостей. Ничего не меняется и БД не трогается, но заявление §8 «отказ
    происходит до всего» имеет это исключение, а различие 422/404 позволяет
    установить существование маршрута без входа в портал.
18. **CSP на портале нет.** Заголовков `Content-Security-Policy`,
    `X-Frame-Options`, `X-Content-Type-Options` не выставляет никто. Экран
    воркеров от XSS защищён тем, что нигде не собирает HTML из данных (§26), —
    то есть защита однослойная, и любая будущая правка `audit-workers.js`
    снимает её целиком. Заголовки — общепортальная задача.
19. **`created_by` виден роли `view`.** История попыток отдаёт
    `operator:<портальный логин>`. Для настроенных наблюдателей это законная
    операционная информация; при `ALLOW_INSECURE_ADMIN=true` её видит аноним —
    см. оговорку в §7.
20. **Отмена на воркере с ДВУМЯ живыми исполнителями.** Второй исполнитель на
    одном `worker.db` — не штатный режим, и сироты локальных команд теперь
    разбираются только когда живой сосед один (§30.3, находка 3). Полноценной
    защиты «один исполнитель на каталог» (pid-файл, advisory lock) нет.
21. **`mark-lost` на ОНЛАЙН-воркере не шлёт команду остановки.** Процесс на VPS
    продолжает работу, локальный слот остаётся занятым, центр считает свой
    свободным. Расхождение теперь ВИДНО оператору (§30.3, находка 29), но
    автоматически не разрешается: остановить процесс — отдельное решение
    оператора, и делать это неявно внутри `mark-lost` неправильно.
22. **Транзакционен только один из четырёх источников ёмкости исполнителя.**
    Внутри `claim_next` сверяется счётчик состояний очереди; потоки, живые
    процессы и диск остаются снаружи (§15). Комментарий в коде, утверждавший
    обратное, исправлен. Дыра не открывается на живом пути (цикл `_tick`
    однопоточный, а `live_process_count` читает общую worker.db), но состояние
    «процесс жив, строка очереди уже терминальна» транзакционному счётчику
    невидимо.
23. **Запасной путь исполнителя при недоступной worker.db оптимистичен.** При
    ошибке чтения занятость падает до числа своих потоков
    (`claimed = live = len(self._workers)`) — противоположно политике агента,
    который в этом случае честно возвращает ноль свободных слотов (§30.3,
    находка 14). Прикрывает только то, что при недоступной базе и сам
    `claim_next` не выполнится. Приводить обе стороны к одной политике следует
    вместе с ExecutionBackend.
24. **Счётчик занятости может показать «3/2».** Отмена задания, которое воркеру
    ещё НЕ выдали, переводит попытку в `cancel_requested`, а это состояние слот
    занимает — потому что для уже выданной попытки процесс мог идти, и центр не
    вправе считать её остановленной (I-06). Для попытки, до воркера не
    доехавшей, процесса нет, но счётчик её считает: три отмены на воркере с
    лимитом 2 дают `occupied = 3`, `occupancy_label = "3/2"`.
    Воспроизведено живой пробой и закреплено тестом
    `test_occupancy_counter_may_exceed_limit_but_only_conservatively`.
    **Ошибка идёт в безопасную сторону:** `center_free_slots` становится 0,
    следующее задание не выдаётся (`SlotLimitReached`), третьего процесса
    появиться не может — `claim_next_job_for_worker` выбирает только `assigned`,
    и отменённая попытка воркеру не уходит никогда. Само рассасывается, как
    только воркер подтвердит отмену (`not_running_locally`); на офлайн-воркере
    держится до его возвращения.
    Безопасное закрытие — отдельным шагом: переводить попытку, отменённую в
    состоянии `assigned`, сразу в `cancelled`, без команды воркеру. Это правка
    центральной машины состояний (`ALLOWED_TRANSITIONS`), и делать её заодно с
    отчётом было бы неоправданным риском.
25. **Ключ идемпотентности ротации токена глобален.** `find_admin_action_by_key`
    ищет по паре (`action_type`, `idempotency_key`) без привязки к воркеру — как
    и уникальный индекс `ux_admin_actions_idem`. Повторное использование
    администратором одного ключа заблокирует ротацию токена ДРУГОГО воркера
    (ответ 409). Поведение безопасное (отказ, а не лишняя ротация), но
    сообщение об ошибке в этом случае вводит в заблуждение.
26. **`effective_limit` считается один раз ДО цикла long-poll.** Транзакционно
    свежа только ЗАНЯТОСТЬ; сам лимит — снимок возрастом до `wait_sec` (≤60 с).
    Отзыв регистрации, уход воркера в offline или критический диск, случившиеся
    внутри этого окна, текущий вызов `/jobs/next` не увидит. Следующий увидит.

## 33. Готовность к ExecutionBackend

Оба блокирующих пункта §30 отчёта 04 закрыты: роли операторов есть,
`max_slots=2` проверен на настоящих процессах. Оставшееся для реального аудита
(и это следующий этап, а не этот):

* **ExecutionBackend и контракт с PipelineManager** — главный оставшийся шаг;
* **сборка настоящего пакета проекта** (`projects_v2`) вместо синтетического;
* **измерение RAM/диска реального аудита** и пересмотр профиля слотов;
* **лимит частоты регистрации** перед выставлением наружу (§32.6).

Точки врезки не изменились — §32 отчёта 04 остаётся актуальным. Дополнение: при
подключении реального аудита предикат `attempt_occupies_execution_slot`
менять не потребуется, а вот `MAX_VERIFIED_SLOTS` придётся повышать отдельным
этапом с собственным доказательством.

## 34. План отката

1. **Выключить флаг:** `DISTRIBUTED_WORKERS_ENABLED=false`, рестарт backend. Из
   маршрутов подсистеме остаются `/api/workers/status`, `/api/workers/me` и
   HTML-страница. База не создаётся, фоновых задач нет.
2. **Вернуть один слот:** поставить `AUDIT_WORKER_MAX_SLOTS=1` в ОБОИХ юнитах
   (`audit-worker-agent.service` и `audit-worker-executor.service`) и
   перезапустить обе службы; на центре — `approve` с
   `configured_max_slots: 1`. Идущие задания при этом не прерываются.
   Достаточно и одного из трёх мест — центр берёт минимум, — но оставлять их
   рассогласованными не стоит: следующий, кто будет поднимать лимит обратно,
   потратит время на «настроил, а не работает» (§30.3, находка 30).
3. **Убрать роли:** очистить три переменные `DISTRIBUTED_WORKERS_*_SUBJECTS`.
   **Внимание:** это НЕ открывает доступ всем — пустая конфигурация не даёт прав
   никому. Откат ролей означает «экран закрыт», а не «защита снята».
4. **Остановить воркер:** `systemctl stop audit-worker-agent audit-worker-executor`.
   Процессы аудита при этом не останавливаются — это осознанно.
5. **Откатить схему центра:** миграция 4 аддитивная (только `ALTER TABLE ADD
   COLUMN`), поэтому предыдущий код работает с новой базой без изменений —
   лишние колонки он просто не читает. Если откат всё же нужен: остановить
   backend, заменить `workers.db` копией `workers.db.before_v3_to_v4`, удалить
   `-wal`/`-shm`, запустить backend.
6. **Откатить схему воркера:** миграция 2 `worker.db` создаёт две НОВЫЕ таблицы
   и ничего не меняет в существующих. Прежний код их не видит; счётчик событий
   вернётся к файловому. Удалять таблицы не требуется.
7. **Результаты сохраняются:** `validated_results/`, `superseded_results/`,
   `rejected_results/`, `source_packages/` при откате не трогаются.
8. **PipelineManager не менялся** — откатывать нечего.

## 35. Точные границы следующего этапа

Следующий этап — **создание ExecutionBackend**. В него входит:

* `JobType.real_audit_v1` рядом с `test_pipeline_v1`;
* сборка исходного пакета из дерева `projects_v2/<version>` вместо
  синтетических `job.json` + `README.txt`;
* список обязательных артефактов реального аудита вместо
  `TEST_JOB_REQUIRED_ARTIFACTS`;
* `ExecutionBackend`, вызываемый из `executor.run_attempt` вместо
  `test_runner.run_test_job`; argv по-прежнему строит воркер;
* валидация параметров реального аудита с теми же тремя рубежами зажима;
* распаковка `_output/` в версию проекта при приёме результата;
* измерение реального потребления RAM/диска и пересмотр профиля слотов.

В него НЕ входит и требует отдельного решения: точка вызова из
`PipelineManager` (сейчас платформа о подсистеме не знает), повышение
`MAX_VERIFIED_SLOTS` выше двух, лимит частоты регистрации, подключение боевого
VPS.
