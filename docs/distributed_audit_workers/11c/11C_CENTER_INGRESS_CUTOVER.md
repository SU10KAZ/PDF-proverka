# 11C_CENTER_INGRESS_CUTOVER — план включения приёма от воркеров на боевом центре

**Статус: НЕ ПРИМЕНЁН.** Этап 11C останавливается перед этим действием. Ниже —
что именно нужно сделать, чем это проверить и как откатить. Ни одна строка
плана на боевом центре не выполнена.

Всё, что можно было проверить без него, проверено на **изолированном** стенде:
тот же объект `backend.app.main:app` под uvicorn на свободном порту, отдельный
каталог данных, отдельная SQLite, настоящий HTTP-сокет между воркером и центром.
Боевой конфигурации прогон не касался — это подтверждено сверкой sha256 файла
`.env` до и после.

---

## 1. Что сейчас выключено

| Факт | Значение |
|---|---|
| Переменная | `DISTRIBUTED_WORKERS_ENABLED` |
| Где читается | `backend/app/core/config.py:1260` → `DistributedWorkersSettings` (`services/distributed_workers/settings.py`) |
| Значение по умолчанию | `False` |
| Фактическое значение на боевом центре | не задана → выключено |

Выключено при этом **три вещи сразу**, и это важно понимать до включения:

1. **Роутер воркеров** `/api/v1/worker/*` не регистрируется вовсе
   (`backend/app/main.py:254`). Не «отвечает 403», а физически отсутствует —
   любой запрос воркера получает 404.
2. **Операторский API** `/api/workers/*`, кроме `status_router`
   (`/api/workers/status`, `/api/workers/me`), который отвечает всегда.
3. **Создание SQLite и каталогов подсистемы**: `database.ensure_ready` первым
   делом зовёт `settings.require_enabled()`.

Двойной рубеж: даже если роутер поднять иначе, `require_worker`
самостоятельно проверяет `settings.enabled` и отдаёт 404
(`services/distributed_workers/authorization.py`).

**Второй, независимый флаг** — `DISTRIBUTED_AUDIT_EXECUTION_ENABLED`
(`config.py:1309`, по умолчанию `False`). Он не про ingress, а про право
СОЗДАВАТЬ задания `audit_pipeline_v1`. Включение подсистемы воркеров реальный
аудит не включает — намеренно.

**Третий** — `DISTRIBUTED_WORKERS_BOOTSTRAP_SECRET`. Дефолта нет: при включённой
подсистеме пустой или короче 16 символов секрет даёт 503 на регистрацию. Это
фактически способ включить ingress, не открывая приём НОВЫХ воркеров.

---

## 2. Какой маршрут должен заработать

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/worker/register` | заявка на регистрацию (Bearer = bootstrap-секрет) |
| POST | `/api/v1/worker/heartbeat` | состояние воркера и провайдеров |
| POST | `/api/v1/worker/jobs/next` | long-poll за заданием |
| GET | `/api/v1/worker/jobs/{id}/source` | пакет исходников (Range-докачка) |
| POST | `/api/v1/worker/jobs/{id}/accept` | принятие задания |
| POST | `/api/v1/worker/events` | события попытки (батч по `first_seq`) |
| POST | `/api/v1/worker/jobs/{id}/result` | загрузка архива результата чанками |

Портальная cookie к ним не применяется:
`backend/app/core/portal_auth.py` — `EXEMPT_PREFIXES = ("/api/v1/worker/",)`.

---

## 3. Аутентификация воркер → центр

| Слой | Как |
|---|---|
| Регистрация | `Authorization: Bearer <DISTRIBUTED_WORKERS_BOOTSTRAP_SECRET>` |
| Рабочие маршруты | `Authorization: Bearer <worker_token>` + `X-Worker-Id` + `X-Instance-Id` + `X-Protocol-Version: 1` |
| Маршруты по попытке | дополнительно `X-Execution-Token` (перевыпускается при каждой выдаче задания) |
| Идемпотентность | `Idempotency-Key` на POST |
| Транспорт | `httpx.Client(verify=True, follow_redirects=False)`; HTTP разрешён ТОЛЬКО к localhost и только с `AUDIT_WORKER_ALLOW_INSECURE_LOCALHOST` |

Токен воркера хранится файлом `<worker_root>/token` (0600) и известен **только
агенту**: исполнитель его не читает, в окружение процесса конвейера он не
попадает, в окружение CLI провайдера — тем более (I-P2).

---

## 4. Firewall и reverse-proxy

Воркер ходит к центру **исходящим** HTTPS; входящих соединений на воркер не
нужно. Отсюда требования к центру:

1. TLS обязателен: воркер откажется стартовать с `http://` на внешний хост
   (`config.validate_transport_security`);
2. reverse-proxy (nginx/cloudflared) обязан пропускать `/api/v1/worker/*`
   **без** портальной аутентификации и без редиректов
   (`follow_redirects=False` у клиента);
3. тела запросов до 2 ГиБ (`max_package_bytes`) и чанки по 32 МиБ —
   `client_max_body_size` должен это допускать;
4. long-poll `/jobs/next` держит соединение до 25 с — таймауты proxy должны быть
   больше (`proxy_read_timeout ≥ 60s`).

## 5. Какие файлы меняются

| Файл | Изменение |
|---|---|
| `.env` боевого центра | `DISTRIBUTED_WORKERS_ENABLED=true`, `DISTRIBUTED_WORKERS_BOOTSTRAP_SECRET=<секрет ≥16 символов>`, при необходимости `DISTRIBUTED_WORKERS_DATA_DIR` |
| `.env` боевого центра (ОТДЕЛЬНЫМ решением) | `DISTRIBUTED_AUDIT_EXECUTION_ENABLED=true` — только когда решено запускать реальные аудиты |
| конфигурация reverse-proxy | правило для `/api/v1/worker/*`, если оно ещё не пропускается |

Кода менять не нужно.

---

## 6. Нужен ли рестарт

**Да.** Роутеры регистрируются на импорте `backend/app/main.py`, поэтому смена
переменной без рестарта не даёт ничего. `get_settings()` перечитывает окружение
на каждый вызов, но это влияет только на уже поднятые маршруты.

Ожидаемый простой: время рестарта uvicorn (обычно 5–15 с) плюс прогрев. Идущие
аудиты **не прерываются**: они живут в отдельных процессах и переживают рестарт
бэкенда.

Рестарт боевого бэкенда выполняется только с явного подтверждения оператора.

---

## 7. Откат

1. убрать/перевести в `false` `DISTRIBUTED_WORKERS_ENABLED` в `.env`;
2. рестарт бэкенда;
3. проверка: `GET /api/workers/status` отвечает, `POST /api/v1/worker/heartbeat`
   даёт 404.

Данные подсистемы (SQLite, пакеты) при этом остаются на месте: откат выключает
приём, а не стирает состояние. Выданные worker-токены продолжают существовать —
отзыв это отдельное действие через операторский API.

## 8. Smoke-проверка после включения

```bash
# 1. Подсистема отвечает и объявляет себя включённой
curl -s https://<центр>/api/workers/status | jq '{enabled, config_error}'

# 2. Маршрут воркера существует и требует авторизацию (401/403, НЕ 404)
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<центр>/api/v1/worker/heartbeat

# 3. Регистрация воркера с VPS (под coder, на воркере)
AUDIT_WORKER_DISPATCHER_URL=https://<центр> \
AUDIT_WORKER_ROOT=/home/coder/audit-worker \
python -m audit_worker register --bootstrap-secret '<секрет>'

# 4. Оператор одобряет на экране «Аудит-воркеры», воркер забирает токен
python -m audit_worker register

# 5. Воркер выходит на связь, реальных заданий ещё нет
python -m audit_worker agent      # в systemd-юните
curl -s https://<центр>/api/workers | jq '.workers[] | {worker_id, connectivity}'
```

Никаких заданий на этом шаге не создаётся: доказывается только приём.

## 9. Проверки безопасности после включения

| Что | Как |
|---|---|
| маршруты воркера не отдают операторских данных | `GET /api/workers` без cookie → 401; `/api/v1/worker/*` без Bearer → 401 |
| портальная сессия не открывает агентский контур | запрос к `/api/v1/worker/heartbeat` с cookie портала и без Bearer → 401 |
| bootstrap-секрет не пускает в рабочие маршруты | Bearer = bootstrap-секрет на `/jobs/next` → 401 |
| чужой worker-token не видит чужие задания | `X-Worker-Id` не совпадает с токеном → 401 |
| execution-token обязателен на маршрутах попытки | `POST /events` без `X-Execution-Token` → 401 |
| тела запросов не содержат секретов | `logs/actions/*.jsonl` центра: ни одного `sk-…`, `wtk_…`, JWT |

## 10. Как доказать, что endpoint принимает ТОЛЬКО payload воркера

1. схемы pydantic с `extra="forbid"` (`AuditPipelineParams`,
   `ProviderRequirementPayload`, `CancelAttemptPayload`,
   `DeleteAttemptDataPayload`) — лишнее поле отвергается, а не игнорируется;
2. закрытые enum `JobType` и `WorkerCommandType` — канала «выполни
   произвольное» не существует (I-10, I-11);
3. проверка на живом центре: `POST /api/v1/worker/events` с полем, которого нет
   в схеме, обязан дать 422, а не 200.

---

## 11. Как проверить идемпотентность после включения

| Сценарий | Ожидание |
|---|---|
| повтор `POST /jobs/next` с тем же `Idempotency-Key` | то же назначение, без второй попытки |
| повтор батча событий с тем же `first_seq` | `last_seen_seq` не растёт, дублей в БД нет (I-04) |
| повторная загрузка того же архива | тот же `result_package_hash`, второго результата нет (I-06) |
| **повторная доставка результата после вызова модели** | `inference/<key>.result.json` уже есть → модель НЕ вызывается (I-P9) |

---

## 12. Как выключить ingress обратно

См. §7. Есть и два более мягких способа, не требующих рестарта:

* перевести воркера в `draining` через операторский API — новых заданий он не
  получит, текущие доработает;
* стереть `DISTRIBUTED_WORKERS_BOOTSTRAP_SECRET` — регистрация НОВЫХ воркеров
  перестанет работать (503), уже выданные токены продолжат действовать.

---

## 13. Чего делать НЕ нужно

* не менять `AUDIT_PIPELINE_REVISION` ради совпадения с воркером: несовпадение
  ревизий — сигнал, а не помеха, и лечится обновлением кода на воркере;
* не включать `DISTRIBUTED_AUDIT_EXECUTION_ENABLED` одновременно с ingress:
  это два независимых решения, и второе означает «разрешаю реальные аудиты»;
* не открывать входящие порты на воркер: транспорт заданий — исходящий HTTPS
  от воркера, а SSH к воркеру остаётся ТОЛЬКО административным каналом.
