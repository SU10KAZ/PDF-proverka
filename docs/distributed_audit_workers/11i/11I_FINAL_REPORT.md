   в такой ситуации закрываются только на контрактном уровне;
2. **targeted-проходы свода на воркере по-прежнему не исполняются** (KI-11I-2):
   провайдерский путь делает один вызов. Так было и до 11I; новое — что
   расхождение стало видимым;
3. **центральный хвост читает глобальную конфигурацию**, а не план (KI-11I-3).
   Данные для исправления в плане есть, подключения нет;
4. **живой сокет не поднимался** — сетевой контракт проверен на настоящих

## 3. Проблема старого контракта

`ProviderRequirementPayload` нёс ОДНУ пару «провайдер + способность» на весь
worker-участок, причём способность была ровно одна: `strong_audit`.

Этого не хватает по трём независимым причинам:

* **этап 01 требует трёх провайдеров сразу** — OpenRouter, Codex стандартного
  класса и Codex усиленного, плюс судью. Заказав одного, центр теряет остальных;
* **этап 05 требует Claude и Codex одновременно**, в ОБОИХ пресетах, включая
  «Full Codex». Заказав `provider=codex`, центр терял ногу Claude; заказав
  `claude` — ногу Codex;
* **одна способность не различает классы моделей.** «Сильная модель для свода» и
  «дешёвая для критика» на одной подписке — разные строки, и выразить эту
  разницу было нечем.

Плюс два дефекта исполнения, каждый из которых сам по себе делал удалённый
прогон несравнимым:

* `use_dual = (not use_provider_bridge) and …` — мост схлопывал ансамбль в одну
  ногу;
* ключ журнала не содержал идентификатора ноги: три детектора с одинаковым
  промптом и одинаковой картинкой давали ОДИН ключ, и две ноги получили бы
  `replay` ответа первой. Ансамбль из трёх моделей выродился бы в одну,
  скопированную трижды, без следа в артефактах.

## 4. Новый routing plan

Схема — `11I_ROUTING_PLAN_SCHEMA.json`, устройство и обоснования —
`11I_ROUTING_PLAN_DESIGN.md`.

| Свойство | Значение |
|---|---|
| Версия схемы | 1 |
| Версия вычислителя условий | 1 |
| Хэш | `sha256` по канонической сериализации СОДЕРЖАНИЯ |
| Не входит в хэш | `routing_plan_id`, `created_at` |
| Провайдеров | 3 (claude, codex, openrouter) |
| Способностей | 6 |
| Ролей | 14 модельных + 7 детерминированных |
| Типов условий | 10, все типизированы; `eval` отсутствует |
| Типов мультипликативности | 4 |
| Правил валидатора | 16 |

Неизменяемость обеспечивается не соглашением, а конструкцией: все узлы —
`frozen` dataclass'ы, хэш считается по содержанию и сверяется на воркере с
хэшем в привязке. Два независимо посчитанных значения, совпав, доказывают, что
стороны держат один маршрут; расхождение — отказ исполнения.

## 8. Что проверено

81 новый тест + 3 сетевых, ноль обращений к модели. Подробности —
`11I_TEST_REPORT.md`.

Ключевые доказательства:

* **заморозка**: задание A на «Full Codex» не меняет маршрут после переключения
  глобального пресета на «Claude+GPT+Codex» (`test_p_…`);
* **ансамбль на поддельных CLI**: две codex-ноги с одинаковым промптом и
  картинкой дают два ФАКТИЧЕСКИХ запуска подпроцесса и два разных ключа журнала;
  судья — отдельное четвёртое обращение; повтор той же ноги читается из журнала
  и не оплачивается;
* **отказ в назначении**: воркер без OpenRouter не получает задание — ошибка
  возникает ДО создания задания, и ни одного обращения к другому провайдеру
  «вместо» не происходит;
* **нет точной модели в контракте центра**: проверяется машинным сканированием
  всех значений плана на двух независимых рубежах (центр и воркер).

Регресс: 1252 теста распределённых воркеров зелёные. Три падения
воспроизводятся на базе 11H. Регресс-гейт показал 9 «новых» падений — все
девять суть ошибки СБОРА тестов геометрического корпуса из-за отсутствующих
файлов данных, и все проверенные из них воспроизводятся на `de2f84f2`. Это
дрейф окружения, а не регрессия.

## 9. Совместимость воркера .31

`11I_WORKER31_PRESET_COMPATIBILITY.json`. Снято без чтения учётных данных:
только факт существования файлов, режим доступа и состав локальной политики (в
ней моделей нет — только способности).

| Пресет | Вердикт |
|---|---|
| Claude+GPT+Codex | **NOT_COMPATIBLE** |
| Full Codex | **NOT_COMPATIBLE** |

Четыре блокирующие причины:

1. OpenRouter отсутствует полностью: адаптера нет, ключа нет, а имя переменной
   ключа занесено в запрещённые для окружения подпроцесса провайдера;
2. локальная политика объявляет одну способность `strong_audit` из шести нужных;
3. боевая сборка 11H держит в политике только `codex` — маршрута для стража
   отсутствия и основной ноги оптимизации не будет;
4. установленная сборка предшествует 11I и не объявляет `routing_plan_v1`.

Учётные данные на `.31` не устанавливались и не менялись (§48 задания).

## 10. Что дальше

1. **Развилка по OpenRouter — продуктовая, не техническая.** Либо своя учётная
   запись и адаптер на воркере, либо отдельный пресет без GPT-ноги (но это
   другой аудит, и называться он должен иначе), либо точные пресеты остаются
   центральными;
2. **targeted-проходы свода через мост** (KI-11I-2) — по образцу
   `provider_judge.py`;
3. **план для центрального хвоста** (KI-11I-3) — требует переноса держателя
   плана из процессного в контекст задания, потому что центр исполняет
   несколько проектов в одном процессе;
4. **боевая валидация**: 11I не проверялся оплаченным прогоном намеренно (§53).
   Следующий этап — реальная сверка следа с эталоном на живом документе.

## 11. Замечание о хэшах в артефактах

`11I_PRESET_*_PLAN.json` и `11I_FAKE_NETWORK_*.json` содержат РАЗНЫЕ хэши
одного и того же пресета. Это не расхождение: `pipeline_revision` входит в
содержание плана, а скрипт артефактов и тест сетевого контракта проставляют её
по-разному (короткий хэш git против ревизии центра). Внутри одного прогона хэш
устойчив — это и проверяет `test_ax_routing_hash_survives_the_whole_roundtrip`.
