# 11H — изоляция Codex на воркере 176.12.77.31

Этап 11b оставил открытым остаточный риск: «filesystem scope Codex под
песочницей не доказан реальным прогоном». Задание 11H требует закрыть его ДО
платного прогона и не полагаться на формулировку промпта (§11). Ниже — что
именно проверено и чем держится изоляция.

## 1. Главный факт: команды модели на этой машине не выполняются вовсе

Codex — агентный CLI: у модели есть инструмент выполнения команд, и «мы не
просили её ничего запускать» изоляцией не является. Поэтому проверялся не
промпт, а механизм.

`codex sandbox -- <команда>` запускает команду ТОЙ ЖЕ песочницей, которой CLI
исполняет запросы модели, и не обращается к модели вообще — то есть даёт
прямой ответ на вопрос «что произойдёт, если модель попросит».

Измерено на .31 (0 обращений к модели):

```
$ codex sandbox -- /bin/echo HELLO_FROM_SANDBOX
exit=1   stderr: bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
$ codex sandbox -- /bin/cat /home/coder/provider-auth-canary/DO_NOT_READ.txt
exit=1   stdout пуст
$ codex sandbox -- /bin/ls /home/coder
exit=1   stdout пуст
$ codex sandbox -- sh -c "echo test > /home/coder/codex_sandbox_probe.txt"
exit=1   файл не создан
$ /bin/echo HELLO_PLAIN          # контроль, без песочницы
HELLO_PLAIN
```

Причина: Codex приводит песочницу в исполнение через `bwrap`, а на этой машине
`kernel.apparmor_restrict_unprivileged_userns=1`, и непривилегированный `bwrap`
не поднимает пространство имён.

Поведение при этом **fail-closed**: команда не выполняется, а не выполняется
без песочницы. Ни `echo`, ни `cat`, ни запись — ничего.

Практический вывод для 11H: на .31 модель физически не может ни прочитать
файл, ни выполнить команду. Единственное, что она получает, — это то, что
конвейер сам положил ей в промпт и во вложение.

Оговорка, которая обязана быть произнесена: это свойство ЭТОЙ машины, а не
переносимая гарантия. На VPS, где `bwrap` поднимается, команды будут
исполняться в песочнице `read-only` — тоже без записи, но с чтением. Перенос
воркера на такую машину требует отдельной проверки этим же зондом.

## 2. Что ограничивает вызов помимо песочницы

Слой `ProviderAdapter` (инварианты I-P1…I-P8, `providers/base.py`) действует
одинаково для обоих провайдеров:

| | как обеспечено |
|---|---|
| `cwd` | `providers/codex/runtime` — пустой каталог, не git-репозиторий. Ни репозитория, ни файлов задания, ни соседних кропов |
| окружение | собирается С НУЛЯ: `PATH` фиксированный (`/usr/local/bin:/usr/bin:/bin`), из хоста наследуются только `LANG/LC_ALL/TZ/SSL_*/LD_LIBRARY_PATH` |
| секреты | `FORBIDDEN_ENV_NAMES` — worker-token, адрес центра, ключи платных API до подпроцесса не доходят физически (их нет в белом списке, и адаптер их не получает) |
| `TMPDIR` | внутрь `providers/codex/runtime`, а не общий `/tmp` чужой машины |
| argv | только константы модуля + значения, вычисленные адаптером. Промпт уходит через stdin — его нет в `ps` |
| stdin | `/dev/null`, когда своего ввода нет (на подготовке 11b унаследованный stdin однажды стал промптом) |
| таймаут | обязателен, по нему убивается ГРУППА процессов |

## 3. Нейтрализация личного контекста владельца машины (§12)

Флаги рабочего вызова (те же, что у контрольного, — рабочий путь не имеет
права быть мягче проверенного):

```
codex exec --json --sandbox read-only --skip-git-repo-check --ephemeral
           --ignore-rules --ignore-user-config [--model=…] [--image=…] -
```

Что каждый снимает — по факту, измеренному на .31:

* `--ignore-user-config` — не читается `$CODEX_HOME/config.toml`. В нём на этой
  машине лежит `model = "gpt-5.6-sol"`, `model_reasoning_effort = "ultra"`,
  `service_tier = "priority"`, шесть доверенных проектов
  (`/home/coder/projects/PDF-proverka` в их числе) и MCP-сервер
  `openaiDeveloperDocs`. Без флага «минимальный» вызов поднимал бы внешний
  MCP-сервер, а модель и усилие зависели бы от настроек человека;
* `--ignore-rules` — не читаются user/project `.rules` (execpolicy);
* `--ephemeral` — файлы сессии не остаются в личном каталоге;
* `--skip-git-repo-check` — runtime не репозиторий, без флага CLI не стартует.

`AGENTS.md` в `~/.codex` существует и имеет размер 0 байт; проектных
`AGENTS.md` в cwd нет — cwd пустой. Авторизация при этом продолжает браться из
`CODEX_HOME` (документированное поведение `--ignore-user-config`), то есть
доступ к учётным данным сохранён, а семантика — нет.

## 4. Что осталось доступным намеренно

Учётные данные (`~/.codex/auth.json`, 0600, владелец `coder`). Это и есть
смысл режима `ambient_user`: воркер не копирует и не читает их — их находит
сам CLI. На центр они не уезжают (см. `11H_CREDENTIAL_SECURITY.json`).

## 5. Канарейка

`/home/coder/provider-auth-canary/DO_NOT_READ.txt` (0600) лежит ВНЕ всех
каталогов, к которым имеет отношение вызов. sha256 и `atime` снимаются до и
после каждого прогона; прямая попытка прочитать её под песочницей Codex
завершилась `exit=1` без вывода (см. §1).
