# 11J — модель безопасности ключа OpenRouter

## 1. Чем этот секрет отличается от двух предыдущих

Слой провайдеров живёт с учётными данными с этапа 11, и до 11J они ни разу не
были **строкой, которую можно передать**. Claude и Codex авторизуются входом
оператора на самой машине: центр их учётных данных не знает, не видит и не
может передать даже по ошибке — их нет ни в одном объекте, который едет по
проводу. Всё, что центр умеет сказать, — «нужна сильная модель», а чем за неё
платить, решает машина.

Ключ шлюза ломает эту симметрию: это строка. Строку слишком легко положить в
задание, а положив — уже не вынуть. Она уедет в `logical_jobs.payload`, в пакет
источника, в EventOutbox, в отчёт о прогоне, в резервную копию БД центра и в
выгрузку журналов — то есть на машины, которыми владелец ключа не управляет, и
в носители, которые он не контролирует.

Поэтому модель безопасности строится не вокруг «мы аккуратно с ним обращаемся»,
а вокруг **невозможности передачи**.

## 2. Канал провижининга: один и однонаправленный

```
оператор VPS ──(ssh, один раз)──> файл 0600 в каталоге данных воркера
                                            │
                                            ▼
                          adapter читает В МОМЕНТ ЗАПРОСА
                                            │
                                            ▼
                                 заголовок Authorization
```

Центра в этой схеме нет нигде. Он присылает `provider=openrouter` и
способность; чем именно воркер расплатится — его собственное дело, ровно как с
подпиской Claude.

**Раскладка.** Та же, что у остальных провайдеров, и это не симметрия ради
симметрии:

```
<worker_root>/providers/openrouter/
├── home/.openrouter/credentials.json   ← ключ, 0600
├── runtime/
└── metadata/                            ← соль отпечатка
```

Каталог даёт три вещи бесплатно: 0700 на всю ветку, участие в общей проверке
прав (`credential_facts` считается по `credential_path` для ВСЕХ провайдеров
одним кодом), и место для отпечатка учётной записи — единственного способа
заметить, что ключ на машине подменили.

Путь переопределяется администратором машины:
`AUDIT_WORKER_PROVIDER_OPENROUTER_CREDENTIAL=/abs/path`. Значение — путь, не
ключ; относительный путь отвергается.

**Формат.** Принимаются две формы:

```json
{"api_key": "sk-or-…"}
```
```
sk-or-…
```

Вторая нужна затем, чтобы провижининг сводился к одной команде и не требовал
собирать JSON руками в ssh-сессии.

## 3. Что запрещено конструкцией, а не соглашением

| Утверждение | Чем обеспечено |
|---|---|
| Ключ не хранится на объекте | `read_secret()` возвращает строку и ничего не запоминает; поля, в котором он пережил бы вызов, нет — значит его нет ни в `repr`, ни в дампе |
| Ключ не берётся из окружения | `OPENROUTER_API_KEY` в `FORBIDDEN_ENV_NAMES` слоя и отсутствует в белом списке окружения конвейера |
| Ключ не приходит из задания | `ProviderRequirementPayload` и `AuditPipelineParams` — закрытые наборы полей (`extra="forbid"`); поля для ключа нет, и задание с ним не разбирается вовсе |
| Ключ не уезжает в пакет | `project_package.find_secrets_in_files` ловит и `sk-…`, и имя переменной; проверено тестом в обе стороны |
| Ключ не уезжает в привязку | `ProviderBinding` не имеет поля для него; тест сканирует записанный на диск файл |
| Ключ не уезжает в heartbeat | `ProviderIdentity.as_center_payload` — перечисление разрешённого, а не вычитание запрещённого |
| Права шире 0600 — отказ | `probe()` возвращает `configured=False`; ключ, доступный соседнему сервису VPS, — это ключ, который уже утёк |
| Права проверяются перед КАЖДЫМ чтением | между heartbeat и вызовом файл мог смениться; «когда-то было 0600» — не утверждение о настоящем |
| Ключ не уводится на чужой хост | `resolve_base_url` принимает неофициальный адрес только при объявленном режиме заглушек, а объявление видно центру |
| Окружение не влияет на маршрут запроса | `httpx.Client(trust_env=False)` — `HTTP_PROXY`/`HTTPS_PROXY` игнорируются |

Последняя строка стоит отдельного слова. Переменная окружения `HTTPS_PROXY`
увела бы запрос **вместе с заголовком авторизации** на произвольный хост, и ни
один рубеж этого бы не заметил: ответ пришёл бы нормальный, этап отчитался бы
успехом. `trust_env=False` закрывает канал целиком.

## 4. Что НЕ является утверждением

`configured=True` означает ровно «файл на месте, права узкие, содержимое похоже
на ключ». Оно **не** означает, что ключ действителен. Проверка стоила бы
запроса к платному шлюзу, и §7 задания решает эту развилку явно: показывать
`configured`, не выдумывать `verified`.

Практическое следствие для оператора: воркер, объявивший способность, может
получить 401 на первом же вызове. Это отказ КОНКРЕТНОГО действия с кодом
`auth_required`, а не тихая деградация ансамбля.

## 5. Что происходит, если ключ пропал в середине прогона

§24 задания: падает конкретное действие. Проверено тестом
`test_key_disappearing_mid_run_fails_only_that_action`:

* нога Codex до пропажи — исполнена;
* нога шлюза после пропажи — `ProviderBridgeError`, отказ до заявки в журнале
  (то есть не стоит ни единицы разрешения, ни вечного replay);
* судья после — исполнен.

Ни подмены провайдера, ни пропуска ноги, ни исполнения ноги шлюза центром за
спиной воркера.

## 6. Общий счёт на нескольких VPS

Если один и тот же ключ выдан нескольким воркерам, у них общий бюджет, и
планировщик обязан однажды это учесть. 11J готовит метаданные и не делает
планировщика (§21): `account_group_id` у провайдера `openrouter` работает так
же, как у подписок — непрозрачный идентификатор, которым **оператор** помечает
воркеры, делящие счёт. Из ключа он не выводится и ключа не содержит:
соответствие задаёт человек, потому что вывести его из секрета значило бы
секрет прочитать.
