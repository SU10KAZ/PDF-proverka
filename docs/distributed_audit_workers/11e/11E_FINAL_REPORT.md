## 4. Production `findings_merge` BEFORE

```
PipelineManager → stages/findings_merge/runner.py
  → claude_runner.run_findings_merge
      ├─ codex:      _run_codex_json_stage + targeted (ДВА вызова)
      ├─ claude CLI: prepare_findings_merge_task → _run_cli
```

`11E_FINDINGS_MERGE_RUNTIME_BEFORE.md`.

## 6. Input contract

`01_blocks_analysis.json` (обяз.), плюс EN-шаблон этапа и `{DISCIPLINE_ROLE}`.

KI-2.

исторический `03_findings.json` не читаются вовсе. Полностью —
`11E_INPUT_CONTRACT.json`.

## 22. Recommendation

**Следующий минимальный этап — 11E.1: повторить ОДИН боевой `findings_merge`
на том же документе и том же входе.**

Почему именно это, а не следующий по списку этап: переносить `block_analysis`
поверх неподтверждённого свода значит копить непроверенные слои. Всё, что можно
доказать без модели, уже доказано и зелено — недостаёт ровно одного факта:
принимает ли production-валидатор реальный ответ Opus на этом промпте.

Что делает 11E.1 дешёвым и безопасным:

* код готов и уже развёрнут: релиз `20260810T054528-56f0b6efe13f` (коммит
  `43d2437f`) с исправленной диагностикой KI-3 стоит на `.31`;
* вход неизменен и сверен по хэшам, промпт детерминирован
  (`sha256 3b54ae46…`), гейт 93/93 воспроизводится;
* нужны только новые `task_id`, `attempt_id` и одно новое разрешение оператора.

Что 11E.1 обязан дать сверх повторного вызова: если отказ повторится, `detail`
теперь назовёт причину словами самого CLI — и вопрос «лимит общей подписки или
временный лимит API» закроется первой же строкой отчёта, без третьей попытки.

Перед запуском стоит развести во времени работу центральной сессии Claude Code
и вызов на воркере: подписка одна (KI-4), и одновременная нагрузка — один из
двух кандидатов на причину нынешнего отказа.
