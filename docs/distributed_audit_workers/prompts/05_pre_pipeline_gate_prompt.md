ЗАДАЧА №5: закрыть пред-пайплайновый контрольный этап распределённой системы audit-worker.

Цель этапа — устранить два оставшихся блокирующих риска перед созданием ExecutionBackend и подключением реального аудита:

1. ввести серверную ролевую модель для опасных операторских действий;
2. доказать безопасную параллельную обработку двух test_pipeline_v1 на одном VPS.

Реальный аудит, Claude Code, Codex, PipelineManager и VPS 176.12.77.31 на этом этапе НЕ подключать.

Итоговый возможный вердикт:

- PRE-PIPELINE GATE COMPLETE — можно переходить к созданию ExecutionBackend;
- PRE-PIPELINE GATE PARTIAL — тестовый контур работает, но реальный аудит подключать нельзя;
- PRE-PIPELINE GATE BLOCKED — продолжение небезопасно.

Первый вердикт допускается только после полного подтверждения ролевой защиты и двухслотового E2E-сценария.

## 2.1. Нет ролевой модели

Сейчас любой пользователь, прошедший общую аутентификацию портала, потенциально может выполнять опасные действия:

- отменять попытку;
- признавать попытку потерянной;
- создавать новую попытку;
- запрашивать удаление данных с воркера.

Также необходимо проверить права на:

- одобрение и отклонение регистрации VPS;
- ротацию и отзыв worker-token;
- создание тестовых заданий;
- изменение retention;
- включение физического удаления;
- просмотр audit log.

## 2.2. Не проверено max_slots > 1

Текущий контур доказан только с одним заданием.

Необходимо доказать на настоящих процессах:

- два задания одновременно выполняются на одном воркере;
- третье задание не запускается сверх лимита;
- процессы и каталоги полностью изолированы;
- события двух заданий не конфликтуют;
- отмена одного процесса не затрагивает второй;
- restart Agent не останавливает оба процесса;
- restart Executor не создаёт дубликаты;
- offline-доставка двух результатов работает;
- upload-сессии не смешиваются;
- после освобождения слота третье задание запускается.

# 4. Критические инварианты

Добавь их в документацию и закрепи тестами.

R-01. UI не является границей безопасности. Все права проверяет сервер.

R-02. Субъект и роль пользователя берутся только из фактической portal auth.

R-03. Роль нельзя передать через JSON, query, header клиента или localStorage.

R-04. При неизвестном пользователе, отсутствующей роли или ошибке конфигурации опасное действие запрещено.

R-05. При PORTAL_AUTH_ENABLED=false опасные операторские endpoint не монтируются либо всегда возвращают fail-closed.

R-06. Viewer не может выполнять ни одного изменяющего действия.

R-07. Operator может выполнять только предусмотренные операции управления заданиями.

R-08. Admin имеет расширенные действия управления воркерами и безопасностью.

R-09. Worker-token никогда не даёт операторских прав.

R-10. Отказ в доступе не изменяет состояние задания и не создаёт WorkerCommand.

S-01. Одновременно на одном воркере выполняется не более двух test_pipeline_v1.

S-02. Третье задание не получает локальный execution claim до освобождения слота.

S-03. Два задания имеют разные job_id, attempt_id, execution_token, каталоги, PID и process group.

S-04. Отмена задания A не отправляет сигнал процессу задания B.

S-05. Sequence EventOutbox уникален и монотонен отдельно для каждой попытки.

S-06. Одновременная запись событий несколькими процессами не создаёт одинаковых sequence.

S-07. Restart Agent не останавливает Executor и два test_process.

S-08. Restart Agent не создаёт третий или повторный процесс.

S-09. Restart Executor не запускает дубликат живого процесса.

S-10. Потеря связи не завершает ни одно из двух заданий.

S-11. Два результата и две upload-сессии не смешиваются.

S-12. Disk critical блокирует новое задание, но не убивает два текущих.

S-13. После завершения одного задания освобождается ровно один слот.

S-14. После освобождения слота третье ожидающее задание может быть запущено.

S-15. Центр не доверяет только заявленному воркером free_slots.

S-16. Локальный Executor также независимо проверяет собственную ёмкость.

S-17. max_slots=2 не означает автоматическую готовность к max_slots=5.

Предпочтительный порядок:

1. существующая ролевая модель портала;

Названия адаптируй к стилю проекта.

- не использовать данные запроса;

# 10. Fail-closed

Обязательное поведение:

- PORTAL_AUTH_ENABLED=false:
  - изменяющие operator/admin endpoint не монтируются либо возвращают 404/503;
  - никакого режима «раз аутентификация выключена, значит разрешено всё»;

- пользователь не аутентифицирован:
  - 401;

- аутентифицирован, но нет permission:
  - 403;

- подсистема ролей не сконфигурирована:
  - опасные действия 403/503;
  - понятная диагностика для администратора;
  - никаких прав по умолчанию;

- feature flag выключен:
  - подсистема не создаёт БД;
  - опасные маршруты не выполняют работу;
  - существующее поведение локального аудита не меняется.

Отказ должен происходить до:

- изменения БД;
- создания WorkerCommand;
- создания новой попытки;
- формирования пакета;
- записи опасного действия как успешного;
- выдачи живого токена.

# 11. CSRF и browser security

Все изменяющие endpoint, вызываемые браузером, должны использовать существующую CSRF-защиту либо подтверждённый эквивалент.

Проверь:

- same-origin;
- cookie flags;
- CSRF-token;
- content type;
- CORS;
- Origin/Referer, если это используется проектом.

Не создавай отдельный слабый механизм только для audit-workers.

Worker API не использует portal session и не должен принимать browser CSRF-token как авторизацию.

# 15. Двухслотовая модель

На этом этапе поддерживается:

configured_max_slots = 1 или 2.

Значение по умолчанию остаётся 1.

Значение 2 включается только явной конфигурацией воркера.

Значение:

- 0;
- отрицательное;
- нечисловое;
- больше 2

должно быть отклонено либо безопасно ограничено с понятной диагностикой.

Не заявляй поддержку 5.

Добавь capability:

- max_verified_slots=2;
- или эквивалентное поле.

Центр не должен назначать воркеру больше, чем минимум из:

- configured_max_slots центра;
- configured_max_slots воркера;
- max_verified_slots;
- локально рассчитанной доступности;
- центрально рассчитанного числа свободных reservation;
- disk gate;
- состояния Executor;
- состояния Agent;
- совместимости protocol_version.

# 16. Определение занятого слота

Чётко определи, какие состояния занимают execution slot.

Предпочтительная модель:

Слот занят, пока попытка:

- assigned;
- source_uploading;
- source_ready;
- accepted_by_worker;
- running;
- cancel_requested.

Слот освобождается после достоверного прекращения локального исполнения:

- completed_locally;
- cancelled;
- failed;
- executor_interrupted;
- либо другого подтверждённого терминального состояния процесса.

`result_uploading` сам по себе не должен обязательно занимать execution slot, если процесс уже завершён.

Но:

- upload должен иметь отдельный сетевой/дисковый контроль;
- незавершённый upload не разрешает удаление данных;
- освобождение execution slot не означает удаление attempt.

Если текущая машина состояний требует иной границы, обоснуй её и закрепи одним централизованным predicate:

attempt_occupies_execution_slot(attempt)

Не дублируй списки состояний в нескольких местах.

# 17. Центральное резервирование слота

Центр обязан рассчитывать доступность самостоятельно.

Нельзя доверять только heartbeat-полю `calculated_free_slots`.

При выдаче задания используй транзакцию:

1. прочитать worker;
2. проверить online/stale policy;
3. проверить Agent;
4. проверить Executor;
5. проверить disk critical;
6. посчитать активные reservations по БД;
7. сравнить с эффективным лимитом;
8. атомарно закрепить задание;
9. зафиксировать assignment_generation;
10. вернуть задание.

Два параллельных `/jobs/next` не должны получить задания сверх лимита.

Используй:

- BEGIN IMMEDIATE;
- условное UPDATE;
- уникальные индексы;
- либо равноценную атомарную конструкцию.

Проверь гонку реальными конкурентными запросами.

# 18. Локальное резервирование слота

Executor независимо проверяет локальную ёмкость.

Перед запуском test_process:

- подсчитать живые process_registry;
- подсчитать локально claimed attempts;
- проверить executor lease;
- проверить configured_max_slots;
- проверить disk critical;
- атомарно захватить попытку.

Даже если центр по ошибке передал третье задание, Executor не должен запустить третий процесс.

Третья попытка остаётся:

- queued;
- waiting_for_slot;
- либо в другом явно определённом состоянии.

Не переводить её в failed только из-за отсутствия слота.

# 19. Agent при двух слотах

Agent должен:

- продолжать long poll, пока есть локальная доступность;
- получить максимум два задания;
- не ждать полного завершения первого перед запросом второго;
- не запрашивать третье, если локально нет свободного слота;
- корректно обрабатывать race между heartbeat и локальным claim;
- продолжать отправлять события обоих заданий;
- продолжать два upload;
- не блокировать один job ошибкой другого.

Ошибка задания A не должна завершать agent-loop задания B.

# 20. Executor при двух слотах

Один Executor может управлять двумя дочерними test_process.

Требования:

- разные process group;
- разные stdout.log;
- разные stderr.log;
- разные progress;
- разные completed.marker;
- разные process_registry;
- разные attempt directories;
- разные command fingerprint;
- отдельная отмена;
- отдельная финализация;
- исключения одного watcher не завершают второй watcher.

Если архитектурно используется worker-pool, размер пула для текущего этапа максимум 2.

Не создавай бесконтрольный `asyncio.create_task` без реестра и завершения.

# 21. EventOutbox при конкуренции

Известное ограничение hardening:

межпроцессный замок счётчика событий деградирует вне POSIX.

Для двухслотового режима sequence должен выделяться транзакционно через SQLite, а не зависеть от:

- чтения последнего числа в памяти;
- файла-счётчика;
- `fcntl` как единственной защиты;
- окна последних 500 событий.

Предпочтительно:

1. отдельная строка sequence counter на job_id + attempt_id;
2. BEGIN IMMEDIATE;
3. атомарное увеличение;
4. вставка события в той же транзакции;
5. UNIQUE(job_id, attempt_id, sequence).

Требования:

- два процесса одновременно пишут события одной попытки → sequence не дублируется;
- две разные попытки имеют независимые sequence;
- restart не сбрасывает sequence;
- повторная доставка не создаёт дубликат;
- interleaving событий разных попыток допустим;
- порядок внутри каждой попытки сохраняется.

Проверь нагрузочным тестом с несколькими процессами.
