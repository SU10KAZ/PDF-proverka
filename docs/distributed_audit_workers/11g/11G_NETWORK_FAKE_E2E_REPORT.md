# 11G — сетевые прогоны без обращений к модели

Два прогона, и они проверяют РАЗНОЕ. Это не дублирование: второй существует
именно потому, что первый по построению не может проверить предмет этапа.

| | прогон 1 | прогон 2 |
|---|---|---|
| режим | `audit-fake` | `audit-provider` |
| настоящие модели на воркере | выключены (`ALLOW_REAL_LLM=false`) | включены |
| требование к провайдеру от центра | **не формируется** | формируется |
| привязка и разрешение | **не выписываются** | выписываются штатным кодом |
| подделан | весь путь к модели (`fake_providers`) | только сам бинарь (`provider_bridge_stub`) |
| обращений к настоящей модели | 0 | 0 |
| что доказывает | транспорт, устойчивость, приём | цепочку этапа 11G целиком |

## 1. Почему `audit-fake` не годится как доказательство 11G

В fake-режиме воркер объявляет центру `provider_mode="fake"`. Центр по этому
признаку СОЗНАТЕЛЬНО не формирует требования к провайдеру (поведение до 11C
сохранено дословно), воркер не активирует мост, привязка не выписывается.
То есть вся цепочка, ради которой затеян этап, в этом режиме выключена — и
подтвердить её исправность прогон не может ни одной проверкой.

Он проверяет другое, и это другое нужно: что задание доезжает, события не
теряются, результат возвращается и принимается.

## 2. Прогон 1 — `audit-fake`: 106/114

Полностью зелены: транспорт (TLS проверен воркером, `ssl_verify_result=0`),
регистрация и одобрение по HTTP, разделение Agent/Executor по процессам,
тестовое задание, **обрыв связи посреди задания** (события копятся в дисковом
outbox 36 → 62 и досылаются после восстановления), **рестарт Agent** (Executor
не перезапустился, дубля попытки нет), **рестарт Executor** (аудит пережил,
второго исполнителя нет), **отмена online и offline** (отложенная команда
доставлена после возвращения связи), retention (неподтверждённые результаты не
попадают в кандидаты на удаление), сборка исходного пакета центром с правильной
дисциплиной, применение профиля дисциплины на воркере.

### Что нашёл этот прогон

**Пакет результата отвергался ЦЕЛИКОМ.** `md_prescan` пишет в
`01_text_prescan.json` поле `md_file` с абсолютным путём каталога попытки на
воркере; контракт переносимости `portable_paths` называл соседнее имя `md_path`
и не называл этого. Отказ был **правильным**: непоименованное поле с чужим
путём отвергает пакет намеренно — пропущенный путь остался бы в дереве
заказчика навсегда. Недоставало ровно строки в таблице.

Почему не всплыло на 11F: предсканирование MD молча не выполнялось из-за
неверного корня версии (исправлено `b2247d8a` там же, на 11F, но без живой
проверки). Первый же сетевой прогон эту живую проверку и выполнил.

Шесть из восьми провалов — следствия этого одного дефекта. Ещё два — ошибка
самой проверки: она утверждала, что настоящего CLI на машине нет, и проходила
лишь потому, что искала его в PATH, где `~/.local/bin` отсутствует.

## 3. Прогон 2 — `audit-provider`: цепочка 11G под нагрузкой

Механизм остаётся боевым целиком: `provider_mode="real"`, `ProviderResolver`,
`inference_grant`, `ProviderBinding`, `inference_ledger`, `ProviderAdapter`,
argv с `--model`. Подделан ровно последний метр — бинарь, отвечающий на все
четыре фактических контракта настоящего CLI (`--version`, `auth status`,
текстовый JSON, мультимодальный stream-json).

Доказано (номера — из журнала прогона):

* центр положил в задание `provider_requirement`: `provider=claude`,
  `capability=strong_audit`, `model=null`;
* **имени модели в нагрузке задания нет ни в каком виде** — поиск по
  `opus|sonnet|gpt-|claude-|codex/` в сериализованных параметрах пуст
  (слово `claude` без дефиса — имя ПРОВАЙДЕРА и обязано там быть);
* воркер выписал привязку на ЭТУ попытку, и модель в ней взята из ФАЙЛА
  ПОЛИТИКИ машины (сверка идёт с файлом, а не с литералом в скрипте: литерал
  совпал бы и в мире, где модель выбрал CLI по умолчанию);
* разрешение выписано **автоматом**: `grant_id = auto-<attempt_id>`, заметка
  называет задание и способность; сам прогон разрешений не выписывает —
  проверено структурно по его исходнику;
* журнал вызовов: начато = завершено, неизвестных исходов ноль (I-P9);
* обращений к заглушке ровно столько же, сколько вызовов в журнале — то есть
  **ни один вызов не ушёл мимо неё**;
* центральные этапы на воркере не выполнялись, нарушений границы ноль.

Оператор не создавал ни привязки, ни разрешения. Это и есть HARD GATE §20.
