# 11G — HTTPS-транспорт центр ↔ воркер

## 1. Что требовалось

Воркер обязан ходить к центру **исходящим HTTPS** с проверкой сертификата.
Входящих портов на .31 не открывать. Боевой ingress не переключать (§14).

## 2. Что выбрано и почему

**Временный quick-туннель cloudflared к ИЗОЛИРОВАННОМУ тест-центру.**

Перебор вариантов — не в этом этапе; он сделан на этапе 10 и с тех пор не
изменился:

| вариант | статус |
|---|---|
| прямой порт наружу | отвергнут: провайдер пропускает только 22/80/443/3389 |
| `location` в боевом nginx `auditmanager.app` | отвергнут: нужен sudo и правка боевого конфига живого портала (§14 прямо запрещает) |
| SSH-туннель | запрещён условием: SSH — административный канал, не транспорт |
| HTTP без TLS | невозможно: `verify_tls` в воркере зашит константой, послабление только для localhost |
| **cloudflared quick-tunnel** | **использован** |

Условия §13 выполнены:

* боевой nginx не менялся — конфиг `auditmanager.app` не трогался;
* боевой маршрут не подменялся: продовые туннели (`:8081`, `:5050`) работали
  всё время прогонов, тест-центр поднимался на СВОБОДНОМ порту;
* токена в URL нет: авторизация — заголовок `Authorization: Bearer`, а адрес
  туннеля случайный и одноразовый;
* учётные данные туннеля в Git не попадают: quick-туннель их не имеет вовсе —
  cloudflared выдаёт разовое имя `*.trycloudflare.com` и не хранит секрета;
* TLS проверяется штатно — доказано не декларацией, а замером с воркера:
  `ssl_verify_result=0` при обращении к `/api/v1/worker/` (проверка [18]);
* туннель поднимается на время прогона и снимается вместе со стендом.

Quick-туннель **не является production ingress** и таковым не объявляется:
имя меняется при каждом запуске. Постоянный ingress — отдельная задача
production cutover (см. `11G_KNOWN_ISSUES.md`).

## 3. Что фактически работало

```
worker 176.12.77.31
   │  исходящий HTTPS, verify=True, follow_redirects=False
   ▼
https://<случайное>.trycloudflare.com     ← cloudflared quick tunnel
   │
   ▼
127.0.0.1:<свободный порт>                 ← изолированный тест-центр
   (backend.app.main:app под именем tests.distributed_audit_e2e.center_app)
```

Имя процесса выбрано не для красоты: продовый вотчдог машины ищет
`pgrep -f "uvicorn.*backend.app.main"` и убил бы стенд посреди прогона.

Маршруты, которые реально прошли по этому каналу: `register`, `heartbeat`,
`jobs/next` (long-poll), `jobs/{id}/source` (скачивание пакета), `accept`,
`events` (батчи), `uploads/*` (чанковая загрузка результата), `commands`,
`reconcile`.

## 4. Входящие порты воркера

Не открывалось ни одного. Слушающие сокеты .31 инвентаризованы до и после
прогонов; их 94, и все принадлежат постороннему почтово-веб стеку машины.
Аудит-воркер не добавил ни одного — это свойство архитектуры (центр не ходит
на воркер, воркер сам забирает задание), а не настройка firewall.

## 5. Границы применения

Туннель — транспорт ТОЛЬКО до изолированного тест-центра. Боевой центр
(`auditmanager.app`, backend на 127.0.0.1:8081) в прогонах не участвовал:
у него `DISTRIBUTED_WORKERS_ENABLED` не задана, то есть агентского роутера
физически нет и любой запрос воркера получил бы 404.
