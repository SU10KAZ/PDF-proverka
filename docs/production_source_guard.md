# Страж происхождения прод-кода (production source guard)

`scripts/production_source_guard.py` разделяет две операции: иммутабельный
кандидат релиза можно собрать до push, но переключить production можно только
на коммит из канонической удалённой ветки.

## Почему появился

18.08.2026 два одинаковых инцидента за один день. Каноническая ветка была
сведена и запушена, после чего параллельная сессия коммитила локально, собирала
релиз центра и переключала `current`:

| время | релиз | коммит-источник | где лежал коммит |
|---|---|---|---|
| 12:11 | `ui-real-78199ef7` | `78199ef7` | только клон `/tmp/12i-distributed-ui-real` |
| 14:11 | `ui-real-08666e4d` | `08666e4d` | только тот же клон |

Оба раза боевой исходник отсутствовал и на `origin`, и в рабочем дереве: потеря
`/tmp` уничтожила бы код работающего портала, а release-manifest не
воспроизводился бы ни из одного коммита. Дисциплина «сначала запушь» здесь не
работает — она держится на внимательности оператора, который в этот момент
занят инцидентом.

## Что проверяется

1. **Свежесть.** `git fetch` канонической ветки выполняется в момент проверки.
   Без него страж подтвердил бы достижимость по устаревшему remote-tracking
   ref — то есть по снимку, сделанному до появления нужного коммита.
2. **Происхождение.** Для deploy коммит-источник обязан быть *достижим* из
   `origin/main`. При сборке центра разрешён ещё один случай: чистый локальный
   `HEAD` ветки `main`, линейно продолжающий свежий `origin/main`. Посторонняя
   ветка и разошедшаяся история не проходят.
3. **Чистота отслеживаемых файлов.** `git diff --quiet` и
   `git diff --cached --quiet`. Это не формальность: `deploy_audit_worker.py`
   собирает bundle из **рабочего дерева** (по allowlist'у отслеживаемых путей),
   поэтому изменённый, но не закоммиченный файл уехал бы на воркер, не оставив
   следа ни в одном коммите.
4. **Неотслеживаемое в кодовых каталогах.** Отказ. В релиз такие файлы сами по
   себе не попадают (`git archive` и `tracked_only=True` их не берут), но их
   присутствие означает несохранённую работу в сборочном дереве.

Грязная **разработка** при этом разрешена: рабочий корень
`/home/coder/projects/PDF-proverka` может быть сколь угодно грязным. Страж
срабатывает только на пути production build/switch/restart.

Безобидное неотслеживаемое (рабочие заметки, отчёты, `docs/`, `deliverables/`,
кэши инструментов, `projects*/`, `knowledge_base/`) пропускается по узкому
списку `HARMLESS_UNTRACKED_PREFIXES`. Разово можно расширить через
`--allow-untracked <путь>` / `allow_untracked=[...]`.

## Смена канонической ветки: feature/block-vector-graphs → main (19.08.2026)

До 19.08.2026 прод-истиной была `feature/block-vector-graphs`, а `main`
принимала её периодическими PR и отстала на 153 коммита. Production authority
на ветке с именем «feature/…» — ровно тот беспорядок, из которого выросли
инциденты 18.08: непонятно, куда пушить и что считать опубликованным.

Теперь каноническая ветка — **`main`**, и это не переименование, а смена
полномочий: коммит, лежащий ТОЛЬКО в `feature/block-vector-graphs`, страж
отвергает так же, как любой неопубликованный. Проверено тестом
`test_commit_only_in_old_feature_branch_is_refused`.

Перенос выполнен слиянием (`origin/main` осталась предком), без force push и
без переписывания опубликованной истории: `main` уникальной работы не несла —
её собственные два коммита это merge PR #28 и `5d636afb`, патч которого уже был
в проде как `d58c254b` (patch-id совпадает), а `git diff prod...main` пуст.

## Обязательный порядок операций

```
BUILD:  COMMIT → git fetch → страж кандидата → тесты/проверки релиза
DEPLOY: PUSH → git fetch → строгий страж публикации → ЗАМОК ВЫКАТКИ
        → гейт живой работы → мутация прода
```

Страж стоит **до** замка намеренно: падать после захвата общего ресурса значит
держать чужую выкатку в отказе на время своей диагностики. Оба условия
обязательны и независимы — `PRODUCTION_SOURCE_CANONICAL=YES` **и**
`DEPLOY_LOCK_ACQUIRED=YES`.

Политика выкатки:

```
COMMIT → BUILD → PUSH В КАНОНИЧЕСКУЮ ВЕТКУ → DEPLOY
```

Сборка до push безопасна, потому что создаёт только иммутабельный каталог и
пишет в его манифест `publication_required_before_deploy: true`. Переключатель
не доверяет этой отметке на слово: он снова делает fetch и запускает строгую
проверку коммита из манифеста. До публикации не меняются ни `current`, ни
systemd-сервис.

## Где включён

| компонент | точка вызова |
|---|---|
| Центр, сборка релиза | `scripts/build_center_release.py::build()` — до захвата замка, в режиме локального кандидата; квитанция уходит в `release-manifest.json` (`production_source_guard`) |
| Центр, переключение релиза | `scripts/deploy_center_release.py::deploy()` через `_verify_release_source()` — коммит берётся **из манифеста собираемого релиза**, а не из HEAD дерева выкатки; квитанция уходит в deploy-receipt |
| Воркер | `scripts/deploy_audit_worker.py` — `cmd_build` и `cmd_deploy` (в том числе при готовом `--artifact`: проверяется `source_commit` его манифеста) |
| Шлюз | репозиторного установщика ещё нет (ставится вручную под sudo). Предписанная точка вызова — CLI: `python scripts/production_source_guard.py --component gateway --commit <sha>`; ненулевой код = не начинать установку |

## Использование

```bash
# из дерева-источника, перед сборкой
python scripts/production_source_guard.py --build-candidate
python scripts/production_source_guard.py --commit <sha> --json
python scripts/production_source_guard.py --component gateway --commit <sha>
```

Коды возврата: `0` — источник допустим для выбранного режима; `4` —
`PRODUCTION_SOURCE_NOT_CANONICAL`. Успех `--build-candidate` не даёт права на
deploy: перед ним обязательна повторная строгая проверка без этого флага.
Четвёрка выбрана намеренно: у установщика шлюза `4` уже означает
`PRECHECK_FAILED` — «живой прод не тронут».

Причины отказа (`exc.reason`): `commit_not_published`, `dirty_worktree`,
`staged_changes`, `untracked_build_files`, `remote_unreachable`,
`canonical_ref_missing`, `git_failed`.

## Настройка

| переменная | смысл |
|---|---|
| `AUDITMANAGER_CANONICAL_PRODUCTION_REMOTE` | remote канонической ветки (умолчание `origin`) |
| `AUDITMANAGER_CANONICAL_PRODUCTION_BRANCH` | каноническая ветка (умолчание `main`) |

Переменные существуют для тестов и для второй инсталляции, **не** для обхода:
подстановка видна в квитанции стража, которая уезжает в манифест релиза и в
рецепт выкатки. Флага «выключить стража» нет — его отсутствие закреплено
тестом `test_guard_module_has_no_environment_bypass`.

## Тесты

`tests/test_production_source_guard_12j1.py` — поведенческие проверки
на офлайн-фикстуре (bare-репозиторий в `tmp`, сеть не нужна):

* опубликованный коммит → PASS, в том числе когда прод отстаёт от головы ветки;
* неопубликованный локальный коммит → отказ в строгом режиме;
* чистый локальный HEAD `main`, линейно продолжающий `origin/main` → разрешён
  только как кандидат сборки; feature-ветка и divergent main → отказ;
* коммит на посторонней (пусть даже опубликованной) ветке → отказ;
* коммит из отдельного клона `/tmp` → отказ, а после слияния в каноническую
  ветку и push тот же коммит проходит (воспроизведён инцидент 18.08);
* грязное дерево / индекс / неотслеживаемый файл в кодовом каталоге → отказ;
  рабочие заметки и отчёты — не мешают;
* устаревший remote-tracking ref не даёт разрешения; недоступный remote и
  отсутствующая каноническая ветка — отказ закрыто;
* страж прошёл, но замок держит другая выкатка → `DEPLOY_LOCK_HELD`;
* отказ стража = ни переключения симлинка, ни рестарта, ни рецепта выкатки;
* страж вызывается ДО замка и в сборке, и в переключении.
