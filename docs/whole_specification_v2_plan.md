# Сравнение полных спецификаций, v2: план

Дата: 21.10.2026. Статус: **план**. Реализация ведётся в отдельной ветке и
на production не выкатывается, пока Андрей Иванович не решит иначе.
Текущий механизм описан в [whole_specification_comparison.md](whole_specification_comparison.md).

## 1. Задача

Этап «ИИ-описание изменений: спецификации» должен давать верное сравнение СО
между версиями, быстро и без отказа целой версии из-за отдельных строк.
Поводом стал ОВ3 21.10: 13 ответов Луны получены, но полных переходов 0 из 14,
четыре часа работы модели ушли впустую.

## 3. Корень проблем

1. **Одна ошибка гасит всю версию.** `specification_structure.validate()`
   при любой структурной ошибке возвращает пустой разбор. Одна неверная
   строка 49 выбрасывает 1700 верных, а в отчёт уходят тысячи следственных
   «line is not extracted as a row».
2. **Каждая версия размечается заново.** Это долго, упирается в 429, и
   одинаковые строки в соседних версиях размечаются по-разному. В ОВ3 до
   правки это давало ложные «+1146 / −1143» на переходе V10→V11.
3. **Модели отдано однозначное.** Шапки таблиц, маркеры систем («| Д 1 |»),
   строки «Примечание:» программа определяет сама. Каждая ошибка модели на
   них стоит целой версии.
4. **Автоисправление ограничено и не везде применяется.** `strict_autofix`
   отказывается работать при числе исправлений больше `AUTOFIX_MAX × 3`
   (`AUTOFIX_MAX = 5`, [specification_portions.py:26](../backend/app/services/version_comparison/specification_portions.py#L26)).
   При чтении сохранённого ответа (`one()` в
   [specification_run.py:231](../backend/app/services/version_comparison/specification_run.py#L231))
   автоисправление не применяется вовсе. Ответ, которому нужно 1–2
   исправления, снова уходит к Луне.
5. **Двойной проход «обычных листов».** Если сравнение СО исключило версию,
   очередь заново запускает листовой ИИ проекта
   ([stage_queue.py:460](../backend/app/services/version_comparison_ai/stage_queue.py#L460)).
   21.10 из-за этого ОВ3 пошёл по обычным листам второй раз.

## 4. Этапы

Порядок выбран по отдаче. Каждый этап — отдельный коммит в ветке плана,
каждый проверяется на контрольном наборе (этап 1) до перехода к следующему.

### Этап 0. Данные, без кода

- Снять `rejected.json` в ОВ2.1, ОВ2.2, ВК1, ВК2, ВК3, АГПТ, записать
  автоисправленную разметку там, где новая проверка её принимает, и вернуть
  этап спецификаций в очередь. Это делается тем же скриптом, что для ОВ3
  21.10, с копиями `*.bak-<дата>`. Ожидается около 46 полных версий без
  обращений к модели.
- ЭМ2: перезапустить спецификации. Текущий код делит большую СО на части,
  6 версий уйдут к Луне впервые.
- Запись в боевые данные: командой Андрея Ивановича в терминале или по его
  разрешению на такие правки.

### Этап 1. Контрольный набор и метрики

Без него нельзя доказать, что правка лучше.

- Скрипт `scripts/spec_compare_census.py` по сохранённым ответам объекта
  `0b540226` (а также другим объектам, где есть `whole_specifications/`).
  Считает:
  - полные версии;
  - полные переходы;
  - причины отказов;
  - «ложные расхождения»: на паре версий с ≥ 95 % дословно совпадающих строк
    число добавленных и удалённых позиций должно быть не больше числа
    различающихся строк;
  - потерянные строки: каждая строка данных таблицы попадает ровно в одну
    позицию или в список «не разобрано».
- Эталонные пары с ручной сверкой. Минимум: ОВ3 V3→V4 и V8→V9 (тексты почти
  совпадают, ожидается около 0 изменений), ОВ3 V10→V11, ОВ2.2, ЭО2.
- Сохранённые ответы копируются в фикстуру, чтобы тесты шли без `/srv`.

### Этап 2. Отказ по группе, а не по версии

- `validate()` возвращает статус по группам. Группа — участок от одного
  заголовка или маркера до следующего, с её родителями и продолжениями.
  Ошибочная группа помечается «не разобрано» вместе со своими строками,
  остальные строки собираются.
- Версия получает третье состояние, «частично». Сравнение пары работает по
  разобранным группам. Для неразобранных групп добавления и удаления не
  публикуются, вместо них в отчёте отметка «группа не сравнена». Это
  уточнение правила «при неполном входе добавления и удаления не
  публикуются», теперь на уровне группы, а не всей СО.
- Повтор у Луны идёт только по строкам неразобранных групп, с соседним
  контекстом и текстом замечаний, а не по всей части.
- В `one()` сохранённый ответ проходит то же автоисправление, что и после
  повтора.
- Досрочная остановка (`break_after`) срабатывает по доле неразобранных
  строк, а не по числу неполных версий.
- Листовой ИИ (причина 5) доописывает только листы неразобранных групп,
  а не все листы СО версии.

### Этап 3. Наследование разметки от прошлой версии

Это главный шаг и для скорости, и для согласованности.

- Версии обрабатываются по цепочке. Первая (или первая полная) размечается
  целиком: это якорь.
- Строка версии N+1, дословно совпадающая (после нормализации пробелов)
  со строкой принятой версии N с тем же окружением (соседние строки),
  получает её разметку без модели: заголовок, маркер, родитель,
  продолжение, примечание.
- Изменённые и новые участки (подряд идущие строки и по 2 строки контекста
  с каждой стороны) уходят Луне маленькими заданиями. Если изменённый
  участок задевает диапазон родителя, задание расширяется на всю его группу.
- Ожидаемый эффект на ОВ3: один полный проход и 14 × около 15–20 %, то есть
  примерно в 4–5 раз меньше символов и обращений. Соседние версии
  размечаются одинаково, поэтому ложные расхождения из-за разной разметки
  исчезают по построению.
- Сбой якоря — откат на полную разметку следующей версии.

### Этап 4. Правила вместо модели для однозначного

- Предварительная разметка программой: шапки и разделители таблиц, маркеры
  систем («Поз.» без остальных граф, в том числе перенесённые в
  «Наименование»), строки «Примечание…», обычные строки-заголовки перед
  таблицей. Луна получает их как «уже размечено программой» и решает только
  остальное: продолжения разорванных строк, родителей «… в составе:».
- Безопасные исправления без лимита: склейка строк с разными
  количеством, единицей, маркой или кодом снимается. Каждая строка остаётся
  отдельной позицией, текст не теряется. Каждое исправление записывается в
  отчёт, как сейчас.

### Этап 5. Выкатка

Только по отдельному «выкатывай». Перед выкаткой — полный прогон контрольного
набора и сравнение метрик с текущим продом.

## 6. Как работаем

- Ветка `feature/spec-compare-v2` в отдельном worktree
  `../PDF-proverka-spec-v2`. `main` — источник выкатки, и незавершённый
  алгоритм в нём уехал бы на прод со следующим чужим релизом.
- Разработка и проверка идут на сохранённых ответах, без обращений к модели.
  Новые обращения к Луне нужны для проверки этапа 3 на живых данных
  (ОВ3, ОВ2.2). Перед ними — оценка объёма и разрешение Андрея Ивановича.
  Качество важнее числа обращений, расход сообщается по факту.
- Тесты: файлы `tests/test_whole_specification_*.py` и
  `tests/test_version_comparison_specification_structure.py`, плюс контрольный
  набор этапа 1.

## 7. Решения Андрея Ивановича (21.10.2026)

1. **Этап 0 — позже, вместе с новым алгоритмом.** До этого боевые данные

3. **Якорь цепочки — по замерам.** На контрольном наборе проверяются оба
   варианта (первая версия и последняя). Выбирается тот, где меньше ошибок
   и ложных расхождений, результат показывается Андрею Ивановичу.
